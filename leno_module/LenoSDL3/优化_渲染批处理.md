# 渲染批处理优化（fillRect / drawRect / drawLine 透明自动合并）

## 1. 背景与瓶颈

改造前，`Renderer` 的绘制原语每次调用都是一次独立的 SDL 调用：

- `fillRect` → `SDL_RenderFillRect`
- `drawRect` → `SDL_RenderRect`
- `drawLine` → `SDL_RenderLine`

在大量小控件的场景下（列表行、表格网格线、图表刻度、粒子、HUD 元素等），即使这些图元**材质相同**（同色、同混合、同裁剪），也会被拆成上百次 draw call，成为 CPU↔GPU 的提交瓶颈。

SDL3 已提供批量接口，原本就可用、只是没被默认路径使用：

- `SDL_RenderFillRects(renderer, rects, count)`
- `SDL_RenderRects(renderer, rects, count)`
- `SDL_RenderLines(renderer, pts, count)`

## 2. 方案：透明自动批处理

对现有控件代码**零侵入**：`fillRect` / `drawRect` / `drawLine` 的函数签名与行为不变，内部改为「缓冲提交」。

### 2.1 缓冲结构

在 `sdl_renderer.leno` 用 `ffi` 预分配三块连续内存（在 `initDefault` 中 `ffi.malloc`）：

| 缓冲 | 容量 | 提交 API | 对应原语 |
|------|------|----------|----------|
| `_bxFill` | 2048 个 `SDL_FRect`（16B/个） | `SDL_RenderFillRects` | `fillRect` |
| `_bxOut`  | 2048 个 `SDL_FRect`（16B/个） | `SDL_RenderRects` | `drawRect` |
| `_bxLine` | 4096 条线（每线 2×`SDL_FPoint`=8B） | `SDL_RenderLines` | `drawLine` |

原语调用时把几何 `ffi.write_float` 写入缓冲并递增计数，**不立即提交**。

### 2.2 保序：按类型切换即 flush（`_bxCur`）

三种图元缓冲独立，但提交顺序必须不破坏「调用顺序 = 绘制顺序」。例如「先 `drawRect` 描边、后 `fillRect` 填充内部」是常见写法，若把所有填充先于描边提交，描边会被覆盖。

解决办法：用 `_bxCur`（`0=空 / 1=填充 / 2=描边 / 3=线段`）记录**当前缓冲类型**。

- 同类型连续调用 → 累积进同一缓冲（合并）。
- 类型切换（如 fill 之后来 draw） → 先 flush 旧类型，再开始新类型。

因为「跨类型必然 flush」，旧类型一定在新类型之前提交，**绘制顺序天然保序**；同类型内部按入队顺序提交，亦保序。

### 2.3 状态快照：变化才 flush

`SDL_*` 批量接口只能用「当前绘制状态」（颜色 + 混合 + 裁剪 + 渲染目标 + 缩放 + 颜色缩放）。所以缓冲必须在状态改变前提交。维护一份状态快照（`_bxR/_bxG/_bxB/_bxA/_bxIsFloat`、`_bxBlend`、`_bxClip`、`_bxTarget`、`_bxSx/_bxSy`、`_bxCScale`），在以下 setter 中**值比较**，仅当新值 ≠ 快照时才 flush 再设置：

- `setColor` / `setColorFloat`（含 int↔float 标记区分，避免误判）
- `setBlendMode`、`setScale`、`setColorScale`（值比较）
- `setClipRect` / `clearClip` / `setRenderTarget` / `setLogicalSize` / `setViewport` / `resetViewport`（无条件 flush，低频且必须正确）

「值比较」保证：**连续同色绘制不会被无谓 flush**（例如一个控件 `setColor` 一次后画多个矩形，仍合并为 1 次提交；跨控件若中间无任何状态变化/绘制调用，同色矩形也会合并——而真实控件流中控件内部常有 `drawText`/状态切换自然隔开，不会错误跨控件合并）。

### 2.4 立即绘制 / 帧末 flush 点

以下调用前先 `_flushBatches()`，保证已缓冲图元按当前状态及时提交、不拖延、不乱序：

- 纹理绘制：`drawTextureAt` / `drawTextureRect` / `drawTextureFromTo` / `drawTextureRotated` / `drawText`
- 几何：`drawTriangle` / `drawTriangleGradient` / `drawGeometry` / `drawCircle` / `fillCircle` / `fillPie` / `fillRoundedRect` / `drawRoundedRect`
- 直接批量 API（绕过缓冲）：`drawLines` / `drawPoints` / `drawRects` / `fillRects`
- 像素读取：`readPixels` / `readPixelsAt`
- 帧生命周期：`clear()` / `present()` / `destroy()` / `flush()`

### 2.5 复合图元用 `_emit*` 立即版

`fillCircle`（内部 `drawLine`）、`fillRoundedRect`（内部 `fillRect`）等复合图元若直接调用缓冲版原语，会把这些子调用也塞进缓冲、延迟到 flush 才提交，破坏与周围图元的相对顺序。因此引入三个内部立即版：

- `_emitFill` / `_emitRect` / `_emitLine`

复合图元**开头先 `_flushBatches()`**，内部改用 `_emit*`（立即提交，不经过缓冲），自身仍保序、且不污染缓冲。

## 3. 统计接口（验证用）

为精确验证「N 个同色图元合并为 1 次提交」，并作为性能探针，新增 6 个统计读取函数（模块级全局函数，经 `SDL3.getBatchXxx()` 暴露）：

- `SDL3.getBatchFillBatched()/getBatchFillSubmits()`
- `SDL3.getBatchOutBatched()/getBatchOutSubmits()`
- `SDL3.getBatchLineBatched()/getBatchLineSubmits()`

> 注：统计用**模块级全局变量**而非 `Renderer` 字段，是因为当前 leno 编译器对 `use` 转导出的 struct **新增方法**存在可见性限制（原有方法可见、新增方法跨模块报「没有方法」）。改用 `export func` 全局函数 + 全局变量绕过，单渲染器场景精确。

## 4. 验证

运行时冒烟测试：`examples/性能测试/batch_render_smoke.leno`（创建窗口、自退出）。实测输出（节选）：

```
[SMOKE] PASS 用例1: 100 个同色矩形合并为 1 次批量提交
[SMOKE] PASS 用例2: 两色各 50 -> 颜色切换分割为 2 次提交（累计 3）
[SMOKE] PASS 用例3: 描边已提交（跨类型切换触发 flush，保序）
[SMOKE] PASS 用例4: 80 条同色线合并为 1 次批量提交
[SMOKE] 统计 fill: batched=201 submits=4
[SMOKE] 统计 line: batched=80  submits=1
```

关键结论：
- 100 个同色 `fillRect` → 仅 **1 次** `SDL_RenderFillRects`（`submits=1`）。
- 颜色切换会把同帧矩形按材质分段（用例2 → `submits=3`）。
- 跨类型（描边/填充）切换触发 flush，绘制顺序保序（用例3 通过）。

另用 `leno -c` 编译 `fireworks_run` / `test_layout` / `test_charts` / `hello_window` 均 EXIT=0，确认未破坏现有控件绘制路径。

## 5. 收益与边界

- **收益**：大量同材质小控件（列表、表格网格、图表刻度、HUD）的 draw call 数量从 O(图元数) 降为 O(同色段数)，CPU 提交开销显著下降。
- **边界**：
  - 每次「绘制状态改变」或「穿插立即绘制」都会 flush，因此「每矩形都换色」的写法无法合并（本就不同材质，物理上也无法合并）。
  - 缓冲满（2048/4096）会自动 flush 后继续，不会越界。
  - 统计为模块级全局，多渲染器实例会共享计数（仅诊断用途，不影响绘制）。
