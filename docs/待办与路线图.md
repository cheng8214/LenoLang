### T3（P1）async 类型推断三连：C3 + C6 + C5

**为什么**：这三条是**同一个子系统** —— "`Future` 出现在某个位置时，静态类型推不出来"，
现状是**合法 async 代码在编译期就过不去**。合起来做最省。

| 项 | 现象 | 现状 |
|---|---|---|
| C3 | `a?.b()`（安全访问调 async 方法）静态类型是 `int?` | 运行时**是对的**、类型错（已实测，见下） |
| C6 | `await` 作用于**声明为 `Future` 的形参 / 字段** | 推不出类型 |
| C5 | `func` 形参里 `await cb(x)` | 推成 `func()` |

**已实测证据（C3）**：

```leno
struct W {
    int v = 7
    async func go(): int {
        await asyncs.sleep(5)
        return self.v
    }
}

async func driver() {
    var w = new W()
    var b = w?.go()        // 运行时正确：实测方法体里 current() = 3 ⇒ 确实建了协程、在协程里跑
    io.print(type(b))      // object（运行时是 Future）
    // 但**静态类型**是 `int?` ⇒ 下面这条编译期就失败：
    //   asyncs.is_done(b)  →  「参数 1 类型错误: 期望 'Future'，但传入 'int?'」
}
```

**判据**：`w?.go()` 的静态类型是 Future（可选包装则为"可选 Future"）⇒
`await w?.go()` / `is_done(w?.go())` / `all([w?.go()])` 都能编译通过；
`await` 声明为 `Future` 的形参/字段、`await cb(x)`（`func` 形参）同样能编译；**补断言**。

### T4（P2）`asyncs.all` 的语义：C8 + C10 —— ⛔ 需要先拍板

**现状**（不是纯 bug，是"文档这么写、但直觉相反"）：
- 文档原话：`### all(futures)` 「收集多个**已完成** Future 的结果」；
- 未完成的成员 ⇒ 结果里给 `null`（C10）；
- 失败的 future ⇒ 也给 `null`，错误**延后到 `run()`** 才炸（C8）。

**两个方向**：

| 方向 | 内容 | 影响 |
|---|---|---|
| (a) | 保持文档语义，把"调用 `all` 前必须 await"写成显式警示 | 不改行为，只改文档 |
| (b) | 改成"等齐全部 + 汇总错误" | 更符合 `all` 的名字，但**与现有文档相反**（新 A 类差异） |

**我的倾向：(b)**。理由是这几轮一贯的优先级 —— **静默错值 > 编译期报错 > 性能** ——
而"`all([失败future])` 返回 `[null]`、错误跑到别处才炸"属于最该消灭的那一类。

**判据（若选 b）**：`all` 等待所有成员完成；有失败 ⇒ 抛**汇总错误**（与 `run()` 的
「N 个协程失败: …」同口径）；`docs/module_asyncs.md` 同步改写；补断言。

### T5（P3）性能

#### ✅ 已修：`OP_MODULE_CALL` 的内联缓存是死字段（`a40f0fa`）

用户实测 `examples/性能测试/函数调用数学计算.leno`：栈式 4528ms / 寄存器式 7903ms（**慢 1.68x**）。

分解实验（关键：先把"哪一段慢"隔离出来）：

| 探针 | 栈式 | 寄存器式 | 结论 |
|---|---|---|---|
| 纯浮点循环 2000 万次 | 236ms | 148ms | 0.63x，**寄存器式更快** |
| 整数循环 2000 万次 | 1153ms | 643ms | 0.56x，**寄存器式更快** |
| `maths.sqrt` 1000 万次 | 199ms | 310ms | 1.55x 慢 |
| `sin*cos` 2000 万轮 | 802ms | 1465ms | 1.83x 慢 |

⇒ 差距**全在原生模块调用**这一条路上（≈22ns/次），与 VM 模型/算术/循环无关。

根因：`OP_MODULE_CALL` 每次调用都 `native_find_module_method()`（哈希 + 两次 `strcmp`），
而 `vm.ic_module_cache`（`InlineModuleCallCacheEntry` + `IC_MODULE_CACHE_SIZE 2048`）
**定义了、初始化了，handler 里从没读写过** —— 死字段（注释还写着"避免每次调用都做哈希表查找"）。
接上后：**7903ms → 3878ms（0.85x，反超 18%）**；`maths.sqrt` 探针 310→162ms。

#### ✅ 已修：另外两个死 IC（`8642aeb`）—— struct 方法查找 / struct 定义查找

| 缓存 | 用在哪 | 接线后的键 |
|---|---|---|
| `ic_method_cache` | `OP_GET_METHOD`（struct 分支） | 调用点 + `def` 指针 + 方法名哈希 + `struct_def_generation()` ⇒ 缓存**预创建闭包** |
| `ic_structdef_cache` | `OP_STRUCT_INIT` | 调用点 + 名字哈希 + 定义表代数 + `mod_owner` ⇒ 缓存 `def` |

键与判据都照栈式 `op_struct.inc` 的同名实现（它这两处是接上的）。
**A/B 实测**（`git stash` 回退前后各跑一次）：`光线追踪对象版` 5546ms → **5108ms（−8%）**；
另两个样例噪声级 ⇒ 有效但不大，**这两个不是当前最大的瓶颈**。

#### ✅ 已修：`ic_cache`（死字段）+ 内建方法调用的窥孔优化（`759d45a`）

`vm.ic_cache` 同样是死字段 ⇒ `OP_GET_METHOD` 的内建类型分支（`arr.len()` / `str.len()` /
`d.has(x)`）每次调用都查一遍方法表。按（调用点、receiver 类型、方法名哈希）缓存
`ObjNative*` 接上；**更大的头**是照栈式 `op_property.inc` 加了窥孔：

> 下一条就是 `OP_CALL` 且调用的正是本寄存器 ⇒ **不构造 `ObjBoundMethod`**，
> 直接把 receiver 当第 0 个实参调 `method->function()`，并就地吃掉那条 `OP_CALL`。

实测 `examples/性能测试/内联缓存 (Inline Caching) 性能对比测试.leno`：
**708ms → 671ms（只接缓存）→ 188ms（再加窥孔）**，对栈式 92ms 即 **7.64x → 2.04x**。
行为探针与栈式**输出完全一致**（0 参/1 参取值、热路径循环、循环内 try/catch）。

> 至此 **5 个内联缓存全部接上**：native / module / method / structdef / ic_cache。

#### ✅ 部分已修：立即数加减（`4f4cc86`）—— 递归基准 fib 1.45x → 1.33x

用户实测 `examples/性能测试/经典斐波那契数列测试_int.leno`：栈式 ~70ms / 寄存器式 ~101ms。
反汇编对齐后，**每次递归**的指令数：栈式 **11** 条、寄存器式 **23** 条，差距三处：

| 写法 | 栈式 | 寄存器式（改前） |
|---|---|---|
| `n - 2` / `n - 1` | `SUB_INT_IMM`（1 条） | `MOV + LOADI + SUB_INT`（3 条）✗ |
| `n <= 1` | `CMPJMP_LI_INT`（比较+跳转融合，1 条） | `MOV + LOADI + LE_INT + JMP_IF_FALSE`（4 条）✗ |
| 递归调用 `fib(x)` | `CALL_GLOBAL_FUNC_TYPED`（1 条） | `GETGLOBALFUNC + MOV + CALL + MOV`（4 条）✗ |

**已完成**：立即数加减（`OP_ADD_INT_IMM` / `OP_SUB_INT_IMM`，8 位有符号立即数）
⇒ fib 每次递归 23 → 19 条指令，中位数 1.45x → **1.33x**；`assert/test_int_imm.leno` 锁住。

> 实现期间踩到的三个坑（都写进了 codegen 的注释，别重犯）：
> ① 跳过右值求值的条件必须与"真的会用立即数指令"完全一致 —— 否则 `n <= 1` 会被编成
>    `OP_LE_INT A=1 B=1 C=0`＝`n <= n` 恒真（fib 返回 30 而非 832040）；
> ② `gen_binop` 收尾是**无条件** `reg_free(gen, r)` ⇒ 立即数路径必须补一个占位
>    `reg_alloc`，否则 free 掉寄存器 0、分配器全乱（runner 里 351 个用例挂）；
> ③ 左操作数必须是 int：`big1 + 100`（左为 bigint）只有通用 ADD 能算。

#### ✅ 又修两处：立即数比较（`efde937`）+ 免掉多余 CAST

| 改动 | 省下的指令 |
|---|---|
| `OP_LE_INT_IMM` 等 4 个立即数比较（`efde937`） | `n <= 1` 少一条 `LOADI` |
| `assign_cast_needed`：int/float 的**算术/一元**结果与目标类型一致时免 CAST | `return <int 运算>` 少一条 `CAST_INT` |

fib 每次递归：**23 → 22（加减立即数 `4f4cc86`）→ 21（比较立即数）→ 20（免 CAST）**，
耗时 **1.45x → 1.33x → 1.29x**（各 5 次取中位数；`函数调用数学计算` 仍 0.83x 反超，
`光线追踪对象版` 1.17x → 1.12x）。
> ⚠ 更正：`4f4cc86` 提交信息里"23 → 19"的 19 是**带 bug 的中间版本**上数的，
> 修好后实际是 22（已在 `efde937` 的提交信息里更正）。

#### ⬜ 下一步（fib 打平的账，20 → 11）

| 还差的 | 条数 | 做法 |
|---|---|---|
| **全局函数直呼** | ~6 | 递归调用现在是 `GETGLOBALFUNC + MOV + CALL + MOV` ×2 ⇒ `CALL_GLOBAL_FUNC`（函数索引 + 实参个数），并把实参**直接算进**实参寄存器（省掉那次搬运） |

#### ⬜ 仍待做：内建方法调用还差 2x ⇒ 需要**融合调用指令**

### T9（P3）解释器：抽巨型 handler 成 `static` 函数（方案 B）

**已完成的前置（方案 A，`bbb95c2`）**：`src/vm/vminc/vm_run.inc` 从 4249 行单文件拆成
`src/vm/vminc/run/01..14_*.inc`（14 块、合计仍 4249 行），`vm_run.inc` 退化为 31 行的聚合文件。
拆分是**纯文本搬运**（拼回去与原文件逐字节一致），切点一律在 `LABEL(...)` 之前。

**为什么不能"拆成 .c"**：它本质是**一个函数体** —— `vm.c` 的 `vm_run()` 与

**只动这 6 个（实测 >100 行）**：

| handler | 行数 |
|---|---|
| `OP_STRUCT_INIT` | 285 |
| `OP_INDEX` | 256 |
| `OP_CALL` | 205 |
| `OP_STRUCT_DEF` | 171 |
| `OP_GET_METHOD` | 118 |
| `OP_INDEX_SET` | 107 |

其余 **116 个 handler 中位数只有 15 行，不要动**（动了只增加间接层）。建议顺序：
`INDEX`（纯值计算最多）→ `CALL` 的 native 分支 → `STRUCT_INIT`（最独立）。

**模式**：照 `vminc/vm_helpers.inc` 里的 `read_ext_const` —— 抽成 `static` /

1. handler 里的错误路径现在是"报错 + `DISPATCH()`"，抽出去的函数**不能跳分发** ⇒

**① 比较+跳转融合 —— ✅ 已完成**

- **编码**：新增 `OP_CMPJMP_LT/LE/GT/GE`，占 **8 字节**：第一个字
  `[op][A=左操作数寄存器][B=右操作数][C(最高位=1 表示立即数形式)]`，
  **第二个 4 字节字**的前 2 字节是跳转偏移（`offset + 32768`，与 iAsBx 同约定）。
- **发射条件**（与 `*_INT / *_INT_IMM` 完全一致 ⇒ 语义等价）：`if`/`while` 条件是有序比较
  （`< <= > >=`）、两侧静态类型都是 int、左操作数是普通局部变量/参数（`SYM_LOCAL`/`SYM_PARAM`
  ⇒ 就是 `R[index]`）、右操作数是 int8 字面量或另一个局部变量/参数；任一不满足即不融合。
- **实测**：fib 递归路径 **9 → 8 条**；**同一份二进制 A/B**（`LENO_NO_CMPJMP=1` 关闭融合）
  65.7ms → **61.6ms = 0.938x**；`assert/test_cmpjmp.leno` 在**开/关两种模式下都过**
  （语义等价的直接证据）；断言套件 **354/354**。
- **三个坑**（都已踩过，后人别重踩）：
  1. `patch_jmp` / `patch_jmp_to` 的偏移必须按**指令自身长度**扣（`len - pos - size`）：
     融合指令是 8 字节，沿用 `- 4` 会静默写出错误的跳距 ⇒ 加了 `instr_bytes_at()`；
  2. **反汇编器**（`decode_trailing`）与**自检**（`disasm_self_check`）都必须知道这 8 字节，
     否则 `--debug` 的清单从那条指令起整体错位（看着像"凭空多出一条指令"），自检也核对不了它的跳转；
  3. **A/B 不要用"两次构建 + git stash"**：慢、易被机器频率漂移误导，还有把改动留在 stash 里的
     风险（本次取消时正好停在那一步）。用 `LENO_NO_CMPJMP` 这类**同二进制环境变量开关**最稳
     —— 栈式本来就有这个开关，当时就该照抄。

**② 语句上下文 `*_NOPUSH` —— ✅ 已完成（只做 `arr.add`）**

- 做法：**不新增 opcode**，直接让 `OP_ARRAY_APPEND` 认 C 位（`need_result`）——
  `C == 0` 时跳过"写回新长度"。codegen 侧在 `AST_EXPR_STMT` 里识别语句位置的
  `arr.add(x)`（`AST_CALL` + `ast.add` / `arr["add"]` 两种 callee 形态、接收者静态类型是数组、
  实参恰 1 个）⇒ 走 `gen_array_add(..., need_result=0)`。
- 效果：`a.add(i)` 作为语句从 **4 条**（MOV/MOV/APPEND+搬回 MOV）降到 **3 条**；
  **同轮 A/B 0.86x**（3.80ms vs 栈式 4.40ms）。
- 为什么没做 `INDEX_SET_NOPUSH` / `INC/DEC_LOCAL_NOPUSH`：`OP_INC/OP_DEC` 的写回**就是
  自增本身**（局部变量原地自增），`OP_INDEX_SET` 也只有赋值一条路径 ⇒ 没有"结果是废的"可省；
  真要做得多加 opcode 且收益 <1 条指令 ⇒ 暂缓（有需求再回来看）。

**③ 整数特化补全 —— ◐ 只补了 `MUL_INT_IMM`（其余有意不做）**

  codegen 把 `TOK_STAR` 也纳入立即数路径 ⇒ `x * 3` 从 `LOADI + MUL_INT` **2 条降到 1 条**、

  ⚠ 立即数路径的前提是**左操作数静态类型为 int**（沿用原有判断）—— 左值是 bigint 的

- **清单纠错**：`LE_INT`（双变量）**本来就有**（`leno_vm.h:82`），之前那条是 grep 漏看 ⇒ 无需补。
- **有意不做**：
  - `EQ_INT_IMM` / `NE_INT_IMM`：**语义有风险** —— `==`/`!=` 目前刻意走通用 `OP_EQ`（跨 int/bigint/float
    的相等语义与"按位比较"的 `*_INT` 家族不同），补特化版要先厘清 `1 == 1.0` 这类口径，
    收益却只有"省一次类型分支"⇒ 不值得冒险；

**④ 浮点有序比较特化 —— ✅ 已完成（附带一个通用收益）**

- 新增 `OP_LT_F / LE_F / GT_F / GE_F`：两侧静态类型都是 float 时替代通用 `OP_LT/LE/GT/GE`，
  不再每次调用 `value_compare_stdlib()`。**语义与通用版逐条一致**：null ⇒ false；两边是数值
  （非 bigint）⇒ 按数值比；其余（字符串 / bigint / 其它）**回退**通用比较，连报错文案都用同一份。
- **实测**（`examples/性能测试/特化指令基准.leno`，同二进制 `LENO_NO_FLOAT_CMP` 开关、

- **顺带发现的通用问题**：`gen_binop` 里**右操作数**即使是普通局部变量/参数也会先 `OP_MOV`
  搬进临时寄存器（左操作数早就优化过，右边漏了 ✗）。修掉后 `a < b` 少一条指令、
  `x = x + 1.0` 这类别名情形也安全（指令先读两个操作数再写结果）。
  ⚠ 收尾的 `reg_free` 必须按 `r_is_temp` 守卫 —— 与文档里记过的 `rl` 那次是**同一类坑**

- **方法论教训（重要）**：这类 ~10% 的改动**不能靠单两次运行定论** —— 实测单两次的噪声就能
  把 0.91x 淹成"看不出效果"。口径固定为：**同一份二进制 + 环境变量开关 + 5 次取 min**。

**⑤ typed 直呼（`OP_CALL_GLOBAL_FUNC_TYPED`）—— ✅ 已完成（调用路径的第一刀）**

- **动机**：建帧时每个参数都要走一遍类型转换检查（int→float / bigint→float / float→int），
  每参数 4–6 个判断 —— 栈式为此专门有 `OP_CALL_GLOBAL_FUNC_TYPED`。
- **做法**：新增同编码的 `OP_CALL_GLOBAL_FUNC_TYPED`，与 `OP_CALL_GLOBAL_FUNC` **共用同一个处理体**

- **安全门槛（关键）**：只有当"**每个实参的静态类型 == 形参声明类型**、且都限定在 `{int, float}`"

**⑤-i 数值 for 改计数制（借鉴 Lua 5.5 的 `forprep`）—— ✅ 已完成**

- **动机**：`全部测试.leno` 的空体 for 我们 159.2ms、栈式 113.9ms、Lua 38ms ⇒ 落后栈式 1.40x、
  落后 Lua 4.2x。原因是三寄存器比较制：每轮 3 次寄存器读 + 加 + 比较 + `inclusive`/符号两支，
  外加每轮 4 次槽位越界检查。
- **Lua 做法**（`lvm.c:214-265` 的 `forprep` + `1831-1848` 的 `OP_FORLOOP`）：入口算好
  **"首轮之外的额外迭代次数"** 存进寄存器，循环内只做「减一 + 判零 + 回绕加」——
  **不读上界、不判 step 正负**（边界/float 由入口一次处理）。
- **移植做法（不动指令编码、不动 codegen）**：`OP_FOR_PREP` 运行时若 start/end/step 全是 int48，
  就把 count 写进 **end 槽**（该槽是 codegen 给本循环分配的临时槽、循环内只有 `OP_FOR_LOOP`
  读它 ⇒ 复用安全；Lua 同样复用 `ra`）；非全 int 时把 end 槽**规范成非 int**（float / bigint，
  int48→double 无精度损失）⇒ `OP_FOR_LOOP` 见到 end 槽是 int 即走计数制，否则原样退回通用
  double/bigint 路径（语义不变）。排他式折成含上界：整数下 `x < end` ⟺ `x <= end-1`
  （下行 `x > end` ⟺ `x >= end+1`）。同时删掉循环内重复的槽位越界检查（`OP_FOR_PREP`
  已就同一批槽位号查过，槽位号全程不变）。
- **⚠ 口径坑（第一稿踩了）**：count 必须是"**首轮之外**的额外次数"（Lua 口径）。写成"总次数"
  ⇒ 每个循环多跑一轮（首稿实测 `i++` 结果 `10000001`、断言套件大面积 FAIL）。
- **实测**（同会话；before = 本改动前的二进制 `660b7ba`）：

  | 项 | before | after | 收益 |
  |---|---|---|---|
  | 空体 for | 159.2ms | 105.6 / 108.0ms | **−33%** |
  | for + `arr.add` | 362.6ms | 276.9 / 281.0ms | **−23%** |
  | 嵌套 for | 16.1ms | 13.3 / 13.5ms | −17% |
  | for + `i++` | 153.6ms | 136.6ms | −11% |
  | for `to var` | 138.5ms | 124.3ms | −10% |
  | while（对照，未改） | 187.9ms | 188.5ms | — |

  ⇒ 空体 for **105.6ms 已快于栈式 113.9ms**、数组添加 for **276.9ms 已快于栈式 344.4ms**
  （这两项此前分别落后 1.40x / 1.05x，是本轮"只剩 4 项落后栈式"里的两项）；
  对 Lua 空体 for 仍差 2.8x（38ms）。
- **语义变化（登记在案）**：计数制下**循环体给控制变量赋值不再影响迭代次数**（与 Lua 一致）；
  原先比较制下会提前/延后终止。断言套件 **358/358** 通过。

**⑤-j 结论（负）：K 常量操作数族**不划算** —— 静态计数会骗人**

- **动机**：Lua 5.5 有一整套 K 型常量操作数（`OP_ADDK/MULK/DIVK/IDIVK/MODK`、`OP_EQK/EQI`、
  `OP_SHLI/SHRI`，`lopcodes.h:261-315`），右操作数**直接从常量表读**（`lvm.c:1013` 的 `KC(i)`），
  不必先 `LOADK` 进寄存器。我们只有 int8 立即数。
- **先量后否**：对两个热基准 dump 统计「常量装载指令紧跟算术指令」的对数：
  光线追踪 **18** 对 / 全部测试 **59** 对（看着有 18–39% 的算术都能省一条）。
- **但分类后真相相反**：全部测试那 59 对里 **51 对是 `LOADK -> ADD`** —— 是 `print("..." + x)`
  这类**字符串拼接**（冷路径，且在打印行里）；真正热的只有光线追踪的 `LOADI -> MOD` **5 处**
  （`i % 3` 这类）加零星 `MUL_F/DIV_F`。
- **结论**：为 K 型新增 opcode（8 字节编码 + codegen 发射 + 反汇编）换不到 5–10 个热点，
  **不值得**；int8 立即数族（`*_INT_IMM`）已经覆盖 `x-1`/`x*3` 这类真正高频的写法。
  **别再用静态计数判断 K 型收益**——它会把你引向冷路径。

**⑤-k 字典写路径加调用点内联缓存（第 6 张 IC 表）—— ✅ 已完成**

- **动机**：`全部测试.leno` 里 `dict[key]=value` 我们 517ms、Lua 110ms（**4.7x**）。读代码定位到

- **做法**：VM 加第 6 张 IC 表 `InlineDictCacheEntry`（`dict` 指针 + `key` + `capacity` + `slot`）。

  地址被复用都挡得住），（b）不必依赖 GC 保活缓存里的裸指针。写路径保留 GC 写屏障
  （与 `dict_set` 的"更新现有键"分支逐字一致）。

- **⑤-l 读路径 IC —— ✅ 已完成（真因：编译期字面量不在内化表里）**：

**⑤-n 两项指令数削减（无返回值函数末尾的 `LOADNIL`；Array 立即数下标）—— ✅ 已完成**

两项都是「**减少指令条数**」而不是改结构 —— 与 ⑤-g 的结论一致（调用路径没有单点"肥肉"，
可动的是条数）。

1. **无返回值函数末尾不再发 `LOADNIL`**（`codegen_func.c` 的补 return、`codegen_stmt.c` 的裸 `return`）：
   `OP_RETURN` 在 `nresults == 0`（B 字段 = 1）时本就返回 null，与
   「`LOADNIL` + `RETURN(nresults=1)`」**结果完全相同**，但空体函数从 2 条降到 1 条
   （`func f() {}` 现在只有一条 `RETURN A=0 B=1`）。
   ⚠ `reg_alloc/reg_free` **保留** —— `max_reg`（→ `local_count` → locals 数组大小与 GC
   扫描范围）的记账必须与改动前逐位一致，不能顺手把槽位也省掉。
   **实测**（`全部测试` 5 次取 min）：空函数调用 **170.0 → 156.8ms（−7.8%）**，双向 A/B 同向。

2. **新增 `OP_INDEX_ARRAY_IMM`（iABC，C = 无符号 0..255 立即数下标）**：
   `arr[0]` 原是「`LOADI tmp,0` + `OP_INDEX_ARRAY_INT`」两条派发 —— 那个临时寄存器纯为凑一个
   寄存器操作数（Lua 的 `GETI` 把小下标直接编在指令里）。现在一条：
   `OP_INDEX_ARRAY_IMM A=7 B=1 C=0`（循环体 3 条 → 2 条）。
   与 `OP_INDEX_ARRAY_INT/_FLOAT` 是**同一份逻辑**（那两个 handler 本来就逐字相同）⇒ 一条指令
   同时服务 `Array[int]` 与 `Array[float]`；越界处理与寄存器版**完全一致**
   （同一个无符号比较 + 同一句报错文案）。opcode 追加在枚举**末尾**
   ⇒ 既有编号不动、旧 `.lenb` 仍可执行；4 字节定长、无附加数据。
   **★ 下标宽度：为什么取无符号 0..255 而不是 int8（口径对齐 Lua）** —— 第一版写的是
   `int8_t`（−128..127），复核 Lua 源码后改掉：
   Lua 5.5 的 `OP_GETI` 用 `int c = GETARG_C(i)`（`SIZE_C = 8`、`MAXARG_C = 255`，**无符号**），
   而发射判据 `lcode.c:isCint()` 是 `l_castS2U(ival) <= l_castS2U(MAXARG_C)`
   —— 先转无符号再比 ⇒ **负字面量下标直接落回寄存器路径**（`VINDEXED` → `OP_GETTABLE`），
   `GETI` 从不确定表示负数。对 Leno 而言负半边更是纯浪费：`arr[-1]` 在本语言里**必然越界**
   （handler 里同一个无符号比较恒假）⇒ 用立即数只是把"注定报错"的路径省一条指令，
   却把 **128..255** 这段真会用到的（查找表 / 定长数组）挤回两条指令。
   改成 [0,255] 后边界实测：`arr[0]/[2]/[127]/[128]/[255]` 全部一条 `OP_INDEX_ARRAY_IMM`
   （C = 0/2/127/128/255），`arr[256]`、`arr[-1]`、变量下标照旧回退 `LOADI + INDEX_ARRAY_INT`
   —— **回退路径行为逐位不变**，只是 128..255 那一段从"两条"变"一条"。
   ⚠ 与 ⑤-j 的"K 常量操作数族"负结论**不矛盾**：那条讲的是"把常量编进指令以省一条 `LOADI`"
   在**字典/字符串键**上不划算（要过常量表 + 判型）；这里是「**静态已特化的数组 + 整数下标**」，
   省掉的是纯 `LOADI` 且保留了跳过判型的快路径 ⇒ 两头都赚。
   **实测**（同轮双向 A/B，`全部测试` 5 次取 min）：`arr[index]` **50.7 → 35.8ms（−29.4%）**，
   反向复测 −25.9%，两次同向不重叠。

- **⑤-n 的负结论：handler 序言里的 `GET_CURRENT_LINE()` 不是瓶颈（别再改）**。
  各算术 handler 开头都无条件算一次 `int line = GET_CURRENT_LINE();`，而

**⑤-p 写路径直取变量寄存器（`arr[i] = v` / `obj.f = v`）—— ✅ 已完成**

**动机**：按 ⑤-n 的结论继续做"**整条指令削减**"（唯一被证明有效的杠杆），方法是
**反汇编真实负载的热循环、逐条找可以整条删掉的**。这次挑了排序基准的 `partition`
（原地快排的热点）。

**发现**：`arr[i] = v` 每次要付 **2~3 条 `OP_MOV`** —— 因为 `codegen_stmt.c` 的写路径
（`gen_index_assign`、`gen_assign` 的 AST_INDEX/AST_INDEX_ASSIGN/AST_FIELD_ACCESS 分支）
一律 `gen_expr(接收者)` / `gen_expr(下标)` / `gen_expr(值)`，各产生一条搬运。
而**读路径早就做了"直取变量自己的寄存器"**（`AST_INDEX` 里那段 `obj_is_temp`）——
写路径只是**漏了同一个手法**。`INDEX_SET A B C` 的 A/B/C 本来就是任意寄存器 ⇒ 可省。

`partition` 内层循环（`if arr[j] <= pivot { 交换 arr[i],arr[j]; i++ }`）：

```
改前（14 条/轮）                          改后（10 条/轮）
INDEX_ARRAY_INT  ; arr[j]                 INDEX_ARRAY_INT  ; arr[j]
LE_INT                                    LE_INT
JMP_IF_FALSE                              JMP_IF_FALSE
INDEX_ARRAY_INT  ; temp = arr[i]          INDEX_ARRAY_INT  ; temp = arr[i]
MOV  arr → 临时                            INDEX_ARRAY_INT  ; arr[j]
MOV  i   → 临时                            INDEX_SET        ; arr[i] = arr[j]   ← 原来 4 条
INDEX_ARRAY_INT  ; arr[j]                  INDEX_SET        ; arr[j] = temp     ← 原来 4 条
INDEX_SET                                  INC
MOV  arr → 临时                            FOR_LOOP
MOV  j   → 临时
MOV  temp→ 临时
INDEX_SET
INC
FOR_LOOP
```
⇒ 函数代码 176 → **120 字节**，内层 **14 → 10 条**（−29%）。

**⚠ 安全性：写路径比读路径多一条约束（这是本次的核心难点）**
- 读路径的论证照旧：`OP_INDEX_SET` 是"先读 R[A]/R[B]/R[C]，再写数组元素"，
  即使三者是同一个寄存器也安全（写的是数组内部，不是寄存器槽）。
- **新增约束**：值的求值发生在**派发 `INDEX_SET`/`SET_FIELD` 之前** ⇒ 若右值会改写
  「下标 / 接收者」所绑的局部量，直取就会读到**新值**：
  `arr[i] = f()`，而 f 内部把 i 改了 ⇒ 直取版写 `arr[新 i]`、快照版写 `arr[旧 i]`。
- 修法：新增 `ast_may_write_slot()`（`ast_may_read_slot()` 的写侧对偶）：认得的节点精确递归，
  **含调用/赋值一律返回 1**（闭包可能改写捕获的局部量，编译期看不出来）⇒ 回退到
  "先搬进临时寄存器"的老路径，只多占一个寄存器，语义不变。值那一侧只对**裸变量**
  （`AST_VAR`，无副作用）直取。

**⑤-q `while` 回边融合（每轮省一条 `JMP`）+ 顺手修掉 `while` 里 `continue` 的静默错值 —— ✅ 已完成**

**起因**：查 ⑤-p 之后的剩余项时回到 `while` —— 它不是"每条指令更贵"（那点早被证伪），
而是**每轮多一条控制指令**：`CMPJMP_false(cond) → exit` + `<body>` + `JMP head`。

**① 顺手发现的 bug（静默错值，优先修）**：`gen_while` **收集了 `ctx.continue_jumps` 却从不
`patch_jmp_to` 回填**（`continue_target` 这字段写了没人读；`for`/`for_iter` 都会回填）⇒
那条 `OP_JMP` 的偏移停在 **0**，`frame->ip += 0` 等于**不跳** —— `continue` 之后的语句照样执行。
- 实测：`while i < 10 { i++; if i == 5 { continue }; s += i }` 得 **s=55（应为 50）**。
- **为什么一直没被发现**：套件当时 359 项全绿 —— `continue` 的用例（`test_control_flow`、
  `test_for`）**全在 `for` 里**，`while` 这一格零覆盖。
- 修法：在 `gen_while` 里回填（目标 = 回边那次条件重测）。新增用例
  `assert/test_while_continue.leno`（5 组判据：融合路径 / **复合条件走回退路径** / 嵌套只作用于
  内层 / break 与 continue 混用 / continue 在体末）。
- **"用例必须能红"的零构建验证**：直接拿仓库里改动前的 `build/lenoreg_old.exe`（`b49ada9`）跑新用例
  ⇒ 报 `断言失败: 期望 50, 实际 55` ✓ 不是空用例（**比临时回退再重建省一次构建**，值得沿用）。

**② 回边融合（本次的性能改动）**：把条件的重测挪到循环体之后，复用「比较 + 条件跳转」指令：

```
原形态（每轮 2 条控制指令）              现形态（每轮 1 条）
head: CMPJMP_false(cond) → exit          entry: CMPJMP_false(cond) → exit
      <body>                             body:  <body>
      JMP head        ← 白付一次派发           CMPJMP_**true**(cond) → body
exit:                                    exit:  （fall through 即退出）
```
- **`CMPJMP` 一族原本只有"为假则跳"**（4 条指令全是），回边要的是"真则跳"。
  **没有新增 opcode**：`C` 字段本来就只当标志用（bit7 = 立即数），而 **bit6 在寄存器模式与
  立即数模式下都是空闲的** ⇒ 用它当极性位（`0x40`）。既有字节码语义完全不变。
- **语义等价性**：条件求值次数不变（入口 1 次 + 每轮 1 次）；`break` → exit 不变；
  `continue` → 回边那次重测（与"跳回循环头重测"等价，只是少走一条 `JMP`）；
  融合不成立时（复合条件、非 int 比较）回退成 `cond + JMP_IF_TRUE body`，仍比原形态省一条。
- **反汇编同步**：`debug.c` 现在按极性照实打印「为真则跳 / 为假则跳」——
  否则会照旧印成"为假则跳"，让人按反汇编反推错语义（文档里记过"按名字查错指令、白折腾"的坑）。
- **⚠ 自己挡掉了一个"改动引入的静默错值"**：`CMPJMP` 的偏移是 **16 位带偏置**
  （`patch_common` 对超范围是**截断到边界**而非报错），而原形态的回边是 `OP_JMP`（24 位、8MB 内安全）
  ⇒ 换成融合回边后，**>32KB 的循环体会静默跳错**。已加尺寸闸门：偏移不够时就回退到
  `cond; JMP_IF_FALSE → 跳过; JMP body`（24 位）—— 宁可多一条也不静默跳错。

**⑤-t 位运算/移位的**常量化**（T14）—— ✅ 已完成**

**起因**：`examples/性能测试/bench_bitwise_loop.leno`（对齐 Java 的位运算跑分）实测
**Leno 慢 Lua 1.96x**（2 亿轮：Leno 3002ms / Lua 1532ms，结果两边都是 1198）。
- 该基准原先写 20 亿轮（Lua 侧要跑上百秒），已改成 **2 亿**并新增 `.lua` 对照
  （`.leno` 的 `for 0 : N to i` 里 `:` 是**闭区间**，Lua 的 `for i = 0, N` 同样闭区间 ⇒ 轮数严格一致）。

**根因（反汇编）**：每轮 **10 条**，其中 **4 条 `LOADI` 是纯搬运** ——
`inp & 7` 必须先 `LOADI r,7` 再 `OP_BITAND r`，而且**每轮重装同一个常量**：

| | 每轮字节码 |
|---|---|
| Leno | `LOADI 8` +SHR、`LOADI 7` +BITAND、`LOADI 1125` +BITXOR、`LOADI 1135` +BITAND、`ADD_INT_IMM`、`FOR_LOOP` = **10 条** |
| Lua 5.4+ | `SHRI`、`BANDK`、`BXORK`、`BANDK`、`ADDI`、`FORLOOP` = **6 条** |

算术家族早有 `*_IMM`（`ADD/SUB/MUL/LT/…_INT_IMM`），**位运算与移位家族一条都没有**。

**改法**：新增 6 条常量化指令 `OP_{BITAND,BITOR,BITXOR,SHL,SHR,USHR}_K`
（`A` = 结果寄存器，`B` = 左操作数寄存器，`C` = 常量索引；
`C` 为 0 或 >255 时紧随一条 `EXTRAARG` 携带 24 位索引 —— **与 `OP_CALL_NATIVE` 同一惯例**）。
- **为什么走常量表而不是 int8 立即数**：`x & 0xFFFF`、`x & 1135` 这类超 8 位常量同样常见
  （本例的 `1125`/`1135` 就在 int8 之外），常量表没有幅度限制。
- **不复制 handler**：把 6 个 op 的函数体抽成宏（`BITAND_BODY(CV)` …），
  **寄存器版与 K 版各实例化一次** ⇒"语义逐字同体"由编译期强制成立（唯一差异是右操作数
  取 `R[C]` 还是 `constants[C]`），bigint 免装箱快路径、移位量的边界判断等全部只有一份。
  仓库有《单一事实来源与重复实现收敛》待办 ⇒ 新指令不该再抄一份 handler。
- **codegen**（`gen_binary`）：右操作数是整数字面量 ⇒ 右值**不物化**，直接走 K 版。
  **可交换的 AND/OR/XOR 还支持字面量在左边**（`1125 ^ inp`）：常量放 `C`、变量放 `B`
  （交换律保证等价；被换的只有"字面量那一侧"，字面量无副作用、另一侧又限定为普通局部变量
  ⇒ 求值顺序不可观测）。位移类不可交换 ⇒ 只处理右操作数（移位量）。
- ⚠ **两处占位寄存器必须补**（`rl` 在"字面量在左边"时、`r` 在右值是字面量时）：
  与 `rhs_imm` 同一坑 —— 不补占位，收尾会去 `reg_free` 寄存器 0 ⇒ **整个分配器错乱**
  （文档里记过"单跑测试都过、runner 里 351 个用例全挂"）。
- opcode 追加在末尾 ⇒ 既有编号不动、旧 `.lenb` 仍可执行。

**⑤-t 运行期错误被残留 try handler 反复接住 ⇒ 挂死（死循环）—— ✅ 已修复（正确性优先）**

**怎么撞上的**：⑤-s 之后做 T11（null 不能参与运算）时，新写的运行期用例
`assert/test_null_arith_error.leno` **只有一条断言失败**，表现却是"跑几分钟没有任何输出" ——
不是用例慢，是**挂死**：`try { … } catch { … }` **之后**的运行期错误被那个 catch 反复接住，
控制流一次次回到 catch 段（每轮计数 +1），永不退出。

**最小复现**（除零就够；与 T11 **无关**，是**既有**缺陷）：

```leno
main() {
    var z = 0
    var c = 0
    print("A")
    try { var v = 1 / z } catch { c = c + 1 }
    print("B c=" + c)      // ← 只打印一次
    var boom = 1 / z       // ← try **之外**抛错
    print("C")
}
```
修复前：`A / B c=1 / B c=2 / B c=3 …` **永不退出**。

**根因：两处异常派发分叉**（`vm/vminc/vm_exception.inc` 的运行期错误派发 vs
`vm/vminc/run/09_exception.inc` 的 `OP_THROW`）：

| | `OP_THROW`（对） | 运行期错误（错，已修） |
|---|---|---|
| 找 handler | `catch_ip ?: prev_catch_ip`（认外层兜底） | 只看 `catch_ip`/`finally_ip` ✗ |
| 接住之后 | **注销所用 handler** ✓ | 不注销 ✗ |
| `finally` 相关 | `in_finally` 守卫 + `catch_finally_ip` 分支 | 都没有 ✗ |

第 ② 条是主凶：`} catch {`（**无变量**）根本不发 `OP_CATCH`（codegen 侧注释里记着同一件事），
所以"OP_CATCH 会清 `catch_ip`"这个假设对最常见的 `catch { … }` **从来不成立** ⇒ handler 永远挂着。

**为什么它比"一条用例慢"严重得多**：任何带 `try` 的用例**只要断言失败一次**，就会挂死而不是判红
⇒ 门禁退化成一堆 120s 超时，而**真凶（断言失败）完全看不到** —— 本次排查就被它误导了整整一轮。

**修法**：运行期错误派发与 `OP_THROW` 逐条对齐（`prev_*` 兜底 / 接住后注销 / `catch_finally_ip`
分支 / `in_finally` 守卫），并在两处都写明"必须同口径，别再一次分叉"。

**用例必须能红**：新增 `assert/test_runtime_error_after_try.leno`（3 判据：try 之后的运行期错误必须
报错退出 / catch 体内抛错要传给外层 catch / finally 体内抛错不得绕回自己）。拿改动前的

**⑤-u T11：`null` 不能参与算术运算 —— 编译期能定的提到编译期，其余运行期拦 —— ✅ 已完成**

**规则出处**：教程的运算符类型规则（「bool 和 null 不能参与算术运算」）与「值类型字段必须指定默认值」
一节（不写默认值的值类型字段初值是 **null**，参与算术会「**编译警告或运行时报错**」）。
此前只实现了一半：字面量报错、可空类型只给警告，而**特化指令把 null 静默读成 0**
（`val_as_int(NULL_VAL) == 0`，`TAG_NULL = 0`）⇒ 值类型字段那种最危险的写法反而**无声算 0**。

**按"编译期能确定就别拖到运行期"分两层**（作者拍板）：

| 形态 | 判定 | 结果 |
|---|---|---|
| `null + 1`（字面量） | 编译期 | **编译错误**（既有） |
| `var a = null; a + 1`（声明即 null、此后没被写过） | 编译期 | **编译错误**（新增） |
| `int? a = null; a + 1`（同上） | 编译期 | **编译错误**（新增，教程此前只承诺警告） |
| 未赋默认值的值类型字段 `s.x + 1` | ✗ 静态无解（静态类型就是 `int`，运行期才是 null） | **运行期错误**（新增） |
| nullable 被别处赋过值 / `s.x += 1` / `s.x & 3` … | 不确定 | **运行期错误**（新增） |

- 编译期那半：`Symbol.is_null_value`（声明时初始化为 `null` 字面量 ⇒ 置位；任何写操作
  （`a = v` / `a += v`）⇒ 清位），在 `semantic_type.c` 的二元 / 一元取负 / 复合赋值三处报错。
  **⚠ 判据是「宁漏勿误报」**：误报会让本来能跑的程序编译不过，比漏报严重得多 ⇒ 拿不准一律不报。
  专门的**误报守卫**在用例里（声明后赋过值、条件赋值、闭包内赋值、循环内赋值、同名遮蔽
  ⇒ 必须全部编译通过）。
- 运行期那半：特化算术/位运算指令的守卫从「非 bigint」改成「**两侧都是 int48**」（都是两次 tag 比较，
  快路径代价不变），null 走冷路径报错 —— 文案逐字取自通用路径与栈式，不另起炉灶。
- **兼容性影响（有意为之）**：仓库里两处用例的 `struct` 值类型字段原本没写默认值、恰好参与算术
  ⇒ 已补默认值（`test_call_arg_reg_reuse.leno` 的 `float aframe`、`test_cross_module_method_args.leno`
  的 `int x`）。这正是教程警告的那种写法，规则上线后它**必须**显式写默认值。
- 用例：`assert/test_null_arith_error.leno`（运行期那一半，14 组判据 + 对照组）、
  `assert/test_null_arith_compile_error.leno`（编译期那一半 + 误报守卫）。

**⑤-s `for 容器 to v` 迭代条件融合（T13）—— ✅ 已完成**

**起因**：⑤-q 收掉 `while` 之后，同类候选只剩 `for_iter` 的回边。一开始的疑虑是
"它的条件带内置 `len()` 调用"——**先查清再说**：反汇编显示条件不是原生调用，而是专有指令
`OP_LEN`（`for_iter` 的 codegen 自己发），所以"把原生调用换成专用指令"这条路**不存在**。

**真正的账**（同机实测，1e6 元素数组迭代 1e7 轮）：

| 循环形态 | 每轮固定开销 | 实测 |
|---|---|---|
| `for a to x {}`（空体） | **6 条**（LEN, LT, JMP_IF_FALSE, ITER_GET, INC, JMP） | **10.03 ns/轮** |
| `for M to i {}`（数值 for，对照） | 2 条（INC, FOR_LOOP） | **3.12 ns/轮** |

⇒ 容器迭代的每轮开销是数值 for 的 **3.2 倍**，这就是要收的东西。

**先否掉一个"看起来白赚"的改法：把长度提到循环外。**
- 先量现行为（改动前，`for a to x` 起于 `[1,2]`、每轮 `a.add(9)`）：
  **6 轮结束、最终 len=6** ⇒ 长度是**每轮重读**的，追加会把循环"撑长"。
- 栈式实现的 `gen_for_iter` 同样每轮 `GET_LOCAL obj; OP_LENGTH; OP_LT`
  ⇒ **两侧口径一致，这是有意语义，不是缺陷**。
- 提到循环外会静默把它变成 **2 轮** —— 属于**语义决策**（还牵扯"迭代中 `remove` 会不会变成越界"），
  不是代码生成优化，**不做**（要改必须两侧一起改 + 写进语言文档）。

**改法：新增一条融合指令 `OP_CMPJMP_ITER`**（语义等价，长度仍在每次测试时读）：
```
原先每轮: LEN, LT, JMP_IF_FALSE, ITER_GET, [体], INC, JMP
现在每轮: ITER_GET, [体], CMPJMP_ITER(先自增 + 比较 + 真则跳回)
```
- 编码：`A` = 索引寄存器，`B` = 容器寄存器，`C` 只当标志 —— **bit6 = 真则跳**
  （⑤-q 为 `while` 回边引入的那一位，这里直接复用）、**bit5 = 先自增索引再测试**；
  紧随 4 字节字的低 16 位 = 跳转偏移（与 `CMPJMP` 同约定）⇒ 8 字节。
- **opcode 追加在末尾** ⇒ 既有编号不动、旧 `.lenb` 仍可执行。
- 索引寄存器恒为 int（codegen 用 `LOADI idx,0` 初始化，此后**只有**这条指令写它，
  用户可见的索引变量是另一个槽）⇒ 无需类型检查；自增用 `VM_INT_RESULT`
  与 `OP_INC` 同口径（超 int48 提升 bigint）。
- **顺手收掉一处重复实现**：长度规则原先内联在 `OP_LEN` 里，现在抽成
  `vm_helpers.inc` 的 `static inline vm_container_len(Value)`，`OP_LEN` 与
  `OP_CMPJMP_ITER` 共用（仓库有专门的《单一事实来源与重复实现收敛》待办，
  新指令不该再抄一份；字典 `acount+count`、struct 字段数、enum 成员数这三支
  "缺了就会静默不进入循环"的坑，注释一并搬进 helper）。
- **尺寸闸门**：融合指令是 16 位偏移，循环体 >32KB 时回退成
  `INC + LEN + LT + JMP_IF_FALSE + 24 位 JMP`（与 ⑤-q/T12 同一手法，宁可多一条也不静默跳错）。

**实测（同机同轮 A/B，`git stash` 出基线；4 次取最小）**：

| 场景 | 改前 | 改后 | 变化 |
|---|---|---|---|
| `for a to x {}`（空体） | 98.60ms | **51.97ms** | **−47.3%** |
| `for a to x { s = s + x }` | 112.27ms | **75.13ms** | **−33.1%** |
| 数值 for（**对照**，机制上不受影响） | 30.52 / 63.75ms | 29.24 / 61.89ms | −4.2% / −2.9%（漂移）|

- 与指令数模型对得上：空体 6 条 → 3 条（理论 −50%，实测 −47%）。
- 每轮固定开销 **10.03ns → 5.20ns**；容器迭代相对最紧的数值循环（+下标读）
  差距由 **1.76x 收到 1.21x**。
- 对照项也"快了 3~4%"是熟悉的老毛病（布局/漂移），方向与本改动一致 ⇒ 只会让收益被低估。

**⑤-r T12：跳转偏移溢出从「静默截断」改成「编译期报错」—— ✅ 已完成（正确性优先）**

**动机**：⑤-q 做 `while` 回边融合时自己踩到了这条 —— `patch_common` 对超范围偏移是
**截断到边界**（16 位编码把 `bx` 夹到 `[0,0xFFFF]`；`OP_JMP` 连夹都没有、直接按掩码写低 24 位），
于是生成一条"跳到别处"的指令，运行期行为错乱且**没有任何提示**。按本文档一贯判准，
"静默错值"比"报错"严重得多，所以整条清掉。

**前提验证（先证明它不是空想）**：造一个"单个 `if` 体 = 4 万字节"的程序
（`var x = 1; var y = 0; if x < 1 { y = y + 1 × 10000 }`，每条 4 字节 ⇒ 体正好 **40000 字节**）：

| exe | 现象 |
|---|---|
| 更早的 `b49ada9` | **直接崩溃**（exit `-1073740791` = fail-fast），零输出 |
| ⑤-q 那版（有截断、无检查） | 编译"成功"并执行 ⇒ 报运行期 `字段访问需要结构体对象`，**行号 271312790** |
| 反汇编器 | 自检印出 `[反汇编自检] OP_CMPJMP_LT 的跳转目标 32783 不在指令边界上` |

⇒ 三种表现都"没有任何有用诊断"（崩溃 / 垃圾错误 / 只有反汇编时才看得见）。

**实现**（`src/codegen/codegen_emit.c`）：
- 新增 `report_jump_overflow(gen, pos, offset, limit)`：从 `chunk->lines[pos]` 取行号
  （`lines` 是**按字节偏移索引**的，与 VM 的 `GET_CURRENT_LINE()` 同一张表），
  `error_add(ERR_SEMANTIC, line, msg)`。
- `patch_common` 三种编码各加一道范围检查 + 夹断兜底（32 位不溢出）：
  `OP_JMP` = 24 位有符号 ±8388607；`CMPJMP` 与 `iAsBx` = 16 位带偏置 ±32767。
- `patch_sbx_at`（`FOR_PREP` 前跳 / `FOR_LOOP` 回跳，同样是 16 位）同样检查。
- **报错能让编译真的停下**：`main.c:801` 在 `codegen()` 之后就有
  `if (error_has_any()) goto compile_fail;` ⇒ 不会去写 `.lenb`、不会执行，**退出码 -1**（已实测）。

**修后表现**（同一个 4 万字节程序）：

  而且正好绕开了 ⑤-k/⑤-l/⑤-m 新加的字典 IC；
- `arr[index]` **1.28x**：Leno 是 `arr[0]`（**结果丢弃**），Lua 是 `k = arr1[1]`（存下来）；
- `try 有` **0.08x**：Lua 每轮 `pcall(function() ... end)` 要**新建闭包**（天然极慢）；
- `arr.add` / 步长2：Lua 的 `table.insert` 是函数调用；
- fib 记忆化/迭代/尾递归/n=1000、嵌套 for/while：**绝对值 <8ms，Lua 侧被 1ms 量化** ⇒ 比值无意义。

**逐指令边际成本（2026-09-22 新算 —— 用来定位"基线"到底是什么）**

同一份微基准里的边际差（1e7 次，单位 ms；带「衍生」的是由相邻项相减得到）：

| 边际项 | Leno | Lua | 读法 |
|---|---|---|---|
| 循环指令本身（`for 空体`，1 条/轮） | 28.8 | 21.0 | 比值 1.37x |
| + 一条 `MOV`（`a=b` − `for 空体`） | +4.8 | +5.0 | **边际成本相同** ⇒ 普通指令的"增量"两边一样 |
| + 一条 `ADD_INT`（`a=b+c` − `for 空体`） | +14.2 | +6.0 | 差在**语义**：我们要判 bigint + 溢出 + int48 提升 |
| + 一条 `INC`（`for i++` − `for 空体`） | +11.2 | +6.0 | 同上 |
| `CMPJMP_LT`+`JMP` 这一对（衍生） | ≈52.5 | ≈33.0 | 1.59x；for 侧融合指令对是 1.48x |

⇒ **一处结论修正（重要）**：此前把 `while` 记成"比基线还差的一种形态"，**这个读法是错的**。
按**绝对边际成本**看，while 的每条目成本（63.7÷3 ≈ 2.12ns）与 for 的（40.0÷2 ≈ 2.00ns）
基本一致，且两边 VM 各自内部也一致（Lua 1.30 / 1.35ns）⇒ while 的比值看起来更大，
只是因为它**多一对"比较+跳回"**，而这一对的比值（1.59x）略高于融合指令对（1.48x），
量级落在噪声内 ⇒ **不是独立缺陷，并入下面的"基线"问题一起看**。

- **已排除（都做了实测，别再重复试）**：
  1. 编译优化等级：两边 `build.bat` 都是 `-O2` ✗；
  2. 每条指令的行号写回（`DISPATCH` 里的 `vm.current_line`）：消融只值 **7–13%**；
  3. 寄存器基址缓存（把 `frame->locals` 缓存成局部 `cur_regs`、175 处改帧统一换成
     `FRAME_RESYNC()`）：**完全中性**（探针 1.02/1.00/1.01/0.98x、排序 1.94→1.96x）⇒
     `-O2` 早已在寄存器里缓存了这一层 ⇒ **已回退**（中性收益不值得多一条不变量风险）；
  4. 测量口径（见上）；
  5. handler 序言里无条件算的 `GET_CURRENT_LINE()`（`frame->chunk->lines[…]`，3 次依赖加载）——
     消融（宏改常量 `(0)`）后 36 项全量 A/B **差异方向随测量顺序翻转** ⇒ 中性，详见 **⑤-n**；
  6. **回边的 GC 安全点检查**（`FOR_LOOP` 每轮一次的 `vm.gc_force_request` 全局加载 + 分支）——
     消融后 `for i++` 看似 −4.4%，但**对调 A/B 顺序翻成 +3.5%**，且完全不经过 `FOR_LOOP` 的
     `while` 三种形态也在同轮里动了 ±3.6~3.9% ⇒ 纯布局漂移，**无信号**。
     （该检查是 `LENO_GC_FORCE_EVERY` 测试钩子的落点，别删。）
- **⚠ 量测分辨率上限（本轮的新认识，比任何单项结论都重要）**：
  本机 A/B 的噪声底约 **±1ns/轮 ≈ ±4%**（判据：同轮里**与改动无关**的项目也会动 ±4%）。
  由此把三次消融排成一列就看得很清楚：

  | 消融对象 | 量级 | 结果 |
  |---|---|---|
  | 去掉一条 `LOADI`（**整条派发**） | ~0.9ns | **−29%**，清晰可辨 ✅ |
  | handler 序言的行号计算 | ~0.2ns | 中性（方向随顺序翻转）|
  | 缓存 `frame->locals`（175 处） | ~0.2ns | 中性 |
  | 回边 GC 检查 | ~0.2ns | 中性（方向随顺序翻转）|

  ⇒ **整条指令的削减（0.9~2.9ns）测得出来；几个 uop（0.1~0.3ns）测不出来。**
  继续在 handler 里抠 uop 等于闭着眼睛改 —— 要么先上**周期级探针**（rdtsc）把分辨率压下去，
  要么只做"整条指令"级别的改动。**别再交"中性"的微优化了。**
- **剩余嫌疑（按可操作性，已按上面证据修订）**：
  1. **代码密度 / I-cache**：`vm_run` 是**一个 4000+ 行的函数**，其中 `OP_INDEX` 单个 handler
     就有 256 行 ⇒ 热派发循环与巨型冷路径纠缠在一起（Lua 的 handler 大多 ~20 行）。
     对应 **T9**（把巨型 handler 的冷路径抽成 `static` 函数）—— 现在多了一个**性能**理由；
  2. 各算子里比 Lua 多的检查（bigint/溢出/int48 范围/GC/类型派发）—— 由边际成本表算出：
     `FOR_LOOP` 比 Lua 重 **+7.8ms/1e7**、`INC` **+5.2ms**、`ADD_INT` **+8.2ms**，
     即**每条指令额外 0.5~0.8ns**。这是 Leno 数字语义（int48 提升 + bigint + null）的**固有代价**，
     不是 bug，抠不掉；且逐项都**低于上面的分辨率上限** ⇒ 不构成可攻目标；
  3. ~~派发本身的固定开销（间接跳转 + `ADVANCE` + `frame->ip` 经结构体字段访问）~~
     —— **已证伪（2026-09-22）**：`MOV` 的边际成本两边**几乎相同**（+4.8 vs +5.0ms/1e7），
     说明"多一条派发指令"的代价并不比 Lua 贵 ⇒ 派发机制不是瓶颈。
     `frame->ip` 提局部变量 / 寄存器窗口这一族**不必再试**（与已排除项 3、5 同源，第三次同向否定）。
- **下一步建议（已改向）**：
  1. 唯一"量级够大"的剩余目标是**调用路径（微基准 2.27x）** —— 结构性：`CallFrame` ≈384B、
     每次调用写 14 个字段跨 6 条 cache line；Lua 的 `CallInfo` 只有几十字节。风险高，需先想清方案。
  2. 继续做**整条指令削减**（唯一被证明有效的杠杆：`a+=1` −28%、`arr[0]` −29%、空体返回 −7.8%）：
     方法是 dump **真实程序**的字节码数条数，找可以整条删掉的，而不是在 handler 里省 uop。
  3. 若仍要做微优化，**先解决量测精度**（周期级探针），否则做出来的结论不可信。

**判据**（每条独立验证、独立提交）：`lenoreg --debug` 里能 dump 出新融合指令；
相关样例耗时不变差；断言套件 **366/366**；提交信息附 **同轮双向 A/B 数据**
（机器频率与**构建布局**都会漂移，跨轮比较不可信 —— F1 那次差点被误导；
⚠ 本轮补一条：**同一轮里不相关的项目也可能动 ±4%**，所以必须对调顺序双向验证）。

> 注：F1（`arr.add(x)` 融合 + `OP_ARRAY_APPEND` 补 GC 写屏障，`b209f07`）就是"反向差异"的第一条，

**⑤-v 追 Lua 的第二轮（2026-09-23）：零拷贝原地帧 / 位运算裸位运算 / int48 越界修复**

> ⚠ **教训（本轮最大的收获，写给下一次的自己）**：动手消融前**先读本节的"已排除"清单**。
> 本轮我先试了 `GET_CURRENT_LINE()` 消融、`FOR_LOOP` 回边 GC 检查消融 —— 做完才发现
> 这两条**早就在下面第 5、6 项里记着"中性"**，白烧了两轮构建。

- **宽口径复核**（`全部测试.leno` vs `.lua` + `各种排序`）：差距**仍是弥散的 1.3–1.7x**，
  唯一量级够大的仍是**调用路径（2.27x → 本轮 2.51x）**。**没有新的单点肥肉** —— 与 ⑤-g 一致。
- 本轮拿下三笔**整段算子级别**（不是 uop 级）的改动：

**✅ 已完成（三笔，各自独立提交、独立验证）**

1. **零拷贝原地帧**（`0cab715`）—— 照 Lua `luaD_precall / prepCallInfo`：被调方的寄存器区
   **直接复用调用方实参那一块**（`locals = caller->locals + arg_base`）⇒ 实参零搬运、
   非参数槽位零 nil 填充、不另占内存。原先每次调用要「另取一块 locals 数组 + 逐个复制实参
   + 其余槽位全填 null」。
   关键第二刀：判定用**物理容量**（新增 `CallFrame.locals_capacity`）而**不是** `local_count`
   这个寄存器高水位 —— 自有 `inline_locals` 有 64 格，用高水位（往往一二十）会白白漏掉
   一大片本来可以安全别名的空间。
   实测 **PBKDF2 主耗时 11.43ms → 10.07ms（−12%）**，反超栈式（11.42ms）。
   ⚠ 踩过的坑：`call_reg_impl` 漏写 `locals_capacity` ⇒ alias 帧读到**帧槽复用的脏容量**，
   递归链上层层误判"装得下"直到数组越界（`fib(20)` 直接崩）⇒ **6 处建帧点都要写**。
   ⚠ 帧数组扩容时 `locals` 指针的搬迁也改了：原实现无条件写成自己的 `inline_locals`，
   会把原地帧指向调用方的指针改错 ⇒ 改成按地址差统一平移。

2. **位运算快路径改"裸位运算"**（`e91ed86`）—— 见 `04_compare_bit_cast.inc` 的 ★★ 注释。
   NaN 装箱下两个 int48 是 `T | p`（T = `QNAN|SIGN_BIT|TAG_INT` **两侧相同**，p 是 48 位补码
   载荷、只占 bit 0..47）⇒ **AND/OR 直接在原始 64 位上做就是精确的**，XOR 补回 T 即可
   （负数只是 48 位补码，照样成立）。省掉两次拆箱（其中符号扩展带**分支**）+ 一次装箱。
   实测 `bench_bitwise_loop`（2 亿轮 × 6 条）**2588ms → 1946ms（−25%）**，对 Lua **1.80x → 1.36x**。
   ⚠ 定位过程（方法论）：先反汇编确认**指令数完全相同**（Lua 的 `MMBINI/MMBINK` 在整数快路径上
   被 `pc++` **跳过**，实际每轮也是 6 条）⇒ 差距全在每指令成本；再两步消融：守卫 384ms、
   拆箱/装箱 **504ms** ⇒ **拆箱/装箱才是大头**，不是类型检查。

3. **int48 越界必须提升 bigint**（`27669a0`）—— 正确性修复（静默错值，比崩溃更难查）。
   · 左移：守卫只看**移位量**、看不到**左值大小** ⇒ `123456789012345 << 3` 静默截成
     -138245594743864（正确 987654312098760）。判据必须**先比阈值再移位**（先移位会撞
     int64 左移 UB，回绕后还会被误判成"在范围内"—— `hi << 1` 就是这么算成 -2 的）。
   · 除法：只有一个越界组合 `INT48_MIN / -1 == +2^47`。
   · 同族已核过、**无需改**：ADD/SUB（`VM_INT_RESULT`）、MUL（`LENO_MUL_OVERFLOW`）、
     NEG（范围检查）、USHR（`val_int_safe`）、MOD（结果绝对值恒小于除数）、BITNOT（`~x` 封闭）。
   · 新增 `assert/test_int48_overflow.leno` —— **这两个边界原先一个都没被覆盖**，
     套件全绿也漏（"全绿"不等于"覆盖到了"）。

**❌ 已回退（中性 —— 接在 ⑤-c"已排除"清单的第 6 项之后，别再试）**

7. **把 `frame->ip` / `frame->locals` / `frame->chunk->constants` 提成局部量**
   （207 处帧切换点统一 `RELOAD_FRAME()`）：改动正确（365/365）但**零收益甚至略差**
   （2622~2655ms vs 基线 2588ms）。与已排除项 3、5 同源 ⇒ **第四次同向否定**。
8. **K 版位运算守卫削减**（`_K` 的常量由 codegen 保证是 int48 ⇒ 那次 `val_is_int(cv)` 可证冗余）：
   **零收益**（1957 vs 1920，噪声内）⇒ 那 384ms 来自**守卫的分支本身**，不是比较次数。
9. **`FOR_LOOP` 非计数制回退路径（bigint/float）整体短路**：**中性**（33.2~35.6 vs 30.4ms）
   ⇒ "代码密度 / I-cache" 这个假设**在 `FOR_LOOP` 上不成立**（它在位运算族上成立）
   ⇒ 剩余嫌疑 1（T9）的**适用范围比原先设想的窄**：要挑 handler 做，不是普遍规律。

**✅ 本轮新做的一笔（整段级，非 uop 级）**

4. **`OP_FOR_LOOP` 计数器"原始值减一"**（Lua `chgivalue` 同口径）：end 槽本来就是 canonical
   的 int48 Value `T | count`，而 `count ∈ [1, 2^47-1]` ⇒ 减 1 **不会借位到标签位**，
   结果恰等于 `val_int(count-1)`。省掉「拆箱（含符号扩展分支）→ 减 → 装箱」三步。
   **A/B 分布不重叠**（各 5 轮，空体 for 1e7）：BASE 31.8 / 32.5 / 34.0 / 34.0 / 34.1ms
   vs NEW 30.7 / 28.9 / 29.2 / 30.3 / 28.8ms ⇒ **min −9.4%、中位数 −14.3%**。
   ⚠ **量测提醒**：这条**第一版 3 轮判成了"中性"** —— 正是 ⑤-c 末尾警告的那种情形。
   凡是要下"有/无收益"的结论，必须做到**分布不重叠**，否则不要下结论。

**⚠ 口径提醒（本轮复核，与 ⑤-c 结论一致）**
- `dict[k]=v` 在 `全部测试` 里 Leno 跑的是 `d.set("key",1)`＝**方法调用**（`GET_METHOD+CALL`），
  Lua 跑的是 `d["key"]=1`（1 条）⇒ 表里的 **4.10x 不是差距**。同一二进制内实测三形态：
  `d.set(k,v)` **157.6ms** / `d[k]=v` **69.5ms** / `d[k]` 读 **62.1ms**
  ⇒ **公平对照是 `d[k]=v` 对 Lua 的 41ms = 1.70x**（与基线一致）。
- 排序组（≥10 万档，Lua 量化误差 <5%）：原地/优化快排 **1.27–1.34x**，
  与 ⑤-c 记录的 1.26–1.37x 一致 ⇒ 那批数字仍然可信。
