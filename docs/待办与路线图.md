### T3（P1）async 类型推断三连：C3 + C6 + C5

**为什么**：这三条是**同一个子系统** —— "`Future` 出现在某个位置时，静态类型推不出来"，
现状是**合法 async 代码在编译期就过不去**。合起来做最省。

| 项 | 现象 | 现状 |
|---|---|---|
| C3 | `a?.b()`（安全访问调 async 方法）静态类型是 `int?` | 运行时**是对的**、类型错（已实测，见下） |
| C6 | `await` 作用于**声明为 `Future` 的形参 / 字段** | 推不出类型 |
| C5 | `func` 形参里 `await cb(x)` | 推成 `func()` |

**已实测证据（C3）**：

```leno
struct W {
    int v = 7
    async func go(): int {
        await asyncs.sleep(5)
        return self.v
    }
}

async func driver() {
    var w = new W()
    var b = w?.go()        // 运行时正确：实测方法体里 current() = 3 ⇒ 确实建了协程、在协程里跑
    io.print(type(b))      // object（运行时是 Future）
    // 但**静态类型**是 `int?` ⇒ 下面这条编译期就失败：
    //   asyncs.is_done(b)  →  「参数 1 类型错误: 期望 'Future'，但传入 'int?'」
}
```

**判据**：`w?.go()` 的静态类型是 Future（可选包装则为"可选 Future"）⇒
`await w?.go()` / `is_done(w?.go())` / `all([w?.go()])` 都能编译通过；
`await` 声明为 `Future` 的形参/字段、`await cb(x)`（`func` 形参）同样能编译；**补断言**。

### T4（P2）`asyncs.all` 的语义：C8 + C10 —— ⛔ 需要先拍板

**现状**（不是纯 bug，是"文档这么写、但直觉相反"）：
- 文档原话：`### all(futures)` 「收集多个**已完成** Future 的结果」；
- 未完成的成员 ⇒ 结果里给 `null`（C10）；
- 失败的 future ⇒ 也给 `null`，错误**延后到 `run()`** 才炸（C8）。

**两个方向**：

| 方向 | 内容 | 影响 |
|---|---|---|
| (a) | 保持文档语义，把"调用 `all` 前必须 await"写成显式警示 | 不改行为，只改文档 |
| (b) | 改成"等齐全部 + 汇总错误" | 更符合 `all` 的名字，但**与现有文档相反**（新 A 类差异） |

**我的倾向：(b)**。理由是这几轮一贯的优先级 —— **静默错值 > 编译期报错 > 性能** ——
而"`all([失败future])` 返回 `[null]`、错误跑到别处才炸"属于最该消灭的那一类。

**判据（若选 b）**：`all` 等待所有成员完成；有失败 ⇒ 抛**汇总错误**（与 `run()` 的
「N 个协程失败: …」同口径）；`docs/module_asyncs.md` 同步改写；补断言。

### T5（P3）性能

#### ✅ 已修：`OP_MODULE_CALL` 的内联缓存是死字段（`a40f0fa`）

用户实测 `examples/性能测试/函数调用数学计算.leno`：栈式 4528ms / 寄存器式 7903ms（**慢 1.68x**）。

分解实验（关键：先把"哪一段慢"隔离出来）：

| 探针 | 栈式 | 寄存器式 | 结论 |
|---|---|---|---|
| 纯浮点循环 2000 万次 | 236ms | 148ms | 0.63x，**寄存器式更快** |
| 整数循环 2000 万次 | 1153ms | 643ms | 0.56x，**寄存器式更快** |
| `maths.sqrt` 1000 万次 | 199ms | 310ms | 1.55x 慢 |
| `sin*cos` 2000 万轮 | 802ms | 1465ms | 1.83x 慢 |

⇒ 差距**全在原生模块调用**这一条路上（≈22ns/次），与 VM 模型/算术/循环无关。

根因：`OP_MODULE_CALL` 每次调用都 `native_find_module_method()`（哈希 + 两次 `strcmp`），
而 `vm.ic_module_cache`（`InlineModuleCallCacheEntry` + `IC_MODULE_CACHE_SIZE 2048`）
**定义了、初始化了，handler 里从没读写过** —— 死字段（注释还写着"避免每次调用都做哈希表查找"）。
接上后：**7903ms → 3878ms（0.85x，反超 18%）**；`maths.sqrt` 探针 310→162ms。

#### ✅ 已修：另外两个死 IC（`8642aeb`）—— struct 方法查找 / struct 定义查找

| 缓存 | 用在哪 | 接线后的键 |
|---|---|---|
| `ic_method_cache` | `OP_GET_METHOD`（struct 分支） | 调用点 + `def` 指针 + 方法名哈希 + `struct_def_generation()` ⇒ 缓存**预创建闭包** |
| `ic_structdef_cache` | `OP_STRUCT_INIT` | 调用点 + 名字哈希 + 定义表代数 + `mod_owner` ⇒ 缓存 `def` |

键与判据都照栈式 `op_struct.inc` 的同名实现（它这两处是接上的）。
**A/B 实测**（`git stash` 回退前后各跑一次）：`光线追踪对象版` 5546ms → **5108ms（−8%）**；
另两个样例噪声级 ⇒ 有效但不大，**这两个不是当前最大的瓶颈**。

#### ✅ 已修：`ic_cache`（死字段）+ 内建方法调用的窥孔优化（`759d45a`）

`vm.ic_cache` 同样是死字段 ⇒ `OP_GET_METHOD` 的内建类型分支（`arr.len()` / `str.len()` /
`d.has(x)`）每次调用都查一遍方法表。按（调用点、receiver 类型、方法名哈希）缓存
`ObjNative*` 接上；**更大的头**是照栈式 `op_property.inc` 加了窥孔：

> 下一条就是 `OP_CALL` 且调用的正是本寄存器 ⇒ **不构造 `ObjBoundMethod`**，
> 直接把 receiver 当第 0 个实参调 `method->function()`，并就地吃掉那条 `OP_CALL`。

实测 `examples/性能测试/内联缓存 (Inline Caching) 性能对比测试.leno`：
**708ms → 671ms（只接缓存）→ 188ms（再加窥孔）**，对栈式 92ms 即 **7.64x → 2.04x**。
行为探针与栈式**输出完全一致**（0 参/1 参取值、热路径循环、循环内 try/catch）。

> 至此 **5 个内联缓存全部接上**：native / module / method / structdef / ic_cache。

#### ✅ 部分已修：立即数加减（`4f4cc86`）—— 递归基准 fib 1.45x → 1.33x

用户实测 `examples/性能测试/经典斐波那契数列测试_int.leno`：栈式 ~70ms / 寄存器式 ~101ms。
反汇编对齐后，**每次递归**的指令数：栈式 **11** 条、寄存器式 **23** 条，差距三处：

### T9（P3）解释器：抽巨型 handler 成 `static` 函数（方案 B）

**已完成的前置（方案 A，`bbb95c2`）**：`src/vm/vminc/vm_run.inc` 从 4249 行单文件拆成
`src/vm/vminc/run/01..14_*.inc`（14 块、合计仍 4249 行），`vm_run.inc` 退化为 31 行的聚合文件。
拆分是**纯文本搬运**（拼回去与原文件逐字节一致），切点一律在 `LABEL(...)` 之前。

**为什么不能"拆成 .c"**：它本质是**一个函数体** —— `vm.c` 的 `vm_run()` 与
`vm_run_with_vm()` 各 include 一次（后者用 `#define vm (*vm_ptr)`），内部是
`LABEL(OP_x)` + 计算跳转。所以再往下只能做**函数级抽取**。

**只动这 6 个（实测 >100 行）**：

| handler | 行数 |
|---|---|
| `OP_STRUCT_INIT` | 285 |
| `OP_INDEX` | 256 |
| `OP_CALL` | 205 |
| `OP_STRUCT_DEF` | 171 |
| `OP_GET_METHOD` | 118 |
| `OP_INDEX_SET` | 107 |

其余 **116 个 handler 中位数只有 15 行，不要动**（动了只增加间接层）。建议顺序：
`INDEX`（纯值计算最多）→ `CALL` 的 native 分支 → `STRUCT_INIT`（最独立）。

**模式**：照 `vminc/vm_helpers.inc` 里的 `read_ext_const` —— 抽成 `static` /
`static inline`，**显式传 VM 和参数**（宏能靠 `#define vm (*vm_ptr)` 生效，函数不行）。

**两个坑**：
1. handler 里的错误路径现在是"报错 + `DISPATCH()`"，抽出去的函数**不能跳分发** ⇒
   必须用**返回值/状态码**表达失败，由 handler 决定怎么跳（别把控制流一起搬走）；
2. 分块文件里不得出现**文件级 `static`**（同一 TU include 两次会重复定义）。

**判据**：抽完后 `.\build.bat` + **断言套件 353/353**；每个被抽的 handler 体在
原分块文件里显著变短（理想 < 60 行）。（差分对照按需，不作日常判据。）

或**同义异名**（`ADD_FLOAT`≡我们 `ADD_F`、`LENGTH`≡`LEN`、`NULL`≡`LOADNIL`、`JUMP`≡`JMP`、

**真正值得补的是这几类**（已逐条核实"栈式有、我们没有"）：

| 序 | 项 | 我们的现状 | 栈式 | 预期收益 | 成本 |
|---|---|---|---|---|---|
| **1** | **比较+跳转融合** ✅ **已完成** | `LE_INT_IMM` + `JMP_IF_FALSE`（**2 条**） | `OP_CMPJMP_LI_INT` / `_LG_INT` / `_LL_INT`（1 条） | **每个 `if`/`while`/`for` 条件少 1 条**；fib 递归路径 9 → 8（**实测 0.938x**） | 中 |

**证据（fib `--debug` dump 对照）**：

| | 递归路径指令序列 |
|---|---|
| 栈式 | `CMPJMP_LI_INT` / `GET_LOCAL` / `RETURN` / `JUMP` / `GET_LOCAL` / `SUB_INT_IMM` / `CALL_GLOBAL_FUNC_TYPED` / `GET_LOCAL` / `SUB_INT_IMM` / `CALL_GLOBAL_FUNC_TYPED` / `ADD_INT` / `RETURN` ≈ **12 条** |
| 我们 | `LE_INT_IMM` / `JMP_IF_FALSE` / `RETURN` / `SUB_INT_IMM` / `CALL_GLOBAL_FUNC` / `SUB_INT_IMM` / `CALL_GLOBAL_FUNC` / `ADD_INT` / `RETURN` = **9 条** |

⇒ 栈式执行**更多**指令却打平（66.2ms vs 66.5ms）：我们**单条更便宜**、栈式**条数多但每条更薄**。
补上 1 号即可在条数上反超（9 → 8），且它作用于**所有**条件判断。

**① 比较+跳转融合 —— ✅ 已完成**

- **编码**：新增 `OP_CMPJMP_LT/LE/GT/GE`，占 **8 字节**：第一个字
  `[op][A=左操作数寄存器][B=右操作数][C(最高位=1 表示立即数形式)]`，
  **第二个 4 字节字**的前 2 字节是跳转偏移（`offset + 32768`，与 iAsBx 同约定）。
- **发射条件**（与 `*_INT / *_INT_IMM` 完全一致 ⇒ 语义等价）：`if`/`while` 条件是有序比较
  （`< <= > >=`）、两侧静态类型都是 int、左操作数是普通局部变量/参数（`SYM_LOCAL`/`SYM_PARAM`
  ⇒ 就是 `R[index]`）、右操作数是 int8 字面量或另一个局部变量/参数；任一不满足即不融合。
- **实测**：fib 递归路径 **9 → 8 条**；**同一份二进制 A/B**（`LENO_NO_CMPJMP=1` 关闭融合）
  65.7ms → **61.6ms = 0.938x**；`assert/test_cmpjmp.leno` 在**开/关两种模式下都过**
  （语义等价的直接证据）；断言套件 **354/354**。
- **三个坑**（都已踩过，后人别重踩）：
  1. `patch_jmp` / `patch_jmp_to` 的偏移必须按**指令自身长度**扣（`len - pos - size`）：
     融合指令是 8 字节，沿用 `- 4` 会静默写出错误的跳距 ⇒ 加了 `instr_bytes_at()`；
  2. **反汇编器**（`decode_trailing`）与**自检**（`disasm_self_check`）都必须知道这 8 字节，
     否则 `--debug` 的清单从那条指令起整体错位（看着像"凭空多出一条指令"），自检也核对不了它的跳转；
  3. **A/B 不要用"两次构建 + git stash"**：慢、易被机器频率漂移误导，还有把改动留在 stash 里的
     风险（本次取消时正好停在那一步）。用 `LENO_NO_CMPJMP` 这类**同二进制环境变量开关**最稳
     —— 栈式本来就有这个开关，当时就该照抄。

**② 语句上下文 `*_NOPUSH` —— ✅ 已完成（只做 `arr.add`）**

- 做法：**不新增 opcode**，直接让 `OP_ARRAY_APPEND` 认 C 位（`need_result`）——
  `C == 0` 时跳过"写回新长度"。codegen 侧在 `AST_EXPR_STMT` 里识别语句位置的
  `arr.add(x)`（`AST_CALL` + `ast.add` / `arr["add"]` 两种 callee 形态、接收者静态类型是数组、
  实参恰 1 个）⇒ 走 `gen_array_add(..., need_result=0)`。
- 效果：`a.add(i)` 作为语句从 **4 条**（MOV/MOV/APPEND+搬回 MOV）降到 **3 条**；
  **同轮 A/B 0.86x**（3.80ms vs 栈式 4.40ms）。
- 为什么没做 `INDEX_SET_NOPUSH` / `INC/DEC_LOCAL_NOPUSH`：`OP_INC/OP_DEC` 的写回**就是
  自增本身**（局部变量原地自增），`OP_INDEX_SET` 也只有赋值一条路径 ⇒ 没有"结果是废的"可省；
  真要做得多加 opcode 且收益 <1 条指令 ⇒ 暂缓（有需求再回来看）。

**③ 整数特化补全 —— ◐ 只补了 `MUL_INT_IMM`（其余有意不做）**

- **已完成**：`OP_MUL_INT_IMM`（语义与 `OP_MUL_INT` 逐条一致，含 bigint 与溢出提升）；
  codegen 把 `TOK_STAR` 也纳入立即数路径 ⇒ `x * 3` 从 `LOADI + MUL_INT` **2 条降到 1 条**、
  **同轮 0.50x**（2.17ms vs 栈式 4.35ms）。
  ⚠ 立即数路径的前提是**左操作数静态类型为 int**（沿用原有判断）—— 左值是 bigint 的
  `big * 100` 必须走通用 MUL，否则通用路径会读到空寄存器（原有注释里的老坑）。
- **清单纠错**：`LE_INT`（双变量）**本来就有**（`leno_vm.h:82`），之前那条是 grep 漏看 ⇒ 无需补。
- **有意不做**：
  - `EQ_INT_IMM` / `NE_INT_IMM`：**语义有风险** —— `==`/`!=` 目前刻意走通用 `OP_EQ`（跨 int/bigint/float
    的相等语义与"按位比较"的 `*_INT` 家族不同），补特化版要先厘清 `1 == 1.0` 这类口径，
    收益却只有"省一次类型分支"⇒ 不值得冒险；
  - `MOD_INT`：通用 `OP_MOD` 的**第一个分支就是 int 快路径**（`val_is_int && val_is_int`），
    特化版只省两次类型判断（~1–2ns）⇒ 收益太小，不值得多一条指令的维护面。

**④ 浮点有序比较特化 —— ✅ 已完成（附带一个通用收益）**

- 新增 `OP_LT_F / LE_F / GT_F / GE_F`：两侧静态类型都是 float 时替代通用 `OP_LT/LE/GT/GE`，
  不再每次调用 `value_compare_stdlib()`。**语义与通用版逐条一致**：null ⇒ false；两边是数值
  （非 bigint）⇒ 按数值比；其余（字符串 / bigint / 其它）**回退**通用比较，连报错文案都用同一份。
- **实测**（`examples/性能测试/特化指令基准.leno`，同二进制 `LENO_NO_FLOAT_CMP` 开关、
  5 次取 min）：float 比较 **0.893x ~ 0.913x**；float 字面量比较 0.956x。
- **顺带发现的通用问题**：`gen_binop` 里**右操作数**即使是普通局部变量/参数也会先 `OP_MOV`
  搬进临时寄存器（左操作数早就优化过，右边漏了 ✗）。修掉后 `a < b` 少一条指令、
  `x = x + 1.0` 这类别名情形也安全（指令先读两个操作数再写结果）。
  ⚠ 收尾的 `reg_free` 必须按 `r_is_temp` 守卫 —— 与文档里记过的 `rl` 那次是**同一类坑**
  （误释放活着的变量槽 ⇒ 变量被就地覆盖、runner 全挂）。
- **方法论教训（重要）**：这类 ~10% 的改动**不能靠单两次运行定论** —— 实测单两次的噪声就能
  把 0.91x 淹成"看不出效果"。口径固定为：**同一份二进制 + 环境变量开关 + 5 次取 min**。
  基准文件 `examples/性能测试/特化指令基准.leno` 就是为这个建的（各段都在同一进程内计时）。

**⑤ typed 直呼（`OP_CALL_GLOBAL_FUNC_TYPED`）—— ✅ 已完成（调用路径的第一刀）**

- **动机**：建帧时每个参数都要走一遍类型转换检查（int→float / bigint→float / float→int），
  每参数 4–6 个判断 —— 栈式为此专门有 `OP_CALL_GLOBAL_FUNC_TYPED`。
- **做法**：新增同编码的 `OP_CALL_GLOBAL_FUNC_TYPED`，与 `OP_CALL_GLOBAL_FUNC` **共用同一个处理体**
  （用 `frame->ip[-4]` 区分 opcode），只是改调 `call_reg_typed()` ⇒ `call_reg_impl(..., no_convert=1)`
  跳过转换循环、直接复制。
- **安全门槛（关键）**：只有当"**每个实参的静态类型 == 形参声明类型**、且都限定在 `{int, float}`"
  时才发 typed 版 —— 这两种类型正好是那套转换**唯一**会动的类型 ⇒ 跳过是**可证明的等价**。
  形参表缺失、实参个数 ≠ 形参个数（默认值补齐）、any/null/其它类型 ⇒ 一律走非 typed 版。
- **实测**（同二进制 `LENO_NO_TYPED_CALL` 开关、5 次取 min）：

  | 调用形状 | typed | 非 typed | 比值 |
  |---|---|---|---|
  | 结果丢弃（1 参） | 62.7ms | 71.2ms | **0.880x** |
  | 用结果（2 参） | 69.1 | 81.3 | **0.850x** |
  | 5 参数 | 99.1 | 118.4 | **0.837x** |
  | 8 局部变量 | 144.0 | 153.7 | 0.937x |

  （相对本会话开始时：函数调用 89.1 → **69.1ms = -22%**；5 参数 119.0 → **99.1 = -17%**。）
- **顺手澄清一件事**：`call_reg` 里那条 `TYPE_INT && val_is_float` 运行期转换分支，在本语言里
  **走不到** —— 实测"浮点字面量传进 int 形参""`any` 传进 int 形参"都被**语义层直接拦成编译期错误**
  （「参数类型不匹配」）。所以那条分支只有显式 `_int()` 这类转换后的值才可能碰到。
- **验证**：`assert/test_typed_call.leno`（同类型 / int→float 加宽 / any 形参 / 默认参数 / 多参数混合 /
  递归），**typed 开与关两种模式都过**；**关掉 typed 跑全量套件也是 357/357** ⇒ 语义等价的强证据。

> 调用形状的**横向**数据（同文件基准，栈式为参照）：纯调用 0.63x、用结果 0.75x、5 参数 0.63x、
> 8 局部变量 0.50x —— 每种形状我们都比栈式快 25–37%，所以"调用是短板"只相对于我们自己的其它段而言；
> 真正还差的是 Lua 那种"不搬参数的寄存器窗口"结构（尚未做，风险高）。

**⑤-b `OP_ACC_FIELDS`（字段访问密集场景，尚未做）—— 从"存疑"升级为"有实测证据"**

- **现象**（用户实测 `examples/性能测试/光线追踪对象版.leno`）：Phase A（对象字段访问）

- **dump 对照**（`s.cx + s.cy + s.cz + s.r` 每轮）：

**⑤-d `OP_ACC_FIELDS` + `OP_GET_FIELD_FAST` —— ✅ 已完成（借鉴栈式的两条字段访问指令）**

**⑤-c Leno vs Lua（新基准口径）—— 已排除项与剩余嫌疑**

- **基准**：`examples/排序测试/各种排序.lua`（与 `.leno` 版同算法/同规模/同跳过规则）。
  实测（各 3 次取 min）：紧循环密集的三类排序 **Leno 慢 ~1.8–1.95x**；
  而**分配密集**的"原始快速排序"**打平（0.99x）** ⇒ 差距在紧循环的指令执行，不在分配。
- **口径校验**（重要）：我们 `times.us()` 用 `QueryPerformanceCounter`（**墙钟**），
  Lua `os.clock()` 是 **CPU 时间** —— 但用**外部墙钟**测整个进程（1101 vs 636ms = 1.73x）
  与各自内部计时（1078 vs 601ms = 1.79x）**一致** ⇒ 口径差异不是原因。
  ⚠ 另外 Lua 的 `os.clock()` 在 Windows 分辨率 ≈1ms ⇒ **它的小规模数字会被量化成 0/1000**
  （2000/5000 那两档不可用），只有 100000/400000 可信。
- **已排除（都做了实测，别再重复试）**：
  1. 编译优化等级：两边 `build.bat` 都是 `-O2` ✗；
  2. 每条指令的行号写回（`DISPATCH` 里的 `vm.current_line`）：消融只值 **7–13%**；
  3. 寄存器基址缓存（把 `frame->locals` 缓存成局部 `cur_regs`、175 处改帧统一换成
     `FRAME_RESYNC()`）：**完全中性**（探针 1.02/1.00/1.01/0.98x、排序 1.94→1.96x）⇒
     `-O2` 早已在寄存器里缓存了这一层 ⇒ **已回退**（中性收益不值得多一条不变量风险）；
  4. 测量口径（见上）。
- **剩余嫌疑（按可操作性）**：
  1. **代码密度 / I-cache**：`vm_run` 是**一个 4000+ 行的函数**，其中 `OP_INDEX` 单个 handler
     就有 256 行 ⇒ 热派发循环与巨型冷路径纠缠在一起（Lua 的 handler 大多 ~20 行）。
     对应 **T9**（把巨型 handler 的冷路径抽成 `static` 函数）—— 现在多了一个**性能**理由；
  2. 各算子里比 Lua 多的检查（bigint/溢出/边界/类型派发）×…× 单条指令的固定开销；
  3. 派发本身的固定开销（间接跳转 + `ADVANCE` + `frame->ip` 经结构体字段访问）。
- **下一步建议**：先做 **T9 的示范一例**（抽 `OP_INDEX` 的冷路径），用同一套基准前后对照 ——
  能测出来就说明是 I-cache，测不出来就排除它，两种结果都有价值。

**判据**（每条独立验证、独立提交）：`lenoreg --debug` 里能 dump 出新融合指令；
相关样例耗时不变差；断言套件 **353/353**；提交信息附 **`git stash` 同轮 A/B 数据**
（机器频率会漂移，跨轮比较不可信 —— F1 那次差点被误导）。

## 五、维护约定

1. **做完一项**：差异清单补"事实"（现象 / 最小复现 / 根因 / 修法 / 回归锁定），
   这里把状态改成 ✅ 并写 commit。
2. **新发现的问题**：先判断是不是已有条目的同类 —— 是就挂到那条下面（或扩成子项），
   别新开条目，否则这份清单会碎片化。
3. **每项必须有判据**：没有"怎么算做完"的条目不算条目。
4. **改了寄存器式行为、且与栈式不同** ⇒ 差异清单必须同步（那是以后唯一的事实来源）。
