# 单文件打包（`-p --onefile`）使用指南

> 目标：**一条命令产出一个 exe**，拷到别的电脑就能跑 —— 原生库（DLL）和随包资源
> 都内嵌在 exe 尾部，首次运行时自动解包到**用户缓存目录**，不会往桌面 / 下载目录倒文件。
>
> 实现落在：`src/main.c`（打包侧）、`src/vm_main.c`（运行期解包）、
> `src/module/dirs/dirs.c`（`dirs.res_dir()`）、`src/module/ffi/ffi.c`（DLL 搜索链）、
> `src/vm/vm.c`（资源目录的存储与出口）、`src/platform/platform_path.c`（自身 exe 路径）。

---

## 1. 两种打包模式的区别

| | 目录模式（`-p`） | 单文件模式（`-p --onefile`） |
|---|---|---|
| 产物 | `<源码名>.exe` + 原生库副本（放同一目录） | **只有** `<源码名>.exe` |
| 原生库 | 复制到 dist/ 旁 | 内嵌进 exe |
| 随包资源 | **不带**（会打印提示） | 内嵌进 exe（`resource.toml` 声明） |
| 分发方式 | 整个 dist/ 目录一起拷 | 只拷 exe |
| 首次运行 | 无额外动作 | 解包到用户缓存目录（约几十 MB，一次性） |

> 目录模式仍然是默认行为，两种模式可以随时切换。切换过模式后 dist/ 里可能留着上次
> 目录模式拷进去的同名文件 —— 打包器**只提示不删**（输出目录是用户的，误删代价更大）。

## 2. 快速上手（三步）

### 第 1 步：写 `resource.toml`（放在应用目录 / 包根）

```toml
# resource.toml — 打包资源配置（独立于 leno.toml，没有 leno.toml 也能用）
[pack]
onefile   = true
resources = ["anim/**", "font/**", "image/**", "sound/**"]
```

- `onefile = true` ⇒ 这个应用**默认**就是单文件打包，不用再敲 `--onefile`。
- `resources` 是相对**本文件所在目录**（包根）的通配模式数组，声明什么就嵌什么。
- 不加 `resource.toml` 也能用命令行 `--onefile` 临时开启（那就只嵌原生库，没有资源）。

### 第 2 步：打包

```bash
# 用 resource.toml 的配置（onefile = true）
build\leno.exe -p "leno_gui\游戏\植物大战僵尸\pvz.leno"

# 或显式指定，并指定输出目录
build\leno.exe -p --onefile -o "leno_gui\游戏\植物大战僵尸\dist" "leno_gui\游戏\植物大战僵尸\pvz.leno"
```

典型输出：

```
[pack] 检测到 _console(false)，使用无控制台版 leno_vm_gui.exe
[pack] 内嵌资源: 151 个文件（来自 resource.toml [pack] resources）
[pack] 单文件模式: 内嵌 4 个原生库 + 151 个资源文件（11.6 MB）
[pack] 输出目录: leno_gui\游戏\植物大战僵尸\dist
[pack] 单文件: dist 内只产出 exe；库与资源在首次运行时解包到用户缓存目录
打包成功: ... -> leno_gui\游戏\植物大战僵尸\dist\pvz.exe (14654.1 KB) [单文件]
```

### 第 3 步：分发

只拷 `dist\<源码名>.exe` 一个文件。目标机器**不需要装 Leno、不需要装那些 DLL**，
也不需要任何配置。

## 3. 命令与选项

| 选项 | 说明 |
|---|---|
| `-p` / `--pack` | 编译并打包为独立可执行文件（嵌入 `leno_vm`） |
| `-o <目录>` / `--pack-dir <目录>` | 打包输出目录，**相对当前工作目录**；默认 `<源码目录>/dist` |
| `--onefile` | 单文件模式：内嵌原生库 + `resource.toml` 声明的资源 |
| `--console` | 打包时**强制**用控制台版 `leno_vm.exe` 作基底 |
| `--no-console` | 打包时**强制**用无控制台版 `leno_vm_gui.exe` 作基底（Windows） |
| `-c` / `--compile` | 只编译成 `.lenb`，不执行、不打包 |
| `--no-cache` | 关闭模块编译缓存（`import` 的 `.lenocache`）—— 做 A/B 对比时必加 |

约定：

- **产物命名**：`<源码文件名去扩展名>.exe`（`pvz.leno` → `pvz.exe`）。
- 打包时会在源码旁留一个 `<源码名>.lenb`（编译产物，已在 `.gitignore` 里）。
- `--console` 与 `--no-console` **互斥**（两个都给会直接报错退出）。

### 控制台 vs 无控制台（Windows）

产物 exe 是"控制台程序"还是"无控制台程序"，由**prepend 进去的 VM 基底**决定
（PE 头的 Subsystem 字段：`3` = 控制台，`2` = 无控制台），**打包后改不了**。选择顺序：

```
显式开关（--console / --no-console）  >  脚本里的 _console(false) 自动检测  >  默认控制台
```

| 命令 | 结果 |
|---|---|
| `-p app.leno` | 脚本里有 `_console(false)` ⇒ 无控制台；否则控制台（**原有行为不变**） |
| `-p --no-console app.leno` | 强制无控制台（双击不弹黑框） |
| `-p --console app.leno` | 强制控制台（**覆盖** `_console(false)` 自动检测，便于排查问题） |

为什么要有显式开关：自动检测是"用运行期调用去猜链接期需求"的静态启发式，有三个坑 ——

1. 只认**字面量** `false` / `0`：`var v = false; _console(v)` 检测不到；
2. 写在**永远不执行的分支**里也会误判；
3. 打包后 PE 子系统已定型，**猜错没法改**，只能重新打包。

> ⚠ 开关只决定"用哪个 VM 基底"；脚本里 `_console(false)` 的**运行期**语义不受影响
> —— 用 `--console` 打包 + 脚本调 `_console(false)`，运行时仍会隐藏控制台窗口
> （表现为黑框闪一下再消失）。
>
> 非 Windows 平台只有 `leno_vm` 一个变体（`-mwindows` 是 Windows 专属），传开关会
> **提示一句并忽略**，不报错（免得跨平台构建脚本因为多个开关就失败）。

## 4. `resource.toml` 配置

### 4.1 `resources` 通配语法

模式按 `/`（或 `\`）切段，**逐段**匹配整条相对路径：

| 写法 | 含义 |
|---|---|
| `*` | 段内任意长（含空），**不跨目录** |
| `?` | 段内单个字符 |
| `**`（**必须单独成段**） | 吃掉任意多层目录（含 0 层） |
| 普通段 | 字面匹配，**大小写敏感** |

示例：

```toml
resources = [
  "image/**",             # image 目录递归全部（** 在末尾：吃掉剩余全部）
  "font/*.ttf",           # font 下所有 ttf（不递归）
  "data/*.json",          # data 下所有 json
  "shaders/**/*.glsl",    # shaders 下**跨任意层**的所有 .glsl（** 单独成段）
  "config.ini",           # 单个文件（包根下）
]
```

> ⚠ `**` 只有**单独占一段**才是"跨多层"。写成 `shaders/**.glsl` 时它落在段内，
> 按 `*` 处理 ⇒ 只匹配 `shaders/<一层>/x.glsl`，不会递归。

行为细节（照抄即可，不用猜）：

- **包根**：有 `leno.toml` 用它所在目录；没有就退回入口 `.leno` 所在目录
  ⇒ 纯应用目录（无 `leno.toml`）也能用 `resource.toml`。
- **跳过**：`.` 开头的目录（`.git` / `.lenocache` / 隐藏目录）和 `dist` 目录，避免把产物打进去。
- **递归深度上限** 16 层。
- **同一目标路径只收一次**（多个模式重叠时自动去重）。
- **某个模式一个文件都没匹配到** ⇒ 打印警告并跳过该模式，**不中断打包**。
- **内嵌时保留相对目录结构**（`anim/xxx.txt` 解包后仍是 `anim/xxx.txt`）。

### 4.2 `icon` —— 每个应用自己的图标

```toml
[pack]
icon = "ico5.ico"     # 相对本文件所在目录（写绝对路径也认）
```

打包产物的**应用图标**就换成这个文件。**两种模式都生效**（目录模式 / `--onefile`）；
不写 ⇒ 用 VM 自带的默认图标（也就是 `leno.exe` 那个）。

- **只认 `.ico`**：Windows 的图标是 PE 资源（`RT_GROUP_ICON` + `RT_ICON`），PNG/JPG
  必须先转成 ICO 容器。ICO 里的图像数据**原样搬运**，所以 DIB 编码与 PNG 编码的条目都支持。
- 一个 `.ico` 里可以放多张，**建议放 16 / 24 / 32 / 48 / 256**：
  系统会按显示场景取用（列表 16、任务栏 32、中图标 48、超大图标 256）；
  **只放一张会被系统缩放**，小尺寸发虚。
- 惯例上 ≥256 才用 PNG 压缩条目（Vista+ 才认）；48 这种小尺寸用 DIB 编码兼容性最好。
- **指定的图标打不进去 ⇒ 响亮报错并中止打包**（宁可打不出来，也不要静默给一个没图标的产物）。
- 非 Windows 平台：提示一句并忽略（图标不是 PE 资源：macOS 用 `.icns`、Linux 靠 `.desktop`）。

实现要点（改代码时别踩）：图标必须**在 prepend 之前**替换 —— 产物是
`[VM 二进制][资源段][lenb]`，图标在文件最开头那段（VM 二进制）的 PE 资源段里，
而 `EndUpdateResource` 会按 PE 结构重写整个文件，对**最终 exe** 调用会把尾部的资源段
和 lenb 一起丢掉。所以流程是：VM 映像写临时文件 → `BeginUpdateResource` 换图标 →
读回 → 再 prepend。详见 [package_icon.c](../src/package/package_icon.c)。

## 5. 原生库（DLL）从哪来

不需要手写清单，打包器**按实际 `import` 的模块反推**：

1. 每个已加载模块的源路径向上找最近的 `leno.toml` ⇒ 那就是它所属的**包**；
2. 取该包的 `[native-libs.*]`，按当前平台展开（`win` / `linux` / `mac` 三键之一）；
3. 按**目标文件名**去重（同名视为同一个库，后到者忽略）。

```toml
# build/leno_module/LenoSDL3/leno.toml（示例）
[native-libs.sdl3]
win   = "lib/SDL3.dll"
linux = "lib/SDL3.so"
mac   = "lib/SDL3.so"

[native-libs.sdl3_image]
win   = "lib/SDL3_image.dll"
...
```

为什么必须按包推导：原生库是**包**的属性，一个包可以需要多个库 —— 比如 `LenoSDL3`
的 `sdl_core.leno` / `sdl_image.leno` / `sdl_font.leno` 分别 `ffi.load` 了
`SDL3.dll` / `SDL3_image.dll` / `SDL3_ttf.dll`，手抄必漏。

> 声明的库文件不存在，或通配没匹配到任何文件 ⇒ 打印错误并**中止打包**
> （宁可打不出来，也不要产出一个跑不起来的 exe）。

## 6. 运行期：解包到哪里

### 6.1 释放目录

```
<缓存根>/<exeStem>/pack/<hash16>/
```

| 平台 | 缓存根 |
|---|---|
| Windows | `%LOCALAPPDATA%`（拿不到退 `%TEMP%`） |
| Linux | `$XDG_CACHE_HOME`，未设置则 `$HOME/.cache` |
| macOS | `$HOME/Library/Caches` |
| 兜底 | `$TMPDIR` / `/tmp`；缓存目录不可用则退回 **exe 所在目录**（旧行为，至少还能跑） |

- `<exeStem>` = exe 文件名去扩展名（`pvz.exe` → `pvz`）。
- `<hash16>` = **资源段内容**的 FNV-1a 64（16 位十六进制），**打包时算好写进头部**，
  运行期零计算。
- 实测：`C:\Users\<user>\AppData\Local\pvz\pack\2491acd1d41b936b\`，解包后 156 个文件
  = 151 个资源 + 4 个 DLL + 1 个哨兵。

### 6.2 为什么按 hash 分目录

- 两个不同构建（哪怕同时运行）**互不覆盖**；
- 同一构建再次启动 ⇒ **哨兵快路径**：只读一个 `.leno_pack_ok`（内容 = hash16）就返回，
  **零写入**（比"逐文件读一遍算哈希"更快）；
- 代价：**每次重新打包 hash 就变、目录就变** —— 所以这个目录**绝不能用来存用户数据**
  （详见 §7）。

### 6.3 原子性与清理

- 先释放到 `<hash16>.tmp.<pid>/`，全部写完（含哨兵）后**原子改名**成 `<hash16>/`
  ⇒ 最终目录"要么不存在、要么完整"，并发启动的另一个实例不会读到半截目录。
- 改名失败（别的实例先到）⇒ 校验对方哨兵，可用就直接用它的，丢掉自己的暂存。
- 启动时**惰性 GC**：同层里非当前 hash 的目录超过 **7 天**就删，崩溃残留的
  `*.tmp.*` 超过 **1 天**就删。
- **退出时绝不删**：并发实例 + Windows 下 DLL 还被进程锁着，删了就是自找麻烦。

## 7. 代码里怎么读资源：`dirs.res_dir()` vs `dirs.script_dir()`

这是使用单文件打包时**唯一需要改代码**的地方。

| 函数 | 未打包（脚本 / exe / `.lenb`） | 单文件打包后 | 用来干什么 |
|---|---|---|---|
| `dirs.script_dir()` | 脚本 / exe 所在目录 | **同一个**（exe 所在目录） | **写**用户数据：存档、书签、配置 |
| `dirs.res_dir()` | 与 `script_dir()` **完全一致** | 内嵌资源的**释放目录**（hash 目录） | **读**随包资源：图片、音频、字体、DLL |

规则一句话：**读随包资源用 `res_dir()`，写用户数据用 `script_dir()`。**

为什么不能把 `script_dir()` 直接指向 hash 目录（曾经的备选方案，已否决）：
`file_manager.leno` 的 `bookmarks.json` 是**读 + 写** `script_dir()`；一旦把它指到 hash 目录，
**每次重新打包 hash 一变目录就变**，用户的书签会"凭空消失"，而且不会有任何报错。
所以两个语义必须分开：`res_dir()` 只服务"读"，`script_dir()` 语义**一行没动**。

典型写法：

```leno
import dirs
import SDL3

// 读随包资源
var fontPath = dirs.res_dir() + "/font/SmileySans-Oblique.ttf"
var tex = SDL3.loadImageTexture(renderer, dirs.res_dir() + "/image/f1.png")

// 写用户数据（必须用 script_dir）
var saveFile = dirs.join(dirs.script_dir(), "save.json")
```

已迁移到 `res_dir()` 的调用点（本仓库）：

| 文件 | 用途 |
|---|---|
| `leno_gui\游戏\植物大战僵尸\pvz_art.leno` | image / anim |
| `leno_gui\游戏\植物大战僵尸\pvz.leno` | sound / font |
| `leno_gui\游戏\植物大战僵尸\anim_editor.leno` | anim / image |
| `leno_gui\游戏\塔防\tower_defense.leno` | image / font |
| `leno_gui\游戏\俄罗斯方块\tetris.leno` | music |
| `leno_gui\游戏\扫雷\minesweeper.leno` | music |
| `leno_gui\游戏\飞机大战\plane_war.leno` | image |
| `leno_gui\应用\文件管理器\file_manager.leno` | images（图标） |

**保持 `script_dir()` 不动**的（写数据 / 写产物，动了会出问题）：

- `file_manager.leno`：`bookmarks.json`（书签，读 + 写）、根目录定位
- `file_search.leno`、`pe_analyzer.leno`：默认搜索位置（用户目录语义）
- `gen_assets.leno`、`test_table_image.leno`：**生成**资源到脚本目录的开发工具（产物，不是读资源）

## 8. 打包后 DLL 怎么被找到

库不再位于 exe 旁，所以 `ffi.load` 的自动搜索链补了一站（只对相对路径 / 纯文件名生效）：

1. 给定路径直接加载
2. 当前模块目录 `/bin/<文件名>`
3. 当前模块目录 `/<文件名>`
4. 所有已加载模块目录 `/<文件名>`
5. **单文件打包的资源释放目录 `/<文件名>`** ← 新增
6. exe 所在目录 `/<文件名>`
7. 系统 PATH（交给系统加载器）

**兄弟依赖**（`SDL3_image.dll` 的导入表里有 `SDL3.dll`）：Windows 解析"某个 DLL 自身的依赖"
时**不会去看那个 DLL 所在的目录**，只搜主 exe 目录 / `SetDllDirectory` 指定的目录 / 系统目录 / PATH。
所以打包模式下会调一次 `SetDllDirectoryW(释放目录)`，否则 `SDL3_image → SDL3` 这条链会断。
未打包时该函数是空操作，**不改变原有行为**。

## 9. 内嵌格式（维护者视角）

exe 尾部布局（资源段在 `lenb` **之前** ⇒ 末尾 8 字节仍是 `LENB_MAGIC`，旧 VM 读新 exe 依然正常）：

```
[原始 exe][资源段][资源段大小:u32][RES_MAGIC][lenb][lenb大小:u32][LENB_MAGIC]
```

资源段内部（v2，索引在前、内容在后）：

```
"LENOPACK"(8) | version:u32(=2) | payload_hash:u64 | entry_count:u32
entry_count × [ rel_len:u16 | size:u64 | hash:u32 | rel_path(rel_len) ]
各文件内容按索引顺序紧随其后
```

- `payload_hash` = FNV-1a 64 over `[entry_count .. 末尾]`，**打包时算好**（运行期零计算），
  同时充当**释放目录的键**。
- `version` 只做**格式自检**：exe 与它内嵌的资源段永远出自同一次打包，不需要跨版本兼容，
  对不上就响亮报错（宁可报错，也不要按错误布局解析、写出乱七八糟的文件）。
- 运行期不再重算整段哈希；只有"兜底释放到 exe 目录"那条路径才用逐文件 FNV-1a 跳过已存在的文件。

## 10. 常见问题（FAQ）

**Q：打包后 dist 里只有 exe，但里面有个上次目录模式留下的同名 DLL？**
只提示不删。确认只需要 exe 时自行删除即可。

**Q：改了资源重新打包，旧目录还在？**
按 hash 分目录，旧目录与新目录并存；**目录最后修改时间**超过 **7 天**的，会在下次启动时被
惰性 GC 清掉（快路径不写文件 ⇒ 时间戳不会因为"又跑了一次"而刷新）。

**Q：为什么不能把存档写进 `res_dir()`？**
hash 目录随每次重新打包变化，写进去的数据会"凭空消失"（且无任何提示）。写数据一律用
`script_dir()`。

**Q：首次启动慢、磁盘写了几十 MB？**
正常，一次性解包；之后每次启动只读一个哨兵文件，零写入。

**Q：双击 exe 没反应 / 一闪而过？**
看脚本里是否有 `win.ok` 之类的早退分支。打包时若用了**无控制台**基底，`print` 的输出看不到。
排查手段：直接 `build\leno.exe <脚本>` 跑源码，或用 `-p --console` 重新打包一版带黑框的
exe（`--console` 会覆盖 `_console(false)` 自动检测），就能看到完整输出。

**Q：打包报错「即将内嵌的 VM 读不了本次编译产物」？（以前是打包"成功"、双击才闪退）**
含义：exe 里要内嵌的 `leno_vm*.exe` **比编译器旧** —— 编译器侧改过序列化格式 /
`LENO_BIN_VERSION`（如"行号表 RLE"那次升到 v3.0.2），而 VM 二进制没重建，读不了新 `.lenb`
（旧行为：产物照样"打包成功"，双击时才以 `内存反序列化失败: 5`（5 = `SERIALIZE_ERR_VERSION`）
一闪而过）。
处理：**先 `build_vm.bat` 重建 VM，再重新打包**（`build.bat` 只重建编译器）。
现在打包前会自动握手：用即将内嵌的那个 VM 跑 `leno_vm --check-bin <产物>`（只校验、不执行），
读不通就**报错并放弃产出 exe**（已编译出的 `.lenb` 会保留，重建 VM 后可直接复用）。

**Q：脚本里没有 `_console(false)`，为什么打出来的 exe 还是没有黑框？**
说明打包时用了 `--no-console`，或 `resource.toml`/命令行里带着它。想确认用了哪个基底，
看打包输出那一行（`[pack] ... 使用...版 leno_vm...`）；也可直接查 PE 头 Subsystem
（3 = 控制台、2 = 无控制台）。

**Q：目标机器要装什么？**
什么都不用。系统自带库（如 `kernel32`）除外。

**Q：缓存目录不可写（权限 / 杀软）怎么办？**
会自动退回"释放到 exe 所在目录"（旧行为），至少还能跑，只是会污染 exe 旁边。

## 12. 已知边界

- **Windows 为实机验证平台**；Linux / macOS 的释放目录、原子改名、自身 exe 路径都已在
  代码层面补齐，但**尚未实机验证**。
- 单文件打包**只影响打包产物**；未打包运行时 `res_dir()` 与 `script_dir()` 完全等价，
  行为与改造前一致。
- 资源段**不做压缩**；体积 ≈ 原生库 + 资源原大小之和。

### 自身 exe 路径已收敛（5 处 → 1 处）

"取当前进程 exe 的路径"原先在 5 个地方各写一份 `readlink("/proc/self/exe")`，
其中一处漏了补 `'\0'`（readlink 不写结束符）⇒ 路径尾部是栈垃圾 ⇒ 单文件 exe 检测不到
内嵌数据。现已全部收敛到 [`src/platform/platform_path.c`](../src/platform/platform_path.c)：

| 调用点 | 用途 |
|---|---|
| `src/vm_main.c` | 解包内嵌资源段 |
| `src/main.c` | 打包时定位 `leno_vm` 运行时 |
| `src/package/package_install.c` | 内置模块搜索路径 `exe_dir/leno_module/` |
| `src/serialize/serialize.c` | 字节码缓存指纹（按自身 exe 失效） |
| `src/module/ffi/ffi.c` | DLL 搜索链的最后一站（exe 目录） |

- Linux：`/proc/self/exe` + 补 `'\0'` + 判长度；macOS：`_NSGetExecutablePath` + `realpath`。
- 取不到时返回 0 并置空串，各调用点按 **fail-closed** 兜底（不假装知道自己在哪）。
- Windows：该函数**不提供实现**，调用点继续用 `GetModuleFileNameW`
  —— 那是已验证工作的代码，不因"新增 macOS 支持"而改动（项目约定）。
