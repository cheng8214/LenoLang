# Leno 写 Android app：能力实测报告

> 测试日期：2026-11-18 · 设备：Android 10（API 30）x86_64 模拟器
> 产物：`libleno.so`（arm64-v8a 965KB / x86_64 1.1MB）、APK 3.8MB
> 口径：**11 个探针 / 100 条断言，全部在设备上真跑**，输出经 logcat（tag `leno_jni`）回收
> 探针源码：`android/app/assets/c*.leno` · 一键复跑：`bash android/run_probes.sh`

## 一句话结论

**逻辑层已经齐了：语言、文件、JSON、正则、时间、并发、网络（含 HTTPS）、SQLite、二维码、
PNG/JPEG/WebP 编解码、字体栅格化、音频、FFI 全部实测可用，纯 `.leno` 标准库也能直接用。
缺的只剩"界面（开窗）"和"系统集成（剪贴板/通知/权限/Toast）"这两层。**

## 本轮顺带修掉的两个运行时缺陷

这两个是**任何 app 都绕不过**的，之前一直没人踩到，因为桌面端 `_script()` 有 argv 兜着：

| 现象 | 根因 | 修法 |
|---|---|---|
| `_script()` 返回 `null` | 它只从 `argv` 取"第一个非选项参数"，而 JNI 调 `lenolang_run_lenb(path)` 时**没有 argv** | 新增 `leno_set_script_path()`；`lenolang_run_lenb()` 入口自动写入 |
| `_tmpdir()` 返回 `/tmp` | POSIX 分支在没有 `TMPDIR` 时硬编码 `"/tmp"`，Android 沙箱里既不存在也不可写 | 新增 `leno_set_data_dir()`；宿主在 `onCreate` 里传 `getFilesDir()` |

修完的效果（设备实测）：

```
_tmpdir() = /data/user/0/com.leno.app/files
_script() = /data/user/0/com.leno.app/files/app.lenb
dirs.mkdir_p → files.write → files.read → dirs.stat → dirs.walk → 删除  全通过
```

## 模块（`leno_module/`）在 Android 上的可用性

**结论：模块的 `.leno` 部分开箱可用，但模块里"找动态库"的那一步是平台相关的，
必须逐个检查 —— `LenoSqlite` 就踩了这个坑。**

先说清一个容易误解的点：这个精简 VM（`sources_core.txt` 里没有 parser / package / compiler）
**不做运行时 `import` 解析**。`import "LenoSqlite/lib/sqlite3.leno"` 是**桌面编译时**就把模块
源码内联进 `.lenb` 了 ⇒ 运行时不存在"模块目录找不到"的问题，`LenoResult / LenoCrypto /
LenoSqlite` 这类纯 `.leno` 或薄 FFI 封装的模块，只要能编过就能在设备上跑。

真正会挂的是**模块自己去 dlopen 的那一刻**。

### 库文件按平台分目录（2026-11-18 起的布局）

```
build/leno_module/LenoSqlite/lib/
├── sqlite3.leno / sqlite3_core.leno
├── win/sqlite3.dll                  Windows
├── linux/sqlite3.so                 Linux 桌面
└── android/arm64-v8a/libsqlite3.so  Android（构建 APK 的输入）
    android/x86_64/libsqlite3.so
```

原来是 `lib/` 下平铺，只有 `sqlite3.dll` + `sqlite3.so` 两个文件。改成子目录是因为
**Android 的库必须按 ABI 各带一份**（`arm64-v8a` / `x86_64` 是两份不同的 ELF），
平铺在一个目录里只能占一个文件名 ⇒ 两份互相覆盖。

配套要改两处，否则分目录根本加载不到：

| 改动 | 位置 | 为什么必须 |
|---|---|---|
| `ffi.load` 支持**带子目录的相对路径** | `src/module/ffi/ffi.c`（新增 2a-2 步；2c 遍历也补上） | 原实现会把路径**剥成纯文件名**（`filename = last_sep + 1`）再拼模块目录 ⇒ `win/sqlite3.dll` 永远命中不了 |
| `_os()` 在 Android 上返回 `"android"` | `src/module/sys/sys.c` 的 `native_os` | bionic 同时定义 `__linux__`，原来报 `"linux"`，与桌面无法区分；`__ANDROID__` 必须排在 `__linux__` **之前**判断 |

> `ffi.c` 里最关键的其实是 **2c 那一轮**（遍历所有已加载模块目录），不是 2a-2：
> 模块被编译期内联后 `current_module_frame` 的 `source_path` 可能为空 ⇒ `mod_dir` 取不到
> ⇒ 2a/2a-2/2b 整段跳过。实测就是 2c 把分目录救回来的。

`leno.toml` 的 `[native-libs]` 也要跟着改（`win = "lib/win/sqlite3.dll"`），
否则 `run_all_tests.leno` 的 `missing_lib()` 会判定"缺原生库"直接 **SKIP** 整个模块 ——
这个跳过是静默的，汇总里只多一个 SKIP，很容易当成"跑过了"。

Android 那一份**不写进 `leno.toml`**：一个平台键只能指一个路径，装不下两个 ABI。
`build_android.sh` 第 5 步直接读 `lib/android/<abi>/`，优先于 `app/jniLibs/<abi>/`（旧布局兜底）。
`app/jniLibs/*/*.so` 因此已 gitignore —— 库的真实源在模块里，两份二进制进仓库只会悄悄走岔。

### 为什么 Android 运行时加载的是"裸文件名"

即使模块里有 `android/<abi>/libsqlite3.so`，设备上也**不会**从那里加载：当前 VM 不做运行时
`import`，模块目录在设备上并不存在。真正生效的是 `ffi.load("libsqlite3.so")` 这条裸名 ——
APK 的 `jniLibs/<abi>/` 由打包器落到 `/data/app/.../lib/<abi>/`，与 `libleno.so` 同目录，
`dlopen` 按裸名直接命中。**不能拼绝对路径**：Android linker 的 namespace 只放行白名单库名
与自己 lib 目录里的裸名，拼出来的路径反而会被拒。

系统目录里只有 `/system/lib64/libsqlite.so` —— **另一个库名**，且不在 `public.libraries.txt`
白名单 ⇒ 按名、按路径都 dlopen 不了；`libsqlite3.so*` 一个都没有（`ls` 实测确认）。

`lib()` 的候选顺序因此是"逐级降级"，每一级失败都靠 `try` 兜住再试下一个；
命中错误平台的库不会造成"能加载但行为诡异"——ELF 架构/magic 不符时 dlopen 直接失败。

**验证证据**（`c12_module_sqlite` 探针，走模块 API 而非裸 FFI）：

```
桌面： _os()=windows  libversion() = 3.53.4   ← 模块自带的 win/sqlite3.dll
设备： _os()=android  libversion() = 3.46.1   ← APK 里 NDK 编的那份
两边都是 14 项断言全过（建表/参数绑定/多行读/NULL 语义/事务回滚/错误文案/关库重开）
```

写这类模块探针时会被 Leno 的三条语法卡住（都是编译器现状，不是 Android 的问题）：

1. 被导入模块**不传递**它自己的 `import` ⇒ 探针里要自己再 `import dirs` / `import files`；
2. `Result[Statement]` 的 `unwrap()` 静态类型是 `T`，**泛型不单态化** ⇒ `r.unwrap().bind(…)`
   报「类型 T 没有方法 bind」。拆两步：`prepareResult` 只验成功契约，取句柄用 `db.prepare()`；
3. 回调参数必须写具体类型 `func(sqlite3.Statement st)`；写 `func(var st)` 会报
   「参数不能使用 var 类型」，写 `any` 则不允许直接调方法。

## 五个模块的 Android 产物（2026-11-19 补齐）

| 模块 | 原生库 | 版本 | 双 ABI 大小（arm64 / x86_64） | 设备实测 |
|---|---|---|---|---|
| LenoSqlite | `libsqlite3.so` | 3.46.1（NDK 编） | 929K / 916K | c8 + c12 共 23 项 |
| LenoQR | `libquirc.so` | quirc 1.0（vendored） | 35K / 43K | c13 共 10 项 |
| LenoMusic | `libminiaudio.so` | miniaudio 0.11.25 | 691K / 758K | c15 共 3 项 |
| LenoSDL3 | `libSDL3.so` + `_image` + `_ttf` | 3.4.20 / 3.4.8 / 3.2.2 | 2.2M+223K+1.6M / 2.4M+240K+1.7M | c14 共 10 项 |
| LenoWeb | `libcurl.so` | 8.23.0 + mbedTLS 3.6.8 | 1.6M / 1.7M | c16 共 7 项 |

每个模块的 `src/` 下都有 `build_android.sh` 和**上游源码**（裁掉测试/示例/IDE 工程，
总计约 104MB），所以是自包含的：拿到模块目录就能离线重编，不用向仓库另要二进制。
`lib/android/<abi>/` 是产物；`android/build_android.sh` 会遍历**所有**模块的这个目录打包，
新增模块不需要回来改脚本。

### 各模块的取舍

**LenoQR** —— 纯 C、零外部依赖，`clang -shared -fPIC` 一步出，最适合当"验证打包链路"的样板。

**LenoMusic** —— miniaudio 是单头文件库。Android 后端是 AAudio（API 26+）/ OpenSL ES（API 21+），
两者都由 miniaudio **运行时 dlopen** ⇒ 链接时不需要 `-lOpenSLES -lAAudio`，只留 `-lm -llog`。

**LenoSDL3** —— 唯一需要 CMake 全家桶的。三个库都走 `vendored`：png/jpeg/webp/zlib/
freetype/harfbuzz 全部静态链入，所以 `libSDL3_image.so` / `libSDL3_ttf.so` 的 `NEEDED`
里只有 `libSDL3.so`（Windows 侧还要另外摆三个 `libwebp-*.dll`，Android 侧不用）。
⚠ 开窗渲染**做不到**，见坑 #8。

**LenoWeb** —— curl 8.23.0 + mbedTLS 3.6.8，TLS 静态链入（系统 BoringSSL 不在
`public.libraries.txt` 白名单，`dlopen` 会被拒）。
证书**不随包**：`caBundle()` 首次用到时把 `/system/etc/security/cacerts/*.0`
（每个文件就是一张 PEM）拼成 741KB 的 bundle 落到临时目录，
`HttpClient.init()` 自动设 `CURLOPT_CAINFO` ⇒ 证书跟着系统更新走，不会过期。

## 十一个必须记住的坑（都是实测撞出来的）

1. **`set_timeout` 是毫秒**。写成 `set_timeout(8)` 以为是 8 秒，实际 8ms ⇒ `recv` 立刻返回 null，
   表现成"对端没发数据"，排查方向完全错。
2. **`regexs` 的参数顺序是 `(文本, 模式)`**，而且引擎只支持 `* + ?`，**没有 `{n}` 量词**。
   手机号校验写不出 `\d{11}`，得展开成 `[0-9][0-9]…`。
3. **`import "Crypto"` 用库文件名，不是包目录名**。写 `import LenoCrypto` 会报"未知的原生模块"；
   写 `import "LenoResult"` 也不行（目录下是 `Result.leno`）。
4. **`adb logcat -c` 是异步的**。清空后立刻回读，读到的是没清掉的旧数据 ⇒
   探针脚本如果"清完就抓"，会把上一轮输出算进本轮（实测汇总数虚高到 357，实际 100）。
   正确做法：`-c` 之后等约 0.5s 再回读验证，不干净就重试。
   反过来，用**固定 sleep 等探针跑完**也不可靠：`c6_net` 在 10s 窗口下只抓到 3 条（实际 6 条），
   汇总数偏低。现在 `run_probes.sh` 是"轮询等探针自己打印结果行"。
5. **`_os()` 在 Android 上现在返回 `"android"`**（2026-11-18 改，此前伪装成 `"linux"`）。
   这是**行为变更**：原来写 `_os() == "linux"` 的代码在设备上会失效
   （本仓库 `LenoSys.isLinux()` 因此返回 false —— 语义上是对的）。要表达"POSIX 就行"，
   得写 `_os() == "linux" or _os() == "android"`。
6. **`leno.exe` 和 `leno_vm.exe` 各自内嵌一份 VM**。改了 `src/` 下的 C 代码（`ffi.c` / `sys.c` / …）
   必须 `bash build.sh` **和** `bash build_vm.sh` 都跑一遍。否则会出现
   "`leno_vm.exe` 跑 `.lenb` 正常、`leno.exe` 跑 `.leno` 却报库加载失败"这种极难归因的现象
   —— 本轮就因为只重编了 VM，`run_all_tests.leno` 里 LenoSqlite 一路报错。
7. **`run_all_tests.leno` 要用 `leno.exe` 跑，不能用 `leno_vm.exe`**。它内部用
   `_executable()` 拼子进程命令，而 VM 只吃 `.lenb` ⇒ 拿 VM 当 runner 会全线 `exit=1`
   （看着像"所有模块都挂了"，其实是一个都用错了工具）。

8. **`dlopen` 不会触发 `JNI_OnLoad`**。SDL3 的 JavaVM 是靠**它自己的** `JNI_OnLoad`
   缓存的，而那个钩子只有 `System.loadLibrary` 才会被调 ⇒ `ffi.load("libSDL3.so")` 之后
   `SDL_Init` 一律失败：`Failed, there is no JavaVM`。
   **不要**试图手动调它的 `JNI_OnLoad` —— 里面 `FindClass("org/libsdl/app/SDLActivity")`
   找不到就抛 pending exception，ART 的 `AssertNoPendingException` 直接杀进程
   （实测 tombstone：`ClassLinker::FindClass` → `Thread::Abort`）。
   正路是把宿主改成 SDL 官方的 `android-project` 形态（Java 继承 `SDLActivity`）。

9. **mbedTLS 3.6 的 git 源码树不含生成文件**。GitHub 上按 tag/branch 下载是 git 检出，
   没有 `error.c` / `version_features.c` / `ssl_debug_helpers_generated.c` /
   `psa_crypto_driver_wrappers.{h,c}` ⇒ 必须 `-DGEN_FILES=ON` 现场生成
   （要 Perl + Python + jsonschema + jinja2）。官方 **release 压缩包**里才带这些文件。

10. **CMake 会自己挑 Python**。脚本里检查的是 PATH 上那个，`find_package(Python3)`
    可能挑到另一个（实测 3.13.12 vs `Program Files` 下的 3.13.2）⇒ 必须在 configure 时
    显式 `-DPython3_EXECUTABLE=...`，否则要等 build 阶段才报 `No module named 'jsonschema'`。

11. **删上游目录前先确认 CMake 是否引用**。curl 的 `add_subdirectory(scripts)` 是**无条件**的；
    libpng 的 `scripts/cmake/*.cmake`、libwebp 的 `cmake/`、freetype 的 `builds/`
    都是 CMake 的输入。剪枝只删 `test/ examples/ docs/ Xcode/ VisualC/` 是安全的。
