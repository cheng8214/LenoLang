# 优化方案：内存态序列化运行（让 .leno 与 .lenb 性能一致、去除临时文件）

## 1. 目标

1. **性能对齐**：直接运行 `.leno` 源码时，让 VM 执行路径与 `.lenb` / 打包 exe **完全一致**，消除「编译器内存税」（实测 `.leno` 236ms vs `.lenb` 195ms 的 ~22% 差距）。
2. **去除临时文件**：打包 exe 加载内嵌字节码时不再往磁盘写临时 `.lenb`，做到真正 **100% 跨平台**（当前 `run_lenb_from_memory` 用 `GetTempPathA` / `/tmp`，是平台相关 + 多余磁盘 I/O）。

核心思路一句话：

> 编译 → **序列化到内存** → **释放全部编译器资源** → **反序列化** → 跑 VM。

---

## 2. 现状分析

### 2.1 当前两条执行路径

| 路径 | 入口 | 流程 | 编译器是否驻留 |
| --- | --- | --- | --- |
| `.leno` 源码 | `lenolang_run(source)` (`main.c:128`) | 解析→语义→codegen→`vm_run()` | **是**（AST/符号表在 `vm_run` 返回后才释放，`main.c:189-194`） |
| `.lenb` / 打包 exe | `lenolang_run_lenb(filename)` (`vm_main.c:144`) | `chunk_deserialize`→`vm_run_chunk` | 否 |

关键证据：`main.c` 中 `vm_run()` 在第 186 行，而 `ast_free` / `semantic_cleanup` / `chunk_free` 在第 189–194 行——也就是说 **`vm_run` 执行期间编译器资源根本没释放**，挤占 CPU 缓存。

### 2.2 序列化 API 现状（瓶颈不在逻辑，在文件 I/O）

- `chunk_serialize(path, chunk, scope)`（`serialize.c:1588`）：先 `wb_init` 把字节码写进 `WriteBuffer`，**最后才** `fopen/fwrite` 落盘。内存态逻辑已现成。
- `chunk_deserialize(path, out_chunk, out_scope)`（`serialize.c:1661`）：先 `fread` 进 `data`，再用 `DeserializeCtx{data,size,pos}` 反序列化。真正干活的逻辑都在 `ctx` 构建之后（`serialize.c:1697` 起），文件读取只是前置。

结论：**序列化/反序列化的核心已经是内存态，只差一层文件 I/O 包装。**

### 2.3 打包 exe 的临时文件问题

`run_lenb_from_memory`（`vm_main.c:101`）：
```c
// 写入临时文件
GetTempPathA(...); snprintf(temp_path, ..., "vm_%lu.lenb", pid);
FILE* fp = fopen(temp_path, "wb"); fwrite(data,1,size,fp); fclose(fp);
int ret = lenolang_run_lenb(temp_path);   // 再从文件读回
remove(temp_path);
```
平台相关、且多一次「写+读」磁盘往返。

## 3. 方案设计

### 3.1 新增两个内存态序列化函数

在 `src/include/leno_serialize.h` 声明，在 `src/serialize/serialize.c` 实现。把现有 `chunk_serialize` / `chunk_deserialize` 的「内存缓冲构建 / 解析」部分抽出复用。

```c
// 序列化到内存：返回 malloc 的缓冲（调用方负责 free），不落盘
// 返回值 SERIALIZE_OK 时 *out_data / *out_size 有效
SerializeResult chunk_serialize_to_memory(Chunk* chunk, Scope* global_scope,
                                          uint8_t** out_data, size_t* out_size);

// 从内存缓冲反序列化：直接在 data 上解析，不 free 调用方缓冲
SerializeResult chunk_deserialize_from_memory(uint8_t* data, size_t size,
                                              Chunk* out_chunk, Scope** out_scope);
```

**实现要点（复用现有代码，仅去掉文件层）：**

- `chunk_serialize_to_memory`：把 `chunk_serialize` 中 `wb_init` … `wb_write_*` … 的部分保留，**去掉** `wb` 落盘那段（`serialize.c:1635-1657`），改为 `*out_data = wb.data; *out_size = wb.size;`（转移 `WriteBuffer` 所有权，不 `wb_free`）。
  - 关于 `src_hash`（`serialize.c:1598-1623`）：当前回读 `chunk->filename` 源文件算 hash。内存路径建议 **直接用调用方传入的源码字符串算 hash**（或新增参数 `const char* source`），避免回读磁盘；若嫌麻烦也可先保留回读（它读的是输入 `.leno`，不是临时文件，不算污染本方案目标）。
- `chunk_deserialize_from_memory`：把 `chunk_deserialize` 中 `fread` 进 `data` 之后的全部逻辑（`serialize.c:1697-1738`）原样搬过来，**去掉** `fopen/fread` 前置与末尾 `free(data)`（调用方持有缓冲）。`DeserializeCtx` 直接指向 `data/size`。

### 3.2 重构 `lenolang_run`（`.leno` 直跑路径）

`src/main.c` 的 `lenolang_run` 改为：

```c
int lenolang_run(const char* source) {
    // ... 原有：parser_parse / semantic_analyze / optimize / codegen ...
    // 生成 chunk 与 sem.root_scope（不变）

    // ★ 新增：序列化为内存缓冲
    uint8_t* lenb_buf = NULL; size_t lenb_size = 0;
    SerializeResult sr = chunk_serialize_to_memory(&chunk, sem.root_scope, &lenb_buf, &lenb_size);
    if (sr != SERIALIZE_OK) { /* 失败回退到原 vm_run 路径 */ goto run_direct; }

    // ★ 新增：立刻释放编译器资源（核心！清零「内存税」）
    codegen_cleanup(&gen);
    ast_free(parser.root);
    semantic_cleanup(&sem);      // 注意：会置 root_scope=NULL，但 chunk 已序列化，无碍
    chunk_free(&chunk);

    // ★ 新增：从内存反序列化出全新 chunk + scope
    Chunk run_chunk; Scope* run_scope = NULL;
    sr = chunk_deserialize_from_memory(lenb_buf, lenb_size, &run_chunk, &run_scope);
    free(lenb_buf);              // 缓冲已用完，立即释放
    if (sr != SERIALIZE_OK) { /* 回退 */ goto run_direct; }

    // ★ 与 lenb 路径一致的运行前准备（关键：补 native 函数指针）
    register_defs_from_chunk(&run_chunk);
    gc_init();
    fix_module_function_ptrs(&run_chunk);
    vm_init_with_scope(run_scope);
    vm_load(&run_chunk);
    int ret = vm_run();

    // 释放
    chunk_free(&run_chunk);
    if (run_scope) scope_free(run_scope);
    gc_free_all();
    return ret;

run_direct:   // 序列化失败时的兜底：沿用原逻辑
    gc_init();
    vm_init_with_scope(sem.root_scope);
    vm_load(&chunk);
    ret = vm_run();
    codegen_cleanup(&gen);
    ast_free(parser.root);
    semantic_cleanup(&sem);
    chunk_free(&chunk);
    gc_free_all();
    return ret;
}
```

> **关键点**：反序列化后 scope 丢失了 native 函数指针（如 `times.us`），**必须**调用 `fix_module_function_ptrs`（与 `lenolang_run_lenb` 一致），否则 native 调用会崩。直接编译路径不调它，是因为语义分析阶段已绑定好。

### 3.3 可选：打包 exe 也走内存态（去临时文件）

`src/vm_main.c` 的 `run_lenb_from_memory` 改为直接调用内存反序列化，去掉临时文件：

```c
static int run_lenb_from_memory(unsigned char* data, size_t size) {
    if (size < 20) { ... }
    Chunk chunk; Scope* scope = NULL;
    SerializeResult r = chunk_deserialize_from_memory(data, size, &chunk, &scope);
    if (r != SERIALIZE_OK) { ... }
    register_defs_from_chunk(&chunk);
    gc_init();
    fix_module_function_ptrs(&chunk);
    vm_init_with_scope(scope);
    int ret = vm_run_chunk(&chunk);
    chunk_free(&chunk);
    if (scope) scope_free(scope);
    gc_free_all();
    return ret;
}
```

这样 `check_embedded_lenb` 提取出的内嵌数据直接进内存反序列化，**完全不碰磁盘**，跨平台更干净。

## 5. 验证步骤

1. `build.bat` 重新编译，确认无 warning/error。
2. 性能对比（计时只包住 `fib(30)`）：
   - `leno 经典斐波那契数列测试_int.lenb` → 基线 ~195ms
   - `leno 经典斐波那契数列测试_int.leno` → **预期从 236ms 降到 ~195ms**
3. 正确性回归：跑若干依赖 native 模块的脚本（如 `import times`、`import SDL3` 示例），确认 `fix_module_function_ptrs` 后 native 调用正常、无崩溃。
4. （若改了 `vm_main.c`）重新打包一个 exe 并运行，确认仍能正常启动。

## 6. 风险与注意

- **错误行号 / 调试信息**：反序列化是否完整保留 `chunk` 的源码行号映射，影响运行期报错定位。需确认 `deserialize_chunk_data` 已包含行信息（预计有，因其服务于 `.lenb` 报错）。
- **`src_hash` 来源**：内存路径建议改用源码字符串算 hash，避免回读磁盘；对执行无影响，仅完整性校验。
- **兜底路径**：序列化/反序列化任何一步失败都应回退到原 `vm_run` 直跑逻辑，保证兼容性。
- **大脚本内存峰值**：序列化缓冲 + 反序列化副本会短暂占用约 2 倍字节码内存，但编译器 AST 已释放，净占用通常更低。

---

*方案提出背景：实测 `.lenb`(195ms) ≈ 打包 exe(190ms) << `.leno`(236ms)，差距全来自编译器驻留导致的 CPU 缓存污染。本方案通过「编译后序列化→释放→反序列化」在内存中复刻 `.lenb` 路径，从而消除差距。*
