## 一、A 类：不是 Leno 的问题（记录即可）

### A1 ★ `mobi.kuwo.cn` 按 User-Agent 风控 —— 桌面 Chrome UA 会拿到「HTTP 200 + 空 body」

**现象**：同一个 URL、同一时刻，只换 UA，响应正文长度差别巨大：

| UA | 响应正文 |
| --- | --- |
| 不设（curl 默认 `curl/8.21.0`） | **292 字节**（正常，含 `url=` 行）✓ |
| `okhttp/3.10.0` | 292 字节 ✓ |
| `test/1.0` | 292 字节 ✓ |
| `Mozilla/5.0` | 292 字节 ✓ |
| 桌面 Chrome 完整 UA（`Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/148.0.0.0 Safari/537.36`） | **0 字节**（HTTP 仍 200）✗ |
| 同上，把空格全删掉 | 292 字节 ✓ |

**关键对照**：`Python(requests)` 用**同一个 Chrome UA** 也是 **0 字节**，无 UA / `okhttp` 则 292 字节
⇒ **与 Leno / LenoWeb 无关**，是服务端按 UA 做的策略（musicdl 用 `okhttp/3.10.0` 正是这个原因）。

**判据（可复跑）**：同一 `mobi.s?...&q=<加密串>`，逐个 UA 请求比 `len(resp.body)`。

**本轮处置**：`kuwo_core.leno` 里官方取链**单独起一个 client 并设 `okhttp/3.10.0`**，不改调用方（搜索用）的 UA。
⇒ 也是"顺手排掉一个误判"：一开始我以为是 LenoWeb 的 `setUserAgent` 把请求头写坏了
（用 httpbin 验过：**发出的 UA 干净且完整，只有一条**），后来并排复测 Python 才定位到真因。
**另一个误判**：曾怀疑 `officialurl` 的参数名 `format` 遮蔽了内置 `format()`（改名后仍失败）——**不成立**，注释已改回。

### A2 第三方取链 API 会给"降档"结果

**现象**：搜索列表标注 `mp3 7.73 MB`，`music.nxinxz.com` 实际返回 `m4a`、3,085,464 字节（≈2.94 MB）。
**判据**：下载后比 `实际字节数` 与搜索列表的 `size`。musicdl 的判据是
`file_size_bytes * 8 < 320000 * duration_s` ⇒ 判为低质并丢弃。
**本轮处置**：`musicdl.leno` 在下载后打印对照，明显偏低时warning：
`! 实际体积低于列表标注（列表 7.73 MB）⇒ 直链只给了低档，非无损`。

### A3 酷我 `MINFO` / `N_MINFO` 的档位顺序**不固定**

**现象**：同一首歌，`MINFO` 与 `N_MINFO` 的档位先后相反（实测都出现过）。
⇒ "取最后一段即最高档"是错的。
**判据**：按 `;` 切段后逐个解析 `size:`，**按数值比大小**取最大那档。
**本轮处置**：`kuwo_core.leno` 的 `bestfield()` 按 size 比大小。

### A4 酷我歌词接口（`newlyric.kuwo.cn`）的三个服务端事实

| # | 事实 | 现象 / 判据 | 处置 |
| --- | --- | --- | --- |
| 1 | **必须带 `Referer`** | 不带 Referer 时回 15 字节 `TP=DENY REQUEST`（HTTP 仍是 **200**，不是 4xx！）；只带 Referer、不带 UA 也能拿到正文 ⇒ 这个接口看 Referer，不看 UA（与 A1 的 UA 风控是两回事） | `kuwo_lyric.leno` 的 `fetchlyric()` 自己起 client 并加 `Referer: http://www.kuwo.cn/` |
| 2 | 正文是 **zlib + gb18030**，且**不是** `Content-Encoding` | 响应用 `Content-Type: text/html` 直接吐二进制：`"tp=content\r\npath=…\r\nscore=…\r\n\r\n"` + zlib（前两字节恒为 `78 9C`） | 头体分隔按 `CRLFCRLF` 定位（兼容 `LFLF`），**剥掉 2 字节 zlib 头**再用 `web_gzip.inflateRaw`（详见 B8），最后 `web_charset.decode(…, "gb18030")` |
| 3 | `&lrcx=1`（逐字时间轴）与不加**是两种打包** | 不加：`gb18030( 标准 LRC )`（带 `[ti:]/[ar:]` 头、**译文行已是独立的 `[时间]行`**）；加了：`base64+xor(gb18030( 带 `<mm,dd>` 逐字标签的 LRC ))`，且译文行要自己并 | **本实现选"不加"** ⇒ 少一层解密、省掉上游那条 `convertrawlrc` 正则转换链；两种都实测过，内容质量对播放器等价 |

> 另：同一首歌、同一 `rid`，两次请求的 `path=` 字段会变（服务端分配），不影响正文。

### A5 ★ 酷我 `MINFO` 的 `size` 有四种形态 —— 粗糙解析会让**整个搜索**失败（"青衣"事故）

**现象**：搜 `青衣` 时 Leno 端**一条都搜不出来**，GUI 只显示"没搜到结果"；同一时刻 Python/浏览器打同一个接口命中 10 条。

**真因**：`MINFO` 的 `size` 实测有 4 种写法，而 `kuwo_core.bestfield()` 原来只做
`to_lower().replace("mb","")` 就 `_float()`：

| 原文 | 剥 "mb" 后 | `_float()` |
| --- | --- | --- |
| `size:43.64Mb` | `43.64` | ✓ |
| `size:999.06Kb` | `999.06kb`（**单位是千字节，且 "mb" 不匹配 "kb"**） | ✗ **抛异常** |
| `size:365.84Kb` | `365.84kb` | ✗ **抛异常** |
| `size:zpMb`（臻品档的假尺寸） | `zp` | ✗ **抛异常** |

异常在 `search()` 里抛出 ⇒ 整次搜索空手而归。**"青衣"只是第一首带 `Kb`/`zpMb` 档的歌**
（`晴天` 的全是 `Mb`，所以之前一直没暴露）。

**判据（可复跑）**：`-s 青衣` vs `-s 周杰伦 晴天`——前者崩、后者正常。

**本轮处置**（`kuwo_core.leno`）：

1. 新增 `parsecellsize()`：按 **Kb/Mb/Gb/B** 选 1024/1048576/1073741824/1 的系数，
   并且**先 `isnumber()` 判数字再转**（认不出 ⇒ -1，绝不抛异常）；
2. `bestfield()` 改用 `parsecellsize` 比大小 ⇒ 认不出的档位（`zp`）自动不参与比较；
3. `normalizeSize()` 原样保留单位（`999.06Kb` → `999.06 KB`，不再一律贴 MB）；
4. `parsesongs()` 里**每条结果各自 try**：单条脏数据只丢这一条，不再让一个畸形字段毁掉整次搜索。

**教训（两条，都值得复用到别的源）**：

- 服务端 JSON 里"看起来是数字"的字段，**必须"先判再转"**；`_float()`/`_int()` 遇到脏串是**抛异常**不是返回 0。
- **别把异常翻译成"没搜到结果"**：GUI 的 `finishSearch()` 原来无条件用"没搜到结果（接口可能被限流…）"
  覆盖状态栏，把真因（`kuwo_core.leno:104 无法将字符串转换为浮点数`）盖掉了 ⇒ 用户只能看到"搜不到"，
  排查从"看一行日志"变成"猜"。现已改成 `searchErr` 记下 worker 报的错，收尾时优先显示 `搜索失败：<原因>`。

### B4【中】`_str(异常/容器)` 给 `<object>`，而 `$"{e}"` / `print(e)` 正常 —— **两个"转字符串"口径不一致**

| 项 | 内容 |
| --- | --- |
| 现象 | `print(_str(_args()))` → `<object>`（`_args()` 是 `Array`） |
| 危害 | 调试时完全看不出内容；还会让人怀疑"参数没传进来" |
| ★ 实测更正（2026-10-07，作者指正后重测） | **异常对象本身很好读，是我用错了写法。** 四种读法实测：`print(e)` → `{msg: "…", line: 8, file: "…", stack: […]}` 可读 ✓；**`$"{e}"` → msg 全文**（多行：首行原因 + `[位置]` + `[调用栈]`）✓；`e.msg` / `e.line` / `e.file` → **字段可直接取** ✓（异常对象带这四个字段，文档里从没写过）；而 **`_str(e)` → `<object>`** ✗ |
| 更正前的错误结论（留档） | 我先前据此写下"捕获到异常却看不到任何原因"，**这是错的**——真相是"只有 `_str(e)` 这一种写法看不到"。教训：一个语言里"换个等价写法结论就翻转"的现象，必须换写法复测后才能下笔 |
| ★ 这次口径不一致的**真实代价**（本轮实证） | ① 我因此得出了**错误结论**（上一条），还写进了本文档；② 我的代码里留了 **3 处 `_str(e)`**——`dl_engine` 的搜索报错回传、GUI 的"刷新出错"、下载线程异常。其中**搜索报错那处正好是"青衣"事故要走的路径** ⇒ 就算修好 A5，界面也只会显示 `搜索失败：<object>`，等于白修 ✗。已全部换成 `errmsg()`（取 `$"{e}"` 首行）并实测验证 ✓ |
| 为什么它比"不好看"严重 | `_str(x)` 是"把任意东西转成字符串"的**通用入口**，却偏偏是唯一读不出异常的写法 ⇒ 越是"顺手转一下塞进日志/状态栏/channel"的人越中招。插值 `$"{e}"` 能读、`_str(e)` 不能读，两者**看不出该用哪个** |
| 建议 | ① 让 `_str(x)` 对**有 to_string 的对象走 to_string**（与插值口径统一）——这是本条的根因；② 顺带把"异常对象 = `{msg, line, file, stack}`、拼文案用 `$"{e}"`、**别用 `_str(e)`**"写进 `module_io.md` 或教程；③ `Array` → `<Array(len=3)>`、`Dict` → `<Dict(len=5)>` |
| 成本 | ① 低（转换函数加分支）；② 文档：低；③ 低 |

### B7【中】`threads.start` 的入口**只能是本文件的函数**（GUI 版踩到，报错很清楚）

| 项 | 内容 |
| --- | --- |
| 现象 | `threads.start(eng.search_entry, ...)` 当场抛错：`线程入口必须是**当前文件**的函数 ✗ 收到的是模块 'dl_engine' 里的 'search_entry'（子线程不会加载别的模块的全局变量 ⇒ 模块函数在子线程里跑不起来）` |
| 后果 | 报错发生在 `threads.start()` 那一行 ⇒ 若调用点在 `try/catch` 里（GUI 的定时器回调就是），会表现为**静默失败**：搜索永远返回空、状态栏只闪一条"刷新出错" |

### B8【低】`LenoWeb` 的 `web_gzip` 有 `gunzip` / `inflateRaw`，**没有 zlib 入口**

| 项 | 内容 |
| --- | --- |
| 现象 | zlib 流 = 2 字节头（`78 9C`…）+ deflate + 4 字节 adler32：`gunzip` 认 gzip 头（10 字节），`inflateRaw` 认裸 deflate，**两个都对不上 zlib** |
| 影响面 | 不止酷我歌词：HTTP `Content-Encoding: deflate`、PNG 的 IDAT、任何 `.zlib` 体都是这个格式 |
| 本轮绕法 | `inflateRaw(raw.byte_slice(2, raw.byte_len()))`（剥头；尾部 adler32 不参与解压，`inflate` 遇到 BFINAL 自然停） |
| 建议 | `web_gzip` 补一个 `export func inflateZlib(string raw): GzipResult`（顺手校一下 adler32 更好），或让 `gunzip` 自动按魔数分流 |
| 成本 | 低（现有 `_State`/`_inflateAll` 直接复用，只多两行剥头） |

### B9【高】`_float()` / `_int()` 遇到脏串**抛异常**，而标准库自己在绕开它

| 项 | 内容 |
| --- | --- |
| 现象 | `_float("999.06kb")`、`_float("zp")` 是**抛异常**（`[错误] …: 无法将字符串转换为浮点数`），**不是**返回 0/null。一次就能把整条功能变成"不存在"：搜索崩 ⇒ 界面只剩"没搜到结果"（完整事故见 **A5「青衣」**） |
| 最小复现 | 冷启动三行：`print(_float("zp"))` / `print(_float(""))` / `print(_int("abc"))` |
| 旁证（最硬） | `LenoWeb\lib\web_net.leno` 自己手写了 `_digitsToInt()`（脏值返回 -1）并注释"响应头里什么脏值都可能有" ⇒ **标准库作者在用私有函数绕开自己的运行时原语**；本轮 `kuwo_core` 也不得不手写 `isnumber()` + `parsecellsize()` 做"先判再转" |
| 建议 | ① 加 `float.try_parse(s): float?` / `int.try_parse(s): int?`（脏串给 null）；② 或让 `_float` 宽容（脏串→0）+ 另给 `_float_strict`；③ 无论选哪种，**让 `_int`/`_float` 语义一致**（现在都是抛） |
| 成本 | 低（原生函数加一个分支）；文档补一行"`_float` 会抛，脏值请先判"≈ 0 |

> 这条与 B2 是同一类毛病：**失败路径把"调用方必须处理的事"变成了"整个调用栈的爆炸"**。
> 本轮一共撞了三次（B2 目录不存在、B9 脏数字、A5 搜索崩），值得作为一条统一原则来收：*库函数要么返回哨兵值，要么抛"能被局部 catch 的具名异常"，不要中途打死程序*。
>
> 配套的另一半见 **B14**：既然它要抛，抛出来的那句话就得**带上坏值**（`无法转换为 float："999.06kb"`），
> 否则调用方既拿不到哨兵值、也看不出是哪个值坏了。

### B10【中】类型收窄**不穿过局部别名**（`var c = x` 之后 `c` 还是 `any`）

| 项 | 内容 |
| --- | --- |
| 现象 | 形参声明为 `any`，写 `if cmd is Channel { var c = cmd; c.try_receive() }` ⇒ 一次报三条：`不能在 any 类型上调用方法 'try_receive'` / `不能对未初始化的变量 'c' 调用方法` / `不能在 any 类型 'c' 上直接访问字段`；**而同一个块里直接写 `cmd.try_receive()` 是对的** ✓ |
| 复现 | 同一函数里把 `if x is T { var c = x; c.m() }` 与 `if x is T { x.m() }` 各写一遍对比（本轮在 `dl_engine.waitcmd()` 上撞到，见文件内注释） |
| 更难受的地方 | **规则不一致**：`Channel?` 这类**字段**走 `var c = x` 是能收窄的，只有 `any` 形参不行 ⇒ 同样写法两种结果，最容易记错 |
| 建议 | 让收窄结果流进 `var c = x` 这类新绑定（错误提示里已给的替代方案"或把参数声明为具体类型"要求改签名，代价比修收窄大） |
| 成本 | 中（类型检查器把收窄信息带进赋值处的推断） |

### B11【中】模块级 `pri` 是**语法错误**，而"文件私有"只能靠"没写 export"隐式表达

| 项 | 内容 |
| --- | --- |
| 现象 | 文件顶层写 `pri func foo() {}` ⇒ `[语法错误] 期望表达式`，**指不到真正病因**（`pri` 只在结构体成员上合法） |
| 危害 | ① 最直觉的写法直接撞墙，且报错文不对题；② 更麻烦的是"读"——顶层 `func foo()` 与 `export func foo()` 的可见性差异**只能靠有没有 `export` 反推**，一眼看不出哪些是本文件私有 |
| 溯源 | **上一轮会话实测**（本轮为避免踩坑，一开始就按"顶层不写 pri"写，未再复现） |
| 建议 | ① 支持顶层 `pri func`（与结构体成员口径一致）；② 或至少把文案改成"模块级函数不支持 pri；不写 export 即为文件私有" |
| 成本 | ② 几乎为零；① 改解析器 + 可见性判定 |

### B12【低】没有 `--check`（只做语法 + 语义检查、不产出）

| 项 | 内容 |
| --- | --- |
| 现象 | `--help` 里只有 `-c/--compile`（编译成 `.lenb`）与 `-p/--pack`；想"只验证能不能过编译"只能借用 `-c` |

### B13【中】`threads.start` 的入口规则：**文档口径与运行时不一致**，且两种失败给的信息量天差地别

> 与 **B7** 同源：B7 记的是"别的模块的函数不行（报错很清楚）"，本条补上两条 B7 没记的：
> **闭包其实是可以的**（更正 B7 早前那句"入口不能是闭包"）、以及**文档口径缺失**与**参数校验缺口**。

**实测矩阵（2026-10-07，单文件 5 个用例，直接调用、参数个数写对）**：

| 入口形态 | 结果 |
| --- | --- |
| ① 本文件具名全局函数 `threads.start(named, 21)` | ✅ OK，`join=42` |
| ②a 闭包 无参/无捕获 `threads.start(func(): int { return 7 })` | ✅ OK，`join=7` |
| ②b 闭包 有参/无捕获 `…(func(int n): int { return n+1 }, 7)` | ✅ OK，`join=8` |
| ②c 闭包 无参/**有捕获**（捕获 main 里的 `base`） | ✅ OK，`join=5` |
| ②d 闭包 有参/**有捕获** | ✅ OK，`join=12` |
| ③ 别的 `.leno` 模块里的函数 `threads.start(lyric.fetchlyric, "228908")` | ❌ 明确报错（文案满分，见下） |

| 项 | 内容 |
| --- | --- |
| 文档现状 | `module_threads_api.md` 写着 `func` 是"要执行的函数（闭包），**支持捕获外部变量**"，示例也全是 `threads.start(func(){…})` ⇒ **这一条是对的** ✓ |
| 但文档**没写**的 | "**入口必须是当前文件的函数**——别的模块的函数不行"。这条只存在于编译器的报错文案里；`cleaner_master` 的源码注释里也记着同一个坑（"worker 必须具名全局函数"） |
| 代价 | 每个 GUI 应用都得为此写一层样板包装（`search_worker` / `dl_worker` / `scan_entry` / `delete_entry` …），而新用户第一次写必然撞一次 |
| ③ 的报错文案（值得表扬） | `threads.start(): 线程入口必须是**当前文件**的函数 ✗ 收到的是模块 'kuwo_lyric' 里的 'fetchlyric'。请在本文件写一个具名包装函数再 threads.start（子线程不会加载别的模块的全局变量 ⇒ 模块函数在子线程里跑不起来）` |

**两个副发现（同一轮里撞到的坑，都是"没说清"型）**：

1. **参数个数不足 ⇒ 报错指向完全错误的方向**：
   `threads.start(func(int n): int { return n * base })`（**忘了传实参**）报的是
   `Thread error: 非字符串异常（对象类型 2）—— 常见于**进入函数体之前**就失败（如入口函数所属模块未加载）`
   ——真实原因是**参数个数不对**，文案却把人往"模块没加载"上引。
2. **参数类型不对时不报错，跑出垃圾结果**：
   `named(int n)` 被 `threads.start(named, [21])` 调用（收到的是 `Array` 而不是 `int`）**没有报类型错误**，
   线程照常跑完，`join()` 返回 `4307135132608`（垃圾值）。
   ⇒ 本轮我正是据此先得出了"闭包/具名函数都不行"的**错误结论**，直到把参数写对才看清真相。
   （标注：这是"实测现象"，是否算类型检查缺口**未进一步确认**。）

| 建议 | ① 文档把入口规则写成明确三条：**本文件具名函数 ✅ / 闭包 ✅ / 别的模块的函数 ❌**；② `threads.start` 启动时校验实参个数与类型，报错直接写"期望 N 个参数，实际 M 个"；③ 顺带把"闭包长时间运行可能被 GC"这条**只在源码注释里流传**的警示写进文档（若属实） |
| 成本 | ① 为零；② 中（入口处加一层校验）；③ 低 |

> **教训（给文档整理者）**：`threads.start` 这一处的文档、运行时、示例源码注释三者口径**并不一致**，
> 而且不一致的方向恰好是"注释比文档更接近真相"。凡是这类"规则只活在错误文案和别人源码注释里"的知识，
> 都应该第一时间搬进正式文档——否则下一个人会像我一样先得出一个错误结论再花十几分钟推翻它。

### B14【低】数值转换的报错**不带坏值**，与同运行时的文件报错风格不一致（诊断的一致性）

| 项 | 内容 |
| --- | --- |
| 现象 | `_float("zp")` 的消息是 `无法将字符串转换为浮点数` —— **不带坏值、不带类型名**（`_int("abc")` 同理：`无法将字符串转换为整数`） |
| 内部对照（同一轮实测） | `files.open("D:\\不存在的目录\\x.txt", "rb")` 的消息是 `无法打开文件 'D:\\不存在的目录\\x.txt'` —— **带值** ✓ |
| 所以问题不在"能力" | 不是"Leno 不会带值"，而是**同一个运行时内部风格不统一**：文件/路径类带值，数值转换类不带值 |
| 为什么这条值得修（成本/收益最划算） | 排查时"**哪个值坏了**"就是核心线索。`青衣` 事故（A5）里，我是靠**回到接口原始 JSON** 才看出 `size:999.06Kb` / `size:zpMb` 的；如果消息直接写 `无法转换为 float："999.06kb"`，至少省一轮试错。而这条信息**在抛出的那一刻就在手上**，取不到是纯浪费 |
| 建议 | 文案统一成 `无法转换为 float："<原值>"`（Python 的对照口径：`could not convert string to float: 'zp'`）；`_int` 同理；若原值很长，截断到 N 字符即可 |
| 成本 | 低（原生函数里把入参拼进消息）；文档零 |
