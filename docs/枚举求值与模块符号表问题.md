## 二、ENUM 组：三个计算点实测互不一致

### 2.1 复现（修复前的实测数据）

`md.leno`：

```leno
export enum E5 {
    P = 2 + 3 * 4
    Q = 2 * (3 + 4)
    BIG = 1 << 40
}
export func fp():int { return E5.P }
export func fq():int { return E5.Q }
```

三条访问路径各打印一次，**修复前**输出：

```
mod_side : P=14 Q=14 BIG=1099511627776     ← 同模块（枚举定义处 / 模块内函数）
use_path : P=20 Q=10 BIG=1099511627776     ← use d.E5 后直接写 E5.P      ← 错！
qual_path: P=14 Q=14 BIG=1099511627776     ← d.E5.P 模块限定
```

`2+3*4` 正确是 14，`use` 路径给 20（当成 `(2+3)*4`）；`2*(3+4)` 正确是 14，`use` 路径给 10（当成 `2*3+4`，括号被丢弃）。
**同一份源码、同一个程序，成员值随访问写法而变，且 `use` 那条是错的。**

隐式成员（无 `=`）修复前实测：

```
E1 全隐式 {P,Q,R}      → use 与 qual 都报「枚举 'E1' 中没有成员 'P/Q/R'」
E2 {P=7 Q R=9 S}       → 只有 P、R 可见；Q、S 报「没有成员」
E3 {P=2+3*4 Q}         → P 可见；Q 报「没有成员」
同模块单文件 {A B C}   → A=0 B=1 C=2（正常，说明解析器没问题）
```

### 2.2 三个计算点分别在哪

1. **解析器**（权威）：`parse_enum_stmt` + `eval_const_expr`，AST 递归求值、有优先级、隐式成员按 `next_auto_value = member_value + 1` 递增。
   值流向：同模块访问（`visit_enum.inc` → `sym->enum_values`）与模块字节码（`codegen_stmt.c` → `OP_ENUM_DEF` → 运行期 `enum_def`）。
2. **符号表扫描器**：`scan_enum.inc` 自己重算一遍（`next_auto` + 手写解析 + 「最简从左到右」求值器）。
   值流向：跨模块 `use`（`visit_module.inc`）、成员存在性检查（`visit_expr.inc`）。
3. **运行期** `enum_def`（`op_enum.inc` / `op_utils.inc`）：值来自点 1 的字节码。

### 2.3 ENUM-1 根因：一个错位的括号

`scan_enum.inc` 中 `if (*after_enum == '=') {` 于第 73 行开括号，直到第 309 行才闭合，
而「决定最终取值 + `member_count++`」整段**落在它内部**：

```c
                                if (has_explicit) {
                                    next_auto = member_values_buf[member_count] + 1;
                                } else {
                                    member_values_buf[member_count] = next_auto;
                                    next_auto += 1;
                                }
                                member_count++;
                                }        // ← 这个 } 才是 if ('=') 的收尾（错位）
```

后果：**只有写了 `= 值` 的成员才会 `member_count++`**；无 `=` 的成员名字被写入缓冲区但计数不推进，被下一个成员覆盖。
（用脚本统计全文件花括号深度验证：最终 depth=0，`if ('=')` 覆盖 73-309 行。）

### 2.4 ENUM-2 根因：两套求值语义

扫描器的求值器注释里自己写着「不处理优先级」「从左到右」，且把不认识的字符（含括号）直接 `cp++` 跳过；
求值失败还会静默退回「无显式值」⇒ 值变成自动递增值。解析器走的是 AST 递归下降（优先级、括号、一元运算都正确）。

## 三、MOD 组：模块符号表扫描

### 3.1 MOD-1：一个调用点遍历 3 次

以 `main.leno` 中 `import "M.leno" as m` + 一处 `m.foo()` 为例，M 被完整遍历 3 次：

1. `visit_module.inc`：import 时 `create` + `scan`（结果存在 `info->sym_table`，后续复用）。**走 `create`，不查 `g_sym_memo`** ⇒ 被 k 个文件 import 就扫 k 次。
2. `visit_module.inc`：每个 `m.foo()` 调用点又 `create` + `scan` + `destroy`，只为判断「是不是 struct」。纯冗余 —— `module_info->sym_table` 就在手边（同一分支下面还在用它查函数）。
3. `module_has_method()` → `extract_module_exports_from_file` 再整体读一遍 M 的源码并跑 export 词法统计。

即：**一个调用点 = 2 次符号表全扫 + 1 次导出全扫**；10 个调用点放大到 21 次。

### 3.2 MOD-2：记忆化永不失效

`g_sym_memo` 只有 `sym_memo_lookup` / `sym_memo_store`，没有失效与清空入口；
而 `module_symbol_table_get_shared` 命中时直接返回，**根本不进磁盘缓存的哈希校验**，
于是 `.lenosymc` 的「源文件 + 依赖哈希」失效机制被内存 memo 短路。
长驻进程（`leno_lsp`，消息循环 + 链接同一个 `module_symbol_table.c`）里，用户改了依赖文件后
hover/signature 仍拿旧符号表；另外 memo 表 `shared=1`、`destroy` 是 no-op，内存只增不减。

### MOD-1（P2）一个调用点三次遍历
- 状态：✅ 已修复
- 改动：
  1. `visit_module.inc`：删掉调用点上「为判断是不是 struct」而 `create` + `scan` + `destroy` 一整个模块的冗余扫描，

     文件改动即自动失效（LSP 常驻进程同样安全），于是 `module_has_method` 不再每个调用点重读整份源码。

### MOD-2（P3）记忆化无失效
- 状态：✅ 已修复
- 改动：`sym_table_entry.inc`
  - memo 条目增加 `mtime/size`：命中前 stat 比对，文件改了就当未命中（调用方重扫），
    并把旧表挂到 retired 列表（**不立即 free** —— 同一次扫描链路里上游可能还持有它），
    `reset_memo` 时统一释放；
  - 新增 `module_symbol_table_reset_memo()`（`module_symbol_table.h` 声明），
    在 `main.c` 两处编译入口（`error_clear/reset_scan_stack` 旁）调用；LSP 这类常驻宿主应在每次请求前调用。
- 测试：全量套件通过；`test_module_dep_memo`（关缓存路径）通过；
  记忆化的正确性由 mtime 比对保证（同一进程内多次编译不再复用旧表）。

### ENUM-3（P4）编译期折叠丢精度
- 状态：✅ 已修复
- 改动：`visit_module.inc` 的 enum 折叠不再一律写 `(double)member_value`；
  超出 double 精确整数范围（±2^53）时改走 `is_bigint = 1` + `bigint_str`（与词法层同一判据）。
- 测试：`build\enum_probe\mm4.leno`，成员 `BIG = 1 << 62 = 4611686018427387904`（double 会舍入成 …7900），
  三条路径输出 `5 4611686018427387904 -3` **完全一致**。

### ENUM-4（P4）枚举迭代取值 32 位截断
- 状态：✅ 已修复
- 说明（修正我最初的判断）：该分支不是「死代码」—— 它是 `ITER_GET`（`for E to v`）的 enum 分支，
  可经枚举迭代到达，问题在用 `val_int((int)…)` 把成员值截断成 32 位。`E[0]`（数字索引取 enum 成员）
  本来就按设计要求字符串成员名（报「enum 成员名必须是字符串」），不属于缺陷。
- 改动：`op_utils.inc` 枚举迭代分支改用 `val_int_safe`（与「按名取值」那条路径一致）。
- 测试：`build\enum_probe\mm4.leno` 的 `iter_mod` 输出 `v=5 / v=4611686018427387904 / v=-3`
  （修复前 `BIG` 会被截断成 0）。

### ENUM-5（P5）逗号分隔不一致
