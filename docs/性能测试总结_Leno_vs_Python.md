## 二、光线追踪标量版（`光线追踪对比.leno` / `.py`）

SoA 布局（独立数组存储坐标），无对象创建，纯标量运算。

| Phase | Leno | Python | 倍率 | 说明 |
|-------|------|--------|------|------|
| A 数组索引（300万次×4索引） | 484ms | 1258ms | **Leno 快 2.60x** | OP_INDEX 快速路径 + CAST 消除发挥优势 |
| B sphereHit 多返回值（300万次） | 2969ms | 3150ms | **Leno 快 1.06x** | 多返回值解构直接存储优化生效 |
| B2 sphereHit 单返回值（300万次） | 2437ms | 3569ms | **Leno 快 1.46x** | 单返回值路径 Leno 优势明显 |
| C 递归 trace（30万射线 depth=5） | 11235ms | 10482ms | Python 快 1.07x | 递归+数组索引混合负载，双方持平 |

分析：
- Phase A/B/B2 Leno 全面领先，得益于 OP_INDEX int 索引快速路径、赋值 CAST 编译期消除、INLINE_LOCALS_MAX=32 内联优化
- Phase C 递归 trace 是最复杂的真实场景（30万射线×递归调用×数组索引×算术运算混合），Leno 与 Python 基本打平，仅慢 7%

## 三、光线追踪对象版（`光线追踪对象版.leno` / `.py`）

struct + 方法 + Hit 对象分配（Python 侧 class + `__slots__`）。

| Phase | Leno | Python | 倍率 | 说明 |
|-------|------|--------|------|------|
| A 对象字段访问（300万次×4字段） | 578ms | 772ms | **Leno 快 1.34x** | 字段内联访问优于 Python |
| B hit 方法 + Hit 对象（300万次） | 4172ms | 3835ms | Python 快 1.09x | 对象分配开销（gc_alloc vs pymalloc） |
| B2 hitSingle 方法（300万次） | 3172ms | 2714ms | Python 快 1.17x | 方法分派后的残余差距 |
| C 递归 trace 对象版（30万射线） | 13313ms | 13589ms | **Leno 快 1.02x** | 持平 |

分析：
- 对象版整体与 Python 持平，Phase B/B2 略慢源于对象分配路径（gc_alloc malloc + 分代簿记 vs pymalloc 池化 free-list）
- 方法分派 IC + OP_INVOKE_METHOD 融合指令已将方法调用开销压到最低
- Phase C 递归 trace 持平，说明对象版整体已达到 CPython 3.11 同级水平

| Python | 4491ms | 4486ms | -0.5ns/参 |

分析：
- Leno 1 参调用快 3.38 倍，7 参调用快 2.52 倍，绝对优势明显
- Python 每参增量接近 0（CPython 3.11 zero-cost frame 参数直接在值栈帧基上，无逐参拷贝）

## 八、总结

### 优势场景（Leno 碾压）

| 场景 | 倍率 | 原因 |
|------|------|------|
| 算术运算 | 4~12x | 静态类型 NaN-boxed Value，无 boxing |
| for 循环 | 4~14x | for-to 语法直接生成 LOOP 跳转，无迭代器协议 |
| 空函数调用 | 7.8x | 调用机制轻量（41ns vs 122ns/次） |
| 数组操作 | 3.5~4x | OP_INDEX int 快速路径，无 Python 的 `__getitem__` 协议 |
| native 调用 | 3.5x | 直调 C，无 boxing |
| 字典操作 | 2.4x | 哈希表直接操作，无 Python 的 `__setitem__` 协议 |
| try-catch | 1.7~1.9x | 异常帧预清空，无 Python 的 exc_info 链表 |

### 持平场景（旗鼓相当）

| 场景 | 倍率 | 原因 |
|------|------|------|
| 光线追踪标量 Phase C | 慢 1.07x | 递归+数组+算术混合，Python 3.11 zero-cost frame 优势 |
| 光线追踪对象版 Phase C | 快 1.02x | 对象分配 + 方法分派 + 递归，双方持平 |
| 斐波那契迭代 | 持平 | O(n) 算法，数据量小，差异在计时精度内 |

### 略弱场景

| 场景 | 倍率 | 原因 |
|------|------|------|
| 经典递归斐波那契 | 慢 1.36x | 递归调用热点，Python 3.11 zero-cost frame + 寄存器化 LOAD_FAST |
| 对象版 Phase B/B2 | 慢 1.09~1.17x | gc_alloc malloc + 分代簿记 vs pymalloc 池化 free-list |

### 架构差异本质

- **Leno 优势来源**：静态类型（编译期消除 CAST/类型检查）、NaN-boxed Value（无引用计数）、native 模块直调 C、for-to 语法无迭代器开销
- **Python 优势来源**：CPython 3.11 zero-cost frame（参数零拷贝）、pymalloc 池化分配、LOAD_FAST 寄存器化、30 年优化的内联缓存基础设施
- **结论**：Leno 在调用机制、循环、算术、native 调用上有结构性优势（快 2~14 倍）；在递归深度调用+对象分配+数组索引的混合负载中与 Python 持平。整体性能已达到与 CPython 3.11 同级水平，在多数场景下显著超越。

# 附录：SDL3 图形渲染性能对比

测试文件目录：`leno_module/LenoSDL3/examples/特效动画/`

这两个测试是**真实图形应用**——加载图片、SDL3 窗口、逐像素波纹扭曲渲染、纹理上传。
两者都通过 FFI 调用同一个 SDL3.dll，算法完全对应，测试时长各 15 秒。

## ripple_bench（排除法定位测试）

纯性能基准，关闭 VSync（`SDL_SetRenderVSync(ren, 0)`），跑满帧率上限。
全功能开启：memcpy + rsqrt + ffi.copy4 像素拷贝 + 事件循环 + 自动波纹 + SDL 绘制。

| 指标 | Leno | Python | 倍率 |
|------|------|--------|------|
| 运行时长 | 15013ms | 15083ms | — |
| 总帧数 | 8544 | 5440 | — |
| 平均 FPS | **569.1** | 360.7 | **快 1.58x** |
| 平均每帧 | **1.75ms** | 2.77ms | **快 1.58x** |
| 最低帧 | 0ms | 0ms | — |
| 最高帧 | 70ms | 155ms | — |
| 分辨率 | 384×288 | 384×288 | — |

分析：在关闭 VSync 的纯计算+渲染场景下，Leno 快 **1.58 倍**。热点是
`renderRipple()` 的嵌套像素循环（ffi.copy4 + maths.rsqrt），Leno 的 for-to
循环 + ffi 直调 + NaN-boxed 算术在此场景全面占优。Python 侧最高帧 155ms
（GC 停顿或 ctypes 转换开销），Leno 仅 70ms。

## ripple_image（图片水波纹扭曲特效）

完整特效应用，含字体渲染、波纹标记绘制、帧率限制。
**注意**：Leno 版开启 `ren.setVSync(1)` + `delay(16-elapsed)` 帧率限制（~60FPS），
Python 版关闭 VSync + 无帧延迟跑满上限。因此 FPS 不可直接比较，
**应以每帧渲染耗时（去除帧限制后）为准**。

| 指标 | Leno | Python | 说明 |
|------|------|--------|------|
| 运行时长 | 15033ms | 15030ms | — |
| 总帧数 | 720 | 5266 | Leno 帧率限制~48FPS |
| 平均 FPS | 47.9 | 350.4 | Leno 有 VSync+delay |
| 平均每帧 | 20.6ms | 2.9ms | Leno 含 delay 等待时间 |
| 最低帧 | 2ms | 0ms | — |
| 最高帧 | 85ms | 205ms | — |
| 分辨率 | 384×288 | 384×288 | — |
| 原图 | 1345×1010 | 1345×1010 | — |

关键分析：

Leno 版 `ripple_image.leno` 有帧率限制代码：
```c
ren.setVSync(1)                    // VSync 开
if elapsed < 16 { SDL3.delay(16 - elapsed) }  // 补足到 16ms
```
Python 版注释明确写"无帧延迟，跑满上限"，VSync 关闭。

因此 Leno 的 720 帧 / 47.9 FPS 是**人为限制**的结果，不是性能上限。
从最低帧耗时 2ms 可知，去除帧限制后 Leno 单帧渲染可达 ~500 FPS。

Python 的 5266 帧 / 350.4 FPS、每帧 2.9ms 是无限制跑满的结果。
但 Python 最高帧 205ms（GC 停顿 + ctypes 开销），波动极大。

**公平对比**：以 ripple_bench（双方均关闭 VSync、无帧限制）为准，
Leno 569 FPS vs Python 361 FPS，**快 1.58 倍**。

## 小结

| 测试 | Leno | Python | 倍率 | 结论 |
|------|------|--------|------|------|
| ripple_bench（无限制纯性能） | 569 FPS | 361 FPS | **快 1.58x** | Leno 胜 |
| ripple_image（含帧限制） | 48 FPS | 350 FPS | 不可直接比 | Leno 有 VSync+delay |

在真实 SDL3 图形渲染场景（逐像素操作 + FFI + 数学运算 + 事件循环）中，
Leno 在无帧率限制下快 Python **1.58 倍**，且帧时间更稳定（最高 70ms vs 155ms）。
这验证了 Leno 在"FFI 密集 + 嵌套循环 + 算术运算"混合负载下的综合优势。
