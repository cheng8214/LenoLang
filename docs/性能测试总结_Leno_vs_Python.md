# Leno 性能对比总结：JIT vs VM vs Python 3.13

> 测试时间：2026-09-15
> 测试环境：Windows 10 / Leno 1.0.0（JIT 默认开启）/ CPython 3.13.2 / 同机串行执行（无并行任务干扰计时）
> 本文档取代 2026-08-29 版《Leno vs Python 性能测试总结》。旧版测试时 JIT 尚未落地（2026-09-06 才合入），且 Python 基线存在明显环境噪声（详见第七节），数据已过时。
>
> **计时口径（2026-09-17 补注，读表前务必先看）**：本文毫秒数据由当时的 `times.ms()` 采集，而它当时是
> `GetTickCount64` —— 分辨率 ≈15.625ms 的**刻度计数器**，且返回 int。后果是 JIT 列的小值
> （15 / 16 / 31 / 47 / 62 / 78 / 94 / 109 / 125 / 140ms…）几乎都是 15.625ms 的整数倍，属"整刻度"量化：
> 单次测量误差最大 ±15.6ms（例如"1000 万次调用 16ms"其实只有 1 个刻度，真值可能低到 0.4ms）。
> VM/Python 列多为数百~数千毫秒，量化影响 ≤2.4%，不受此影响。
> `times.ms()` 已于 2026-09-16 改为 QPC / CLOCK_MONOTONIC 的高精度单调时钟并返回 float
> （见 `module_times.md` 与 `待办_单一事实来源与重复实现收敛.md`）——
> **用新口径重测前，本文 JIT 小值列不可跨机（含 i5-14400F）或跨版本直接对照**。
> 另：本文未记录 CPU 型号 / 内存 / 构建提交号；同期文档（`待办_GC与分配优化.md`）记为 i5-3450。

## 一、测试方法

三种执行模式：

| 模式 | 说明 |
|------|------|
| **JIT** | 默认模式，热路径自动编译为 x86-64 机器码 |
| **VM** | `LENO_NO_JIT=1`，纯解释器基线 |
| **Python** | CPython 3.13.2，对照基准 |

**正确性校验**：所有测试的校验值三方一致——光线追踪 `sum=50730000.000273108`、`hits=900000`、`hits=585500`，JIT 覆盖面 `acc=227000002`，`fib(32)=2178309`，`fib(1000)` 的 209 位 BigInt 结果与 Python 逐位一致。JIT 未引入任何数值偏差。

**正确性护栏实例**：`全部测试` 中 `fib_iterative` 触发 3 次 int48 溢出 bailout（`int48 溢出/截断 @bc_off=61`），自动降级解释器执行 BigInt 路径，最终结果仍与 Python 逐位一致——溢出降级机制在真实负载下工作正常。

**本轮测试前的同步修正**（基准文件长期失同步，先修正再测）：

| 文件 | 问题 | 修正 |
|------|------|------|
| `全部测试.py` | csnum 仍为 1000 万、嵌套循环 1000×1000（leno 版 2026-09-06 已改为 1 亿、10000×10000） | 参数同步 |
| `ripple_bench.py` / `ripple_image.py` | SDL3 DLL 路径硬编码旧目录 `LenoC` | 改为 `Leno` |
| `ripple_image.leno` | leno 版开 VSync + `delay(16-elapsed)` 限帧 60，py 版关 VSync 跑满上限，FPS 不可比 | 统一为跑满模式（原代码保留注释） |

## 二、总览结论

1. **JIT vs Python：全场景 1.5~62x 领先，无任何场景被反超**。调用/循环类微基准 35~62x，典型混合负载（光线追踪、数学计算）3~7x，最不利的重对象递归也有 1.5x。
2. **VM vs Python：全场景持平或领先（1.0~4.9x）**。纯解释器已全面追平 CPython 3.13。
3. **JIT vs VM：热路径 1.8~20x**。纯循环 9.2x、空函数调用 20.1x、switch 6.7x；增益最低的是 dict.set（1.8x）与对象分配路径（1.5~1.7x）。
4. **两个明确短板**：字符串插值 JIT 略慢于 VM（0.95x，唯一回退项）；对象分配（gc_alloc）是 JIT 增益的主要天花板。

## 三、微基准

### 3.1 函数调用与递归（单位 ms）

| 测试 | JIT | VM | Python | JIT/VM | JIT/Py |
|------|-----|-----|--------|--------|--------|
| fib(32) 递归 | 62 | 188 | 201 | 3.0x | **3.2x** |
| fib(30) 递归（全部测试内） | 31 | 78 | 78 | 2.5x | 2.5x |
| 调用开销 int（1000 万次） | 16 | 453 | 987 | 28.3x | **61.7x** |
| 调用开销 float（1000 万次） | 16 | 454 | 961 | 28.4x | **60.1x** |
| 参数扩展 1 参（1000 万次） | 16 | 469 | 988 | 29.3x | **61.8x** |
| 参数扩展 7 参（1000 万次） | 31 | 531 | 1094 | 17.1x | **35.3x** |

JIT 模式下 1000 万次函数调用 16ms（1.6ns/次），已达原生调用开销量级；7 参场景增益降到 35x，参数装箱/传递路径仍有优化空间。

### 3.2 算术运算与赋值（1 亿次，全部测试，单位 ms）

| 测试项 | JIT | VM | Python | JIT/Py |
|--------|-----|-----|--------|--------|
| i++ | 109 | 875 | 4040 | **37.0x** |
| a = b | 47 | 656 | 2894 | **61.6x** |
| a = 1 | 63 | 781 | 2523 | **40.0x** |
| a = 1 + 2 | 62 | 735 | 2476 | **39.9x** |
| a = b + c | 63 | 1390 | 4022 | **63.8x** |
| a += 1 | 94 | 922 | 3949 | **42.0x** |
| a = b * c | 78 | 1422 | 4001 | **51.3x** |
| a = b - c | 78 | 1422 | 4013 | **51.4x** |
| a = b + c + d | 110 | 1828 | 4846 | **44.1x** |
| 空函数调用 | 62 | 500 | 3319 | **53.5x** |
| arr.add() | 500 | 1297 | 3930 | **7.9x** |
| arr[index] | 188 | 1110 | 3305 | **17.6x** |
| dict[key]=value | 875 | 1718 | 3306 | **3.8x** |
| 无 try 循环 | 94 | 813 | 1817 | **19.3x** |
| 有 try 循环 | 78 | 1156 | 1882 | **24.1x** |
| for 空循环 | 62 | 516 | 1576 | **25.4x** |
| while 空循环 | 125 | 1234 | 4181 | **33.4x** |
| for to j（带循环变量） | 62 | 703 | 4634 | **74.7x** |
| 嵌套 for+for（10000×10000） | 94 | 828 | 4031 | **42.9x** |
| 嵌套 while+while | 140 | 1563 | 7460 | **53.3x** |

要点：

- JIT 模式下 `a = b` 1 亿次仅 47ms（0.47ns/次），已接近原生 load/store 极限
- try 块开销：JIT 下有 try 与无 try 持平（78 vs 94ms），零成本异常落地
- 容器操作（arr.add / dict.set）是 JIT 相对增益最低的一档，容器内联与 IC 深度是下一档优化目标

### 3.3 数学函数调用（5000 万次 sin·cos + sqrt + log）

| 模式 | 耗时 | 倍率 |
|------|------|------|
| JIT | 4563ms | 基准 |
| VM | 4688ms | 1.03x |
| Python | 14314ms | **3.14x** |

JIT 与 VM 几乎持平——符合预期：此负载 95% 以上时间在 C 数学库函数内部，语言侧调度开销已被两种模式压到可忽略。对 Python 的 3.1x 优势主要来自循环与累加本身。三方结果均为 `236538640619.24002`。

## 四、真实负载：光线追踪

参数：NS=10 球、HITCALLS=300 万次、NUM_RAYS=30 万条（depth=5）。标量版为 SoA 布局纯数组运算；对象版为 struct + 方法 + Hit 对象分配（Python 侧 class + `__slots__`）。

### 4.1 标量版（单位 ms）

| Phase | JIT | VM | Python | JIT/VM | JIT/Py |
|-------|-----|-----|--------|--------|--------|
| A 数组索引（300 万次×4 索引） | 15 | 187 | 179 | 12.5x | **11.9x** |
| B sphereHit 多返回值（300 万次） | 94 | 750 | 695 | 8.0x | **7.4x** |
| B2 sphereHit 单返回值（300 万次） | 78 | 719 | 672 | 9.2x | **8.6x** |
| C 递归 trace（30 万射线） | 797 | 2500 | 2407 | 3.1x | **3.0x** |

### 4.2 对象版（单位 ms）

| Phase | JIT | VM | Python | JIT/VM | JIT/Py |
|-------|-----|-----|--------|--------|--------|
| A 对象字段访问（300 万次×4 字段） | 47 | 110 | 171 | 2.3x | **3.6x** |
| B hit 方法 + Hit 对象（300 万次） | 516 | 969 | 879 | 1.9x | **1.7x** |
| B2 hitSingle 方法（300 万次） | 94 | 671 | 637 | 7.1x | **6.8x** |
| C 递归 trace + 对象分配（30 万射线） | 2031 | 3172 | 3009 | 1.6x | **1.5x** |

要点：

- **对象版 Phase B/C 是 JIT 增益最低的真实负载**（1.6~1.9x）：每球测试分配一个 Hit 对象，gc_alloc 路径（malloc + 分代簿记）无法被 JIT 消除，与 8 月文档"gc_alloc vs pymalloc"的判断一致——**对象分配是 JIT 的下一个突破口**
- B2（无对象分配的同构方法）JIT 增益立刻回到 7.1x，佐证瓶颈确实在分配而非方法分派
- JIT 统计：两版光线追踪均 Compiled 5、Bailouts 0，热循环稳定驻留机器码（Executed 86 万次+）

## 五、JIT 覆盖面基准

专项测量各类字节码模式的 VM→JIT 提速比（`examples/性能测试/JIT覆盖面基准.leno`）：

| 模式 | VM | JIT | 提速 |
|------|-----|-----|------|
| 纯循环 i++ | 45859us | 4990us | **9.2x** |
| 空函数调用 | 79566us | 3968us | **20.1x** |
| 空函数调用（不可内联） | 72623us | 6683us | **10.9x** |
| 字符串插值 | 116128us | 122273us | **0.95x（回退）** |
| switch 4 case | 367900us | 54791us | **6.7x** |
| is 类型判定 | 342446us | 61572us | **5.6x** |
| struct 字段读写 | 158300us | 27079us | **5.8x** |
| arr.add | 38980us | 15158us | 2.6x |
| dict.set | 51356us | 27845us | 1.8x |

- **唯一回退项：字符串插值**（JIT 慢 5%），插值路径应保留解释器执行或单独优化
- dict.set（1.8x）与 arr.add（2.6x）提速偏低，容器内联深度不足

## 六、SDL3 特效动画（渲染主导负载）

`leno_module/LenoSDL3/examples/特效动画/`，15 秒平均 FPS（统一跑满模式、关 VSync）：

| 基准 | JIT | VM | Python |
|------|-----|-----|--------|
| ripple_image（图片水波纹） | 3000 | 2740 | 2765 |
| ripple_bench（排除法波纹） | 3213 | 2865 | 2776 |

三方持平。**但这是基准设计问题而非语言性能问题**：波纹寿命按"每帧 radius += speed"推进，3000 FPS 下波纹毫秒级消亡，空帧（仅 memcpy + SDL 绘制）占绝大多数，瓶颈完全在渲染管线。此组数据只能说明"渲染主导的负载下语言开销无感"。

**改进建议**：波纹寿命改为按真实时间推进（`radius += speed * dt`），保证每帧都有活跃波纹，才能真正测出语言侧像素循环差距。

### 7.2 旧文档 Python 基线的噪声问题

`光线追踪对比.py` 自 8 月 29 日未改过任何参数，但本轮 Python 实测远快于旧记录：标量 Phase A 179ms（旧记录 1258ms，7 倍差距）、标量 C 2407ms（旧 10482ms）、对象 C 3009ms（旧 13589ms）。

## 八、当前短板与下一步方向

| 优先级 | 短板 | 证据 | 方向 |
|--------|------|------|------|
| 高 | 对象分配路径 | 对象版 B/C JIT 增益仅 1.6~1.9x | gc_alloc 快路径 / 逃逸分析 / 栈上分配 |
| 高 | 字符串插值 | JIT 0.95x（唯一回退项） | 插值路径不编译或单独优化 |
| 中 | dict.set / arr.add | 提速仅 1.8x / 2.6x | 容器操作内联加深、专用 IC |
| 中 | 7 参调用 | 增益 35x vs 1 参 62x | 参数传递路径（寄存器传参） |
| 低 | ripple 基准设计 | 空帧占绝大多数 | 波纹寿命按 dt 推进，重测 |
