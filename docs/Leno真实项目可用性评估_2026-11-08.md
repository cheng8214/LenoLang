# Leno 真实项目可用性评估

> 范围：d:\CLeno\Aria、LenoMusic、LenoTrae、LenoWorkBuddy（只读，未修改任何项目代码）；§4.5 另审 `build\leno_module` 标准库（20 个模块，同样只读）。
> 方法：144 个 `.leno`、49,769 行全量抽读 + 关键模式计数；另用 `build\leno.exe` 在临时目录做最小用例实测（§3.5），并审计生成侧引导（§3.6）。计数口径：**包含该模式的行数**（一行多次只算 1 次），含注释/签名/内嵌字符串；`as` 只统计非 `import`/`use` 别名、非纯注释的代码行。用于看趋势，不作为精确值。
> 参照：LenoGame / LenoCleaner 仅作横向对照。

## 0. 总判断

**Leno 已经跨过“能写真实产品”的门槛，但还没跨过“规模化维护”的门槛。**

正面证据是硬的：四个项目都完成打包分发；Aria 24,614 行，里面是一个真正的 HTTP 服务端（线程池 + SQLite + 鉴权 + 管理后台）；LenoMusic 有 17 个可离线运行的测试并产出 Linux 构建；WorkBuddy 有 `doctor`、离线 stub 和成体系的错误码；LenoTrae 有黄金样例回归。单文件 exe 约 10–12MB，目标机不需要装运行时（[WorkBuddy README:16](file:///d:/CLeno/LenoWorkBuddy/README.md#L16)），这条工程链路是通的。

**但成本集中在四个“边界”上，而不是语法：**

1. 数据一旦要跨线程、上表格或落盘，类型就蒸发，退回 `Array[Array[string]]` / `Dict` + `_str`；
2. 状态要么编码成魔法整数/字符串码（int `enum` 本可用，但无约定/提示），要么受限于 enum 不能带载荷，逻辑分散到多个文件；
3. 严格解析和可分类的错误没有标准类型，每个项目自己造一套 `Result`/`Parse`——标准库自己也有 8 种错误写法、4 类空值哨兵（§4.5）；
4. 模块与 VM 的实现细节（`extend` 模块级、256 字段、255 局部量）直接改写应用的架构。

关键计数：

| 项目 | .leno | 行数 | import/use | `Array[Array[string]]` | null 判断 | `as` 收窄 | `_str()` | 测试 |
|---|---|---|---|---|---|---|---|---|
| Aria | 70 | 24,614 | 615 / 161 | 148 | 354 | 132 | ≈900 | 8 个手动探针，`assert` 0 次 |
| LenoMusic | 46 | 16,379 | 212 / 50 | 189 | 175 | 96 | ≈366 | 17 个离线断言脚本 |
| LenoTrae | 12 | 3,454 | 62 / 23 | 13 | 21 | 36 | ≈115 | 2 |
| LenoWorkBuddy | 16 | 5,322 | 92 / 9 | 5 | 115 | 46 | ≈194 | 5 个测试（另有 1 个 GUI stub） |

另有：`switch` 0 处、`enum` 0 处、`face/impl` 0 处、用户自定义泛型 0 处、`map/filter/reduce` 0 处、真正的 `async func` 0 处。

**但这 6 个 0 需要分开看**：`build\leno.exe` 最小用例实测（见 §3.5）表明 `switch`（int/string/enum）、int `enum`、`map/filter/reduce`、用户泛型都能编译并正确运行；`face/impl` 与 `async func` **未实测**，不能据此断言可用。在已测项里，真正缺失的只有 **enum 载荷** 和 **比较器排序**。0 使用改变的是病因判断，不是语言能力判断（见 §3.6、§6）。

**标准库这一层把同一个判断放大了一倍。** `build\leno_module` 有 20 个模块、53,052 行非空 lib 代码（含空行 58,011）、663 个按“每模块单门面文件”口径统计的导出函数（若统计所有 lib 顶层 `export func` 则为 1,590）——HTTP 客户端、JSON、日志、文件遍历、表格读写都在里面，能力层是真实存在的。但四个项目 import 公共门面 `Web` **0 次**，import 它的内部文件 `web_net.leno` **37 次**；77% 的库行数不在 `run_all_tests.leno` 的可见范围内。也就是说，标准库"有能力，但没有成为标准形态"（详见 §4.5）。

**一句话：语言的核心表达力（含 `switch` / int `enum` / `map·filter·reduce` / 泛型）经实测是够用的；问题在"标准数据形态、标准错误形态"缺席——标准库有 20 个模块却同样没有提供这两种形态，生成侧也没有任何机制把作者推向惯用写法。最大的单点天花板仍是 8 位索引限额，已测项里真正缺失的语法只剩 enum 载荷、比较器排序和穷尽性检查（`face/impl`、`async` 未实测）。**

## 1. 哪些代码像“正常语言写出来的”

### 1.1 结构体 + 方法 + 一等函数字段：`cards.leno`

[CardSize](file:///d:/CLeno/Aria/lib/cards.leno#L33-L81) 是纯数据结构 + 方法，[CardHooks](file:///d:/CLeno/Aria/lib/cards.leno#L85-L97) 用函数字段表达可选回调，[song_card](file:///d:/CLeno/Aria/lib/cards.leno#L108-L135) 用字典传样式、用闭包挂事件：

```leno
if h.onPlay != null {
    Song s = sg
    c.on_click(func() { h.onPlay(s) })
}
```

这段没有框架味，也不需要“组件基类”。它证明 Leno 的 `struct + methods + function values + closure` 足以写出可组合的 UI 组件。这是全仓最像“正常语言”的一段。

### 1.2 数据即代码：`routes.leno`

[路由表](file:///d:/CLeno/Aria/server/routes.leno#L23-L72) 直接是一个 `Array[Dict]`，handler 是函数值，加接口只改一处：

```leno
{method: "GET",  path: "/api/square", handler: rep.api_square, auth: true},   // 广场（需登录）
```

这类 DSL 写法比手写 `if path == ...` 好得多，说明语言在“声明式配置 + 闭包”这个方向上是够用的。

### 1.3 纯逻辑分层：`LenoMusic/player.leno`

它刻意不 import SDL3，只依赖 `Music` 与 `parsing`（[player.leno:1-30](file:///d:/CLeno/LenoMusic/player.leno#L1-L30)），注释直接写明“纯逻辑 ✓ 能离线单测”。`Lrc` 用结构体 + 方法组织（[130-140](file:///d:/CLeno/LenoMusic/player.leno#L130-L140)）。**这是四个项目里可测试性设计最好的一处**：把“能测的部分”从 UI 里剥出来。

### 1.4 `any` 边界集中处理：`wb_core.leno`

把 JSON/环境变量/CLI 的 `any` 收在一层转换里：[Num](file:///d:/CLeno/LenoWorkBuddy/wb_core.leno#L251-L276)、`try_float`、`is_int_str`、[as_int/as_str](file:///d:/CLeno/LenoWorkBuddy/wb_core.leno#L278-L290)。虽然这是手写 Result，但写法本身干净、可读、可复用。

### 1.5 线程边界：`net_workers.leno`

后台入口是模块级函数、结果走 `Channel`、UI 线程 `try_receive` 轮询（[641-655](file:///d:/CLeno/Aria/lib/net_workers.leno#L641-L655)）。在“一个独立 VM + 一个通道 + 主线程收”的模型下，这段是自然的，且被 Aria/LenoMusic 两个项目一致采用。

### 1.6 标准库的高光：`cli.spec`

[musicdl.leno:127-136](file:///d:/CLeno/LenoMusic/musicdl.leno#L127-L136) 用声明式 spec 定义参数，比手写 `argv` 循环好一个档次。这是“标准库做对了”的证据，也反衬出下方 `cli.parse` 返回值丢掉类型的遗憾。

## 2. 哪些地方明显在和语言较劲

### 2.1 数据只能住在字符串数组里（最大的样板来源）

[Aria downloads.leno:446-449](file:///d:/CLeno/Aria/lib/downloads.leno#L446-L449) 自己写明了行协议：

```leno
// 一行 = [id, 歌名, 歌手, 状态, 说明, 格式, 已下字节, 总字节, 音源]
// 状态： "0" 排队 / "1" 完成 / "2" 失败 / "3" 已暂停 / "5" 下载中
// 为什么用行而不是 struct 数组：字段要原地更新（状态 0→1、进度 0→N），字符串行最好改
```

紧接着是 `len()` 守卫、下标读写、`_int`/`_str` 转换：[462-476](file:///d:/CLeno/Aria/lib/downloads.leno#L462-L476)、[558-602](file:///d:/CLeno/Aria/lib/downloads.leno#L558-L602)（`pause_all` / `resume_all` / `toggle_pause` 三段同构循环）。落盘时又要换成对象数组：

> `存成对象数组而不是行数组：JSON 读回来的是 Array[any]，按行下标取要反复收窄，字段名一改就静默错位` —— [604-606](file:///d:/CLeno/Aria/lib/downloads.leno#L604-L606)

**同一份数据在内存、协议、磁盘里有三种形态，转换代码全部手写。** 这不是业务复杂度，是语言缺少“记录 ↔ 序列化”的闭环。

同类证据：

- [parse_recent → parse_feed](file:///d:/CLeno/Aria/lib/player_tick.leno#L1663-L1754)：**六个**同构的 `Array[Array[string]]` 映射（五个从 `any` 收窄，`parse_shared` 接收 `Array[Dict]`），每个字段一次 `_str(e.get(...))`。
- [dl_engine.leno:47-61](file:///d:/CLeno/LenoMusic/dl_engine.leno#L47-L61)：十个 `F_*` 常量逐条 re-export，只为跨模块共享列号。
- [wb_gui.leno:51-56](file:///d:/CLeno/LenoWorkBuddy/wb_gui.leno#L51-L56)：`ACCOUNTS` 每项 `[uid, 展示名, 凭据路径]`，每次取值都重复 `CUR bounds` 检查。
- [trae_accounts.leno:57](file:///d:/CLeno/LenoTrae/trae_accounts.leno#L57) 用数组当二元组；[trae_history.leno:67-71](file:///d:/CLeno/LenoTrae/trae_history.leno#L67-L71) 用字符串记录 + `field(rec, idx)` 取值。

四项目共 355 处 `Array[Array[string]]`。**这不是个别项目水平问题，是语言没有更好的默认选择。**

### 2.2 状态机被拆散：魔法整数 + 字符串 tag + 散落的 if 链

- `curNav` 用 `-12 / -11 / -6 / -3 / -2 / -1` 表示不同页面（原始定义见 [player_core.leno:1797 起](file:///d:/CLeno/Aria/lib/player_core.leno#L1797-L1900)）；各种 `curNav ==` 判断共 90 处、跨 10 个文件（其中 `curNav == -12` 就有 19 次）；`page_name` 再把整数翻译成标题（[page_lyric.leno:1039-1055](file:///d:/CLeno/Aria/lib/page_lyric.leno#L1039-L1055)），页面渲染又写一遍（[289-341](file:///d:/CLeno/Aria/lib/page_lyric.leno#L289-L341)）。
- 导航重置逻辑被抄了三份：`set_nav`、[open_last_search](file:///d:/CLeno/Aria/lib/player_core.leno#L1863-L1885)、[open_downloads](file:///d:/CLeno/Aria/lib/player_core.leno#L1887-L1905) 里的清空列表、清空 `netRows`、重置按钮样式几乎逐行相同。
- 下载状态是字符串码 `"0".."5"`；下载线程消息是 `["start", ...] / ["progress", ...] / ["done", ...] / ["fail", ...]`（[dl_flow.leno:273-306](file:///d:/CLeno/LenoMusic/dl_flow.leno#L273-L306)）；音源分派是 `if src == "netease" ...`（[thirdparty.leno:270-274](file:///d:/CLeno/LenoMusic/thirdparty.leno#L270-L274)）。

语言里的 `enum` 只能存 int 常量（§3.5 实测可用），不能带载荷、也没有穷尽检查。四项目 **0 使用**有两个原因：`curNav`、`"0".."5"` 这类纯状态本可以用 int enum 表达，但没有任何约定或诊断提示这么做（**引导缺口**）；而 `Progress(已下, 总长)` 这种带载荷消息确实无法表达（**能力缺口**）。结果就是：**状态在 A 处、数据在 B 处，改一处漏一处**——[page_lyric.leno:95](file:///d:/CLeno/Aria/lib/page_lyric.leno#L95-L95) 记录了“歌词是《真的爱你》、标题栏却写《美丽的神话》”的真实用户故障，[295](file:///d:/CLeno/Aria/lib/page_lyric.leno#L295-L300) 则是标题写死“首页”导致的返工。

## 3. 抽象能力盘点与实测复核

| 能力 | 现状 | 评价 |
|---|---|---|

### 3.5 用 `build\leno.exe` 实测：哪些是“没写”，哪些是“没有”

方法：在临时目录（`build\_probe`，用后删除）用 `leno.exe` 直接编译运行最小用例，不依赖四个项目的任何代码。本节结论对应 2026-11-08 的 `build\leno.exe` 快照；`src/` 正在并发修改，若源码已变需重测。

**① `switch` —— 能用（但不做穷尽检查）**

```leno
func classify(int n): string {
    switch n {
        case 1 { return "one" }
        case 2 { return "two" }
        default { return "other" }
    }
}
```

运行结果：`int switch: one,two,other`；字符串版 `str switch: A,B,?`；enum 值版 `enum switch: ok,nf,err`。
`--debug` 反汇编显示每个 case 是一条 `OP_EQ`（`OP_EQ A=3 B=1 C=2`），确认是线性比较链，但功能正确。
**判定：能用**。补充：enum 的 `switch` 不写 `default` 也能编译、无任何警告（`switch c { case Color.red ... case Color.green ... }` 输出 `red`）⇒ **穷尽性检查：没有**。

**② `enum` —— 半能用（只有 int 常量）**

```leno
enum Status { ok = 200 not_found = 404 error = 500 }
```

`_str(Status.not_found)` 输出 `404`，可用于 `switch`。但带载荷的定义：

```leno
enum JobMsg {
    Start(int id)
    Progress(int done, int total)
    Done(int id)
}
```

直接报 9 条语法错误（`期望 enum 成员名称`、`期望 ')'`、`期望 '}' 结束 enum 定义` 等）。
**判定：int 常量能用；载荷没有。** 这正是四项目把消息写成 `["progress", 已下, 总长]` 的原因之一。

**③ `map` / `filter` / `reduce` —— 能用，且类型没有丢**

```leno
var doubled = nums.map(func(int x, int i) { return x * 2 })
var evens   = nums.filter(func(int x, int i) { return x % 2 == 0 })
var total   = nums.reduce(func(int acc, int x, int i) { return acc + x }, 0)
```

输出：`map type=Array[int] value=[6, 2, 4]`、`filter type=Array[int] value=[2]`、`reduce type=int value=6`；链式 `filter().map().reduce()` 输出 `13`。
**判定：能用**。注意文档 `module_arrays.md:51-52` 写“`reduce` 的返回类型暂为 `any`”，而实测运行时 `type()` 是 `int`；文档说的是类型标注、实测取的是运行时值，**不能据此判定文档过时（待确认，静态类型未验证）**，但该描述确实容易劝退使用者。

**④ 自定义比较器 `sort` —— 没有**

```leno
nums.sort(func(int a, int b) { return b - a })
```

报错：`[语义错误] 调用方法 'sort' 时参数数量不匹配: 期望 0, 实际 1`。
改模块形式 `arrays.sort(nums, fn)` 同样失败：`arrays.sort 参数数量不匹配: 期望 1, 实际 2`，并附 `参数 2 类型错误: 期望 'int'，但传入 'func(int, int):int'`。
**判定：没有。** 所以 [player.leno:269](file:///d:/CLeno/LenoMusic/player.leno#L269-L300) 只能“先排下标再重建并行数组”，[player.leno:742](file:///d:/CLeno/LenoMusic/player.leno#L742-L752) 只能手写二分插入。

**⑤ 用户泛型 —— 能用**

```leno
struct Box[T] { T value }
func identity[T](T v): T { return v }
func max_of[T](T a, T b): T { if a > b { return a } return b }
```

输出 `identity=42`、`unbox=7`、`max=9`，并给一条 `warning: [泛型无约束] 泛型参数 'T' 参与比较运算无约束`。警告只提醒，不阻止编译。
**判定：能用**。

| 特性 | 实测结果 | 判定 |
|---|---|---|
| `switch`（int / string / enum） | 全部命中正确 | **能用**（线性比较链） |
| `enum` 常量 + `switch` 匹配 | 通过 | **能用** |
| `enum` 穷尽性 | 缺 `default` 静默通过 | **没有** |
| `enum` 载荷 | 9 条语法错误 | **没有** |
| `map` / `filter` | `Array[int]`，值正确 | **能用** |
| `reduce` | 运行时 `int`，值正确；静态类型是否 `any` 未验证 | **能用** |
| 自定义比较器 `sort` | 期望 0 参 | **没有** |
| 用户泛型（函数 / struct） | 通过 | **能用**（附提醒） |

**实测结论：四个项目里 `switch / enum / map / filter / reduce / 泛型` 的 0 使用，不能用“语言不支持”来解释。** 只有 enum 载荷与 comparator sort 是真正的“没有”。

| 问题 | Aria | LenoMusic | LenoTrae | LenoWorkBuddy |

线程这一行是**两个使用线程的项目之间唯一一致的**（Aria 与 LenoMusic；另两个项目不用线程）——不是因为有统一文档，而是因为 Channel 的用法足够简单。其余六行都是“每个项目自己发明方言”。补充：六行差异里大部分**不是能力差异**（`switch`/`map`/`enum` 都实测可用，§3.5），而是没有统一惯用法与提示（§3.6）——同一件事本可以有同一个默认写法。

甚至连“十六进制字面量能不能用”都没有共识：Aria 在卡片样式里直接用 `#FFFFFFFF`（[cards:124](file:///d:/CLeno/Aria/lib/cards.leno#L124-L124)），LenoMusic 却在注释里写“十六进制字面量在这个语言里没把握 ✗ 别赌”并全部改十进制（[player.leno:26](file:///d:/CLeno/LenoMusic/player.leno#L26-L26)）。这不是能力缺失，是**文档/示例/惯用法缺位**。

**结论：语言缺的不是能力，是“官方惯用法”。** 当一个语言让四个团队把同一件事做出四种样子，标准库和示例就该背锅。跨项目复制也印证了这一点：Aria 和 LenoMusic 各自维护一份 `kuwo_core`；字节格式化 Aria 1 份、LenoMusic 3 份，`pad2` 则是 LenoMusic 3 份、LenoTrae 1 份（Aria 无）。

> **本节前提已被 §4.5 修订**：此前的说法暗示"标准库/示例缺位，于是各项目自己重写"。对 `build\leno_module` 的审计证明**能力层并不缺**——HTTP、JSON、日志、文件遍历都有模块；四个项目也没有重写 HTTP/JSON/日志，而是直接 import 了 LenoWeb 的内部文件 `web_net.leno`（37 次），绕开公共门面 `Web`（0 次）。因此"背锅"应精确为：**标准库把已有能力组织成了不可发现、不可默认采用的形态**，而不是没有能力。

## 6. 修正后的优先级：先补引导，再补真缺口

> 本节是对原结论的修订。原先把 `switch / enum / map / filter` 的 0 使用当成“能力缺口”，§3.5 实测推翻了这一判断：它们都能用。真正的缺口只剩 **enum 载荷、比较器排序、穷尽性检查**，以及记录 / Result / 宽索引。
>
> 排序基准不变：**P0 生成侧引导，P1 记录类型**。标准库相关的动作不另起一条线，而是挂进这个排序（§4.5 的发现只改变每级的“配套动作”，不改变先后）。

**优先级总表**：

| 优先级 | 主项 | 标准库侧配套动作 |
|---|---|---|
| **P0** | 生成侧引导包 | README 20 模块目录 + import 名映射；`Web` 门面拆分 / 入口收敛；测试入口收编 |
| **P1** | 记录类型 + 自动编解码 | 用库内 CSV / XLSX / JSON 能力做“记录 ↔ 序列化”模板 |
| **P2** | Result / Option | 统一错误契约（8 种 → 1–2 种）与空值契约（4 类 → 1 类） |
| **P3** | 宽索引 | — |
| **P4** | enum 载荷 / 比较器 / 穷尽性 | `hack_log` 并入 `LenoLog`、`web_cdp` 改调 `FS.rmtree`、5 处手写排序退场 |

### P0 生成侧引导包（不是语言特性，优先级最高）

**要交付什么**：

1. **仓库根 + 四个项目的 `AGENTS.md`**：只写“默认形态”，每条 5–10 行可复制样例 + 一个反例：
   - 数据：`struct` + `Array[struct]`，不要 `Array[Array[string]]`；
   - 状态：`enum` int 常量，不要魔法整数 / 字符串码；
   - 分支：≥3 个同值比较用 `switch`，热路径再考虑手写；
   - 集合变换：`map / filter / reduce`，不要手写索引循环；
   - 可空：`T?` + `if x is T => binding`，不要 `any` + `null` 双检；
   - 错误：`Result` 形态（P2 落地前，先给一个 20 行的项目内约定实现）。
2. **`docs/idioms.md`**（或在入门教程加一章“惯用写法”）：按任务给 20 个最小样例——JSON→struct、表格行、下载消息、CLI 解析、错误 Result、状态机、排序、日志。可直接拿本报告 §2 的反例做 before/after。
3. **编译器加 3 类“可改写法”警告**（新增 `WARN_*`，默认开、可 `--no-lint` 关）：
   - 手写索引循环只做 `add(expr)` / 条件 `add`，且无 break、无外部副作用 ⇒ 建议 `map / filter`；
   - 同一变量连续 `==` 常量 ≥3 个分支 ⇒ 建议 `switch`；
   - `int` / `string` 字段被赋 `"0".."5"` 一类常量并参与相等比较 ⇒ 建议 `enum`（误报率高，可先只给 LSP 提示）。
4. **`leno --init` 模板升级**：`src/main.leno` 直接放 5 个惯用样例（struct+Array、enum 状态、switch、map/filter、Result），并生成 `AGENTS.md`；`examples/` 不要留空。
5. **编辑器侧**：VSCode 加 5 组 snippets（`struct` / `enum` / `switch` / `mapf` / `result`）；LSP 增加 `codeActionProvider`，先做“把选中的索引循环转成 map/filter”一个动作。
6. **文档修正两处**：`module_arrays.md:51-52` 说 `reduce` 的“返回类型暂为 `any`”，但实测运行时 `type()` 是 `int`（两者口径不同，静态类型待验证）；`Leno入门教程:11636` 的“switch 一律线性比较链”应标注“冷路径优先 switch，热路径才手写分档”。
7. **标准库目录与入口收敛**（与 P0 同源：让已有能力“到达”作者，依据见 §4.5）：
   - **README 目录与 import 名映射**：`build\leno_module\README.md` 现漏掉 7 个模块（Hack、Music、SDL3、Sqlite、Sys、Web、Win32），也没有“包名 → import 名”对照（`LenoFS` → `"FS"`、`LenoWeb` → `"Web"`、`LenoSQLite` → `"sqlite3"`）；顺带修正 `module_sys.md`（写的是内建 `sys`，不是 `import "Sys"`）与 `module_web.md`（仍写 `web_gzip` 635 行这一历史值，现为 28 行转发壳）。
   - **Web 门面拆分**：`Web.leno` 一次性 import 9 个子模块（[6-14](file:///d:/CLeno/Leno/build/leno_module/LenoWeb/lib/Web.leno#L6-L14)），三种错误模型并存、`postJson`/`postJSON` 双份。拆出 `Web.net` / `Web.html` / `Web.crawl` 三个公开入口，或至少在 README 标注 `web_net.leno` 是内部文件、应用不应直接 import（现状是 37 次内部 import 对 0 次门面 import）。
   - **测试入口收编**：把 LenoWeb 放在 `examples/tests` 的 19 个测试移进 `test/test_*.leno`，让 `--list` 能看见；README 的“13 个模块”改成 runner 的实际数字（31 个测试 / 15 个模块）。

**每一条各自消掉哪类样板**：

| 机制 | 直接消掉 |
|---|---|
| `AGENTS.md` 默认形态 | `curNav` 90 处魔法比较、`"0".."5"` 状态码、`if src ==` 链；把状态/配置类行数组换成 `struct` 数组（剩余序列化部分仍需 P1） |
| `docs/idioms.md` | 同一问题四种解法（CLI 4 种、错误 3 种）、`parse_rank/parse_users` 类映射循环、`trae_sign` 手拼 JSON 的写法 |
| 3 类编译器警告 | 可 `map/filter` 的手写索引循环、≥3 分支的 `==` 链、未命名状态码 |
| `--init` 模板 | 新项目“从零自创方言”（看不到 struct / enum / switch / map） |
| snippets + codeAction | 手写样板本身（每次生成少想一步、少敲一段） |
| 文档修正 | 因“switch 慢”“reduce 返回 any”而绕开已有能力的决策 |
| 标准库目录/门面/测试入口 | “不知道有这个模块”与“绕过 `Web` 直接 import 内部文件”两类采用失败 |

**这是唯一能提升“所有未来代码”、而不是“某一处代码”的一项。**

**验收**：给一个不了解 Leno 的模型只喂 `AGENTS.md` + `--init` 模板，要求写“下载队列”，产出中 `struct` 行、`enum` 状态、`switch` 分派、`map/filter` 各至少出现一次。

### P1 记录类型 + 自动编解码（JSON / 表格 / 通道）——原 ①，仍是最大行数来源
**缺什么**：没有“字段有名字、可序列化、可作为表格行”的记录；没有 `decode<Song>`；没有按列名绑定。
**消掉**：355 处行协议、`F_*` 列号常量、六个 `parse_*` 同构映射、`len()>=4` 防御、`field(rec, idx)`、内存行 vs 磁盘对象的双形态转换、`trae_sign` 的手拼 JSON。
**验收**：`record Song { ... }` + `jsons.decode(Song, text)` + `Table` 直接吃 `Array[Song]`；`Aria downloads` 的队列改成 `Array[Job]` 后行数应显著下降。

### P2 Result / Option + 严格解析 + 类型化错误——原 ③
**缺什么**：没有标准 `Result`；`_int` 失败抛、`_int_or` 把 `null` 变 0、`as` 只认 `any`。
**标准库先行（§4.5）**：把现有 8 种错误写法（`Dict{ok,err}`、`bool`、`int -1`、typed `Result` struct、`error` 字段、`throw`、`Result[T]`、`Response.ok()`）收敛到 1–2 种；空值 4 类哨兵（`null` / `""` / `0`/`0.0` / `[]`）收敛到 `T?` / `Option` 一类。SQLite 的 `column_int/text` 必须先把 NULL 与 0/`""` 区分开（[sqlite3.leno:208-230](file:///d:/CLeno/Leno/build/leno_module/LenoSqlite/lib/sqlite3.leno#L208-L230)），否则上层永远无法判断“查到了空值”。
**消掉**：`parsing.leno` 整文件、`wb_core` 的 `is_int_str/Num`、Aria `util.to_int`、`AuthResult`、`throw "INVALID_FORMAT"` 十连、`catch e` 只打日志、`cli/jsons/env` 后的 310 处 `as`。
**验收**：`strings.parseInt(s): Result[int, ParseError]`；`try { ... } catch (e: AuthError)`；`cli.parse` 返回 typed options 而非 `Dict<string, any>`。

### P3 宽索引：解除 256 字段 / 255 局部量——原 ④
**缺什么**：`OP_GET_FIELD` 的字段索引 8 位、单函数局部寄存器 8 位。
**消掉**：`Player` 250 字段 + `SquareState` 的语义妥协、把一个类型拆成 5 个文件、每文件 45 条 import、`on_tick` 的寄存器腾挪。
**验收**：字段/寄存器索引至少 16 位；或编译器给出“超过上限，建议拆分为 X/Y”的结构化诊断，而不是让作者自己发现。

### P4 实测确认的真缺口——原 ② 与 ⑤ 的排序部分
- **enum 载荷**：唯一“根本没法写”的状态表达（§3.5 实测 9 条语法错误）。`switch` 本身能用但**没有穷尽性检查**，两者应一起做：`enum JobMsg { Start(id), Progress(done,total), ... }` + `switch` 穷尽性错误。
- **比较器 / 稳定排序**：`sort()` 只接受 0 参、`arrays.sort` 只接受 1 参（§3.5 实测）。消掉 [player.leno:269 `lrc_sort`](file:///d:/CLeno/LenoMusic/player.leno#L269-L300)、[player.leno:742 `insert_sorted`](file:///d:/CLeno/LenoMusic/player.leno#L742-L752)、[search_page.leno:294](file:///d:/CLeno/LenoMusic/search_page.leno#L294-L294) 三处手写。
- **switch 跳转表**（`OP_SWITCH_LOOKUP` 空转）是性能问题，不是可用性问题，排在最后。
- **库内低成本收尾（§4.5）**：`hack_log.leno`（非空 158 行）与 `LenoLog`（非空 85 行）职责重叠（重合量待确认），应并入；`web_cdp.leno` 的 `_removeDir` 直接 `rmdir /s /q`（[849-861](file:///d:/CLeno/Leno/build/leno_module/LenoWeb/lib/web_cdp.leno#L849-L861)），应改用 `FS.rmtree`；比较器落地后，四项目 5 处手写排序可删。

其余低成本收尾不变：格式化（时长 / 字节 / 补零）、字符串（`rfind/split/stem`）、日志、常量/函数 re-export。

**降级表**：

| 原结论 | 修正后 | 依据 |
|---|---|---|
| switch 0 使用 ⇒ 缺表达力 | 能用 ⇒ 补引导 | §3.5：int / string / enum 全部通过 |
| enum 0 使用 ⇒ 根本不够用 | 常量能用（补引导），载荷才缺 | §3.5：定义/匹配通过，载荷语法错误 |
| map/filter/reduce 0 使用 ⇒ 生态无 | 能用且类型保留 ⇒ 补引导 | §3.5：`Array[int]` / `int` |
| 用户泛型 0 使用 ⇒ 生态无 | 能用 ⇒ 补引导 | §3.5：identity / unbox / max 通过 |
| comparator 排序 ⇒ 标准库缺口 | 保留 P4（确实没有） | §3.5：期望 0 参 |

> 如果只能做两件：**P0 + P1**。P0 决定未来所有代码是否用上已有能力，P1 决定数据形态的样板量。P2 决定错误面正确性，P3 决定项目规模上限，P4 是剩余真缺口。

## 7. 明确值得肯定的设计

- **LenoMusic**：四个项目里工程化最成熟的。纯逻辑与 UI 分离、17 个离线测试、README 把自检命令与已知坑写得可以直接照做、还产出了 Linux 构建。
- **Aria 服务端**：线程池 + 每 worker 独立 SQLite 连接 + 线程局部限流 + 声明式路由表，是在“隔离 VM、Ptr 不能跨线程、模块 var 无锁”这套约束下做出的正确设计（[server.leno:23-37](file:///d:/CLeno/Aria/server/server.leno#L23-L37)）。
- **WorkBuddy**：`doctor` 子命令、离线 stub、人话错误码（`AUTH_ERROR` / `HELPER_TIMEOUT` / `HELPER_PROTOCOL`），说明作者在没有 typed error 的情况下仍把错误面做清楚了。
- **LenoTrae**：黄金样例回归 + README 的语言注意事项，等于给编译器写了一份真实用户验收清单。
- **语言本身的表达力（已实测）**：`cards` 的 hook 结构、`routes` 的声明式表、`cli.spec`、`use` 类型导入、`if x is T => binding`，以及 §3.5 验证通过的 `switch` / int `enum` / `map·filter·reduce` / 用户泛型，都证明核心语法足以写出“像样”的代码。

**最终判断**：Leno 的语法已经够用，而且比原报告估计的更够用——`switch`、`map/filter/reduce`、泛型都实测可用。短板应分成三类：**（A）已存在的能力没有到达作者**（无 AGENTS.md、无惯用示例、编译器/LSP 不提示、`--init` 模板不示范），这是“生成侧引导缺口”；**（B）确实缺失的能力**：记录类型与编解码、Result、8 位索引、enum 载荷、comparator 排序；**（C）官方模块库有 20 个模块、53,052 行，却没有成为标准形态**——37 处内部 `web_net` import 对 0 处 `Web` 门面 import，README 缺 7 个模块且无 import 名映射，77% 库行数不在测试入口内。C 与 A 同源，但修复对象是库本身（目录、门面、错误/空值契约、测试入口），不是编译器提示。A 类不补，未来每一段新代码都会继续绕开已有能力；B 类不补，Aria 这类 24.6k 行项目会继续用字符串数组和魔法数字自我补偿；C 类不补，20 个模块就继续以“内部文件”的形式被零散使用，而不会成为四个项目共享的标准入口。先做 A（含 C 的目录/门面部分），再做 B 的前两项，才谈得上“多人、长期、可测试”的可用性。
