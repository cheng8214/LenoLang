# 分支分派性能：`if` 链 / `switch` / enum / 带载荷 enum（2026-11-10 实测）

> 复现：`powershell -NoProfile -ExecutionPolicy Bypass -File tools\bench_branch.ps1`
> 生成 `tmp_bench.leno` 后 `leno tmp_bench.leno`。每组 **300,000 次调用**，
> 计时用 `times.us()`；`baseline_loop` 是"同样循环、不调被测函数"的底噪（≈1ms）。

## 1. 结论先说

| 结论 | 依据 |
|---|---|
| 优化前 **`switch` 比 `if` 链慢 15%~20%** | 同一个线性链，但 `switch` 每个 case 是 `LOADK + EQ + JMP_IF_TRUE`（3 条 12 字节），而 `if v == 3` 早就用融合的 `OP_CMPJMP_EQ`（1 条 8 字节） |
| 优化后 **`switch` 比 `if` 链快 35%~40%** | 现在两者都走融合比较，但 `if` 链还要为每个分支生成"不成立则跳到下一个"的额外结构 |
| **带载荷 enum 与普通 enum 几乎同价** | 命中最后一个 case 时：普通 enum 12ms、带载荷 14ms（300k 次）—— 多出来的是 `tag` 字段读 + 绑定变量 |
| **两者都还是 O(n)** | 命中位置越靠后越慢：30 个 case 命中最后一个 23ms，命中第一个 7ms |

## 2. 优化前后对照（单位 ms，300k 次调用）

| 场景 | 优化前 | 优化后 |
|---|---|---|
| baseline（纯循环） | 1 | 1 |
| `if3` 命中第 1 个 / 最后一个 | 6 / 8 | 6 / 8 |
| `switch3` 第 1 个 / 最后一个 / 混合 | 8 / 10 / 10 | **7 / 8 / 9** |
| `if10` 第 1 个 / 最后一个 | 7 / 22 | 6 / 18 |
| `switch10` 第 1 个 / 最后一个 / 混合 | 9 / 24 / 16 | **7 / 12 / 11** |
| `if30` 第 1 个 / 最后一个 | 7 / 42 | 6 / 39 |
| `switch30` 第 1 个 / 最后一个 / 混合 | 8 / 50 / 31 | **7 / 23 / 16** |
| enum `if` 10 成员 第 1 个 / 最后一个 | 8 / 27 | 9 / 26 |
| enum `switch` 10 成员 第 1 个 / 最后一个 / 混合 | 9 / 24 / 18 | **8 / 12 / 13** |
| **带载荷** enum `switch` 10 成员 第 1 个 / 最后一个 / 混合 | 10 / 25 / 19 | **9 / 14 / 14** |

> `if` 那几行的抖动 ±2~3ms 属正常（同一台机器、同一进程内连续测）；`switch` 的改善是稳定可复现的。

## 3. 改了什么（`codegen_stmt.c` 的 `gen_switch`）

```c
// 老路径：每 case 3 条指令
LOADK  vr, <字面量>
OP_EQ  cr, tmp, vr
OP_JMP_IF_TRUE cr, → 跳板[i]

// 新路径：整数字面量 case 且主题静态类型是 int/enum ⇒ 1 条
OP_CMPJMP_EQ tmp, <int16 立即数>, 真则跳 → 跳板[i]
```

- 直接复用既有的 `OP_CMPJMP_EQ`（T31，`if a == 3` 早就在用）⇒ **没有新 opcode、没有字节码版本 bump**。
- 判据收紧：只有"字面量落在 int16 内 + 主题静态类型是 `int`/`enum`"才走融合；`string` / `float` / `any` 主题仍走原路径（字符串比较是内容比较，没法立即数化）。
- 反汇编可自证：`OP_CMPJMP_EQ A=1 B=0 C=192 | 为真则跳 +12（比较 R[1] 与立即数 0）`。

## 4. 已落地：大分支的**二叉比较树**（2026-11-10）

线性链是 O(n)：100 个 case 命中最后一个要 66ms（300k 次）。现在 `case 数 ≥ 16` 且
**全是互不相同的整数字面量**时，codegen 把"N 条平铺"换成**按值排序的二分树**，判定次数降到
log₂N。**没有新指令、不动字节码格式**：每个节点仍是既有的 `OP_CMPJMP_EQ`（相等 ⇒ 跳跳板）
+ `OP_CMPJMP_LT`（小于 ⇒ 左子树），落空自然落到原来的 miss 跳转 ⇒ default / 出口逻辑零改动。

### 实测（300k 次调用，ms）

| 场景 | 线性链（改前） | 二叉比较树（改后） | 变化 |
|---|---|---|---|
| `switch` 10 case 命中最后一个 | 12~13 | 12~13（**低于阈值，仍是线性**） | 0 |
| `switch` 30 case 命中最后一个 | 27 | **13** | −52% |
| `switch` 30 case 混合 | 18 | **13** | −28% |
| `switch` 100 case 命中最后一个 | 66 | **21** | **−68%** |
| `switch` 100 case 混合 | 38 | **17** | −55% |
| `switch` 100 case 命中第一个 | 8 | 15 | +7（树的固定代价） |
| `if` 100 链 命中最后一个（对照） | 101~113 | 101（`if` 链不走树） | — |

**取舍写清楚**：如果热路径**总是命中第一个 case**，树会比线性链慢 7ms（100 case）；
但只要命中位置不是恒定的第一个，树就赢，且分支越多赢得越多。阈值取 **16** 是这个交叉点量出来的
（10 个 case 时两者打平、命中靠前时树还更慢）。

### 判据（任何一条不满足就退回线性链，语义永远不变）

1. 主题静态类型是 `int` / `enum`（树用整数立即数比较）
2. 每个 case **恰好一个**值（`case 1, 2` 多值、`case 1 to 3` 区间都不进树）
3. 值都是整数字面量且落在 int32（int16 之外的大值**照样进树** —— 比较时先把常量装进寄存器，
   只是每个节点多一条 `LOADK`；超过 int32 才退回线性链）
4. 值**互不相同** —— 有重复时"第一个命中"是可观测语义，排序会改掉它
5. case 数 ≥ 16

回归钉子：`assert/test_switch_tree.leno`（20 case 逐值 / 负数区间 / enum 20 成员 / 稀疏值 +
空洞 / 多值 case 退回线性，五组）。

## 5. 还没做的

### 稠密：跳转表（O(1)，但要动字节码格式）

值域连续（如 `0..N` 的枚举/状态码）时可以发一张跳转表，`OP_SWITCH_TABLE idx` 一次间接跳转。
代价比二叉比较树大得多：新 opcode + 常量池存表 + VM 间接跳转 + 序列化/校验器/反汇编三处同步 +
版本 bump（就是"新增 opcode 必做清单"那套）。**当前基准下收益有限**：树已经把 100 case 压到
21ms，而跳转表最多再省一半左右 ⇒ 优先级低于"继续把真实项目跑稳"。

### 用户侧：先粗分档再细判（现在仍然有用）

值域大且分支多、又恰好**总是命中靠前**时，先粗分档比树更划算（教程 §switch 性能那段已写）：

```leno
if v < 100 { switch v { … } }
eif v < 200 { switch v { … } }
else { … }
```

把 100 个 case 拆成 10×10，等效 20 次比较而不是 100 次。

## 6. 一句话建议

- **冷路径 / 分支 ≤ 十来个**：随便用 `switch`（比 `if` 链快，可读性更好）。
- **热路径 + 几十上百分支**：不用特殊写法了 —— 树已经自动接管（≥16 个整数字面量 case）。
  只有在"永远命中第一个"这种极端分布下，手写 `if` 才会快几毫秒。
- **带载荷 enum 的分派不要有心理负担**：比普通 enum 只贵 1~2ms/300k 次，换来的是类型安全。
