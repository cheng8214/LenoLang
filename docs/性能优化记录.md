## 优化详情

### 1. GC 检查优化 (gc.c)

**文件**: `src/gc.c`

**修改内容**:

- 将 `gc_check_safe_point()` 从 VM 主循环移回 `gc_alloc` 函数
- 只在内存分配完成后检查，减少检查频率

**代码变更**:

```c
// 在 gc_alloc 函数末尾添加
if (gc_requested && gc.enabled && !gc.running) {
    gc_check_safe_point();
}
```

**性能影响**: 从 280ms 提升到 210ms

**风险**: 低 - GC 检查点从指令边界移到分配点，对象已初始化，状态相对安全

***

### 2. 快速栈操作函数 (leno\_vm.h)

**文件**: `src/include/leno_vm.h`

**新增函数**:

#### vm\_stack\_pop\_fast

```c
// 栈操作：弹出值（不检查下溢，用于性能关键路径）
static inline Value vm_stack_pop_fast(VM* vm) {
    return vm->stack[--vm->sp];
}
```

#### vm\_stack\_push\_fast

```c
// 栈操作：压入值（不检查溢出，用于性能关键路径）
static inline void vm_stack_push_fast(VM* vm, Value v) {
    vm->stack[vm->sp++] = v;
}
```

#### vm\_stack\_peek\_fast

```c
// 栈操作：查看栈顶值（不检查边界，用于性能关键路径）
static inline Value vm_stack_peek_fast(VM* vm, int distance) {
    return vm->stack[vm->sp - 1 - distance];
}
```

**风险**: 中 - 只在确定栈状态安全时使用，否则会导致未定义行为

## 17. 批量移除 opcode 开头 frame 更新 ❌ 已回退 (2026-08-10)

### 尝试内容

对 14 个文件共 62 个 opcode 移除了开头的 `frame = &vm.frames[vm.frame_cnt - 1];`：

| 文件 | 移除的 opcode |
|------|--------------|
| `op_compare.inc` | OP_EQ, OP_NEQ, OP_IS_NULL, OP_LT, OP_GT, OP_LE, OP_GE |
| `op_bitwise.inc` | OP_BITAND ~ OP_BITNOT (10个) |
| `op_unary.inc` | OP_NEG, OP_NOT, OP_CAST_* 等 (8个) |
| `op_inc_dec.inc` | OP_INC, OP_DEC, OP_*_LOCAL (6个) |
| `op_arith.inc` | OP_ADD, OP_SUB, OP_MUL, OP_DIV, OP_MOD |
| `op_array.inc` | OP_ARRAY, OP_ARRAY_GET/SET/APPEND (5个) |
| `op_dict.inc` | OP_DICT, OP_DICT_GET/SET/GET_KEY (4个) |
| `op_index_slice.inc` | OP_INDEX_SET, OP_SLICE |
| `op_string.inc` | OP_STRING_ADD |
| `op_variables.inc` | OP_GET/SET_LOCAL, OP_MOVE_LOCAL, OP_GET/SET_UPVALUE (6个) |
| `op_for_loop.inc` | OP_FOR_PREP, OP_FOR_LOOP |
| `op_utils.inc` | OP_INDEX, OP_LENGTH, OP_ITER_GET |
| `op_collection.inc` | OP_IN, OP_RANGE |
| `op_iter.inc` | OP_ITER_GET_VALUE |

### 回退原因

- 断言测试 202 passed, 0 failed（功能正确）
- **但全量 `.leno` 测试文件运行后发现整体变慢**
- 回退后恢复到原始速度

### 根因分析

`frame = &vm.frames[vm.frame_cnt - 1];` 虽然看似冗余，但实际上对编译器优化至关重要：

1. **寄存器分配锚点**: frame 赋值给编译器一个明确的“重新加载点”，让 `frame` 指针保持在寄存器中。移除后，编译器可能无法证明 `frame` 在跨函数调用后仍然有效，被迫从内存重新加载

2. **别名分析屏障**: `frame = &vm.frames[vm.frame_cnt - 1];` 明确告诉编译器 `frame` 指向 `vm.frames` 数组的具体位置。没有这行，编译器可能保守地认为 `frame` 指向的内存可能被任何函数调用修改，从而生成更多的内存读写

3. **指令调度优化**: frame 赋值后的代码块，编译器可以更激进地重排指令。移除后编译器变得保守，指令调度质量下降

4. **与 #10、#14 一致**: 之前移除 `OP_CLOSE_UPVALUE`、`OP_DEFINE_GLOBAL`、`OP_GET_NATIVE`、`OP_STRING_ADD` 的 frame 更新时也观测到性能下降，这次是大规模验证了这一现象

### 核心教训

> **`frame = &vm.frames[vm.frame_cnt - 1];` 不能随意移除！**
>
> 即使从语义上看是冗余的（前一个修改 `frame_cnt` 的操作已设置了正确的 `frame`），但编译器需要这行代码作为优化提示。移除它会导致编译器生成更保守、更慢的代码。
>
> 这与“死代码消除”直觉相反——某些“死代码”实际上是编译器的优化锚点。

### 最终结论

- ❌ **不要移除 opcode handler 开头的 `frame` 更新**
- ✅ 唯一安全移除 frame 更新的地方是 `op_arith.inc`（已验证）
- ❌ ~~`op_type_specialized.inc` 快速栈操作~~ **已回退** (2026-08-14，详见 #18)
- ✅ 未来优化方向应转向：JIT、内联缓存深化、超指令合并、字节码内联等

## 18. 回退 `op_type_specialized.inc` 快速栈操作 ❌ 已回退 (2026-08-14)

### 回退内容

将 `op_type_specialized.inc` 中所有 `vm_stack_push_fast` → `vm_stack_push`，
所有 `vm_stack_pop_fast` → `vm_stack_pop`。

涉及 ~30 个类型特化指令（OP_ADD_INT, OP_SUB_INT, OP_MUL_INT, OP_DIV_INT, OP_MOD_INT,
OP_ADD_FLOAT ~ OP_DIV_FLOAT, OP_NEG_INT, OP_NEG_FLOAT, OP_EQ_INT ~ OP_GE_INT,
OP_EQ_FLOAT ~ OP_GE_FLOAT, OP_ADD_INT_IMM ~ OP_EQ_INT_IMM）。

### 回退原因

开发 LenoNet（libcurl 绑定）时，`HttpClient` 多次请求触发 FFI 回调，
回调中执行 Leno 字节码使用了 `vm_stack_push_fast`，
该函数不检查栈溢出，越界写入破坏了堆元数据，
导致程序结束时 `gc_free_all()` 调用 `free()` 触发 **STATUS_HEAP_CORRUPTION (0xC0000374)**。

gdb 堆栈回溯：
```
#7  gc_free_all () at src\gc.c:1625  ← free(gc.vm->stack) 触发堆损坏检测
#8  lenolang_run () at src\main.c:215
```

根因链：
```
FFI 回调 (libcurl write_callback)
  → callback_dispatch_direct → vm_call_value → 执行 Leno 字节码
    → op_type_specialized.inc 中的 vm_stack_push_fast
      → VM 栈已满（FFI 回调复用主线程 VM 栈）
        → 越界写入 vm->stack[vm->sp++] → 破坏相邻堆内存
          → gc_free_all() 时 free() 检测到 STATUS_HEAP_CORRUPTION
```

详见 `docs/LenoNet_崩溃问题排查记录.md`

### 性能影响

从 ~203ms 回退到 ~210ms（约 3% 性能损失）。

### 核心教训

> **`vm_stack_push_fast` / `vm_stack_pop_fast` 不检查栈边界，在任何可能栈空间不足的场景都不安全。**
>
> 2026-05-28 曾因 `更多排序.leno` 失败而部分回退，但保留了 `op_type_specialized.inc` 中的使用。
> 当时认为"编译器生成的类型特化指令栈操作确定，相对安全"，
> 但忽略了 FFI 回调复用主线程 VM 栈时栈空间可能不足的情况。
>
> **结论：不要在生产代码中使用不带边界检查的栈操作函数。**
