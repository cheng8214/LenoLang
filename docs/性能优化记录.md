## 优化详情

### 1. GC 检查优化 (gc.c)

**文件**: `src/gc.c`

**修改内容**:

- 将 `gc_check_safe_point()` 从 VM 主循环移回 `gc_alloc` 函数
- 只在内存分配完成后检查，减少检查频率

**代码变更**:

```c
// 在 gc_alloc 函数末尾添加
if (gc_requested && gc.enabled && !gc.running) {
    gc_check_safe_point();
}
```

**性能影响**: 从 280ms 提升到 210ms

**风险**: 低 - GC 检查点从指令边界移到分配点，对象已初始化，状态相对安全

***

### 2. 快速栈操作函数 (leno\_vm.h)

**文件**: `src/include/leno_vm.h`

**新增函数**:

#### vm\_stack\_pop\_fast

```c
// 栈操作：弹出值（不检查下溢，用于性能关键路径）
static inline Value vm_stack_pop_fast(VM* vm) {
    return vm->stack[--vm->sp];
}
```

#### vm\_stack\_push\_fast

```c
// 栈操作：压入值（不检查溢出，用于性能关键路径）
static inline void vm_stack_push_fast(VM* vm, Value v) {
    vm->stack[vm->sp++] = v;
}
```

#### vm\_stack\_peek\_fast

```c
// 栈操作：查看栈顶值（不检查边界，用于性能关键路径）
static inline Value vm_stack_peek_fast(VM* vm, int distance) {
    return vm->stack[vm->sp - 1 - distance];
}
```

**风险**: 中 - 只在确定栈状态安全时使用，否则会导致未定义行为

***

### 3. 快速整数运算宏 (vm\_helpers.inc)

**文件**: `src/vm/vminc/vm_helpers.inc`

**新增宏**:

- `PUSH_INT64_RESULT_FAST` - 使用 `vm_stack_push_fast`
- `PUSH_SAFE_INT64_ADD_FAST` - 使用 `vm_stack_push_fast`
- `PUSH_SAFE_INT64_SUB_FAST` - 使用 `vm_stack_push_fast`
- `PUSH_SAFE_INT64_MUL_FAST` - 使用 `vm_stack_push_fast`

**风险**: 中 - 只在类型特化指令中使用

***

### 4. 类型特化指令优化 (op\_type\_specialized.inc)

**文件**: `src/vm/vminc/op_type_specialized.inc`

**优化内容**:

1. 移除不必要的 `frame = &vm.frames[vm.frame_cnt - 1];` 更新
2. 使用 `vm_stack_pop_fast` 替代 `vm_stack_pop`
3. 使用 `vm_stack_push_fast` 替代 `vm_stack_push`
4. 使用快速整数运算宏

**涉及的指令**:

- `OP_ADD_INT`, `OP_SUB_INT`, `OP_MUL_INT`, `OP_DIV_INT`, `OP_MOD_INT`
- `OP_ADD_FLOAT`, `OP_SUB_FLOAT`, `OP_MUL_FLOAT`, `OP_DIV_FLOAT`
- `OP_NEG_INT`, `OP_NEG_FLOAT`
- `OP_EQ_INT`, `OP_LT_INT`, `OP_GT_INT`, `OP_LE_INT`, `OP_GE_INT`
- `OP_EQ_FLOAT`, `OP_LT_FLOAT`, `OP_GT_FLOAT`, `OP_LE_FLOAT`, `OP_GE_FLOAT`
- `OP_ADD_INT_IMM`, `OP_SUB_INT_IMM`, `OP_MUL_INT_IMM`
- `OP_LT_INT_IMM`, `OP_GT_INT_IMM`, `OP_LE_INT_IMM`, `OP_GE_INT_IMM`, `OP_EQ_INT_IMM`

**性能影响**: 从 210ms 提升到 203ms

**风险**: 中 - 类型特化指令由编译器生成，保证栈状态正确

***

### 5. 变量操作指令优化 (op\_variables.inc)

**风险**: 低 - 局部变量操作不会修改 frame

## 回滚指南

如果发现 bug，按以下优先级回滚：

1. **高优先级**（最可能导致问题）:
   - `vm_stack_pop_fast` / `vm_stack_push_fast` / `vm_stack_peek_fast` 的使用
   - `FETCH_DISPATCH` 的修改
2. **中优先级**:
   - 类型特化指令的 `frame` 更新移除
   - `OP_CALL` / `OP_RETURN` 的优化
3. **低优先级**（相对安全）:
   - `OP_ADD` 的 `frame` 更新移除
   - `OP_SET_LOCAL` / `OP_GET_LOCAL` 的优化
   - GC 检查点移动

### 16. 快速栈操作部分回退与恢复 (2026-05-28)

**问题**: `更多排序.leno` 测试在副本3中失败，而副本2正常

**原因分析**: 快速栈操作函数 (`vm_stack_pop_fast`, `vm_stack_push_fast`, `vm_stack_peek_fast`) 不进行边界检查，在复杂排序算法的大量函数调用和返回场景下导致栈下溢或上溢

**第一阶段 - 全面回退**:

1. **op_call.inc** - 使用安全版本
2. **op_jump.inc** - 使用安全版本  
3. **op_type_specialized.inc** - 使用安全版本
4. **op_variables.inc** - 使用安全版本
5. **vm_helpers.inc** - 移除快速宏

**第二阶段 - 恢复类型特化指令优化**:

经过测试，`op_type_specialized.inc` 中的快速栈操作是安全的，已恢复：

- 所有 `vm_stack_pop` → `vm_stack_pop_fast`
- 所有 `vm_stack_push` → `vm_stack_push_fast`
- 使用 `PUSH_SAFE_INT64_*_FAST` 宏

**最终状态**:

| 文件 | 使用 fast | 原因 |
|------|----------|------|
| op_type_specialized.inc | ✅ | 栈操作确定（pop 2/push 1 或 pop 1/push 1），由编译器生成，相对安全 |
| op_call.inc | ❌ | 函数调用和返回涉及复杂的栈帧管理，容易出错 |
| op_jump.inc | ❌ | 跳转时栈状态不确定 |
| op_variables.inc | ❌ | 局部变量操作可能涉及边界情况 |

**经验总结**: 
- 快速栈操作虽然能提升性能，但在复杂场景下（如递归调用、大量函数返回）存在栈边界安全风险
- 类型特化指令栈操作确定，由编译器生成，相对安全
- 建议：仅在确定栈状态绝对安全的热点路径使用快速操作，并配合充分的测试
