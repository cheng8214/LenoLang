## 优化 1：`OP_CALL` + `OP_POP` → `OP_CALL_DISCARD`（高收益）

**现象**：几乎每次不关心返回值的函数调用后面都紧跟着 `OP_POP`。

**验证**：`sdl_edit_bytecode.txt`

```
行 100: OP_CALL              1
行 101: OP_POP
```

```
行 120-121:
0135 OP_CALL              2
0138 OP_POP
```

```
行 160-161:
0228 OP_CALL              2
0231 OP_POP
```

```
行 282-283:
0192 OP_CALL              2
0195 OP_POP
```

**统计**：用文本搜索 `OP_CALL.*` 后紧跟 `OP_POP` 的模式，在整个 sdl_edit 字节码中出现 **数百次**。

**方案**：新增 `OP_CALL_DISCARD N`，合并"调用 + 丢弃返回值"，省一条指令且免一次 push/pop 栈操作。

## 优化 2：方法体字段读取未走 `OP_GET_FIELD` 优化路径（最高收益）

**现象**：方法体内裸写字段名（如 `_font`）时，`transform_method_body_ex` 将其转换为 `AST_INDEX`（self["field"]），
导致代码生成使用 `OP_CONST + OP_INDEX`（3 条指令 + 运行时哈希查找），而非已有的 `OP_GET_FIELD`（2 条指令 + O(1) 数组下标访问）。

**根因**：`OP_GET_FIELD` 指令已存在（`leno_vm.h` 第 147 行），VM 实现也完善（`op_struct.inc` 中直接 `field_values[idx]` 访问），
但 `semantic_visit_method.c` 的 `transform_method_body_ex` 将裸字段读取转换为 `AST_INDEX` 而非 `AST_FIELD_ACCESS`。
`AST_INDEX` 没有 `field_index` 字段，无法走 `OP_GET_FIELD` 优化路径。而写入路径转换为 `AST_INDEX_ASSIGN`（有 `field_index`），
语义分析会填充索引，代码生成使用 `OP_SET_FIELD`——读写不对称。

**验证**：`sdl_edit_bytecode.txt`，函数 `_ensure_font`

```
行 63-66:  self._font == null（读取，走慢路径）
0063 OP_GET_LOCAL         0               # 加载 self
0064 OP_CONST             0 (_font)       # 加载字段名
0066 OP_INDEX                             # self["_font"]（运行时哈希查找）
0067 OP_NULL
0068 OP_EQ
```

```
行 121:  self._font = ...（写入，走快路径！）
0138 OP_SET_FIELD         9               # 直接数组下标访问（field_index=9）
```

**统计**：`sdl_edit_bytecode.txt` 中 `OP_GET_FIELD` 仅 21 次，`OP_INDEX` 达 1195 次（其中约 1023 次是 struct 字段访问）。

**方案**：将 `transform_method_body_ex` 中 `AST_VAR` → `AST_INDEX` 的转换改为 `AST_VAR` → `AST_FIELD_ACCESS`，
复用已有的 `field_index` 语义分析和 `OP_GET_FIELD` 代码生成路径。同时将 `AST_MODULE_ACCESS` 中 `field.member`
和 `AST_MODULE_CALL` 中 `field.method()` 的字段访问也改为 `AST_FIELD_ACCESS`。

**预期效果**：约 1023 处 struct 字段读取从 3 条指令（`GET_LOCAL + CONST + INDEX`）变为 2 条（`GET_LOCAL + OP_GET_FIELD idx`），
并从运行时 O(n) 线性搜索变为 O(1) 数组下标访问。字节码总长度减少约 10-15%，字段访问性能提升显著。

## 优化 3：`OP_GET_LOCAL` 连续重复消除（方法调用 self 双载）

**现象**：调用对象方法时，同一个 local 变量被连续 load 两次（一次作为 self 参数，一次作为方法派发对象）。

**验证**：`sdl_edit_bytecode.txt`，函数 `_ensure_font`

```
行 110-113:  调用 fnt.acquireFont(self._fontPath, self._fontSize)
0110 OP_GET_LOCAL         0               # self (参数1)
0111 OP_GET_LOCAL         0               # self (派发) ← 与上行完全重复!
0117 OP_CONST             10 (_fontPath)
0120 OP_INDEX
0121 OP_GET_LOCAL         0               # self (参数2 也需要 self._fontSize)
0124 OP_CONST             11 (_fontSize)
0127 OP_INDEX
```

**验证**：`sdl_edit_bytecode.txt`，函数 `process`

```
行 5336-5339:  ev.isMouseButtonDown()
5336 OP_GET_LOCAL         1               # ev (参数1)
5337 OP_GET_LOCAL         1               # ev (派发) ← 与上行重复!
5338 OP_GET_METHOD        8 (isMouseButtonDown)
5339 OP_CALL              1
```

```
行 5342-5345:  ev.mouseButton()
5342 OP_GET_LOCAL         1
5343 OP_GET_LOCAL         1               ← 重复!
5344 OP_GET_METHOD        9 (mouseButton)
5345 OP_CALL              1
```

**方案**：让 `OP_GET_METHOD` 接受"对象所在 local 槽位"作为参数，自动从该槽位读取对象并压栈作为 self，消除冗余的 `OP_GET_LOCAL`。

## 优化 4：短路求值死跳转消除

**现象**：`or` 短路求值的字节码中存在永远不会执行的 `OP_JUMP`。

**验证**：`sdl_edit_bytecode.txt`，函数 `_ensure_font`

```
行 68-69:  _font == null or not _font.ok
0068 OP_JUMP_IF_FALSE     5 (to 19)       # null == true → 跳到短路结果
0069 OP_JUMP              13 (to 32)      
      ↑ 死指令：永远无法执行（0068 若为 true 则跳走，若为 false 则顺序执行不会经此）
```

**验证**：`sdl_edit_bytecode.txt`，函数 `_text_width_to`

```
行 211-212:
0211 OP_JUMP_IF_FALSE     5 (to 19)
0212 OP_JUMP              13 (to 32)      ← 死指令
```

**统计**：全文件 `OP_JUMP` 后紧跟另一个 `OP_JUMP` 的模式出现几十处。

同一文件还有大量"跳过单个 POP"的 `OP_JUMP 1`：

```
行 100-102:
0087 OP_POP
0088 OP_JUMP              1 (to 94)       # 跳过 0093 的 POP
0093 OP_POP
```

这些在代码生成阶段即可折叠。

## 优化 5：模块 init 重复块合并（启动速度）

**现象**：每个 import 语句生成 `CONST + INIT_LENOMODULE + DEFINE_GLOBAL` 三元组，head 处连续 9 块完全相同的模式。

**验证**：`sdl_edit_bytecode.txt`，主程序

```
行 8-10:
0000 OP_CONST             0 ([object])
0003 OP_INIT_LENOMODULE   (init .leno module)
0004 OP_DEFINE_GLOBAL     0

行 11-13:
0007 OP_CONST             1 ([object])
0010 OP_INIT_LENOMODULE   (init .leno module)
0011 OP_DEFINE_GLOBAL     1

行 14-16:
0014 OP_CONST             2 ([object])
0017 OP_INIT_LENOMODULE   (init .leno module)
0018 OP_DEFINE_GLOBAL     2

... 重复至 line 31（9 个模块 × 3 条指令 = 27 条）
```

**方案**：新增 `OP_INIT_MODULES N`，在 VM 层一次注册 N 个 Leno Module 对象，或至少将 9 个块循环展开。

## 优化 6：类型化常量 `OP_CONST` + `OP_CAST_*` 合并

**现象**：常量池存的是通用类型，使用时再运行时 CAST。

**验证**：`file_manager_bytecode.txt`

```
行 82-84:  int 常量 1
0202 OP_CONST             28 (1)          # 存为通用对象
0205 OP_CAST_INT                          # 运行时转 int
```

```
行 68-70:  空字符串 ""
0166 OP_CONST             26 ()
0169 OP_CAST_STRING
```

**验证**：`sdl_edit_bytecode.txt`，`_build_display_rows` 函数

```
行 13872-13879:
0383 OP_CONST             27 (0)          # 存为通用数字对象
0386 OP_ARRAY_APPEND_NOPUSH                # append 时需运行时推断类型
```

**方案**：引入 `OP_CONST_INT N` / `OP_CONST_FLOAT N` / `OP_CONST_STRING N`，在常量池中以正确的 VM Value 类型存储，省去运行时 CAST。
