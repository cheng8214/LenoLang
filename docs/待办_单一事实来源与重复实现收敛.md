## 一、问题定式

语义性数据（**常量值**、**类型种类**、**符号归属**、**字面量集合**）在编译流程里有多个
计算点；这些点各自实现，靠注释/约定保持同步。一旦漂移，症状几乎总是
**静默错值**，而且常在半个文件之外才爆发。

信条：**同一件语义事实，只允许有一个实现者，其余都是"读"它。**

### Phase 1：把「值」收敛到一处（对应 S1 / S3 / S4）

1. 扫描器的 enum 记录先改成「名字 + **表达式原文**」（只加字段、不改行为，缓存 bump 一次）。
2. 需要值时调用**真解析器**（临时构造 `Lexer/Parser` 指向那段短表达式 → 表达式解析入口
   （`parse_expression` 或同层入口）→ `eval_const_expr`，并按现有机制设置成员引用上下文
   `g_enum_member_names/values`）。
3. 删掉 `sym_table_enum_expr.inc`。**这一步做完，"求值对齐"这件事永久消失。**
   - 备选路线：值一律取自模块**编译产物**（`.lenomc`/symc），扫描器只负责名字与形状。
     注意此路线有**鸡生蛋问题**：首次编译时被引用模块还没有产物 ⇒ 若为此保留"没产物就回落扫描求值"，
     等于**又变成两套**，与本节目标自相矛盾。要么彻底走第 2 步（真解析器），要么明确改成
     "扫描阶段不求值、跨模块 enum 值延迟到语义阶段从产物回填"，二者必须二选一。
   - 词汇表纪律：**字面量/运算符集合以词法器为唯一来源**，扫描器不得"多支持"
     （`0b` 那次正是扫描器比解析器更全，立刻就不一致）。

**实施前先定（不先定就会返工）**：

- **解析错误必须静默化**：`eval_const_expr` 失败会往全局 error 收集器写
  （"enum 成员显式值必须是编译期整数常量表达式"）。扫描阶段是在**读别人的模块**，
  不屏蔽/不快照-恢复，就会把跨模块查询失败报成当前文件的错。
- **重入安全**：扫描本身是递归的（跨模块 + `use` 链），成员引用上下文
  （`g_enum_member_names/values`）必须栈式保存/恢复，不能就地覆盖。
- **缓冲区生命周期**：从原文切子串构造 `Lexer`，别指向即将释放的临时 buffer
  （扫描器状态里存的是原文指针，这类悬垂极难查）。

✅ **2026-09-16 已完成**（实际做法与上面三步略有出入，出入处即经验）：

- **第 1 步不需要**：扫描 enum 时表达式原文本来就在手边（`scan_enum.inc` 里的 `expr_buf`），
  是"扫到就求值"，不存在"稍后再取"的时机，所以没有加字段、也没动 `.lenosymc` 的布局。
- **求值入口**：新增 `parser_eval_const_expr_text(text, names, values, count, &out)`
  （`parser_func.c`，声明在 `leno_parser.h`）——临时 `parser_init` + `parse_expression` +
  `eval_const_expr`，并做了三件事：
  ① **静默**（新增 `error_silence_begin/end`，见 `error.c`）：期间 lexer/parser 的诊断一律丢弃，
     `end()` 返回被丢弃的**错误条数**，"报过错"本身也算求值失败；
  ② **可重入**：进入前保存、退出后恢复 `g_enum_member_names/values/count`；
  ③ **整段消费**：要求 `p.lex.current.type == TOK_EOF`，`1 + (2` 这类残句不能因"解析出前缀"就算成功。
  另外把表达式文本**复制**一份给 Lexer，调用方缓冲区生命周期与本函数解耦（AST 全部 copy 文本，
  已核对无 `= p->lex.current.text` 直取切片的写法）。
- **删掉 `inc/sym_table_enum_expr.inc`**（连同 `module_symbol_table.c` 的 include）。
  扫描器从此与解析器共用同一套词法/语法/求值 —— "词表、优先级、失败口径"三件事不再需要对齐。
- **缓存版本三升**（`.lenosymc` v24→v25、`.lenomc` v7→v8、`.lenb` v2.7.1→v2.7.2）：若模块里存在
  "旧扫描器失败、解析器成功"的形态，旧缓存存的是**自动递增值**，必须整体失效。

**验证**（都做了，结论是不变量守恒）：
- 26 项形态矩阵（冷缓存 + 热缓存两跑）+ 全量 `assert` 309/0 全过 → 三路径取值逐项未变；
- 另有**边界形态探针**（专门找"旧扫描器失败/解析器成功"）：`F = 1.5` → 三路径都是 **1**（浮点截断，
  旧实现下 use 路径是自动值 8）、`HUGE = 99999999999999999999` → 三路径都是 **INT64_MAX**
  （旧实现自己十进制累乘、有符号溢出）、`-0` → 0、`10 % 3` → 1、`1 << 40` → 1099511627776。
  其中 `1.5` / `HUGE` 已固化进矩阵（它们是"手工对齐一定会漏"的形态）；两者当前都**不报错**，
  是否该收紧为编译期错误列为开放问题（与除零同族）。
- **静默段实测**：模块里写 `BAD = 1 +`，编译器只报模块自身解析级联的 3 条（坐标都落在模块文件），
  扫描器那次临时解析的诊断一条没漏出来。
- LSP 照旧构建成功（`leno_lsp/build_lsp.bat`）——它同时链接扫描器与解析器，方向没问题。

🔜 **2b-2 设计（2026-09-16 侦察定案：用"模块槽位"号，而不是别名或路径）**

- **实测结论一（运行期模块身份）**：`ObjModule.source_path` = 规范化绝对路径，`find_loaded_module(path)`
  按它去重；字节码里的模块引用（`CONST_TAG_MODULE_REF`）本来就是 `name + source_path` 存的。
- **实测结论二（别名→模块在运行期确实存在，但是"索引式"的）**：`a.f()` 走 `OP_GET_MODULE_FUNC`
  （`op_module_var.inc`），读的是 **`当前帧的模块->globals[index]`** —— 导入进来的模块对象就躺在
  **导入方自己的 globals** 里，索引由编译期定死。所以"别名 `a` 指向哪个模块"运行期**不需要**新建别名表、
  也不需要路径：**发那个 globals 槽位号**就够了，而且与机器无关（不像 `source_path`）。
- **据此选定**：给 `OP_STRUCT_INIT`（其后 enum / cstruct / face 的同类操作码）**加一个 `module_slot16`
  操作数**（`0xFFFF` = 无/自身）；运行期取 `frame->module->globals[slot]`，是 OBJ_MODULE 就交给
  `*_def_find_in_module(owner, bare_name)` 精确取回，取不到再回退裸名。
- **已试过、被实测否掉的捷径（别重走）**：想在 **codegen** 里把别名直接换算成"运行期模块名"
  （`module_runtime_name_for_import()`：同一进程里 `find_loaded_module` 拿 `ObjModule.name`）。
  **两次假设都被直接观测否掉**：① 先猜"编译期 loaded_modules 是空的"——换成 `chunk->filename`
  后判别用例仍 `A=3`（期望 1）；② 于是打点观测，得到确定答案：
  ```
  [DBG-IMP] not-loaded import='lib/p.leno' cur='...\alias_not_name\main.leno'
            full='...\lib\p.leno' loaded=0
  ```
  即**入口里 `new p2.Point()` 这条指令的生成早于模块被加载**（那一刻 loaded_modules 计数为 0），
  不是"偶尔拿不到"而是关键路径上必然拿不到。③ 更彻底的一条：**缓存路径反序列化依赖时是
  `load_module_file(path, NULL, NULL)`**（`serialize.c` 的递归 pre-load），别名根本不存在 ——
  所以任何依赖"别名"的编译期方案在冷/热两条路径上都不可能一致。
  ⇒ 结论：别名→模块**只能由运行期解决**，且必须用**不依赖名字**的载体（即 globals 槽位号）。
- **落地前必确认的一点（`module_slot16` 的前置）**：`a.f()` 走的是

⚡ **顺带做掉的性能修复（2026-09-16）：定义表查找 O(定义数) → 小表线性 / 大表名字桶**

- **实测问题（探针：200 个 struct 声明，循环 300 万次 `new T199()`）**：215ms → **6252ms（29×）**。
  根因不是"表大"本身，而是 **JIT 把 `OP_STRUCT_INIT` 实现成 callout（`jit_callout_struct_init`），
  那条路径没有内联缓存** ⇒ 每次 `new` 都线性扫满整张定义表（解释器命中 IC 时是零扫描，所以这个坑
  只在 JIT 生效的热循环里显形）。也正因为如此，IC 键里那项 `owner` 与该修的都是"取哪一份"，
  与"快不快"无关 —— 让查找变快的是这个索引。
- **做法**：定义表旁挂"名字 → 槽位"的桶索引（512 桶，桶内链**按注册顺序**串 ⇒ "同名取先注册者"
  的既有语义天然不变；覆盖替换只在同名分支发生、槽位号与名字都不变 ⇒ **索引无需任何维护**，
  只在末尾追加时登记）。`*_def_find*` 与 `struct_def_register` 的遍历全部改走它。
- **踩到的坑（值得记）**：一开始把"小表特判"塞进辅助函数里，结果 1 个定义时每次分配 **+8ns**
  （多一次不可内联的调用 + 重复取下标）。四路交错 A/B 定位到它是**查找路径**而非哈希/布局：

  | 变体 | 3M 次 `new`（1 个定义） |
  | --- | --- |
  | 基线（纯线性扫描） | **208.7ms** |
  | 保留索引维护、查找还原成基线 | 211~216ms（索引维护本身不要钱） |
  | 查找经辅助函数（小表特判写在里面） | 235.4ms（+8ns/次分配） |

  ⇒ 定稿：**小表分支就地写在各查找函数里（内容 = 改动前那几行原样）**，大表才走桶。
- **顺带**：`op_struct.inc` 里 `bare_name` 的 `strchr` 原先在 IC 命中路径上也白算一次，
  已挪进未命中分支（实测中性，但没道理留着）。
- **结果（交错 A/B，同机同探针）**：1 个定义与基线**持平**（211/216/213 vs 213/212/216 ms）；
  200 个定义 **6205ms → 330ms（18.8×）**；真实应用（47 模块）`sum=720` 一致、帧耗时在噪声内。
- **回归覆盖**：判别用例 D 原本只有 3 个定义（走小表线性那条路），已补 5 个无关 `PadN` 声明把
  条目数顶过阈值 ⇒ **哈希那条路同样有用例守着**（两条路都必须有覆盖，否则改动只测到一条）。
- **不 bump 版本号**：只改运行期查找实现，字节码与缓存格式未动 ⇒ 旧 `.lenb` / `.lenomc` 继续可用。

   护栏用例：`assert/test_enum_use_alias.leno`（其模块正是这种一行写法）。
2. **改"会烙进产物"的东西必须 bump 缓存版本**：求值语义、字面量集合、opcode 集合
   都会写进 `.lenb` / `.lenomc` / `.lenosymc`，三个版本号要一起看。
3. **验证时先关缓存**（`LENO_NO_CACHE=1`）：否则命中旧缓存根本进不到语义阶段，
   会得到"只有 1 行输出"这种假象（§8.49 记过一次）。
4. **"扫描器比解析器更正确"也是 bug**：单一来源的意义是**一致**，不是"谁更对"。
   `0b` 那次若只改扫描器去迁就解析器，就是把静默错值固化下来。
5. **扫描器要为"读不出东西"留后路**：手写扫描遇到不认识的构造时，必须前进
   （消费至少一个字符）或明确失败，绝不能原地重试。
6. **新增缓存产物时，先问"它的依赖事实从哪读"**：`.lenomc`/`.lenosymc` 都有"自身 hash + 逐依赖 hash"，
   入口 `.lenb` 当初只有"文件名里的入口 hash"就把**整程序**（所有模块字节码）装了进去 ——
   漏的不是代码，是"这件事实我该去哪里读"。答案是：只能去已实现的那处读（Phase 3）。
7. **"修好"也可能是在制造新的重复**：`fccd1534` 的修法自己写了一份快照校验（还有自己解析
   `.lenomc` 大端 header 的代码）。功能上对，但按本文信条它**是第二个实现者**，
   所以它同时登记为 S8 的待收敛项，而不是"已彻底解决"。新增格式标识（`LENODEPS1`）
   也要进第七节的登记表 —— 包括写明"**为什么这次不 bump `LENO_BIN_VERSION`**"。
8. **"明确不支持"必须写在解析处，否则会退化成 misparse**（2026-09-16 实测）：`parse_type_internal`
   只吃单个类型名、遇到 `a.Point` 就停在 `a`，剩下的 `.Point` 被外层当成属性访问 ⇒ **同一个 bug
   三种面孔**：类型守卫报"if 语句体必须用大括号 {}"、表达式报"类型 'bool' 不支持属性访问 '.Point'"、
   `as` 甚至**语法通过**、运行期才炸"索引操作需要对象类型…"。修法：在所有"要求类型"的位置调用同一
   检查 `parser_reject_module_qualified_type()`（`parser_func.c`），给出与声明处同口径的提示。
   教训：解析层"只吃一半"比语义层报错难查得多 —— 报错位置离真正原因很远，还可能把问题拖到运行期。

## 五、验证手段（照抄今天的做法）

- **三路径探针**：同模块 / `use` 导入 / 模块限定三值互等；**外加绝对值断言**
  （否则"三处一致地错"拦不住）。
- **变异验证**：把修复回退，用例必须失败 —— 证明断言不是空转。
- **冷缓存验证**：`LENO_NO_CACHE=1` 跑一遍全量（覆盖扫描器路径），再热缓存跑一遍
  （覆盖缓存读写往返）。
- **注意套件的覆盖边界**：`run_tests.leno` 跑之前会删掉 `assert` 子树下所有 `.lenocache`
  （`32-43` 行）⇒ **assert 套件默认就是冷缓存**；但 `examples/` 与 `leno_module/**/examples/`
  不受保护。S8 那次是**真实应用**上撞出来的，套件全程绿灯（308/0）。
  缓存类改动必须在真实应用上验，且形态要选"**改被引用模块、入口不动**"。
- **缓存类改动的读数口径**：用"缓存文件 mtime 是否变化"区分**命中**与**重编译**
  （只看输出会说谎：旧字节码与新字节码可能输出相同）。
- **但别指望在 Leno 用例内部用 mtime 判命中**：`dirs.stat()` 在 Windows 上把 `mtime`
  写死为 0（`src/module/dirs/dirs.c:1058` 的"简化版"）⇒ 用例里观测不到"是否重编译"。
  所以自动化用例只断言**行为**（改了被引用模块就必须出新值），mtime 那条读数留在
  PowerShell 侧手工做（见 `jit_probes/README.md`）。
- **改编译器的变异验证必须先关缓存**（2026-09-16 实测踩到）：变异前后版本号相同 ⇒
  `assert/.lenocache` 里上一版写的 `.lenosymc` / `entry_*.lenb` 会被**原样复用**，扫描器
  根本不重跑，变异版跑出**假 PASS**。正确姿势：`$env:LENO_NO_CACHE='1'` 再跑用例
  （或先删 `.lenocache`）。判定"变异有效"的信号是：用例挂在期望的那条断言上 + 进程 exit 非 0。
- **矩阵里"求值失败"类项目必须排在非零前驱之后**：扫描器一旦把某个表达式判成"无显式值"，
  成员会退化成**自动递增值**（前驱 +1）。若这个失败项是枚举首个成员，自动值恰好是 0，
  与正确值 0 撞上 ⇒ 错值被**掩盖**。本次 `ZERO_DIV = 5 / 0` 之所以被抓到，正是因为它排在
  `REF2 = 271`（⇒ `IMPL = 272`）之后，露出了 273 这个刺眼的数。
- **换实现时，既有用例与矩阵都不足以证明等价**：Phase 1 把扫描器的求值器换成真解析器时，
  矩阵里的形态**两套都支持**，所以它对"等价性"没有鉴别力。真正的差异藏在**"旧实现失败、
  新实现成功"**那一侧（浮点字面量、超出 int64 的十进制）—— 做法是按"失败成因"列清单
  （词表缺项 / 优先级不同 / 口径不同 / 类型不同）逐条探三路径。这次探出的两条
  （`FLOAT = 1.5` → 1、`HUGE = 999…` → INT64_MAX）已固化进矩阵。

## 七、缓存格式与版本号登记表（Phase 0.2）

**规矩**：改下面任何一处之前先 `git fetch`，看远端动没动同一处。2026-09-16 撞过车 ——
两个会话都把 `.lenosymc` 升到 v23，但格式不同（一个"每成员多一个字节"，一个"不再丢弃无显式值成员"）：
**数值相同、格式不同**，靠版本号根本区分不开。

| 产物 / 标识 | 定义位置 | 当前值 | 什么时候**必须**升 | 备注 |
| --- | --- | --- | --- | --- |
| `.lenb`、`entry_*.lenb` | `LENO_BIN_VERSION`（`src/include/leno_serialize.h`） | `0x00030202`（v3.2.2） | 读写字节布局变化、**opcode 集合**变化、**常量标签集合**变化、**求值语义变化**（常量会被折叠进字节码） | 旧文件会按 magic+version **通过**校验，却含未知 opcode/标签 ⇒ 跳转发散（0xC0000005）或报格式错；反向同理。⚠ **opcode 即使"追加在末尾"也必须升**（v2.6.0 先例、v3.2.0 同判据） |
| `.lenomc` | `LENO_MODCACHE_VERSION`（`src/include/leno_serialize.h`） | `0x00000013`（v19） | `.lenomc` 布局变化（模块内联方式、依赖清单区）、**常量标签集合**变化、**opcode 集合**变化、求值语义变化 | 与 `.lenb` 同源改动要一起看（同一份编译产物两种落盘形态） |
| `.lenosymc` | `LENOSYMC_VERSION`（`src/module_symbol_table/inc/sym_table_cache.inc`） | `0x0000001D`（v29；⑱ 转正：函数符号加 `param_types` / `param_struct_names`） | 符号表字段增删、**扫描语义**变化（"无显式值成员"的处理、求值器来源/词表） | 只覆盖符号表；等价信息在 `.lenomc` 里没有 |
| `.lenb.deps` | `ENTRY_DEPS_MAGIC`（`src/main.c` 的 `entry_deps_*`） | `"LENODEPS2"`（§8.112 加 `BIN` 行） | 行格式 / 字段增删（加 mtime、换哈希算法、**新增失效输入**） | **不依赖版本号自愈**：清单缺失、`count` 不符、缺末行 `END` 一律判失效 ⇒ 不必与 `.lenb` 严格同批 bump |

**"为什么不升"也要写下来**（实例一）：`fccd1534` 只**新增**了 sidecar（`.deps`），没有改 `.lenb`
的字节布局；而读取侧把"清单缺失 / 不合法"一律当失效 ⇒ 旧缓存自动作废、新缓存下次运行补齐，
所以**不需要** bump `LENO_BIN_VERSION`。反例：哪天变成"缺清单也算命中"，那就必须 bump。

**"为什么升"同样要写下来**（实例二，2026-09-16 求值语义修正）：扫描器补 `not`、除零/取模零与
解析器同结论 —— 这两处改的是**求值语义**，而枚举成员值/常量折叠结果会烙进 `.lenosymc`（扫描器写的）、
`.lenomc` 与 `.lenb`（编译产物）。三者版本号**同时**升（v23→v24、v6→v7、v2.7.0→v2.7.1），
否则旧缓存里的错值会被继续当成事实读出来（表现与"编译器改了但跑旧模块"同类）。

**实例三（同日 Phase 1）**：扫描阶段的 enum 求值改由真解析器执行。对**主流写法**（整数/hex/bin/
移位/位运算/成员引用）取值不变，但"旧扫描器失败、解析器成功"的形态（浮点截断、超大整数饱和）
取值会变 —— 所以照样三号同升（v24→v25、v7→v8、v2.7.1→v2.7.2）。
教训：**"多数情况下不变"不是不升版本号的理由**，只要存在会变的输入就得升。

**实例四（2026-09-17，§8.112）**：`.deps` 加了一行 `BIN\t<运行中 exe 的指纹>`
（size + mtime + 内容 FNV-1a）⇒ 格式标识 `LENODEPS1` → `LENODEPS2`。
**为什么升**：这是"**新增一类失效输入**"（原先只有"有源文件的模块"这一类 ✗，
而 native 模块签名变化不属于任何一类 ⇒ 缓存被判有效却已过期 ✗，实测让基准脚本打印出 10^9 量级的
"毫秒" ✗）。**为什么不升 `LENO_BIN_VERSION`**：`.lenb` 的字节布局与序列化语义**一字未改**，
变的只是"什么时候认这份缓存"的外部条件 ⇒ 升它会让 `.lenomc` / `.lenosymc` 跟着无谓失效 ✗；
而读取侧对"缺 `BIN` 行 / 指纹不符"一律判失效 ⇒ 旧清单自动作废 ✓，不需要与 `.lenb` 同批 bump ✓。

**实例五（2026-09-17，§8.112.1）**：`.lenomc` 与 `.lenosymc` 的 header 末尾各加一个 `bin_fp(8)`
（运行中 exe 的指纹 ✓）⇒ **必须**升版本号（v9→v10、v25→v26 ✓）—— 与实例四不同 ✗：
这里**字节布局真的变了** ✗，旧文件会被按新布局错读 ✓（正是 S5 那次"数值相同、格式不同"的坑 ✓）。
入口缓存那处只动 `.deps` 的行格式（那是独立 sidecar ✓、读取侧又有结构自检 ✓）⇒ 只升它自己的
`LENODEPS2` ✓ 不动 `.lenb` ✓；模块级这两处动的是**主产物自己的 header** ⇒ 必须升 ✓。
**顺带修正一处表内漂移**：`.lenb` 行原写 v2.7.2，实际 `LENO_BIN_VERSION` 已是 `0x00020703`（v2.7.3）✓
—— 登记表本身也是"会静默漂移的语义事实" ✓，发现即修 ✓。

**实例十一（2026-09-25，方法级 DCE）**：`serialize.c` 新增常量标签
**`CONST_TAG_DEAD_FUNCTION(0x14)`** —— 入口 `.lenb` 序列化时，引用图证明不可达的函数只写这
1 字节标签（零载荷，省略名字/参数表/函数体），读侧就地合成"空体 + 一条 `OP_RETURN`"的最小函数
⇒ `LENO_BIN_VERSION` v3.0.2 → **v3.1.0**、`LENO_MODCACHE_VERSION` v15 → **v16**。
**为什么升**：**常量标签集合真的变了** —— 新产物含旧构建不认识的 0x14（旧构建读到它落进
`deserialize_constant` 的 default 分支 `return 0` ⇒ 整个反序列化报 FORMAT 错，**不是**静默错读，
但用户会拿到"编译成功、运行报格式错"的产物），与 v2.6.0"新增 opcode 也必须 bump"同一条判据。
**同批必须重建 VM**：版本号变了 ⇒ 磁盘上的旧 `leno_vm*.exe` 会拒读新产物，`-p` 的
「编译器 ↔ VM 版本握手」（实例十之后的兜底）会拦下并报错，提示先 `build_vm.bat`。
**为什么不升 `.lenosymc`**：它只存符号表、不含字节码与常量序列化 ✓（同实例四/六的判据：
先问"哪个产物真的变了"）；`.lenb.deps` 靠 exe 指纹 fail-closed ⇒ 不动 ✓（exe 一变即失效）。
**为什么不只升 `.lenb` 不升 `.lenomc`**：两者共用同一份 `serialize_constant` 实现；
本次裁剪只发生在入口 `.lenb`（`dce_set_active` 只在 `chunk_serialize` 置位），`.lenomc` 里
**不会**出现 0x14 —— 但"标签集合"是所有产物共享的序列化语义 ⇒ 按登记表规矩一起升，避免
"同一实现两种版本号"的漂移。

**顺带一条实现纪律（入口编译不读模块缓存）**：DCE 的引用图靠 codegen 边生成边收集，
而命中 `.lenomc` 的模块**不走 codegen** ⇒ 图缺一半、该模块的函数会被误判不可达剪掉。
因此 `-c` / `-p` 现在**先关掉模块缓存**再编译（`main.c` 的 compileMode / packMode 分支），
并保留一条兜底（`module_loader.c` 命中缓存时调 `dce_note_module_cached()` ⇒ 整轮不剪）。
这个代价是**真实存在的**：读模块缓存本来快得多（hello_window `-c`：读缓存 168 ms vs
