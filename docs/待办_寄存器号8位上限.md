## 一、现象（原样）

编译某个大模块（实测触发点：`build/leno_module/LenoSDL3/lib/sdl_renderer.leno` 里
给 `export struct Renderer` **加一个字段或方法**）时，stderr 打印：

```
[寄存器号溢出] OP_xxx A=… B=… C=… line=…（>255 会被截断成另一个槽位）
```

⚠ **必须澄清的一个误判** ✗：这**不是**"结构体成员 256 上限" ✓。
实测该结构体只有 **64 字段 + 67 方法 = 131 个成员** ✓（成员表上限 256，还差一半 ✓）。
报的是**寄存器号** ✗ —— 即**某个函数**的寄存器高水位 `func->local_count` 越过了 255 ✓。

## 二、机制（为什么是 255、为什么危险）

1. Leno 指令是 **4 字节 iABC**：`A/B/C 各 8 位` ⇒ **寄存器号 ≥ 256 无法寻址** ✓
   —— `src/include/leno_codegen.h:48`：`#define MAX_REG 256  // 单字节寄存器号上限（超过需 EXTEND 前缀）`
   （注意这句注释本身就写着"**超过需 EXTEND 前缀**" ✓ —— 设计上早留了扩展位，只是没实现 ✓）
2. 编码处只**告警**、**不阻断** ✗（`src/include/leno_vm.h:479` `reg_encode_iABC`）：
   ```c
   if (a > 255 || b > 255 || c > 255) { codegen_reg_overflow_warn(op, a, b, c, line); }
   chunk_write(chunk, (uint8_t)(a & 0xFF), line);   // ← 警告之后照样截断写下去 ✗
   ```
   ⇒ **编译"成功"了，但那条指令的操作数是错的** ✗✗ ⇒ 现阶段这是**最危险的一档**（静默错值 ✓）
3. 高水位来源：`src/codegen/codegen_func.c:212` `func->local_count = gen->max_reg;`
   ⇒ 水位 = **含表达式临时寄存器**的峰值 ✓，不是"声明的局部变量个数" ✓（台账 ⑤-o 同一口径 ✓）
4. 历史同类事故（就是加这条告警的原因 ✓，`src/debug.c:116-120` 注释原文）：
   SDL 的 `Window.run` 高水位 **655**、`process` **563** ⇒ `OP_MOV A=70 B=320` 里的 B 被
   `&0xFF` 截断成 64 ⇒ 把 R64 的值当成循环变量 `i`（恰好是 null ✓）
   ⇒ 现象却是 **`_runEvts[i]` 报「数组索引必须是数字」** ✗ —— 从现象完全反推不到真因 ✓

## 三、为什么会因为"加一个字段/方法"触发 ✓

寄存器分配是**按函数**算的 ✓，而下面三类会把水位往上顶：

| 触发源 | 说明 |
|---|---|
| **巨型方法** | 语句边界虽然回收临时寄存器（`codegen_stmt.c:339` 起 ✓），但**同一语句内**的长表达式、嵌套调用仍线性堆临时寄存器 ✓ |
| **结构体字面量 / 构造** | 每个字段各占一个寄存器 ✓ —— 同类先例：`Array[int] SBOX = [256 项]` 曾因"连号块要 256 个寄存器"**直接变成空数组** ✓（`codegen_expr.c:400-405` ✓） |
| **多字段一次初始化** | `new Renderer(a=…, b=…, …, z=…)` 这种一次性写很多字段的写法 ✓ |

⇒ 用户那一行改动，让**某个函数**（构造、或所改的那个方法）的水位跨过了 255 ✓。
**这不是使用者的写法错误，是编译器应当能处理的情形** ✗ ✓（见 §四）。

## 四、为什么算"要修的 bug"（而不是"设计上限，忍着"）

- 8 位寄存器号本身是 **4 字节指令的固有上限** ✓（Lua 用 32 位指令：OP 7 + A 8 + Bx **17** 位 ⇒ 空间更大 ✓，
  这是**编码位宽的差异**，不是谁的错 ✓）；
- **但"一个函数需要 >256 个寄存器"不该发生** ✗ —— 那是**寄存器水位回收粒度太粗**的产物 ✓：
  `reg_scope_enter/exit`（`leno_codegen.h:244/252`）**历史上从未被调用过** ✗，
  `next_reg` 只升不降 ⇒ **函数越长顶得越高** ✓（`codegen_stmt.c:339-344` 记着这段历史 ✓），
  后来才补了"**语句边界**回收"这一级 ✓ ⇒ 粒度仍有明显下沉空间 ✓✓
- 也就是说：**"编译器把自己的临时槽位记到了 300 号"** ✗ —— 这是编译器该自己解决的事 ✓

## 五、修法候选（按"低风险 → 大工程"排序）

1. **【先做，独立一小步】把告警升级成硬错误** ✓ —— ✅ **2026-10-03 已完成**
   - **先量后做**（§六 判据第一步 ✓）：扫体积最大的 **40** 个 `.leno`，触发 `[寄存器号溢出]` 的
     文件数 = **0** ✓（脚本 `sweep_regoverflow.py`）⇒ 升级成硬错误**不会卡住现有语料** ✓
   - 实现：`codegen_emit.c` 新增 `codegen_reg_overflow_error()`，照 `report_jump_overflow` 的惯例
     用 **`error_add(ERR_SEMANTIC, line, msg)`** ⇒ 编译中断 ✓；`leno_vm.h` 的编码点改调它 ✓
     （含 `leno_vm.h` 里那三处 `reg_encode_*` ✓）；原 `debug.c` 里"只 fprintf、不阻断"的那版**已删除** ✓
     （免得 debug.c 依赖错误收集 API ✓）。提示文案里带 **行号 + 怎么改**（拆函数 / 拆语句）✓
   - 验证：**300 个局部变量**的函数 ⇒ 报 **48 个错误**、**编译失败** ✓
     （改前 = "stderr 告警 + 照样把 `&0xFF` 截断后的字节码写下去" ✗）；正常文件仍能编 ✓；
     断言 **416/0** ✓
   - ⚠ 未做：给"**编译应当失败**"的用例加进测试基建 ✗ —— 现有断言套件只跑**能跑的程序** ✓，
     没有"期望编译失败"的机制 ✓（留到 §五-2 之后再评估 ✓）
2. **【主体】分配器侧：更细粒度回收** ⛔ **已实测判定「没有靶子」⇒ 不做** ✗（2026-10-03）
   - **实测 1（水位分布）**：扫体积最大的 40 个文件（`scan_regwater.py`，只编译 ✓），
     dump 里每个函数都带 `局部变量槽位数` ✓ ⇒ 分布：`≤32` **63317** / `33..64` 1870 /
     `65..127` 196 / `128..191` 90 / `192..255` **1** / **`256` 有 28 个** ✗
   - **实测 2（那 28 个是什么造成的）**：取 `leno_gui\系统\screenshot_hotkey.leno` 的
     `===== 函数: run =====`（水位 256）⇒ **第一条指令就是 `OP_MOV A=241 B=0 C=0`** ✗
     ⇒ 槽位在**函数入口**就排到 241+ ⇒ 这是**声明量（参数/局部变量/大结构体初始化）本身**，
     **不是临时寄存器** ✓
   - ⇒ 语义上无解 ✗：水的**峰值**（`max_reg`）只能升不能降 ✓，而"一条语句内同时活跃 256 个槽位"
     是真的需要 256 个寻址位 ✓ —— 回收临时寄存器**动不了声明量** ✓ ⇒ **本条没有靶子，停** ✗
   - 附带结论 ✓：**唯一根治手段是 §五-3（把寄存器号扩到 16 位）** ✓；
     在那之前，T34（§五-1）已经保证"顶到就**报错**"而不是静默错值 ✓ —— 这是当前能达到的最好状态 ✓

   （下面留的是立项时的原始设想，仅作历史记录 ✓）
   - 真正用起 `reg_scope_enter/exit`（块级作用域进出回收 ✓，而不是只靠语句边界 ✓）
   - 表达式内**用完即还**（求值顺序允许的地方 ✓ —— 注意别破坏"先左后右"的求值顺序与别名 ✓）
   - 长表达式**自动拆多条语句**（可考虑在 codegen 里对"单条语句临时寄存器数超阈值"发出更细的释放点 ✓）
   - 顺带收益：`local_count` 变小 ⇒ **帧更小、GC 扫描范围更小** ✓（不止修 bug ✓）
3. **【大工程】编码侧：按注释预留的 EXTEND 前缀** ✓
   `MAX_REG` 的注释写着"超过需 EXTEND 前缀" ✓，且仓库里已有现成先例：
   `OP_EXTRAARG`（常量索引 0 或 >255 时紧随一条携带 24 位索引 ✓，见 `01_prologue.inc:27` ✓）
   ⇒ 寄存器号 >255 时同样发一条附加字 ✓
   ⚠ 代价：**所有**读 A/B/C 的 handler、反汇编（`decode_trailing` / 跳转扫描）、
   序列化版本都要跟着改 ✓ ⇒ 与 T10 那批"融合指令要教反汇编器"是同一种工作量 ✓

建议顺序：**1 → 2 →（仅在 2 之后仍不够时）3** ✓
