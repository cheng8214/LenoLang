## M1【高】`threads.start` 的入口判据是"module 必须为空"，报错文案却说"当前文件"

**隐式契约**（源码判据 `src/module/threads/threads.c:130` 一带）：线程入口函数 `f` 必须
**不属于任何模块**——子 VM 只继承**调用方 VM** 的 globals，且把自己的 current_module_frame
置 NULL ⇒ **模块函数进不了线程函数体**。

**实测复现**（LenoMusic 拆分当天 ✓）：把 `bang_menu_worker` 搬进模块 `bang_page.leno` 后：

```
threads.start(): 线程入口必须是**当前文件**的函数 ✗ 收到的是模块 'bangpg' 里的 'bang_menu_worker'
```

两层问题：
- 文案说"**当前文件**"，实现判的是"**入口脚本**"——同一次运行里"当前文件"有好几个
  （每个被 import 的模块都是当前文件之一）⇒ 照着文案改不出对的结果；
- `threads使用指南.md` **查不到这条契约** ⇒ 模块化重构第一次起线程必撞，撞完还看不懂。

**可行解（已实测 ✓）**：宿主把 worker **当函数值**传进模块，模块里存成
`func(...):...` 字段再 `threads.start(字段, …)`——此时 `f` 仍是入口脚本的函数
（module == NULL）✓，子线程 globals 正常 ✓（探针实测 join 回值正确 ✓）。
LenoMusic 三个页面模块全部按此落地 ✓。

**修法建议（择一或全做）**：
1. **改报错文案**（最便宜）：把"当前文件"改成"**入口脚本（顶层文件）的具名全局函数**；
   被导入模块里的函数不行——模块函数拿不到子线程的 globals。模块要起线程，
   请让宿主把函数**当值传进来**（`threads.start(field, …)` 也行）"；
2. **文档补节**：`threads使用指南.md` 加"线程入口的模块限制"一节（契约 + 函数值解法 + 探针）；
3. （治本，可选）支持模块函数作入口：子 VM 按需加载该模块的 globals——代价要评估。

## M2【高】调用"函数类型字段"的返回值是 `any`（声明的返回类型没生效）

**实测复现**（探针，2026-10-11 ✓）：

```leno
// 模块里
pri func():string outdirOf
pri func outdir(): string {
    return outdirOf()        // ✗ error: [类型不匹配] 返回类型不匹配：期望 string，实际 any
}
```

哪怕字段声明是 `func():string`，**通过字段调用**的返回值在类型系统里仍是 `any`
⇒ 必须手动收窄：`var d = outdirOf()  return d as string` ✓（`as` 收窄后可用）。
普通函数调用不受影响（返回类型正常）⇒ 洞只在"函数值当字段/变量再调"这一形态。

**为什么疼**：函数值是本语言"跨模块传行为"的正路（M1 的解法就靠它）⇒ 用得越多，
这个洞越常撞；而且报错只说"实际 any"，看不出"明明声明了返回类型"。

**修法建议**：函数类型字段的调用按声明签名推返回类型（签名就在那，信息是现成的）；
顺带把 M1 的解法场景跑一遍回归（函数值 → threads.start 不受影响 ✓）。

## M3【中】`this` 不存在、自引用叫 `self`——但误用 `this` 的报错不提示

**实测**（2026-10-11 ✓，两支探针）：
- 方法里写 `return this` ⇒ `error: [未定义变量] 未定义的变量: this`（无任何提示）✗；
- 方法里写 `return self` ⇒ **完全可用** ✓：经返回的引用写字段，原对象同步变
  （引用语义，探针 `m.v = 42 ⇒ h.v == 42` ✓）——"返回自己"这件事**做得到** ✓。

所以这条的本质是**报错质量**小项：`this` 是最常见的顺手词，报"未定义变量"却不带
"是否想用 'self'？"（仓里已有同款先例：`contains()` 写错提示 `has()` ✓）。

**修法建议**：未定义变量报错对 `this` / `self` / `This` 这几个高频误拼给纠错提示；
`Leno入门教程.md`（struct 一节）补一句"方法内自引用用 `self`"。

## M4【中】模块别名与 struct 字段同名 ⇒ 静默遮蔽，报错指到别处

**实测复现**（LenoMusic 拆分当天 ✓）：入口脚本里

```leno
import "./bang_page.leno" as bang      // 模块别名
struct App { BangPage? bang = null }   // 恰好也有个字段叫 bang

// 方法里：
bang = bang.create_bang_page(...)      // ✗ 后一个 bang 被解析成"字段"
```

报错是"在字段 bang 上找不到方法 `create_bang_page`"之类——**看不出是遮蔽**
（字段把模块名遮了）⇒ 排查烧掉好几轮编译循环。改名 `as bangpg` 后当场通过 ✓。

**修法建议**：语义阶段检测"模块别名 vs 同作用域字段/变量同名"并直接报错
（哪怕只给 warning：「别名 'bang' 被同名字段遮蔽，模块成员将不可达」）——
这种冲突几乎从不合法，报出来没有误伤成本。

## M5【低】三件小摩擦（每个都吃掉一次编译循环）

| # | 摩擦 | 实测 | 建议 |
|---|---|---|---|
| 5a | **内建类型进不了 `use 模块.(…)` 批量导入**：`use SDL3.(…, Thread)` 报"期望类型名" | 2026-10-11 ✓（`Thread` 是内建类型，不是 SDL3 导出的） | 报错说清"X 是内建类型，无需 use"即可（内建类型本来就不该放进来，但报错要指路） |

## M6【高，已修 2026-10-12】C 侧宽值塞进 Value 的**截断面**：`val_int` vs `val_int_safe`

**隐式契约**：`int` 是 **48 位**，而"把 C 的整数塞进 Leno Value"有两条路 ——

```c
// src/include/leno_value.h:183
static inline Value val_int(int64_t n) { return … | ((uint64_t)n & PAYLOAD_MASK); }   // 只留低 48 位，静默
// src/bigint.c:253
Value val_int_safe(int64_t v) { … int48 内给 int、超出给 BigInt … }
```

⇒ 凡是"值域可能超 int32"的地方写了 `val_int((int)…)`，就会**静默截成低 32 位**
（不是 48 位—— `(int)` 先砍一刀 ✗）。它与 `val_int_safe` 的选择**没有编译期护栏**，
所以只能一处一处审（语言层看不出差别：`type()` 一律报 `"int"` ✓）。

**出处（同一天两次踩）**：① LenoTrae 的托盘窗口过程 —— `ffi.callback` 的 64 位实参被截，
lParam 转交回 SDL 后崩在 `SDL3.dll`（10-03~10-11 共 5 次，见 `assert/test_ffi_callback_i64.leno`）；
② 由①引起的全仓审计（2026-10-12）。

**审计结果（本轮修的 6 处）**：

| # | 位置 | 症结 |
|---|---|---|
| A1 | `src/vm/vm.c` `as i64`/`as u64` 四分支 | 64 位目标却 `(int)`：`4294967296.0 as i64` = **0**、`281474976710657 as i64` = **1** |
| A2 | `src/module/ffi/ffi.c` `ffi.sizeof` | `ptr->size` 是 `size_t` ⇒ >2GB 缓冲给错值 |
| A3 | `src/module/files/files.c` `f.tell()` / `f.len()` | `long` 在 LP64 是 64 位 ⇒ >2GB 文件错值（Windows 上 `long` 本就 32 位） |
| A4 | `src/module/types/types.c` `_int(FFI 指针)` | 走 `val_int`（静默截 48 位），与 `ffi.ptr_to_int` 的 `val_int_safe` 口径不一 |
| B1 | `src/module/ffi/ffi.c` `read_uint64` / `read_at(u64)` | 按 INT32 判界 ⇒ 2^32 出来是内部 BigInt，而 `read_int64` 同值给 int（同值不同型 ✗） |
| B2 | `src/module/types/types.c` `_int(bigint)` 单 limb | 同上按 INT32 判界（该值 < 2^32 ⊂ int48，本来就该给 int） |

**回归**：`assert/test_wide_int_convert.leno`（`as i64/u64` × 6、`as i32` 截断不许变宽 × 3、
高地址 `_int(ptr)`、`read_uint64`/`read_int64` 同值同型）。

**没纳入自动套件的三处**（要 >2GB 的缓冲/文件、或语言层造不出的中间态）：A2 / A3 / B2 ——
只靠改动注释与本表钉住 ✓。**未改的**：`as i8/i16/i32/u8/u16/u32` 的截断是**语义本身** ✓。

**建议护城河**：给这类转换加一条 lint/脚本（grep `val_int((int)` 与 `val_int((int64_t)` 白名单），
或在 `val_int` 上加 `__attribute__((deprecated))` 风格的口径提示 —— 不然下次照样漏 ✗。

## M7【中，待评 2026-10-12】指数字面量**只有 enum 成员值那条路能用**（两条路两种结果 ✗）

**实测矩阵**（2026-10-12 ✓）：

| 上下文 | `1e10` / `1.0e10` / `1.5e-3` |
|---|---|
| `float a = 1e10`、`var c = 1e10`、`export const float K = 1e10` | ✗ 报「声明语句后期望换行或 ';'，但同一行出现标识符」 |
| 表达式 / 实参 / 数组字面量（`_str(1.5e3)`、`[1e3, 2.5e2]`） | ✗ 同上（或「期望 ')'」「期望 ',' 或 ']'」） |
| **`enum E { X = 1e10 }`**（同模块 / 跨模块都试过） | **✓ = 10000000000** |

**为什么两条路不一样**：普通表达式走**词法**（`src/lexer.c` 的 `read_number` 只吃
"整数 + 可选小数部分"，没有指数那一段 ✗）；而 enum 成员值走 **const 文本求值器**，
它拿原始文本交给 `strtod`（`strtod` 本来就会吃指数 ✓）⇒ 同一份源码、同一种字面量，
**换个位置结果就不同**：一处报语法错、一处静默算对 ✓。

⚠ 所以这**不是"语言没有这个特性"**（值本身完全可表示），而是**保真度漏洞** ——
与"不再追加特性"那条口径无关（那条管的是**语言特性/语法能力**）。

**建议：支持（补词法）**，理由与成本：

| 项 | 内容 |
|---|---|
| 成本 | `read_number` 里约 10 行：整数/小数部分之后，若 `peek` 是 `e/E`，**且其后（可带一个 `+/-`）紧跟数字** ⇒ 吃掉整段并置 `is_float = 1`（`strtod` 已在用，无需新解析）|
| 下游早就写好了 | `codegen_expr.c` 判"是不是浮点"时**已经**在查 `'.' / 'e' / 'E'`，注释也写着"带符号/小数/**科学计数**" ⇒ 只有词法没接上 |
| 必须排除 | `0x1e10` 仍是十六进制（十六进制数字里本来就有 `e`）⇒ 靠 `is_hex/is_bin` 分流；`1efoo` 必须仍报错 ⇒ 要求"`e` 后必须真跟数字" |
| 不顺手放开 | `1.`（尾点）、`.5`（前导点）、`1_000`（分隔符）**都不动** ⇒ 保持最小面 |
| 反面（不支持）的代价 | 要么把 enum 那条路也改成报错（把能用的地方也弄坏，一致性更差 ✗），要么留着"同字面量两种结果"的洞 ✗；**至少**也得给 `1e10` 一句像样的报错（"不支持指数写法，请写 10000000000.0"），而不是"同一行出现标识符" ✗ |

> 与 `0x1e10` 不被误吃）；选"不支持"⇒ 我把报错文案改准，并**同步把 enum 那条路也收掉**
