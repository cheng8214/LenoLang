## M1【高】`threads.start` 的入口判据是"module 必须为空"，报错文案却说"当前文件" —— ✅ 已修（2026-10-12）

> **结论：限制本身已撤（不是只改文案）** —— 模块函数现在可以直接作线程入口 ✓。
> 实施记录见 `docs/线程并发能力修复追踪.md` 的 TH2；下面的原文保留，用来记住**两层坑**
> （文案与判据不一致、契约查不到）是怎么来的。

**隐式契约**（原源码判据 `src/module/threads/threads.c` 的前置校验）：线程入口函数 `f` 必须
**不属于任何模块**——子 VM 只继承**调用方 VM** 的 globals ⇒ **模块函数进不了线程函数体**。

**实测复现**（LenoMusic 拆分当天 ✓）：把 `bang_menu_worker` 搬进模块 `bang_page.leno` 后：

```
threads.start(): 线程入口必须是**当前文件**的函数 ✗ 收到的是模块 'bangpg' 里的 'bang_menu_worker'
```

两层问题：
- 文案说"**当前文件**"，实现判的是"**入口脚本**"——同一次运行里"当前文件"有好几个
  （每个被 import 的模块都是当前文件之一）⇒ 照着文案改不出对的结果；
- `threads使用指南.md` **查不到这条契约** ⇒ 模块化重构第一次起线程必撞，撞完还看不懂。

**当时的可行解（已实测 ✓，现在仍然能用 ✓）**：宿主把 worker **当函数值**传进模块，模块里存成
`func(...):...` 字段再 `threads.start(字段, …)`——此时 `f` 仍是入口脚本的函数
（module == NULL）✓，子线程 globals 正常 ✓（探针实测 join 回值正确 ✓）。
LenoMusic 三个页面模块全部按此落地 ✓。

**实际修法（2026-10-12 落地，比当年的三条建议更彻底）**：
1. **治本**：协程首帧漏设 `frame->module`（`src/vm/vm.c` 的 `vm_run_coroutine_with_vm`），
   而模块字节码全走 `frame->module` 寻址 ⇒ 补上那一行，模块函数直接可用 ✓
   （连带修好了**主线程 async 协程里调模块函数**的同一处缺口 ✓）；
2. 文案/拦截：`threads.start` 撤掉那条硬拦，只保留"模块尚未初始化"这一种情况的明确报错 ✓；
3. 文档：`threads使用指南.md` 的该节从"限制"改写成"模块函数也能用 + 两个仍然成立的注意点" ✓。

## M2【高】调用"函数类型字段"的返回值是 `any`（声明的返回类型没生效）

**实测复现**（探针，2026-10-11 ✓）：

```leno
// 模块里
pri func():string outdirOf
pri func outdir(): string {
    return outdirOf()        // ✗ error: [类型不匹配] 返回类型不匹配：期望 string，实际 any
}
```

哪怕字段声明是 `func():string`，**通过字段调用**的返回值在类型系统里仍是 `any`
⇒ 必须手动收窄：`var d = outdirOf()  return d as string` ✓（`as` 收窄后可用）。
普通函数调用不受影响（返回类型正常）⇒ 洞只在"函数值当字段/变量再调"这一形态。

**为什么疼**：函数值是本语言"跨模块传行为"的正路（M1 的解法就靠它）⇒ 用得越多，
这个洞越常撞；而且报错只说"实际 any"，看不出"明明声明了返回类型"。

**修法建议**：函数类型字段的调用按声明签名推返回类型（签名就在那，信息是现成的）；
顺带把 M1 的解法场景跑一遍回归（函数值 → threads.start 不受影响 ✓）。

## M3【中】`this` 不存在、自引用叫 `self`——但误用 `this` 的报错不提示

**实测**（2026-10-11 ✓，两支探针）：
- 方法里写 `return this` ⇒ `error: [未定义变量] 未定义的变量: this`（无任何提示）✗；
- 方法里写 `return self` ⇒ **完全可用** ✓：经返回的引用写字段，原对象同步变
  （引用语义，探针 `m.v = 42 ⇒ h.v == 42` ✓）——"返回自己"这件事**做得到** ✓。

所以这条的本质是**报错质量**小项：`this` 是最常见的顺手词，报"未定义变量"却不带
"是否想用 'self'？"（仓里已有同款先例：`contains()` 写错提示 `has()` ✓）。

**修法建议**：未定义变量报错对 `this` / `self` / `This` 这几个高频误拼给纠错提示；
`Leno入门教程.md`（struct 一节）补一句"方法内自引用用 `self`"。

## M5【低】三件小摩擦（每个都吃掉一次编译循环）

| # | 摩擦 | 实测 | 建议 |
|---|---|---|---|
| 5a | **内建类型进不了 `use 模块.(…)` 批量导入**：`use SDL3.(…, Thread)` 报"期望类型名" | 2026-10-11 ✓（`Thread` 是内建类型，不是 SDL3 导出的） | 报错说清"X 是内建类型，无需 use"即可（内建类型本来就不该放进来，但报错要指路） |
| 5b | **保留字撞名无提示**：`Outer alias = o`（`alias` 是关键字）报的是普通语法错，看不出"这是保留字" | 2026-10-11 探针 ✓ | 保留字位置报错统一带一句"'alias' 是保留字，换个名字" |
| 5c | **`pri` 字段逼出成套 setter 样板**：模块工厂没法直填 `pri` 字段 ⇒ 每个都写 `set_xxx`（LenoMusic 两个页面模块各 5+ 个） | 2026-10-11 ✓ | **已决：不修**（2026-10-12 ✓）—— 理由与官方绕法见本节末的决定块；一句话：改用**本 struct 自己的方法**（构造函数 / `init(Dict)` / 析构）把 N 个 setter 收成 1 个 ✓ |

---

#### ✅ M5c 已决：**不修**（2026-10-12）

**结论**：保持 `pri` 的**字段级（struct 级）**边界，**不加** `new T() { field: v, … }` 字面初始化。

**为什么**（按权重排序）：

1. **`pri` 是有实际作用的严格边界，不是多余** —— 实测（2026-10-12）：
   · **同一模块**里的普通函数碰它 ⇒ `'T.x' 是 pri 私有字段…` ✓
   · **兄弟 struct 的方法**碰它 ⇒ 同样被拦 ✓（`struct U { func poke(T t) { t.x = 1 } }`）
   ⇒ 它挡的是"同一模块内、**除本 struct 方法以外**的一切"。放宽成"同模块可见"是**削弱既有封装保证**，
   而收益只是"少写几个 setter" —— 与本仓近两轮"把静默问题往编译期收"（`as` 恒失败报错、`--check` 自报范围、
   M6 的截断审计）方向**相反** ✗
2. **那套 setter 多数不是纯样板**：GUI 控件里 `set_value` 常带 clamp / 标脏 / 重排（如 `Slider.set_value`）
   ⇒ 创建式直填等于**绕过不变量**（`new T() { value: 999 }` 这种越界值最容易写出来 ✗）；
   "可读性收益"与"绕过校验"是同一枚硬币 ✓
3. **字面初始化是新增语法**，且会造出**第二条构造路径**（与"工厂 + init"并存）⇒ 与《Leno语言改进建议》的
   "不再追加特性"、以及本仓反复收敛的"单一事实来源"两条口径都冲突 ✗
4. **关键：痛点有零语言改动的替代** —— 走**结构体自己的方法**（这一族本来就允许直填 `pri` ✓）：

| 场景 | 写法 | 说明 |
|---|---|---|
| 固定初值 | `func T() { x = 7 }` | **构造函数**：`new T()` 后自动跑；**不能有参数** ✓ |
| 参数化初值 | `func init(Dict o) { x = o.get("x", 0) … }` | 一次填完**所有** `pri` 字段 ⇒ 工厂只剩两行 ✓ |
| 释放资源 | `func ~T() { … }` | **析构函数**：与上面成对（不能有参数/返回值 ✓） |

⇒ **N 个 setter → 1 个方法**，而且校验/夹紧留在类型自己的代码里、构造入口唯一 ✓

**实测**（构造函数 + `init(Dict)` + 析构三件套，2026-10-12 ✓）：`make({x: 7, name: "abc"})` ⇒ `7/abc`；
`new` 后 alive = 1、离开作用域回 0 ✓（探针临时文件，已删）。

**落地**：`Leno入门教程.md` 的「构造函数与析构函数」一节新增子节
「`pri` 字段怎么填：工厂**不必**写一套 setter」（三行场景表 + 可跑例子 + 两条"不存在的写法"提示 ✓）；
`语言陷阱速查.md` 新增 **㉜**（用户侧同款 + "struct 方法不需要 export"那条易混点 ✓）。

## M6【高，已修 2026-10-12】C 侧宽值塞进 Value 的**截断面**：`val_int` vs `val_int_safe`

**隐式契约**：`int` 是 **48 位**，而"把 C 的整数塞进 Leno Value"有两条路 ——

```c
// src/include/leno_value.h:183
static inline Value val_int(int64_t n) { return … | ((uint64_t)n & PAYLOAD_MASK); }   // 只留低 48 位，静默
// src/bigint.c:253
Value val_int_safe(int64_t v) { … int48 内给 int、超出给 BigInt … }
```

⇒ 凡是"值域可能超 int32"的地方写了 `val_int((int)…)`，就会**静默截成低 32 位**
（不是 48 位—— `(int)` 先砍一刀 ✗）。它与 `val_int_safe` 的选择**没有编译期护栏**，
所以只能一处一处审（语言层看不出差别：`type()` 一律报 `"int"` ✓）。

**出处（同一天两次踩）**：① LenoTrae 的托盘窗口过程 —— `ffi.callback` 的 64 位实参被截，
lParam 转交回 SDL 后崩在 `SDL3.dll`（10-03~10-11 共 5 次，见 `assert/test_ffi_callback_i64.leno`）；
② 由①引起的全仓审计（2026-10-12）。

**审计结果（本轮修的 6 处）**：

| # | 位置 | 症结 |
|---|---|---|
| A1 | `src/vm/vm.c` `as i64`/`as u64` 四分支 | 64 位目标却 `(int)`：`4294967296.0 as i64` = **0**、`281474976710657 as i64` = **1** |
| A2 | `src/module/ffi/ffi.c` `ffi.sizeof` | `ptr->size` 是 `size_t` ⇒ >2GB 缓冲给错值 |
| A3 | `src/module/files/files.c` `f.tell()` / `f.len()` | `long` 在 LP64 是 64 位 ⇒ >2GB 文件错值（Windows 上 `long` 本就 32 位） |
| A4 | `src/module/types/types.c` `_int(FFI 指针)` | 走 `val_int`（静默截 48 位），与 `ffi.ptr_to_int` 的 `val_int_safe` 口径不一 |
| B1 | `src/module/ffi/ffi.c` `read_uint64` / `read_at(u64)` | 按 INT32 判界 ⇒ 2^32 出来是内部 BigInt，而 `read_int64` 同值给 int（同值不同型 ✗） |
| B2 | `src/module/types/types.c` `_int(bigint)` 单 limb | 同上按 INT32 判界（该值 < 2^32 ⊂ int48，本来就该给 int） |

**回归**：`assert/test_wide_int_convert.leno`（`as i64/u64` × 6、`as i32` 截断不许变宽 × 3、
高地址 `_int(ptr)`、`read_uint64`/`read_int64` 同值同型）。

**没纳入自动套件的三处**（要 >2GB 的缓冲/文件、或语言层造不出的中间态）：A2 / A3 / B2 ——
只靠改动注释与本表钉住 ✓。**未改的**：`as i8/i16/i32/u8/u16/u32` 的截断是**语义本身** ✓。

**建议护城河**：给这类转换加一条 lint/脚本（grep `val_int((int)` 与 `val_int((int64_t)` 白名单），
或在 `val_int` 上加 `__attribute__((deprecated))` 风格的口径提示 —— 不然下次照样漏 ✗。

## M7【中，✅ 已修 2026-10-12】指数字面量曾**只有 enum 成员值那条路能用**（两条路两种结果 ✗）

**实测矩阵**（2026-10-12 ✓）：

| 上下文 | `1e10` / `1.0e10` / `1.5e-3` |
|---|---|
| `float a = 1e10`、`var c = 1e10`、`export const float K = 1e10` | ✗ 报「声明语句后期望换行或 ';'，但同一行出现标识符」 |
| 表达式 / 实参 / 数组字面量（`_str(1.5e3)`、`[1e3, 2.5e2]`） | ✗ 同上（或「期望 ')'」「期望 ',' 或 ']'」） |
| **`enum E { X = 1e10 }`**（同模块 / 跨模块都试过） | **✓ = 10000000000** |

**为什么两条路不一样**：普通表达式走**词法**（`src/lexer.c` 的 `read_number` 只吃
"整数 + 可选小数部分"，没有指数那一段 ✗）；而 enum 成员值走 **const 文本求值器**，
它拿原始文本交给 `strtod`（`strtod` 本来就会吃指数 ✓）⇒ 同一份源码、同一种字面量，
**换个位置结果就不同**：一处报语法错、一处静默算对 ✓。

⚠ 所以这**不是"语言没有这个特性"**（值本身完全可表示），而是**保真度漏洞** ——
与"不再追加特性"那条口径无关（那条管的是**语言特性/语法能力**）。

**建议：支持（补词法）**，理由与成本：

| 项 | 内容 |
|---|---|
| 成本 | `read_number` 里约 10 行：整数/小数部分之后，若 `peek` 是 `e/E`，**且其后（可带一个 `+/-`）紧跟数字** ⇒ 吃掉整段并置 `is_float = 1`（`strtod` 已在用，无需新解析）|
| 下游早就写好了 | `codegen_expr.c` 判"是不是浮点"时**已经**在查 `'.' / 'e' / 'E'`，注释也写着"带符号/小数/**科学计数**" ⇒ 只有词法没接上 |
| 必须排除 | `0x1e10` 仍是十六进制（十六进制数字里本来就有 `e`）⇒ 靠 `is_hex/is_bin` 分流；`1efoo` 必须仍报错 ⇒ 要求"`e` 后必须真跟数字" |
| 不顺手放开 | `1.`（尾点）、`.5`（前导点）、`1_000`（分隔符）**都不动** ⇒ 保持最小面 |
| 反面（不支持）的代价 | 要么把 enum 那条路也改成报错（把能用的地方也弄坏，一致性更差 ✗），要么留着"同字面量两种结果"的洞 ✗；**至少**也得给 `1e10` 一句像样的报错（"不支持指数写法，请写 10000000000.0"），而不是"同一行出现标识符" ✗ |

> 状态：**待你定**（2026-10-12）。选"支持"⇒ 我按上表补词法 + 加断言（`1e10/1.0e10/1.5e-3/2E+8`
> 与 `0x1e10` 不被误吃）；选"不支持"⇒ 我把报错文案改准，并**同步把 enum 那条路也收掉**
> （否则洞还在 ✓）。

#### ✅ 已修（2026-10-12，按"全面支持"落地）

**还多了一条**支持理由（比"别的语言都有"硬）：**输出本来就是科学计数法，输入却读不回来** ——
`print(_str(123456789123456789 as float))` 打印 `1.2345678912345679e+17`（教程 §float 输出规则
写着"大数/极小数自动使用科学计数法 ✓"），可这个**打印出来的形式粘回源码会报语法错** ✗
⇒ 输出不可回读（`_str(x)` 的往返性在同一份文档里被当作卖点，这里却是断的 ✓）。

**改动**：`src/lexer.c` 的 `read_number` 里补"指数段"（约 20 行含注释；`strtod` 本来就会解析，
所以只是把 token 的范围吃全 ✓），三条护栏：

| 护栏 | 内容 | 回归 |
|---|---|---|
| ① 只认十进制 | `0x1E10` 的 `E` 是十六进制数字 ⇒ 必须仍是整数 **7696**；`0b1e10` 也不吃指数 | `assert/test_exp_literal.leno` ②⑤ |
| ② `e/E` 后必须**真跟数字**（可带一个 `+/-`） | `1efoo` / `1e` / `1e+` 保持报错（不把标识符悄悄吞掉 ✓） | 该文件 ④ 的五个负例 |
| ③ 只吃**一次**指数 | `1e1e1` = `1e1` + 标识符 `e1` ⇒ 报错 ✓ | 同上 |

**语义口径**：`1e10` 是 **float**（与 C/JS 一致 ✓，`type()` 报 `"float"`）；而 **enum 成员值**
仍按整数求值（`type(E.X)` = `"int"` ✓，与"枚举成员是整数"的既有口径一致 ✓）——两条路**同值**。

**回归**：`assert/test_exp_literal.leno`（普通上下文 6 个字面量 + 十六进制护栏 + enum 同值 +
五个负例 + 极大/极小量级）。套件 441/441 ✓。文档同步：`Leno入门教程.md` 的 float 输出规则处
补了"字面量也支持指数写法"✓。

## M8【中，✅ 已定口径 2026-10-12】`as` 里的位宽类型名是「转换指令」，不是「可声明的类型」

**疑点从哪来**：审计 M6 时自己踩到 —— `i64/u64/…` 明明是 **C 布局类型**
（`i64 x = 5` 明确报「C 布局类型 'i64' 不能用于变量声明…」），可 `as i64` / `as u8` / `as i32`
**却能编译** ⇒ 看着像"闸门漏了一处"（当时的结论就是"收口它"✗）。

**查证后的事实**（推翻了"收口"这个结论）：

| 事实 | 证据 |
|---|---|
| `as u8 / as i32` 是**早就文档化**的用法 | `Leno入门教程.md` 的「C 窄类型截断（显式丢弃高位）」一节，4 个例子（`255 as u8`、`-1 as u8`、`0x123456789 as i32`…）|
| 一族里只有 `as i64/u64` 没写进文档，且它当时**有 bug** | `vm_as_cast` 写 `(int)` ⇒ 静默截 32 位（已修，见 M6 的 A1 ✓）|
| `as` 的**结果**是 Leno `int`，没把 C 布局类型引进语言层 | `type(4294967296.0 as i64)` = `"int"` ✓ ⇒ "不能用于声明"与"能用于 as"**并不矛盾** |
| 函数式替代**不完整** | 只有 `_int32 / _uint32 / _int64 / _uint64 / _uint8 / _byte`；`_int8 / _int16 / _uint16` **没有** ⇒ 收口会让"8 位有符号 / 16 位截断"彻底没入口 ✗ |

**结论（2026-10-12 拍板"按我的想法来"）**：**保留这一族 `as` 指令**，把它**文档化**（教程那节补
`as i64/u64` + "指令 vs 声明"边界说明 ✓），**不做收口**。理由按权重：
① 收口要砍掉现有能力（`as i8/i16/u16` 无替代）；② 收口要改教程里已文档化的例子（破坏文档面）；
③ 保留的代价只是"教程补几行"。

**回归**：`assert/test_wide_int_convert.leno` 的第 ⑤ 组 —— 钉住这条边界："`as i64` 能用 ✓ +
结果 `type` 仍是 `int` ✓ + `i64 x = 5` 仍报错 ✓"，两边都不许被后来者"顺手统一"掉 ✗。

## M9【中，✅ 已修 2026-10-12】限定名（`模块.类型`）不能做类型标注 —— 但**只有 5 个位置**会这么报，其余位置喷一串看不懂的语法错误

**摩擦本体**：类型名只有两个来源 —— **内置**与 **`use` 导入** ✓。`d.DirEntry` 这种**限定名**
在**表达式**位置合法（`new d.DirEntry()` / `d.walk()` ✓），在**类型**位置**一律不合法** ✓。

**实测复现（2026-10-12，用户问 `import dirs as d` 要不要 `use d.DirEntry` 时顺出来的）**：

```leno
import dirs as d

func show(d.DirEntry e): string {     // ← 形参类型位置
    return e.root
}
```

报 **8 条 7 种**语法错误，第一条是 `期望参数名` ✗ —— 全都在指向标点：

```
error: [语法错误] 期望参数名
error: [语法错误] 期望 ')'
error: [语法错误] 期望 '{'
error: [语法错误] 期望表达式（重复 2 次）
error: [语法错误] 字典解构期望字符串键名
error: [语法错误] 期望 '}' 结束字典解构形状
error: [语法错误] 解构声明期望 '(' 开始变量名列表
```

**没有一条**指向真因（"这里不能写限定名"）✗ ⇒ 写的人会去查参数名 / 括号（实测就是这样 ✓）。

**根因**：这道检查**早就存在** —— `parser_reject_module_qualified_type()`
（`src/parser/parser_func.c`，2026-09-16 为 `is` / `as` 的**静默 misparse** 加的 ✓），
文案本来就是"不支持带模块前缀的类型名（如 `a.Point`）：请先 `use a.Point`，然后直接写 `Point`" ✓
—— **但只在 5 个位置显式调用** ✗（`is` / `as` 两处 + 局部声明三处）⇒
**函数形参 / 返回类型 / struct 字段 / 泛型实参**这些位置全都漏了 ✗。

**修法（单一收口）**：把这道检查挪进 **`parse_type_internal()` 的出口**
（`src/parser/parser_func.c`）—— 凡走类型解析的位置一次覆盖 ✓（含 `Ptr[T]` / `Array[T]`
的元素、泛型实参 ✓）。返回 NULL = 解析失败（既有调用点都有 NULL 分支 ✓）；
错误由该函数报出、`t` 也由它释放 ✓（别在调用点再 free ✗）。原有的 5 处显式调用**保留**
（第二道保险：收到 NULL 会立刻返回 0，**不会重复报**✓）。

**判据（`assert/test_diag_static_errors.leno` 的 M9 组，三条）**：限定名分别做
**形参类型 / struct 字段类型 / 返回类型** ⇒ 首条报错都是「不支持带模块前缀的类型名」✓。

**⚠ 收口当天踩的坑（值得记住 —— 单一收口会撞上"猜测式解析"）**

把检查放进 `parse_type_internal` 之后，**套件立刻红了 4 个用例** ✗：
`test_enum_int_compat` / `test_plane_war_headless` / `test_popup_capture` / `test_sdl_capture`。
根因不在这些用例，而在**解析器有一处会"先猜后回退"**：

```leno
a[Slot.ONE]        // 下标访问 —— 但解析器会先在 `[` 处**试着按泛型类型参数解析** ✗
colors[SDL3.X]     // 同理
```

`src/parser/parser_expr.c` 的泛型调用候选路径（`is_generic_call_candidate` 那段）会
**保存 `saved_lex`、试着 `parse_type`、失败就回退词法器**——**它回滚了词法器，却没回滚已报的诊断** ✗
⇒ 我新加的检查在"猜测"里报了错，而这次猜测最后被判定"不是类型"（真身是下标）⇒ 假报错 ✗。

**修法（用现成机制，口径对齐枚举求值器）**：给这段猜测包上**静默段**
（`error_silence_begin()` / `error_silence_end()`，`src/error.c` ✓ 本来是给符号表扫描器
"借真解析器求值 enum 表达式"用的 ✓），并照同一条口径判定：
**静默段内只要报过任何错 ⇒ 这次猜测不可信**（`if (silenced > 0) parse_ok = 0;`）⇒ 走回退 ✓。

> 教训：**任何"先猜后回退"的解析路径，都必须连诊断一起回滚** ✗。
> 这是本仓的既有陷阱（不只影响 M9）：以前只有"返回 NULL"被当作猜测失败，
> 而"报错后仍返回可用值"的检查一旦加进来，就会从猜测里漏出假报错 ✓。

**有意不改的（留档）**：紧跟其后的**级联**仍是既有的"签名解析失败后继续跑"的恢复噪声 ✓
（改之前同样是 8 条，只是第一条是 `期望参数名` ✗）。要把级联也收敛，得让**函数签名解析**
在失败后 resync 到 `)` / `{` —— 那是**通用错误恢复**的改动（影响面覆盖所有畸形签名 ✓），
列为独立议题，不塞进本条 ✓。

**同题的另一半（用户最初的问题）**：`use d.(DirEntry)` 与 `use dirs.DirEntry` 两种写法**都行** ✓；
**不 `use` 也能用** —— `var ws = d.walk(".")` 后直接 `e.root` / `e.files`（`walk` 的返回规格是
`Array[DirEntry]`，字段类型编译期已知 ✓）；**只有要写类型名标注时**才需要 `use` ✓。
文档面已写在 `docs/module_dirs.md` ✓。
