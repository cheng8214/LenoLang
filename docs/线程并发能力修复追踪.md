## 一、现状快照（模型是什么，别改什么）

| 项 | 事实 | 锚点 |
|---|---|---|
| 线程模型 | 每线程**独立 VM**（独立 stack / frames / globals / **独立 GC 堆**），OS 真线程，**无 GIL** | `src/object/object_thread.c:177-527` `thread_entry_point`（`:286` `gc_init()`） |
| 通信 | `Channel`（Go 式 buffered/unbuffered），**传值即深拷贝** | `src/object/object_thread.c:784-850`；`src/module/threads/threads.c:54-109` |
| 跨线程值的**唯一闸门** | `value_clone_for_channel()` —— 白名单之外一律报错 | `src/object/object_thread.c:74-156` |
| GC | 分代标记-清除，**GC 状态 `THREAD_LOCAL`**；共享对象（thread/channel）扫描时加锁，非 STW | `src/gc.c:59`、`:775-816` |
| 协程 | `async`/`await` 是**语言关键字**，单 VM 协作式事件循环（`g_event_loop` 是**进程级单例**） | `src/coroutine.c:14,239-304` |
| 两模型关系 | **禁止混用**（threads 与 async 不互相调度） | `docs/threads使用指南.md:561-599` |

**结论（本文档前提）**：模型是对的，问题不在"有没有真并行"，而在**能用什么数据**和**能不能封装**。

## 三、明确**不做**（避免反复讨论）

| 不做的事 | 为什么 |
|---|---|
| 共享堆 / 拆掉线程堆隔离 | 要重写 GC 与所有写屏障，收益为零：模型的价值就在隔离 |
| `threads.Mutex` / `atomic` / `Semaphore` | 立项前提是"堆隔离下没有可被两线程同时访问的普通对象"，**该前提 2026-10-20 被实测推翻**（入口脚本的全局 `Array`/`Dict` 是跨堆共享的，见 TH8）。但**结论仍是"不做锁"**：共享对象挂在创建者堆上，子线程写它会走**自己的写屏障**去改别人的堆 ⇒ 锁能挡逻辑竞态，挡不住 `0xC0000374` 堆损坏。正确解法是 ① TH8 深拷贝消除隐式共享 ② 真要共享可变状态就走 `Channel` 单点化，或用 `threads.local_*` 每线程一份 |
| 让模块 globals 按线程深拷贝隔离（旧"方案 C"） | `ObjModule` 由 `loaded_modules` 全局缓存共享，强行隔离破坏模块缓存一致性 + 模块全局语义 + GC 的 module mark 逻辑（见 `多线程struct与模块全局变量问题记录.md` §五） |
| 统一 threads 与 async 的调度器 | 大工程；当前两者定位清晰（算得慢 / 等得久），先各自补短板 |

> 附带纪律：**`value_clone_for_channel()` 是全模型正确性的唯一闸门**。每加一个可克隆类型，
> 必须同时加"拒绝面"（不支持的类型明确报错，不许静默传引用）+ 一条回归用例。
> 历史出血点：dict 的 **key** 漏克隆（`object_thread.c:110-139`）、channel 重入克隆（`:836-840`）。

## 四、逐条详述

### TH1（P0）struct 实例跨 Channel 传值 —— ✅ 已修（2026-10-12，工作区未提交）

**症状**
- `ch.send(point)` 报「不能跨线程传递此类型」（`object_thread.c` 的 default 分支）。
- 连带症状：想让并发库跑起来，只能把 struct **拍平成 `Array[string]`** 在接收方手工重建
  ⇒ 写得越"Leno 风格"（struct 化），越难并发。

**根因（证据）**
- `value_clone_for_channel()` 白名单只有 `null/int/float/bool/string/Array/Dict/Channel`，
  没有 `OBJ_STRUCT` ⇒ 走 default 报错。
- 另有**一道编译期拦截**（`src/semantic/semantic_type_utils.c` 的
  `semantic_check_cross_thread_args`）：静态类型确定为 struct 的实参**直接报错** ✗
  —— 只改运行期不够，这道一并撤（否则"改了运行期也过不去"）。

**实施前查清的关键事实（原计划里列成"必须回答"的，答案如下）**
1. **克隆发生在两侧**：`channel_send` 先把值克隆进 buffer（发送方堆 ✓），`channel_receive`
   取走前**再克隆一次**（接收方堆 ✓）。⇒ struct 只要走同一个 `value_clone_for_channel`，
   **两个调用点一行都不用改** ✓（与 `Array`/`Dict` 完全同口径）。
2. **写屏障**：struct 字段写入的唯一入口是 `struct_set_field()`（`leno_value.h`，内含
   `gc_write_barrier`）⇒ 克隆时走它，**不要直写** `field_values[i]`。
3. **分配方式**：`struct_instance_new(def)` 一次分配"对象头 + 内联字段数组"（`fields_inline=1`）
   ⇒ 克隆必须走这个构造函数，不能自己 `gc_alloc`。
4. GC 会 mark struct 的 `def` / 全部字段 / `declared_face`（`src/gc.c` 的 `case OBJ_STRUCT`）
   ⇒ 带上 face 声明与泛型实参是安全的。

**落地（工作区改动）**
- `src/object/object_thread.c`：克隆闸门拆成**深度感知**的 `channel_clone_value(val, depth)`
  （对外 `value_clone_for_channel` 符号不变 ✓），新增 `channel_clone_struct`：
  递归同一套克隆规则、`CHANNEL_CLONE_MAX_DEPTH 64` 防环、face 声明与泛型实参一并带上、
  不可克隆类型统一走 `channel_clone_reject`（带 `g_channel_clone_ctx` 指认"结构体.字段"）。
- `src/semantic/semantic_type_utils.c`：拦截名单**只留 `TYPE_CSTRUCT`**（struct / face 放行 ✓）。
- `assert/test_channel_struct.leno`（新增）：①深拷贝语义 ②struct 过 Channel 往返（3 条输入 / 3 条回包）
  ③嵌套 struct ④拒绝面（cstruct 字段 ⇒ 报错指认字段，两条通道各一条判据）
  ⑤自引用（环）⇒ 报「嵌套层数超过 64」而不是挂死。
- `assert/test_diag_static_errors.leno`：原来钉"struct 必须编译期报错"的两条**翻了案**
  （改 `expect_ok`），另加一条 cstruct 仍编译期拦 ✓。
- 文档：`语言陷阱速查.md`（§一 ② / §三 ②）、`module_threads_api.md`、`threads使用指南.md`。

**验收（实测）**
- 套件：`443 passed / 0 failed`（新增 1 条用例 ⇒ 442 → 443）。
- 端到端：`threads.start(worker, p)` 与 Channel 往返都能拿到字段值；子线程改字段主线程**看不见**
  （深拷贝语义 ✓）。

**顺带查实的三件事（都写进文档了）**
- ⚠ **`for A : B` 是闭区间**：`for 0 : 3` 跑 **4** 轮（实测）。循环次数若与消息条数对不上，
  `receive()` 永久阻塞 ⇒ 表现是"卡死且无输出"（stdout 被块缓冲，中间 print 看不到 ✓）。
- ⚠ **同一条通道"边收边发"会把自己发出去的消息收回来**（通道不区分发送者）⇒ 收发要分两条通道。
- ✅ **`assert/fixture_thread_cstruct_crash.leno` 的崩溃已不复现**（2026-10-12 复核 3/3 exit 0）
  —— 历史记录见该文件头部（不进套件的原因也写在那儿）。

**端到端（可选，未做）**：LenoWeb 的 `test_thread_parse.leno` 可改为**直接传 `HtmlNode`**。

### TH2（P1）线程入口允许模块函数 —— ✅ 已修（2026-10-12，工作区未提交）

**症状**
- `threads.start(模块里的函数)` 被前置拦截报错（原 `src/module/threads/threads.c` 的守卫）。
- 绕法只能把函数**当值**从宿主传进模块 ⇒ **库自己无法封装并发**
  （LenoWeb 想自开线程池、LenoMusic 想自管后台解码，都做不到）。

**根因（比原计划写的窄得多 —— 这轮勘察的最大收获）**
- 原判据 `closure->function->module != NULL` 直接拦，理由写的是"子 VM 只继承调用方 globals +
  `current_module_frame = NULL` ⇒ 模块函数找不到本模块的 globals"。
- **实际**：模块字节码（`OP_GET_MODULE_VAR` / `OP_SET_MODULE_VAR` / `OP_GET_MODULE_FUNC` /
  `OP_DEFINE_MODULE_FUNC`）寻址用的是 **`frame->module`**，**不读** `current_module_frame`
  （见 `src/vm/vminc/run/10_vars_module.inc` 四处 `ObjModule* module = (ObjModule*)frame->module`）。
  而三条 call 路径（`vm_call.inc` 的 `call` / `call_no_type_check` / `call_reg`）都设了
  `frame->module = func->module`，**唯独协程首帧漏了这一行**
  （`src/vm/vm.c` 的 `vm_run_coroutine_with_vm`）⇒ 进函数体后第一条模块符号指令报
  「不在模块上下文中」。
- ⇒ **不需要"子 VM 按需加载模块"**（原计划的高风险方案）：模块对象由**进程级** `loaded_modules`
  缓存共享（`src/module_loader.c` 的 `static LoadedModules`，非 THREAD_LOCAL），
  init_chunk 主线程已跑过 ⇒ 子线程直接用共享的 `ObjModule` 就对 ✓。
  `child_vm.globals`（入口脚本 globals）的继承与模块函数无关，不必动 ✓。

**落地（两行改动 + 用例）**
- `src/vm/vm.c`：协程首帧补 `frame->module = func->module;`（入口脚本函数 `module == NULL`
  ⇒ no-op ✓）。**顺带修好主线程 async 协程里调模块函数**的同一处缺口 ✓。
- `src/module/threads/threads.c`：撤掉那条硬拦，改为**只拦一种情况** —— 入口函数所属模块
  **尚未初始化**（不在入口脚本 import 链上 ⇒ globals 全空）时明确报错。
- `assert/test_threads_module_entry.leno` + `assert/helpers/th2_mod.leno`（新增）：①入口脚本直接
  `threads.start(模块函数)` ②多参数 + 循环 ③模块函数里再调同模块函数 ④**模块自己开线程跑自己的
  函数**（TH2 的真正价值）⑤模块级可变状态**跨线程共享**（把已知口径钉成显式契约）。
- `assert/test_diag_warnings.leno`：E6/M1 那条"必须抛错"翻成 `expect_ok` ✓。
- 文档：`threads使用指南.md`（该节从"限制"改写为"模块函数也能用 + 两个注意点"）、
  `module_threads_api.md`（入口形态矩阵第③条翻案）、`语言摩擦与隐式契约清单.md`（M1 标已修）。

**验收（实测）**
- `assert/test_threads_module_entry.leno` 全过；`test_diag_warnings.leno` 全过；套件全绿。
- 端到端：模块内 `threads.start(_sum_worker, …)` ×2 + `join()` ⇒ 正确（`parallel_sum(0,1,3) == 6`）。

**遗留（不影响功能，只是注释过期）**
- `build/leno_module/LenoWeb/`（README / `web_net.leno` 的 curl_multi 理由 / 4 个测试注释）与
  `leno_gui/应用/电脑清理大师/test/test_clean_pipeline.leno`（已就地改 ✓）里还写着
  "库函数自己起不了线程" —— **设计结论不变**（curl_multi 仍是对的选择），但理由那句已经不准，
  下次动那些文件时顺手改。

### TH3（P1）并行原语 —— ✅ 已修（2026-10-12，工作区未提交）

**症状**
- 写"4 线程分块排序"要手写 Channel 编排 + 手动 `join()`。
- 没有 `WaitGroup` / `parallelFor` / `map` ⇒ 每个用户都在重复写同一套样板。

**设计取向（与原计划的差异，值得记住）**
- 原计划写的是 `threads.WaitGroup`（`add/done/wait`）—— 那需要**新的对象类型**（`ObjWaitGroup` +
  方法表 + 可能还要新关键字/TypeKind），与语言"够用就行、不再追加特性"的一贯取向相悖。
- 改成**三个普通模块函数**，零类型系统改动：
  | 原语 | 语义 | 回调形态 | 返回 |
  |---|---|---|---|
  | `threads.join_all(Array[Thread])` | "等一组线程"（WaitGroup 的等价物） | — | `int` |
  | `threads.parallel_for(n, f)` | 分 n 份并行（`f(index)`，index = 0..n-1），等全部结束 | `f(int)` | `int` |
  | `threads.map(arr, f)` | 并行 map，结果按输入顺序收回 | `f(item, index)` | `Array[回调返回]` |
- `map` 的返回类型**直接复用** `arrays.map` 那份原生规格 `NATIVE_T_ARR_CB_RET1`
  （`Array[第 1 实参回调的返回]`）⇒ 静态类型精确（`Array[int] doubled = threads.map(...)` ✓）。
- `map` 的回调形态与 `arrays.map` **同口径**（`f(item, index)` 两个形参）—— 用户已有的认知可迁移 ✓。
- ⚠ **实现取舍**：`map` 是"**每元素一个线程**"（线程数 = 元素数）—— 因为**闭包不能作为参数跨线程传**
  （`value_clone_for_channel` 不认函数值），所以"分块 + 子线程循环调 f"这条路走不通；
  要分块只能用 `parallel_for`。代价已写进 API 文档 ✓。
- 原计划里那条"模块内调用时回调能不能跑"的顾虑，**已被 TH2 顺带解决** ✓（模块函数现在能作入口）。

**落地（工作区改动）**
- `src/module/threads/threads.c`：
  - 入口校验收成**一处** `threads_check_entry(closure, got_args, who)`（`start` / `parallel_for` /
    `map` 共用，避免三份拷贝各自漂移 ✓）；
  - 新增 `threads_join_all` / `threads_parallel_for` / `threads_map` 与三条模块方法注册。

### TH7（P3）FFI 回调与多外部线程 —— ✅ 调研完成（2026-10-12，工作区未提交）

**原担心（写这条时的认知）**
- `ffi.callback` 的回调在**外部线程**（Windows 线程池 / C 库工作线程）上跑，而它们与主 VM
  **共享同一个执行环境**（同一套 stack / `sp` / `frame_cnt`）⇒ 多外部线程**并发**回调
  会互相覆盖 VM 栈 ✗。

**调研结论：这个担心已经被解决（比这条立项时更早 —— 编组机制早就落地了）**

`src/module/ffi/ffi.c` 的 `callback_dispatch()` 按**调用方是谁**分两条路：

| 调用方 | 路径 | 为什么安全 |
|---|---|---|
| 主线程 / **Leno 语言线程** | `callback_dispatch_direct` —— 直接在该线程自己的 VM 上执行 | 每个 Leno 线程一套栈与 GC ✓ ⇒ 并发回调各跑各的 ✓ |
| **无 VM 的外部 C 线程**（线程池 / SDL3 对话框线程…） | `callback_dispatch_marshal` —— 参数快照入队，**阻塞该外部线程**，主线程 `ffi.pump_callbacks()` 取出、在**同一个 VM** 上逐个执行、完成后唤醒 | 多个外部线程 ⇒ **串行化到主线程** ✓ 不存在"同时写同一个 VM 栈" ✗ |

⇒ 原计划里讨论的两个方向（"一律异步排队"vs"每外部线程一个子 VM"）**都不需要** ✓：
现在这条设计同时保住了**同步语义**（外部线程阻塞等结果 ⇒ `qsort` 那类"必须同步返回"的 API 可用 ✓）
和**栈安全** ✓。

**本轮实际做的两件事**
1. **订正文档**（`threads使用指南.md` 的「FFI 回调与原生线程的关系」一节）：
   旧版写"多外部线程并发调用 ⇒ 全局变量竞态 / GC 冲突 / `sp`·`frame_cnt` 相互覆盖" ✗
   —— 那是**编组机制落地之前**的描述 ⇒ 已改写为上面这张两条路的表，并把**仍然成立**的三条约束
   写清楚（① 主线程不泵就死锁 ⇒ 别在主线程阻塞等外部线程；② 编组解决"栈不共享"、
   不解决"数据不共享"（模块级 `var` 依旧共享 ✓）；③ 别在回调里起线程/做重活 ✓）。
2. **修掉一条静默错值**（`ffi.c` 的 `callback_dispatch_marshal`）：
   队列满（`MAX_PENDING_CALLBACKS = 64` 个外部线程**同时**在回调里等主线程）时，
   原代码是"直接 `return result`"—— 而 `result = {0}` ⇒ **静默返回全 0** ✗。
   对比较函数来说 0 = "相等" ⇒ `qsort` 之类会**静默给出错序** ✗（正是本仓最想消灭的那类错）。
   改成**等一个空位**（`platform_cond_wait(&g_pending_cond, …)`，空位由回调完成后 signal ✓）。
   ⚠ 这不会引入新失败模式：本路径本来就要求"主线程会泵"（否则下面等 `completed` 同样永久阻塞 ✓）。
   ⚠ **未覆盖自动化测试**：造 64 个无 VM 的外部线程需要 C 侧线程池
   （路子见 `examples/ffi/test_callback_threadpool.leno`）⇒ 本轮只做代码收口 + 注释留档 ✓。

**仍开放的一条（未拍板，暂不动）**
- 回调闭包**跨 VM** 执行的风险：若 VM A 注册的回调被 **VM B（另一个 Leno 线程）** 触发，
  走的是"直接执行"路 ⇒ 在 B 的 VM 上跑 A 堆上的闭包（跨堆访问 ✗）。
  实测能否触发未验证（常见用法是"谁注册谁触发"✓）。要收口得给回调登记"所属 VM"并在
  不一致时改走编组 —— 属独立议题 ✓。

### TH8（P0）入口脚本的全局**对象**是跨线程共享的 —— ✅ 已修（2026-10-20）

**症状（2026-10-20 实测）**

```leno
var arr = [1, 2, 3]
var box = {n: 0}
func w(): string {
    arr.add(4)
    box.set("n", 99)
    return "子: arr.len=" + _str(arr.len()) + " box.n=" + _str(box.get("n", -1))
}
main() {
    arr = [1, 2, 3]; box = {n: 0}
    print(threads.start(w).join())   // 子: arr.len=4 box.n=99
    print("主: arr.len=" + _str(arr.len()) + " box.n=" + _str(box.get("n", -1)))
                                     // 主: arr.len=4 box.n=99  ← 被改到了
}
```

**根因**：`src/object/object_thread.c:354-378` 复制 `vm.globals` 时**逐个 Value 浅拷贝**，
只有标量是"独立副本"，对象（string / Array / Dict / struct / module）全是指针共享。
代码注释自己写着"其他对象类型，浅拷贝 Value（对象本身共享）"—— 是文档（旧版）写错了。

**危害**：子线程写共享对象时，写屏障记在**子线程的**记忆集里，而对象挂在**主线程堆**上
⇒ 两个堆对同一块内存的 mark/释放状态不一致 ⇒ 偶发 `0xC0000374` 堆损坏（与实例三十五一类）。

**方案（已落地）**：把"数据对象"改成 `value_clone_for_channel()` 深克隆，只读元数据 / 资源句柄仍共享。

| 类型 | 处理 | 为什么 |
|---|---|---|
| 标量 / `string` / `Array` / `Dict` / `struct` / **闭包** | **克隆进子线程堆** | 可变（或可被回收）⇒ 必须各一份 |
| `module` / `function` / `native` / `cstruct_def` | 共享 | 只读元数据；`loaded_modules` 是进程级缓存，不能复制 |
| `socket` / `file` / `ffi` 句柄 / `Ptr` | 共享 | 克隆出来是**假句柄**（TH1/TH8 的拒绝面） |
| `Channel` / `Thread` | 共享 | 本来就是引用语义 |

**实现要点（踩过的坑）**：
1. **克隆位置必须挪到 `gc_init()` 之后** —— 原代码在 395 行附近拷 globals，而 GC 在 440 行才初始化，
   克隆要 `gc_alloc` ⇒ 提前做会用到未初始化的 GC。现在：原处只 malloc 槽位 + 填 null，
   克隆放到 struct 定义导入之后（`object_thread.c` 的 TH8 段）。
2. **`current_exec_vm` 要在克隆期间指向子线程 VM** —— 否则克隆失败时 `native_throw_error`
   会把异常写进**主 VM**（`native.c:2231` 取 `current_exec_vm`，子线程此时还没设），
   主线程随后莫名其妙抛错。
3. 克隆失败（容器里藏 `Ptr` / `cstruct`）⇒ **回退成共享旧值 + 清异常**，不让一个全局变量把线程搞挂。
4. `gc_set_enabled(0)` 包住克隆：`saved_globals` 是 malloc 数组、不在 GC 根里。

- 验收：`assert/test_threads_globals.leno`（新，6 条断言）：子线程 `arr.add(4)` / `box.set("n",99)` /
  `cfg.x=7` 后**主线程仍是 3 / 0 / 1**；标量本来各一份；嵌套 Dict 里的 Array 也独立；
  module 对象仍可调。全量断言 **465/0**，LenoHTTP 线程池 / LenoWeb `test_thread_http` 均通过。
- 行为变更（有意）：**子线程改全局对象主线程再也看不见**。要把结果带回来请用 `join()` 返回值或 Channel。
- 代价（实测，`build\tmp_probe_clone_cost.leno`）：空全局起 8 个线程 2.3ms；把全局换成 **10 万元素 Array**
  后起 8 个 2.7ms、64 个 15.3ms（对照：空全局 64 个 12.5ms）⇒ 每万元素约 0.04ms，可接受。
  ⚠ 但**几十 MB 的全局配置表 × 几十条线程**仍然不划算 ⇒ 这种数据应该放**模块级只读 `var`**（共享不复制）。

### TH9（P1）`join()` 没有超时 —— ✅ 已修（2026-10-20）

**症状**：`Thread.join()` 是无限 `cond_wait`（`object_thread.c:823-827`）。worker 卡在阻塞 IO
（`recv` / 文件读 / FFI 调用）时，主线程只能一直等；`state()` 是快照、不能代替等待。

**方案**：新增 `t.join_for(timeout_ms): bool`
- `true` = 线程已结束（收尾逻辑与 `join()` 完全一致：克隆 result、释放子线程堆、抛线程异常）
- `false` = 超时，**状态不变**（线程继续跑，之后还能再 `join()` 取结果）
- 实现：把 `thread_join` 拆成 `thread_wait(t, timeout_ms)` + `thread_reap(t)`；
  `platform_cond_timedwait` 已存在（Windows / Linux 都有），零平台改动
- 成本：约 40 行 C + 1 处方法注册 + 文档；风险低（纯加法，不改 `join` 语义）

**验收**：`assert/test_threads_join_for.leno`（新）：300ms 的线程 → `join_for(50)` 得 `false`、
`state()=="running"`；再 `join_for(2000)` 得 `true`，`join()` 仍能拿到返回值。

（`object_thread.c:177-262`）。直接后果：
- 主线程建好的 `app`（路由表 = handler 闭包）不能传给 worker ⇒ LenoHTTP 只能"每线程 buildApp"；
- 不能把"一组回调"交给线程池；`threads.map` 只能传纯数据。

**方案**：clone 里加 `OBJ_CLOSURE` 分支 —— `function` 是**只读字节码**（进程级，可共享），
`upvalue` 递归 clone 成 **closed upvalue**（`uv->location = &uv->closed`，与 `thread_entry_point`
重建入口闭包的做法一致，见 `object_thread.c:473-492`）；复用已有的 `CHANNEL_CLONE_MAX_DEPTH = 64`
防循环。`OBJ_FUNCTION`（无 upvalue）同理包一层 closure。
- 成本：约 60-100 行；风险中等（upvalue 链、闭包互相捕获的环）⇒ 单独一轮 + 专门用例
- 验收：`threads.start(f, 42)` 传一个捕获了外部变量的闭包；Channel 里传闭包后子线程能调用；
  递归捕获环不挂死（报"嵌套层数超过 64"）

**实测（2026-10-20）**：`assert\test_channel_closure.leno` 全过 ——
① 闭包捕获 main 的局部变量 `base=100`，经 Channel 传子线程调用 ⇒ `103`；
② `Dict` 里装闭包作 `threads.start` 实参 ⇒ 子线程调用 `207`（回环走的是同一 clone 分支）；
③ 闭包捕获闭包 ⇒ `7`；④ 闭包 ↔ Dict 互相持有的环 ⇒ 报「嵌套层数超过 64」不挂死。
文档同步：`module_threads_api.md` / `threads使用指南.md` 的"能传什么"表。
> 后续可选优化：LenoHTTP 的 `serveWorkers` 现在**可以把主线程建好的 app 直接传给 worker**，
> 不再强制每线程 `buildApp()`（当前保留旧用法，行为不变）。

### TH11（P1）线程诊断：`current_id()` + `error()` —— ✅ 已修（2026-10-20）

**症状**
1. 没有线程 id ⇒ 多 worker 的日志分不清是谁打的（LenoHTTP 的 `[http]` 日志只能靠内容猜）。
2. fire-and-forget 的线程抛异常 ⇒ 错误只写进 `thread_obj->error_msg`，**没人 join 就永远看不到**
   （表现是"任务静默没结果"）。
3. **顺带发现的真 bug**：`throw "xxx"` 会被 `wrap_string_exception()` 包成
   `{msg, line, file, stack}`（`vm_exception.inc:295`）⇒ 异常值是 **Dict**；
   而 `thread_entry_point` 的错误提取只认 `OBJ_STRING` ⇒ **所有**用户 `throw "..."` 都被写成
   「非字符串异常（对象类型 2）—— 常见于进入函数体之前就失败（如入口函数所属模块未加载）」✗
   —— 把人往"模块没加载"上引，和 B13 那条是同一种坑。

**落地**
- `src/module/threads/threads.c`：`threads.current_id() -> int`（`platform_thread_self()`）、
  `Thread.error() -> string`（mutex 内取 `error_msg`，没有错误给空串）
- `src/object/object_thread.c`：错误提取加 `OBJ_DICT` 分支，读 `msg` 字段（与
  `exception_msg_dup()` 同口径）
- 用例 `assert\test_threads_diag.leno`：主/子线程 id 不同；正常线程 `error()==""`；
  出错线程 `error()` 含 `boom-in-thread`，且 `join()` 抛的文案也带原文

> ⚠ `current_id()` 只用于诊断：OS 会复用线程 id，别拿它做业务判断。

### TH12（P2）线程池配方（任务 = 闭包）—— ✅ 已落地为示例（2026-10-20）

TH10 之前"闭包不能跨线程"⇒ 任务只能写成"具名函数 + 一堆参数"，通用线程池很别扭；
现在任务可以直接是闭包：`examples/threads/pool.leno`（约 70 行，纯 Leno）。

**结构**：`tasks`（闭包队列）+ `results`（`{ok, value}` 队列）+ N 个 worker 线程；
worker 取出 → 在本线程执行 → 回传 → 循环；停机发 N 个 `null` 再 `join`。

**三个要点**（示例里都写了注释）：
1. **背压**：两个 Channel 都有容量，满了 `send` 阻塞 ⇒ 自然限流，不会无限堆任务；
2. **异常不丢**：worker 里 `try/catch`，把错误作为结果回传（线程池最怕静默失败）；
3. **循环变量要先拷到局部**：`for N to i { int x = i; tasks.send(func(){ return x*x }) }`
   —— 直接捕获 `i` 会让所有闭包看到同一个槽。

**实测**：4 worker / 20 个任务 ⇒ 平方和 **2470**（期望 2470），各 worker 处理数合计 20，失败 0。
