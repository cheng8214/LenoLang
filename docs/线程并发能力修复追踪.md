## 一、现状快照（模型是什么，别改什么）

| 项 | 事实 | 锚点 |
|---|---|---|
| 线程模型 | 每线程**独立 VM**（独立 stack / frames / globals / **独立 GC 堆**），OS 真线程，**无 GIL** | `src/object/object_thread.c:177-527` `thread_entry_point`（`:286` `gc_init()`） |
| 通信 | `Channel`（Go 式 buffered/unbuffered），**传值即深拷贝** | `src/object/object_thread.c:784-850`；`src/module/threads/threads.c:54-109` |
| 跨线程值的**唯一闸门** | `value_clone_for_channel()` —— 白名单之外一律报错 | `src/object/object_thread.c:74-156` |
| GC | 分代标记-清除，**GC 状态 `THREAD_LOCAL`**；共享对象（thread/channel）扫描时加锁，非 STW | `src/gc.c:59`、`:775-816` |
| 协程 | `async`/`await` 是**语言关键字**，单 VM 协作式事件循环（`g_event_loop` 是**进程级单例**） | `src/coroutine.c:14,239-304` |
| 两模型关系 | **禁止混用**（threads 与 async 不互相调度） | `docs/threads使用指南.md:561-599` |

**结论（本文档前提）**：模型是对的，问题不在"有没有真并行"，而在**能用什么数据**和**能不能封装**。

## 三、明确**不做**（避免反复讨论）

| 不做的事 | 为什么 |
|---|---|
| 共享堆 / 拆掉线程堆隔离 | 要重写 GC 与所有写屏障，收益为零：模型的价值就在隔离 |
| `threads.Mutex` / `atomic` / `Semaphore` | **堆隔离下没有可被两线程同时访问的普通对象** ⇒ 锁保护的东西不存在。共享的只有 Channel 内部（已有锁）与 FFI 句柄 |
| 让模块 globals 按线程深拷贝隔离（旧"方案 C"） | `ObjModule` 由 `loaded_modules` 全局缓存共享，强行隔离破坏模块缓存一致性 + 模块全局语义 + GC 的 module mark 逻辑（见 `多线程struct与模块全局变量问题记录.md` §五） |
| 统一 threads 与 async 的调度器 | 大工程；当前两者定位清晰（算得慢 / 等得久），先各自补短板 |

> 附带纪律：**`value_clone_for_channel()` 是全模型正确性的唯一闸门**。每加一个可克隆类型，
> 必须同时加"拒绝面"（不支持的类型明确报错，不许静默传引用）+ 一条回归用例。
> 历史出血点：dict 的 **key** 漏克隆（`object_thread.c:110-139`）、channel 重入克隆（`:836-840`）。

## 四、逐条详述

### TH1（P0）struct 实例跨 Channel 传值 —— ✅ 已修（2026-10-12，工作区未提交）

**症状**
- `ch.send(point)` 报「不能跨线程传递此类型」（`object_thread.c` 的 default 分支）。
- 连带症状：想让并发库跑起来，只能把 struct **拍平成 `Array[string]`** 在接收方手工重建
  ⇒ 写得越"Leno 风格"（struct 化），越难并发。

**根因（证据）**
- `value_clone_for_channel()` 白名单只有 `null/int/float/bool/string/Array/Dict/Channel`，
  没有 `OBJ_STRUCT` ⇒ 走 default 报错。
- 另有**一道编译期拦截**（`src/semantic/semantic_type_utils.c` 的
  `semantic_check_cross_thread_args`）：静态类型确定为 struct 的实参**直接报错** ✗
  —— 只改运行期不够，这道一并撤（否则"改了运行期也过不去"）。

**实施前查清的关键事实（原计划里列成"必须回答"的，答案如下）**
1. **克隆发生在两侧**：`channel_send` 先把值克隆进 buffer（发送方堆 ✓），`channel_receive`
   取走前**再克隆一次**（接收方堆 ✓）。⇒ struct 只要走同一个 `value_clone_for_channel`，
   **两个调用点一行都不用改** ✓（与 `Array`/`Dict` 完全同口径）。
2. **写屏障**：struct 字段写入的唯一入口是 `struct_set_field()`（`leno_value.h`，内含
   `gc_write_barrier`）⇒ 克隆时走它，**不要直写** `field_values[i]`。
3. **分配方式**：`struct_instance_new(def)` 一次分配"对象头 + 内联字段数组"（`fields_inline=1`）
   ⇒ 克隆必须走这个构造函数，不能自己 `gc_alloc`。
4. GC 会 mark struct 的 `def` / 全部字段 / `declared_face`（`src/gc.c` 的 `case OBJ_STRUCT`）
   ⇒ 带上 face 声明与泛型实参是安全的。

**落地（工作区改动）**
- `src/object/object_thread.c`：克隆闸门拆成**深度感知**的 `channel_clone_value(val, depth)`
  （对外 `value_clone_for_channel` 符号不变 ✓），新增 `channel_clone_struct`：
  递归同一套克隆规则、`CHANNEL_CLONE_MAX_DEPTH 64` 防环、face 声明与泛型实参一并带上、
  不可克隆类型统一走 `channel_clone_reject`（带 `g_channel_clone_ctx` 指认"结构体.字段"）。
- `src/semantic/semantic_type_utils.c`：拦截名单**只留 `TYPE_CSTRUCT`**（struct / face 放行 ✓）。
- `assert/test_channel_struct.leno`（新增）：①深拷贝语义 ②struct 过 Channel 往返（3 条输入 / 3 条回包）
  ③嵌套 struct ④拒绝面（cstruct 字段 ⇒ 报错指认字段，两条通道各一条判据）
  ⑤自引用（环）⇒ 报「嵌套层数超过 64」而不是挂死。
- `assert/test_diag_static_errors.leno`：原来钉"struct 必须编译期报错"的两条**翻了案**
  （改 `expect_ok`），另加一条 cstruct 仍编译期拦 ✓。
- 文档：`语言陷阱速查.md`（§一 ② / §三 ②）、`module_threads_api.md`、`threads使用指南.md`。

**验收（实测）**
- 套件：`443 passed / 0 failed`（新增 1 条用例 ⇒ 442 → 443）。
- 端到端：`threads.start(worker, p)` 与 Channel 往返都能拿到字段值；子线程改字段主线程**看不见**
  （深拷贝语义 ✓）。

**顺带查实的三件事（都写进文档了）**
- ⚠ **`for A : B` 是闭区间**：`for 0 : 3` 跑 **4** 轮（实测）。循环次数若与消息条数对不上，
  `receive()` 永久阻塞 ⇒ 表现是"卡死且无输出"（stdout 被块缓冲，中间 print 看不到 ✓）。
- ⚠ **同一条通道"边收边发"会把自己发出去的消息收回来**（通道不区分发送者）⇒ 收发要分两条通道。
- ✅ **`assert/fixture_thread_cstruct_crash.leno` 的崩溃已不复现**（2026-10-12 复核 3/3 exit 0）
  —— 历史记录见该文件头部（不进套件的原因也写在那儿）。

**端到端（可选，未做）**：LenoWeb 的 `test_thread_parse.leno` 可改为**直接传 `HtmlNode`**。

### TH2（P1）线程入口允许模块函数 —— ✅ 已修（2026-10-12，工作区未提交）

**症状**
- `threads.start(模块里的函数)` 被前置拦截报错（原 `src/module/threads/threads.c` 的守卫）。
- 绕法只能把函数**当值**从宿主传进模块 ⇒ **库自己无法封装并发**
  （LenoWeb 想自开线程池、LenoMusic 想自管后台解码，都做不到）。

**根因（比原计划写的窄得多 —— 这轮勘察的最大收获）**
- 原判据 `closure->function->module != NULL` 直接拦，理由写的是"子 VM 只继承调用方 globals +
  `current_module_frame = NULL` ⇒ 模块函数找不到本模块的 globals"。
- **实际**：模块字节码（`OP_GET_MODULE_VAR` / `OP_SET_MODULE_VAR` / `OP_GET_MODULE_FUNC` /
  `OP_DEFINE_MODULE_FUNC`）寻址用的是 **`frame->module`**，**不读** `current_module_frame`
  （见 `src/vm/vminc/run/10_vars_module.inc` 四处 `ObjModule* module = (ObjModule*)frame->module`）。
  而三条 call 路径（`vm_call.inc` 的 `call` / `call_no_type_check` / `call_reg`）都设了
  `frame->module = func->module`，**唯独协程首帧漏了这一行**
  （`src/vm/vm.c` 的 `vm_run_coroutine_with_vm`）⇒ 进函数体后第一条模块符号指令报
  「不在模块上下文中」。
- ⇒ **不需要"子 VM 按需加载模块"**（原计划的高风险方案）：模块对象由**进程级** `loaded_modules`
  缓存共享（`src/module_loader.c` 的 `static LoadedModules`，非 THREAD_LOCAL），
  init_chunk 主线程已跑过 ⇒ 子线程直接用共享的 `ObjModule` 就对 ✓。
  `child_vm.globals`（入口脚本 globals）的继承与模块函数无关，不必动 ✓。

**落地（两行改动 + 用例）**
- `src/vm/vm.c`：协程首帧补 `frame->module = func->module;`（入口脚本函数 `module == NULL`
  ⇒ no-op ✓）。**顺带修好主线程 async 协程里调模块函数**的同一处缺口 ✓。
- `src/module/threads/threads.c`：撤掉那条硬拦，改为**只拦一种情况** —— 入口函数所属模块
  **尚未初始化**（不在入口脚本 import 链上 ⇒ globals 全空）时明确报错。
- `assert/test_threads_module_entry.leno` + `assert/helpers/th2_mod.leno`（新增）：①入口脚本直接
  `threads.start(模块函数)` ②多参数 + 循环 ③模块函数里再调同模块函数 ④**模块自己开线程跑自己的
  函数**（TH2 的真正价值）⑤模块级可变状态**跨线程共享**（把已知口径钉成显式契约）。
- `assert/test_diag_warnings.leno`：E6/M1 那条"必须抛错"翻成 `expect_ok` ✓。
- 文档：`threads使用指南.md`（该节从"限制"改写为"模块函数也能用 + 两个注意点"）、
  `module_threads_api.md`（入口形态矩阵第③条翻案）、`语言摩擦与隐式契约清单.md`（M1 标已修）。

**验收（实测）**
- `assert/test_threads_module_entry.leno` 全过；`test_diag_warnings.leno` 全过；套件全绿。
- 端到端：模块内 `threads.start(_sum_worker, …)` ×2 + `join()` ⇒ 正确（`parallel_sum(0,1,3) == 6`）。

**遗留（不影响功能，只是注释过期）**
- `build/leno_module/LenoWeb/`（README / `web_net.leno` 的 curl_multi 理由 / 4 个测试注释）与
  `leno_gui/应用/电脑清理大师/test/test_clean_pipeline.leno`（已就地改 ✓）里还写着
  "库函数自己起不了线程" —— **设计结论不变**（curl_multi 仍是对的选择），但理由那句已经不准，
  下次动那些文件时顺手改。

### TH3（P1）并行原语 —— ✅ 已修（2026-10-12，工作区未提交）

**症状**
- 写"4 线程分块排序"要手写 Channel 编排 + 手动 `join()`。
- 没有 `WaitGroup` / `parallelFor` / `map` ⇒ 每个用户都在重复写同一套样板。

**设计取向（与原计划的差异，值得记住）**
- 原计划写的是 `threads.WaitGroup`（`add/done/wait`）—— 那需要**新的对象类型**（`ObjWaitGroup` +
  方法表 + 可能还要新关键字/TypeKind），与语言"够用就行、不再追加特性"的一贯取向相悖。
- 改成**三个普通模块函数**，零类型系统改动：
  | 原语 | 语义 | 回调形态 | 返回 |
  |---|---|---|---|
  | `threads.join_all(Array[Thread])` | "等一组线程"（WaitGroup 的等价物） | — | `int` |
  | `threads.parallel_for(n, f)` | 分 n 份并行（`f(index)`，index = 0..n-1），等全部结束 | `f(int)` | `int` |
  | `threads.map(arr, f)` | 并行 map，结果按输入顺序收回 | `f(item, index)` | `Array[回调返回]` |
- `map` 的返回类型**直接复用** `arrays.map` 那份原生规格 `NATIVE_T_ARR_CB_RET1`
  （`Array[第 1 实参回调的返回]`）⇒ 静态类型精确（`Array[int] doubled = threads.map(...)` ✓）。
- `map` 的回调形态与 `arrays.map` **同口径**（`f(item, index)` 两个形参）—— 用户已有的认知可迁移 ✓。
- ⚠ **实现取舍**：`map` 是"**每元素一个线程**"（线程数 = 元素数）—— 因为**闭包不能作为参数跨线程传**
  （`value_clone_for_channel` 不认函数值），所以"分块 + 子线程循环调 f"这条路走不通；
  要分块只能用 `parallel_for`。代价已写进 API 文档 ✓。
- 原计划里那条"模块内调用时回调能不能跑"的顾虑，**已被 TH2 顺带解决** ✓（模块函数现在能作入口）。

**落地（工作区改动）**
- `src/module/threads/threads.c`：
  - 入口校验收成**一处** `threads_check_entry(closure, got_args, who)`（`start` / `parallel_for` /
    `map` 共用，避免三份拷贝各自漂移 ✓）；
  - 新增 `threads_join_all` / `threads_parallel_for` / `threads_map` 与三条模块方法注册。
- `assert/test_threads_parallel.leno`（新增）：①`parallel_for` 起够 n 个 + 每个下标都跑到
  ②**并发性用"栅栏"证明**（n 个线程都报到才发令 —— 串行执行会收不齐而挂住，比"比单线程快"
  这种计时断言稳得多 ✓）③`join_all` ④`map` 顺序对齐 + 静态类型直接是 `Array[int]`
  ⑤`map` 的元素可以是 struct（TH1 + TH3 联用 ✓）。
- 文档：`threads使用指南.md`（新增「并行原语」一节 + API 表三行）、`module_threads_api.md`
  （三个 API 各一节）。

**验收（实测）**
- `assert/test_threads_parallel.leno` 一次全过（含栅栏那条）；套件全绿。

### TH4（P2）`Channel[T]` 泛型 —— ✅ 已修（2026-10-12，工作区未提交）

**症状**
- `ch.receive()` 静态类型恒为 `any` ⇒ `var x: int = ch.receive()` 要显式转换、
  `Point p = pc.receive()` 直接报「类型不匹配」（实际类型: any）、多返回值解构被拒。
- 代码里自己承认过一句「语言里没有 `Channel[T]` 标注…要精确得先给 Channel 加类型参数」
  （`src/module/threads/threads.c`，本轮已作废 ✓）。

**根因（证据）**
- 解析器里**只有 `Ptr[T]` 有泛型解析**（`src/parser/parser_func.c` 的 `TOK_PTR_TYPE` 分支）；
  `Channel`/`Thread` 都 `type_new(...)` 直接返回 ⇒ 连 `[T]` 都吃不下（`Channel[int]` 会被外层语法误解析）。
- `Thread[T]` 已存在但**只由 native 规格内部构造**（`NATIVE_T_THREAD_CB_RET0`；
  `type.c` 的 `type_copy` / `build_generic_type_string` 早已支持 `element_type` 槽）
  ⇒ **先例已有**，`TYPE_CHANNEL` 照此加槽即可，**不需要新 kind** ✓。

**落地（8 处，全在"槽位已存在、只是没人用"的地方）**
1. `src/type.c`：新增 `type_channel_generic` / `type_thread_generic`（照 `type_ptr_generic`）；
   `type_equals` / `type_copy` / `build_generic_type_string` 各补 `TYPE_CHANNEL` 分支
   （**渲染分支是必须的** —— 否则报错里 `Channel[int]` 会显示成 `Channel` ✗）；

- 而**用户已经有显式手段**：`threads.local_*`（想隔离就隔离 ✓）、把状态收进实例（推荐 ✓）、

### TH7（P3）FFI 回调与多外部线程

**症状**
- `ffi.callback` 注册的回调在**外部线程**（Windows 线程池 / C 库工作线程）上跑，
  而它们与主 VM **共享同一个执行环境**（同一套 stack/`sp`/`frame_cnt`）
  ⇒ 多外部线程**并发**回调会互相覆盖 VM 栈（`docs/threads使用指南.md:593-597`）。

**现状**
- 已有**跨线程编组/泵送**（`src/module/ffi/ffi.c:2918-2963`，`g_pending_mutex`）：
  工作线程阻塞、主线程泵送 —— 覆盖了部分场景，但**不是**通用的"多线程并发回调"支持。

**方向（未拍板）**
- 让回调**一律**排队回 VM 所在线程执行（彻底串行化）—— 代价是回调语义变成"异步"，
  对 `qsort` 这类**必须同步返回结果**的 C API 直接不可用。
- 或者引入"每外部线程一个子 VM"（与 `threads` 同款隔离）—— 但回调往往需要回写主线程的闭包状态。

⇒ 本条先**记录**，等 TH1/TH2 落地后再评估。
