## F1 `any as func(...)` 恒产出 `null` ✅

### 已修（2026-11-17）

- **根因**：`src/vm/vm.c` 的 `vm_as_cast()` switch **没有 `TYPE_FUNCTION` 分支** ⇒ 落 default ⇒
  `matches = 0` ⇒ 返回 null（静默）。语义层的"as 恒失败"清单里也没有函数类型，所以编译期没拦。
- **修法（两步）**：
  1. `vm_as_cast` 补 `TYPE_FUNCTION`：值确实是闭包 / 原生函数 ⇒ **透传**（不复制、保留 upvalue）；
  2. `emit_type_op`（`src/codegen/codegen_expr.c`）对函数类型把 C 操作数改记**形参个数**
     （255 = 裸 `func`，不检查）⇒ `vm_as_cast` 比 `arity`，不符 ⇒ null；
     `OP_AS_CAST` 处理器（`src/vm/vminc/run/13_async_ffi.inc`）在"值本来是函数、但签名不符"时
     打一条**带行号**的警告：
     `警告: as func(...) 签名不符（第 N 行）：闭包有 1 个参数，目标签名有 0 个 ⇒ 结果是 null`
- **第二阶段（2026-11-17 同日补完）：形参类型也能校验了**
  - 类型规格新增 `TYPE_FUNCTION` 变体：`param_count(u8) + spec(形参)* + spec(返回)`，
    255 = 不校验形参（裸 `func`）。发射端 `codegen_expr.c` 的 `emit_type_spec`、
    执行端 `vm.c` 的 `type_spec_size_impl` / `type_spec_match`、校验器
    `bytecode_verify.c` 的 `spec_scan` **三处同构**（漏一处就会"校验器把合法字节码判成损坏"）。
    → **同日已单源化**：`spec_scan` 只剩指针薄壳，长度与合法性统一走
    `vm.c` 的 `type_spec_verify()`；发射端每发一条规格还会自检一次（不一致当场报内部错误）。
    详见 `leno_vm.h` 的 `type_spec_verify` 注释与 `bytecode_verify.c` 的 `spec_scan`。
  - `as func(...)` / `is func(...)` 现在走 `OP_AS_CAST_SPEC` / `OP_TYPE_CHECK_SPEC`；
    判据在 `fn_params_match()`：**只比形参个数 + 标量形参类型**（int/float/string/bool）——
    复合（Array/Dict/Ptr）与 struct/face/enum 在运行期只有 kind、没有名字与元素类型，
    硬比会误杀；返回类型不比（`func():int` 可当 `func():void` 用，与静态侧一致）。
  - 失败文案现在带两边签名：
    `警告: as func(int):void 失败（第 62 行）：实际拿到 func(string)（形参不符）⇒ 结果是 null`
  - **格式变了**：`LENO_BIN_VERSION` v3.2.42 → **v3.2.43**、`LENO_MODCACHE_VERSION` v57 → **v58**
    （变长尾随字节，旧 VM 会把签名当指令）⇒ 旧缓存整体失效重编，**打包产物要重打**。
- **仍未做**：返回类型与复合形参的精确比对（需要把完整类型树也存进 `ObjFunction`，
  且 `param_types` 目前只记 kind）。
- **回归**：`assert/test_as_func_cast.leno`（4 条）。断言套件 **642 / 0**；模块测试 **52 / 0**。
- **副作用（已确认是改善）**：签名不符时不再"缺参当 null 传进去"（修前实测 `func(int n)` 当
  `func():void` 调会打出 "cb" + 空值、不报错），现在是 null + 警告 ⇒ 应用侧 `if f != null` 的
  守卫重新有意义。

### 现象（最小复现）

```leno
Dict d = ["cb": func(int n) { print("cb " + _str(n) + "\n") }]
var raw = d.get("cb", null)
print("raw 是 null ? " + _str(raw == null) + "\n")        // false —— Dict 里确实存着闭包
var f = raw as func(int):void
print("cast 后是 null ? " + _str(f == null) + "\n")      // true  ← BUG
print("cast 后 is func ? " + _str(f is func(int):void) + "\n")   // false
```

实测（v0.2.4）：

| 表达式 | 实测 |
|---|---|
| `raw` 的原生类型 | `func` |
| `raw == null` | `false` |
| `raw as func(int):void` 的类型 | `null` |
| `as func(int):void` 后 `is func` | `false` |
| **零参版本 `as func():void`** | **同样是 `null`** |

> ⚠ **零参版本也不能用**。此前有一处误判（"零参恰好能工作"）源于读 `sdl_menu.leno:70`
> 的代码猜出来的，实测已被否掉。

### 为什么危害大

转换**不报错、不抛异常、只是变 null**。症状是"回调永远不触发"：

```leno
// Aria 桌面歌词配色：点「确定」后颜色不变、也不报错
func(Color):void onPick = opts.get("onPick", null) as func(Color):void
if onPick != null { onPick(out) }     // 恒 false ⇒ 永远不会调用
```

### 已存在的受害路径（修完 F1 要顺手回归）

`build/leno_module/LenoSDL3/lib/sdl_menu.leno:70`：

```leno
mi.action = d.get("action", null) as func():void
```

⇒ **用 Dict 构造的 MenuBar 菜单项，动作从来没触发过**（菜单能弹、点了没反应）。
使用面很小（`createMenuBar|addMenu(|action:` 在 Aria + LenoTrae 合计 **2 处**命中），
所以一直没被报上来 —— 属"沉默死代码"。

### 修法（建议，按成本从低到高）

1. **运行时**：`as` 到函数类型时**永不产出 null**
   - 签名匹配 ⇒ **透传原闭包**（保留捕获环境，别复制）；
   - 签名不匹配 ⇒ 抛**可捕获**错误并带行号：`期望 func(int):void，实际 func():void`。
2. **编译期**：源为 `any`、目标为函数类型时，生成 `rt_as_fn(v, sig_hash, line)`，而不是裸转换
   （`sig_hash` 可由形参个数 + 各参数类型 hash 得到，闭包本身已带 arity 信息）。
3. **不要**"直接禁掉 `any as func(...)`"：那只是把成本转嫁给所有使用者（每个回调都得写具名形参）。

### 位置

- 行为定位在 **cast 的语义兼容判定 + codegen 的 `AST_CAST` 生成**这两处
  （`src/type.c` 的 cast/兼容路径、`src/codegen/` 里处理 `AST_CAST` 的地方）。
- 本条只定位到**行为**，未定位到具体函数行 —— 动手前先 grep `TYPE_FUNCTION` 在 cast 分支的处理。

### 判据（回归用例）

新增 `assert/test_as_func_cast.leno`：

1. Dict 存 `func(int)` → `as func(int):void` → 调用，必须真的执行；
2. Dict 存 `func()` → `as func(int):void` → 必须**抛错（带行号）**，而不是 null；
3. 零参往返 `as func():void` 同样成立；
4. `sdl_menu` 路径：`createMenuBar` 建一项带 `action:` 的菜单，`clickItem` 后动作必须执行。

## F2 struct 与 `null`：先修误报，再禁字面量，最后才能升错误 🟡

### 已修（2026-11-17）：误报

- **根因**：`sem_expr_maybe_null()`（`src/semantic/semantic_visit_ast.c:1501`）的 switch 里
  **没有 `AST_NULL` 分支** ⇒ 初值就是 `null` 字面量的变量落 default ⇒ 被判成"不为 null" ⇒
  `P g = null` 之后 `g == null` 照样报「默认被立即分配」✗
- **修法**：`case AST_NULL: return 1;`（5 行注释写明现场）
- **实测（v0.2.4+今天）**：`g == null`（初值 null）/ `loc == null`（不写初值）/ `b.inner == null`
  全部安静；`new P()` 出来的 `made == null` 仍然警告 ✓ —— 正是我们要的判据。
- **未做**：`T x = null`（非可空）报错 + 比较升错误。理由：迁移面 ~60 处（Aria 29 / LenoSDL3 31），
  且现有代码正用 `bool dlOpen` / `rawPtr()` 这类手工 Option 兜；要先给 `T?` 的落地写法。

### 现状（实测）

| 写法 | 编译 | 运行期 |
|---|---|---|
| `P p = null` | 通过 | **真的是 null** |
| `P p`（不写初值） | 通过 | **自动分配，不为 null** |
| `Box { P inner }` | 通过 | 同 `P p`（自动分配） |

⇒ 所以 `p == null` **有时是有意义的**（对应"显式赋过 null"这一种状态）。
之前"这类比较永远是逻辑错误"的判断是**错的**，顺序也反了。

### 现有 warning 的误报（先修这个）

`WARN_STRUCT_EQ_NULL` 的判据是**声明形态**（"`P p` 默认被立即分配"），不是"这个变量是否可能为 null"：

```leno
P g = null
print(_str(g == null))       // 运行期 true，但 warning 仍报"默认被立即分配（不为 null）" ← 误报
```

位置：
- `src/semantic/visitinc/visit_expr.inc:280`
- `src/semantic/semantic_visit_ast.c:1492`

### 正确顺序

1. **修误报**：引入最简 null 状态（`definite_null` / `non_null` / `unknown`，按初始值与赋值传播），只在"比较**不可能**为 null"时才报；
2. **禁字面量**：非可空 `T` 不接受 `null` 字面量（`T x = null` 报错）；
3. **升错误**：此时 `struct == null` 才真的永远无意义 ⇒ 把 warning 升成 error。

### 迁移规模（先量过再动手）

`Type name = null` 粗匹配：**Aria 29 处 / LenoSDL3 31 处 ≈ 60 处**。
而且现有代码已经在用绕法模拟 Option（`Tray.rawPtr()` 判空、`bool dlOpen` 与句柄分开记）
⇒ **先给 `Option[T]` / `T?` 的落地写法**，否则等于逼大家临时发明 60 种绕法。

## F3 `Color` 只是 `int` 别名 🟡

### 现状

```leno
// build/leno_module/LenoSDL3/lib/sdl_core.leno:150
export alias Color      = int               // 颜色：0xAARRGGBB 打包整数
```

- `#RRGGBBAA` 字面量在编译期被转成 `0xAARRGGBB`（**alpha 位置反了**）；
- 裸 int 与 Color 在类型上**完全不可区分**。

### 本轮实例（真实事故）

```leno
// 想要"53% 黑"，实际写出来的是 alpha = 0x00（全透明）
border: true, border_color: 0x00000088
```

⇒ 白色色板在白底对话框上**彻底消失**，查了半天（记录见
`build/leno_module/LenoSDL3/lib/sdl_colorpicker.leno` 里 `swatchBtn` 的注释）。

### @optkeys 现状

颜色键是**裸键**（如 `sdl_alert` 的 `"border_color"`），连"是不是 int"都不查。
但键类型后缀机制已存在（`"spacing:num"`、`":float"`、`":bool"`）⇒ 照抄一个 `:color` 即可。

### 分期（阶段一先堵坑，不动语义）

- **阶段一**：
  1. @optkeys 增加 `:color` 键类型 + `set()` 侧校验；
  2. 新增告警：**Color 类型的形参 / 字段被裸 int 字面量赋值**时提示（`0x00000088` 会被点名）。
     只对字面量生效 ⇒ 零误伤存量代码。
- **阶段二**：`Color` 从 alias 变 distinct type，`#RRGGBBAA` 字面量直接产出 Color，
  与 int 之间要显式 `as`（成本：alias 语义、`#` 字面量、@optkeys 键类型三处一起动）。

### 判据

- 阶段一：`createButton({border_color: 0x00000088})` 期望出告警；`border_color: #00000088` 期望安静；
- 阶段二：`Color c = 0x00000088` 期望编译错误。

## F4 `requestRedraw()` 是全局单标志 ✅

### 已修（2026-11-17）

- `sdl_core.leno` 新增 `requestRedrawWindow(wid)` / `hasWindowRedraw()` / `takeWindowRedraw(wid)` /
  `clearWindowRedraws()`；`requestRedraw()` 保持原义 = **所有窗口脏**（控件内部没有窗口上下文）。
- `sdl_window.leno` 的 run 循环：新增局部 `_fullFrame`（首帧 / 事件 / 全局 requestRedraw /
  toast / tooltip / 尺寸同步 ⇒ 全画），只有 `requestRedrawWindow` 这一条不置全脏；
  逐窗口循环开头 `if not _fullFrame { if not core.takeWindowRedraw(wid) { continue } }`。
- 门面：`SDL3.requestRedrawWindow(wid)` + `Window.redraw()`（自查 `getID()`）。
- **实测**（`SDL_VIDEODRIVER=dummy`，两窗口，定时器里只 `b.redraw()` 三次）：
  `frameTotal()` 增量 **3**（每次只画被点名的那一个）。按修前的判据（全局标志 ⇒ 每次全画两个窗口）
  同一脚本应为 6 ⇒ 单窗路径确实生效（**修前的数字未实跑，是按代码推的**）。
- ⚠ 控件内部（TitleBar hover / PopMenu / MenuBar）仍然走全局 `markFrameRedraw()` ——
  它们不知道自己属于哪个窗口，退化成"全脏"是**保守方向**（宁可多画，不可漏画）。
  要做细需要"渲染期当前窗口"上下文，属下一步。

### ⚠ 应用侧必读：`addTimer()` 默认 `autoRedraw = true` 会**静默吃掉** F4 的收益（2026-11-17 实测）

框架的定时器每拍默认发一次**全局** `requestRedraw()`（`sdl_timer.leno:87` 的 `anyFired`）。
所以：应用里只要有**短周期定时器**（比如浮窗 33ms 心跳），你在回调里多克制地调
`Window.redraw()` 都没用 —— 全局请求每拍照样把 `_fullFrame` 置真，主窗口继续全量重绘 ✗

实测（Aria 桌面歌词，改前/改后同一口径 21.6s）：

| 状态 | 主循环全局请求 | CPU |
|---|---|---|
| 原状（50ms 定时器 + 全局 `markFrameRedraw()`） | ~20/s | 4.72s |
| 只改成 per-window，**忘了关 autoRedraw**（33ms） | **~32/s** | 5.78~6.80s（反而更差 ✗） |
| `autoRedraw = false` + per-window（33ms） | **~5/s**（只剩 200ms 的 on_tick） | **2.12~3.22s（均值 2.5s，−47%）** |

结论：`Window.redraw()` 要生效，**该窗口的定时器必须 `autoRedraw = false`**（`page_lyric` 的
`lyrT.autoRedraw = false` 早在 2026-11-08 就是这么干的，这次浮窗漏了）。

### ✅ 2026-11-17 已从框架侧根治：定时器重绘**按注册窗口归属**

不再要求应用逐个去关 `autoRedraw`（那等于把风险转嫁给全库）——`tickAllTimers()` 里改成：

```leno
if alive and t.tick() and t.autoRedraw {
    if t.ownerWid != 0 { core.requestRedrawWindow(t.ownerWid) }   // 只画注册它的那个窗口
    else { core.requestRedraw() }                                  // 无窗口上下文（如 Edit 光标闪烁）⇒ 全局
}
```

- `Timer.ownerWid` 本来就有（`Window.addTimer` / `addTimerOnce` 会填，`unregisterByWindow` 也按它注销）
  ⇒ 只是把"触发后重绘谁"从全局改成该窗口，语义本来就该如此；
- 直接 `registerTimer()` 注册、没有窗口上下文的定时器（`sdl_edit.leno` 的光标闪烁）`ownerWid == 0`
  ⇒ 退回全局，**行为不变**；
- 定时器里如果要改**别的**窗口的控件，那个窗口不会自动重绘（以前会）——这类跨窗口定时器极少，
  真遇到就在回调里显式 `otherWin.redraw()` / `markFrameRedraw()`。

**回归用例**：`examples/基础示例/窗口管理/test_timer_redraw.leno`（两窗口，稳态 1.5s）

| | A（静态窗口） | B（60ms 定时器） |
|---|---:|---:|
| 修前（定时器 ⇒ 全局） | **26** | 26 |
| 修后（定时器 ⇒ 该窗口） | **1** | 25 |

Aria 侧实测（21.6s 口径）落在 **2.11~3.31s**，与"应用侧自己关 autoRedraw"那一版同档
（Aria 只有一个 33ms 浮窗定时器，本来就关了；框架这版主要救**对话框/多窗场景**和**后来者** ✓）。

定位手段（可复用）：在 run 循环里临时分类计数 `full / evt / glob / carry / winOnly / tip / toast`，
每 120 次循环打一行（`LENO_REDRAW_TRACE`）。这次就是靠它在一屏内锁定"glob ≈ 32/s"的。

### ✅ 2026-11-17（二）：**控件与事件**的重绘也按窗口归属

上面那条只管住了"定时器"，但控件内部 100+ 处 `markFrameRedraw()` 和"任何非 motion 事件"
仍然把 `_fullFrame` 置真 ⇒ 鼠标在主窗口挪一下，浮窗/对话框也跟着整窗重绘 ✗。

改动（`sdl_core.leno` + `sdl_window.leno`）：

| 位置 | 改动 |
|---|---|
| `markFrameRedraw()` | 读 run 循环维护的上下文窗口 `_capWid`：有 ⇒ `requestRedrawWindow(_capWid)`；无（定时器/worker/应用 tick）⇒ 全局（保守，行为不变） |
| 事件循环 | `_hadEvent` 不再一律全脏；改记 `_hadEventWid`（`ev.windowID()`），只脏该窗口；`windowID()==0`（SDL 全局事件）⇒ 全脏 |
| `_fullFrame` 初值 | 从 `_needRedraw` 改为 **false** + 新增 `_pendingFull`：**"欠一次全脏帧"跨轮次保留** |
| `consumeRedrawRequest()` | 从"每轮开头消费"挪到"**确认真要出帧**之后"，否则会被帧率节流吞掉 |
| `Window.destroy()` | 补一次全局 `requestRedraw()`：关对话框要清掉父窗口的蒙版/残影 |
| 逃生阀 | `LENO_GLOBAL_MARK=1` ⇒ 退回旧的"一律全脏" |

⚠ 两个坑（都是实测踩到的，别再踩）：
1. `_fullFrame` 初值取 `_needRedraw` 会把"**欠一帧**"和"**全脏**"混为一谈 —— 节流攒下的 carry
   会让下一帧全脏，分窗收益漏回去。真正的兜底是"欠一帧且**没有任何窗口被点名**才全画"。
2. `consumeRedrawRequest()` 提前消费 = 全局请求被静默吞掉（标志清了、帧没画）⇒ 表现为
   "某个窗口再也不重绘"，而且不报错。必须等真出帧再消费。

**回归用例**：`examples/基础示例/窗口管理/test_mark_attribution.leno`（两窗口，300ms 窗口）

| 场景 | 改前 | 改后 |
|---|---|---|
| 往 A 注入一次点击（事件上下文 = A） | A 与 B 都重绘（B ≈ 15 帧） | **ΔA=16 / ΔB=0** ✓ |
| 定时器里直接 `markFrameRedraw()`（无上下文） | 两边都画 | 两边都画 ✓（保守不变） |
| `LENO_GLOBAL_MARK=1` | 两边都画 | 两边都画 ✓（逃生阀） |

Aria 回归：`--check` 通过、托盘自检 15 项全绿、主窗口截图正常；
空闲 CPU 21.6s 口径 **2.11~3.31s → 1.88~2.02s**（空闲事件少，收益主要在**交互期**：
鼠标划过界面时只有被划的那个窗口重绘）。

**还剩什么**：① 启动期 `sizeSync` 的 10 帧仍是全脏（短暂，可接受）；
② **窗口内部仍是整窗全量重绘**（无脏控件/视口裁剪）—— 这是下一步，也是空闲 CPU 的主要来源
（重界面 ~28ms/帧 × 5 次/秒的 `on_tick` ≈ 14%）。

## 原始分析（留档）

### 现状

```leno
// build/leno_module/LenoSDL3/lib/sdl_core.leno
:740  bool _redrawRequested = false
:745  export func requestRedraw() { _redrawRequested = true }
:747      if _redrawRequested { _redrawRequested = false; return true }
```

run 循环 consume 之后，本轮重绘的是 `_runRens` 里**所有**窗口。

### 影响（本轮实测）

- 桌面歌词 20fps 的 `markFrameRedraw()` ⇒ 主窗口（卡片墙那页重）跟着全量重绘：
  **CPU 3% → 10%**（早期 33ms 心跳时实测）；
- 主窗口那帧慢（~28ms）⇒ **浮窗被拖帧**，观感就是"有些歌平顺有些不平顺"的一半原因；
- 于是应用侧只能自己降频/降采样（Aria 现在：播放中 50ms、暂停 ~100ms），代价是逐字分辨率被人为压低。

### 建议 API

- `requestRedrawWindow(win)` / `requestRedraw(int wid)`：只置该窗口 dirty；
- 兼容层：现有 `requestRedraw()` 语义保留 = "所有窗口脏"。

### 实现边界（难点写在这里，免得低估）

控件内部会直接调 `core.markFrameRedraw()`（`TitleBar` hover、`PopMenu`、`MenuBar`），
它们**不知道自己属于哪个窗口** ⇒ 需要一个"渲染期当前窗口"上下文（`ren.windowID()` 或
thread-local 当前窗口），否则这些路径只能退化成"全窗口脏"。
定时器侧已经按窗口注册（`timer.unregisterByWindow(getID())`），天然支持；各窗口 HWND 独立，无 z 序问题。

### 判据

- dummy 驱动下给 run 循环加"每窗口 render 次数"计数：请求 A 窗口红绘时，B 的计数不增；
- Aria 实测：空闲时主窗口 render 次数应归零（只有桌面歌词窗在刷）。
