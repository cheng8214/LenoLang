## 一、先看这三条（最省时间的）

### ① 明明改了代码，行为 / 性能却一点没变？

先**别急着删 `.lenocache`** —— 现在的入口缓存**会自动失效**：同目录的 `entry_<hash>.lenb.deps`
是**依赖清单**，第 2 行 `BIN <指纹>` 是**编译器二进制身份**，之后每个被引用文件一行
（§8.112 / 2026-09-17 起，见 `src/main.c` 的 `ENTRY_DEPS_MAGIC`）。

**实测（2026-10-09）**：入口脚本一个字不动、只把被引用的 `lib.leno` 返回值从 `"A"` 改成 `"B"`，
**不删缓存**再跑一次 ⇒ 输出跟着变成 `B`（自动重编译 ✓）。

所以按这个顺序排查：

1. 是不是改了**另一个副本**的模块 —— 模块是按 **`leno.exe` 所在目录**找的（见 §五 ①）✗ 最常见
2. IDE / lint 没重载 ⇒ 编译一次（`--check` 就够）就见真章
3. 真怀疑缓存 ⇒ 删一次对照（这本身也是"证明缓存无辜 / 有罪"最快的办法 ✓）

> ⚠ 老笔记里"改了 `src/` 必须手删 `.lenocache`"是 **2026-09-17 之前**的经验（那时 `.deps` 里还没有 `BIN`）
> ⇒ `GC与分配优化.md` 那条现已加注 ✓
> ⚠ **另一套 C 后端（LenoC）**里没查到这套依赖清单（`LENODEPS` 只出现在本仓 `src/main.c`）
> ⇒ 用 LenoC 时若"改了没生效"，仍按老办法手删 `.lenocache` 对照一次 ✓

### ② 跨线程传 struct：编译能过，运行期在"字段访问"处炸

见 §三 ② —— 报错**完全不提线程**，最容易查错方向 ✗

### ③ `use` 列表漏类型：报错点在**使用处**，不在 `import` 那行

见 §二 ② —— 而且**静态检查 / IDE 不一定标出来**（编译才报 ✓）

## 二、模块与可见性

### ① 模块级函数**不加 `export` 就是文件私有**；`pri` 只能用于 struct 成员

```leno
pri func helper(): int { return 1 }      // ✗ 文件顶层
```

报错（照抄）：
```
error: [语法错误] pri 只能用于 struct 成员；模块级不加 'export' 就是文件私有，请去掉 'pri'
```
✅ 新版本的提示**已经直接给出结论与改法**（实测 2026-10-09）—— 见到"期望表达式"那种指不到病因的老报错，
说明用的是老编译器 ✓

### ② `use M.(A, B, …)`：**源码里出现的每个类型都要列**

漏一个（例：`Label` 没进列表）报：
```
error: [未定义变量] 未定义的类型: Label（请检查是否已通过 use 语句导入该类型，如 use module.Label）
```

⚠ 三个容易吃亏的点：
- 报错位置在**使用那一行**（不是 `import` / `use` 那行）⇒ 看到它先往回找 `use` 列表 ✓
- 只出现在**泛型参数 / 返回类型**里的类型也要列（例：`Array[Button]` 里的 `Button`）✗ 最容易漏
- **lint 常抓不到**（它不跑完整模块符号表）⇒ 改完 `use` 列表**一定要编译一次** ✓

### ③ 跨模块用到的 struct 类型要能"传导"出去 ⇒ 子模块 `import` **必须带别名**

```leno
import "./web_html.leno" as html      // ✓ 带别名
import "./web_html.leno"              // ✗ 不带别名：外层 use 不到它的类型
```

不带别名时，外层 `use` 拿不到该模块的 struct/face 类型（表现为"类型未解析"或参数对不上）✓

### ④ 每个入口目录一份 `.lenocache`

缓存目录 = **入口文件所在目录**（不是 cwd、也不是 exe 目录）⇒ 同目录多个入口脚本**共享**
一个缓存目录，清理时别只删当前键（`src/main.c` 的注释里写明了"保留最新 K 个"的理由 ✓）

## 三、类型与值

### ① struct 要 `new`

```leno
struct P { int x = 7 }
P p = P()        // ✗
P p = new P()    // ✓
```
报错（照抄）：
```
error: [语义错误] struct 'P' 需要使用 new 关键字实例化，例如: new P()
```
（报错很清楚 ✓，但从别的语言过来第一下最容易忘 ✗）

### ② 跨线程只传**纯字符串数组**（struct / 多返回值都不行）

```leno
struct P { int x = 7 }
func work(P p): int { return p.x }
Thread t = threads.start(work, new P())     // ← 编译**通过**，运行期炸
```

实测（2026-10-09）报的是：
```
error: [运行时错误] 字段访问需要结构体对象
```
⚠ **这条报错完全不提"线程"二字** ⇒ 见到它先想"**这个值是不是从别的线程传过来的**" ✓

机制（本仓多处注释记过 ✓）：子线程**不加载别的模块的全局变量**；struct / 多返回值过 `threads.start`
或 `Channel` 后静态类型退化成 `any` ⇒ 解构会被静态检查拒掉。
所以跨线程的"协议"就用 `Array[string]`（LenoMusic / 无头自检那一套全是这么设计的 ✓）。

### ③ `is not` **不支持** ⇒ 写 `not (x is string)`

```leno
func f(any x): bool { return x is not string }   // ✗ 报两条语法错误
func f(any x): bool { return not (x is string) } // ✓ 实测通过
```
`is not` 实际报（照抄，两条一起出）：
```
error: [语法错误] 类型检查表达式期望类型名（如 int, float, string, bool, Array[int] 等）
error: [语法错误] 期望表达式
```
（第二条是噪音 ✗ —— 盯**第一条**看 ✓）

### ④ 字符串方法名是 **snake_case**

`starts_with` / `ends_with` / `has` ✓（实测通过）。
别按其它语言的习惯写 `startsWith` / `endsWith` —— 会报"类型 'string' 没有方法 'startsWith'" ✗

### ⑤ 空数组要写清楚元素类型

```leno
var a = []                // 元素类型退化成 any ⇒ 报错点离现场很远 ✗
Array[string] a = []      // ✓
```
（这一条的完整来龙去脉见 `易用性痛点（TraeSign 移植实录）.md` 的 P4 ✓）

### ⑥ 多返回值**只能解构，不能下标**

```leno
var[float, float](w, h) = font.measureString(s)   // ✓
float w = font.measureString(s)[0]                // ✗（本模块真崩过一次）
```
（详见 GUI 速查 §六 ✓）

### ⑦ `as` 到容器 / struct **不会当场失败**，而是"原样带过"

⇒ 别拿 `as` 当运行时校验；要校验就自己判断（`is` / 长度 / 内容）✓
（详见 GUI 速查 §八 ✓）

### ⑧ 禁用态用"向背景混合"，不是"通道减半"

```leno
theme.mixbg(color, bg, 55)          // ✓ 明暗主题下都等于"往后退"
theme.packColor(r/2, g/2, b/2)      // ✗ 浅色主题下会变成"实心深块"，看着像被选中
```
（`sdl_theme.leno` 里 `mixbg` 头上的注释写得很清楚 ✓ 实测踩过：禁用复选框比勾中的还抢眼 ✗）

## 四、报错怎么读

- **格式**：`文件(行,列): error: [类别] 说明`（实测 ✓）。类别见过：
  `[语法错误]` / `[语义错误]` / `[未定义变量]` / `[类型未解析]` / `[运行时错误]`
- **多数新提示自带"怎么办"**（例：`请去掉 'pri'`、`例如: new P()`、`如 use module.Label`）
  ⇒ **先读提示，别猜** ✓（提示词表一直在变好，老笔记里的原文可能已过时 ✗）
- 一次编译**可能同时报很多条**：先修**第一条**、再重编（后面的常是连锁误报 ✓）
- 空 `catch { }` 是**编译期错误**（2026-09-28 由警告升为错误 ✓ 见 GUI 速查 §八）
- 断言别读控件内部字段（例 `lbl.text` 读不到 `set_text` 之后的新值 ✗ 见 GUI 速查 附录 C②）
- 编译检查（不产出、不执行）：
  ```bat
  build\leno.exe --check <file.leno>
  ```

## 五、构建 / 缓存 / 打包

### ① 模块按 **`leno.exe` 所在目录**找

```
<leno.exe 所在目录>/leno_module/<包名>/lib/
```
⇒ **应用源码和发行包放哪都行**，但必须用**那个 exe** 跑（拿 A 副本的 exe 跑 B 副本的源码，
会去 A 的 `leno_module/` 找模块 —— 改了 B 的模块却"没生效"，多半是这里 ✗）

### ② `.lenocache/` 里都是什么

| 文件 | 是什么 | 失效输入 |
|---|---|---|
| `entry_<hash>.lenb` | 入口脚本的字节码 | 入口内容 + 依赖清单（见下） |
| `entry_<hash>.lenb.deps` | **依赖清单**（`LENODEPS2`）：第 2 行 `BIN <指纹>` = 编译器二进制身份；之后每个被引用文件一行 | —— |
| `*.lenomc` | 模块编译产物 | 模块内容 |
| `*.lenosymc` | 模块符号表 | 模块内容 + **exe 指纹**（自动失效 ✓） |

⇒ 结论：**改 `lib/`、甚至重建 exe，缓存都会自己作废**（实测 ✓ 见 §一 ①）。
真正会咬人的是"**改错副本**"和"**没重编译**"，不是缓存本身 ✓

### ③ 打包后读资源：用 `dirs.res_dir()`，**不要** `script_dir()`

单文件包运行时资源解包到**用户缓存目录**，而 `script_dir()` 仍指 exe 所在目录 ⇒ 取不到 ✗
（未打包时两者相同 ⇒ 开发态看不出来 ✓ 详见 `单文件打包使用指南.md`）

### ④ 构建脚本是**两套源码清单**

`build.bat` 与 `build_vm.bat` 各有一份 `sources_*.txt` 清单，且 `build_vm.bat` 是 GBK 文件
⇒ 加新 `src/*.c` 时**两处都要加**（见痛点文档 P9 ✓）
