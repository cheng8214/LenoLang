# Leno 规范文档草稿

## 1. 设计目标

Leno 不是为了堆叠语法特性，而是为了成为一门稳定、工程化、易扩展的脚本语言。

在当前阶段，Leno 的核心目标应当是：

- 稳定核心语义
- 统一工程风格
- 强模块能力
- 自然底层封装
- 真实应用可写性
- 生态可维护性

最终目标不是“支持最多特性”，而是：

> 让人能用 Leno 轻松写出真实工具、桌面应用、系统封装和中型工程项目，而不是只写示例。

---

## 2. 语言定位

Leno 应该被明确定位为：

- 工程脚本语言
- 适合桌面应用、工具链、系统封装、脚本内核开发
- 兼具静态类型检查和运行时灵活性
- 适合 API 层、模块层、底层绑定层协同开发

它不是：

- 纯面向教学的语法展示语言
- 纯动态脚本语言
- 纯底层系统语言
- 一个无约束的特性堆积实验场

---

## 3. 设计原则

### 3.1 稳定优先

一切新能力必须满足以下条件：

- 语义清晰
- 可解释
- 可维护
- 不破坏现有工程风格
- 便于编译器实现和语义检查

新语法应该优先服务工程，而非炫技。

### 3.2 统一优先

语言设计中，统一性比特性数量更重要。

应统一以下规范：

- import / use / export 语义
- 类型导入风格
- 模块入口风格
- 构造函数命名风格
- 常见 API 约定
- 标准库代码组织方式

### 3.3 库优先

Leno 的真正竞争力来自于库生态。

因此，设计重点应该放在：

- 标准库结构
- 模块入口归纳
- 高层 API 封装
- 底层 FFI 友好性
- 工程用法的可读性

而不是无止境增加语法糖。

### 3.4 实用优先

最终要达到的是：

- 能写复杂桌面应用
- 能封装原生能力
- 能写工具和脚本系统
- 能管理中型工程结构

这比“语言概念新奇”更重要。

---

## 4. 语法风格规范

### 4.1 import / use / export 规范

这三者必须具备明确语义：

- `import`：加载模块
- `use`：引入模块中的类型/成员到当前作用域
- `export`：把当前模块中的成员开放给其他模块

#### 推荐语法

```leno
import "maths.leno" as maths
import "SDL3.leno" as SDL3

use SDL3.(Window, Renderer, Event, Font)
```

#### 不建议的风格

- 同一类语义出现多套等价写法
- `import` 和 `use` 混搭造成语义不清
- 大量隐式导出/隐式重导出造成维护困难

### 4.2 模块入口统一要求

每个大型标准库都应提供统一入口模块。

例如：

```leno
import "SDL3.leno" as SDL3
```

而不是让用户在多个子模块里拼接使用。

官方标准库应遵循：

- 低层模块实现细节
- 中层统一入口
- 上层用户只使用入口模块

这保证语言生态保持稳定和慢增长。

### 4.3 命名规范

推荐统一命名风格：

- `createXxx(...)`
- `new Xxx(...)`
- `setXxx(...)`
- `getXxx(...)`
- `isXxx(...)`
- `addXxx(...)`

对于库 API，优先采用：

- 动词开头
- 类型清晰
- 语义一致
- 易读易记

不建议：

- 各个库使用互不相同的命名风格
- 同一语义出现不同动词别名
- 无规则的缩写和混用

---

## 5. 官方库写法规范

### 5.1 入口模块模板

官方库应遵循如下结构：

```leno
import "core_module.leno" as core
import "sub_a.leno" as a
import "sub_b.leno" as b

use core.(TypeA, TypeB)
use a.SomeType
use b.OtherType

export func createSomething(...) { ... }
export func doSomething(...) { ... }
export struct Result { ... }
```

特点：

- 模块入口聚合
- 对外功能统一
- 用户使用简单
- 实现细节隐藏

### 5.2 SDL3 作为标准范式

SDL3 绑定的写法已经非常接近“官方范式”，应当作为标准库风格模板。

它具备的典型特征：

- 一层入口模块聚合多个底层模块
- `use` 统一类型引入
- 低层模块是实现层
- 高层模块是面向用户层
- 函数命名统一
- 复杂 API 组装清晰

因此，Leno 的正式库风格应该是：

> “底层模块实现，入口模块集成，用户使用统一接口”。

## 6. 示例规范

### 6.1 发布前必须具备的示例属性

官方示例必须满足：

- 代码可读
- 能说明一种核心语言能力
- 能说明工程用法
- 能展示实际应用场景
- 不只是“语法演示”

### 6.2 示例分层

建议官方示例分为四层：

#### 第一层：基础语法

- 变量和常量
- 函数
- structs
- face
- 泛型
- 异步
- 安全类型
- 模块导入

#### 第二层：工程能力

- 模块聚合
- 类型导出
- 复杂库入口
- FFI
- 结构体与底层绑定

#### 第三层：应用案例

- 文件管理器
- 图形小工具
- IDE 布局
- 实用桌面程序
- 工具链程序

#### 第四层：生态案例

- SDL3
- 复杂 UI 框架
- 系统封装
- 嵌入式场景

### 6.3 应用案例应作为官方展示正例

像下面这些案例应当被视为“官方展示材料”：

- IDE 布局
- 文件管理器
- PE 分析器
- 桌宠应用
- 游戏
- 图形工具
- SDL3 绑定和 UI 控件模块

这些内容不是“测试文件”，而是“语言能力证明”。

---

## 7. 工程体验规范

### 7.1 目标

Leno 的工程体验要做到：

- 大型模块清晰
- 库开发舒服
- 复杂应用易维护
- 案例可复用
- 语义接近自然编程
- 编译器扩展不破坏结构

### 7.2 规范原则

- 不做无目的语法扩张
- 不引入过多等价语法
- 不让不同模块使用不同写法
- 不让官方库风格破碎
- 优先让代码“可读、可组织、可复用”

### 7.3 工程友好性优先级

优先级排序建议为：

1. 稳定性
2. 可维护性
3. 统一性
4. 表达效率
5. 特性炫技

也就是说：

> 语言越成熟，越应该把“工程体验”放在第一位。

---

## 8. 语法糖的使用准则

### 8.1 语法糖允许，但必须满足三条

新增语法糖必须：

- 能减少样板代码
- 能提高代码可理解性
- 能服务标准库和工程代码

不满足这些条件的糖，不应加入核心语言。

### 8.2 提升工程体验优先于增加特性

本阶段的重点应该是：

- 把库写得更自然
- 把模块表达得更统一
- 把 API 组织方式更稳定
- 提高生产效率

而不是继续堆特性。

---

## 9. 语言成熟度目标

### 9.1 当前阶段目标

当前阶段 Leno 的目标不应该是“追求无所不能”，而是：

- 让语法稳定
- 让库开发稳定
- 让 standard library 统一
- 让工程写法一致
- 让复杂真实应用容易实现

### 9.2 对应发展方向

建议后续采用的路线：

1. 稳定核心语义
2. 统一官方库风格
3. 固化 SDL3 作为官方范式
4. 整理应用案例为标准展示
5. 精简不必要语法糖
6. 提升生态可维护性
7. 让其成为真正的工程脚本语言

---

## 10. 结论

Leno 当前阶段最重要的不是“去做更多”，而是“把已经做出来的能力整理成一套稳定、统一、工程化的规范”。

这套规范的核心是：

- 模块组织统一
- import / use / export 语义清晰
- SDL3 式入口库作为官方范式
- 示例案例作为官方正例
- 工程体验高于特性堆积

一句话总结：

> Leno 的下一阶段，应该从“强功能语言”走向“统一工程语言”。

这意味着：

- 特性不再是重点
- 体验和规范才是关键
- 标准库和案例才是最有说服力的成果

---

## 11. 附录：推荐的官方库模板

```leno
import "core.leno" as core
import "window.leno" as win
import "renderer.leno" as ren

use core.(Color, Rect)
use win.Window
use ren.Renderer

export struct View { ... }

export func createWindow(...) { ... }
export func createRenderer(...) { ... }
export func drawRect(...) { ... }
```

### 说明

这是 Leno 最推荐的标准库结构：

- 低层模块负责实现细节
- 统一入口负责对外暴露
- 用户只用入口模块
- 风格一致，便于维护

---

## 12. 版本路线建议

### v1.x：稳定阶段

- 稳定核心语义
- 收敛 API 风格
- 明确 import / use / export 语义
- 固化 SDL3 入口库风格

### v1.5：工程阶段

- 形成标准库模板
- 增加官方示例套件
- 提升工程代码组织能力
- 整理常用设计模式和库规范

### v2.0：生态阶段

- 成熟标准库生态
- 官方案例库与文档同步
- 语言风格稳定，减少破坏性变化
- 真正具备工程脚本语言特征

---

## 13. 最终原则

Leno 的未来，不能被“功能堆积”牵着走，而应被“工程可用性”牵着走。

如果你们坚持走这条路线，Leno 很可能会形成一套非常鲜明的定位：

> 既能快速脚本化，又能做复杂工程封装，还能承载底层绑定能力的系统脚本语言。

这正是它最值得发展的方向。
