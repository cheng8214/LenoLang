## L1【P1】`as Array[Array[string]]` 遇到混合类型，整块静默返回 null

### 现象

Aria 的 `library.json` 里有一条「最近播放」记录的第 6 项是**数字** `0`（本该是空串或
`"ff"`）：

```json
{"recent": [["2668005064","童话镇","梁玖希","4:17","…ff_2668005064.jpg",0]]}
```

`library.load` 是这么读的：

```leno
var rows = rv as Array[Array[string]]
if rows != null {
    for rows to r { … }        // ← 整个列表都不进来了
}
```

**一行脏数据 ⇒ 整块 recent 被丢弃**，而且**一句日志都没有**。用户看到的是「继续收听」
空空如也，只会以为数据丢了或自己清空了。

### 最小复现（已实测）

```leno
import jsons as jsons

main() {
    var d = jsons.decode("{\"recent\":[[\"id\",\"歌名\",\"艺人\",\"4:17\",\"cover.jpg\",0]]}")
    if d is Dict[string, any] => m {
        var rows = m["recent"] as Array[Array[string]]
        if rows == null { print("null：整块丢弃\n") }
        else { print("成功，第6项='" + rows[0][5] + "'\n") }
    }
}
```

实测输出：

```
null：整块丢弃
```

对照：同一份数据**编码**这边是正常的（int 原样输出 `0`），问题只在**反序列化的类型断言**。

### 根因落点

`as` 的数组转换是"整组严格匹配"：只要有一个元素类型不符，整个 `Array` 转换失败返回
`null`，而调用方通常写成 `if rows != null { … }`（合理防御）⇒ 失败路径就是**静默丢数据**。

### 建议修法

1. **逐元素宽松转换**：目标是 `Array[Array[string]]` 时，元素能转就转（`0` → `"0"`、
   `true` → `"true"`），转不了再整块失败；
2. 或者提供显式宽松函数（`jsons.str_rows(v)`) 供持久化读取使用，`as` 保持严格；
3. 无论哪种，**失败时至少 `print` 一行**（带键名与原因）。当前 `null` 完全无声。

### ★ 已修（2026-10-31）：应用侧改用"两段式宽松解析"

关键技巧：**先 `as Array[any]`（任何元素都装得下，必成功），再逐元素 `_str()`**。
`_str()` 对任何类型都能转（数字 → `"0"`），永不失败 ⇒ 一条脏数据只影响它自己那一格。

```leno
// lib/library.leno —— 原来：var rows = rv as Array[Array[string]]   ← 一粒老鼠屎坏一锅汤
var arr = rv as Array[any]
if arr != null {
    for arr to it {
        var row = it as Array[any]
        if row == null or row.len() < 5 { continue }
        Song sg = new Song()
        sg.sid   = _str(row[0])
        sg.title = _str(row[1])
        sg.dur   = _str(row[3])
        sg.cover = _str(row[4])
        if row.len() > 5 and _str(row[5]) == "ff" { sg.src = "ff" }
        out.recent.add(sg)
    }
}
```

同样的写法也用在 `lib/store.leno` 的 `str_list()`（`likes` 数组）。

**验证**（故意写脏数据：第 6 项是数字 `0`，两条记录）：

| | 修复前 | 修复后 |
|---|---|---|
| `as Array[Array[string]]` 的返回值 | `null`（探针实测） | — |
| 「继续收听」显示条数 | 0（由上面的 null 推得，未单独跑一遍） | **2 条都在**（截图实测 ✓） |

> ⚠ 诚实标注：修复前的"0 条"是从 `as` 探针结果（返回 `null`）推出来的，没有单独回滚代码再跑一遍界面。

> 框架层仍建议改成"逐元素宽松转换"，但那是 `as` 的全局语义变更，风险和收益要单独评估。
> 本文档记录的应用侧写法**无需框架改动**即可彻底规避 ✓

### 附：一条**存疑**记录（未能复现，供参考）

同一条记录最初出现时，第 6 项是**不带引号的** `0`。我试过三种路径都没能复现出这个
编码结果：

```leno
Array[Array[string]] rows = [["id","歌名","艺人","4:17","cover.jpg",""]]
print(jsons.encode(rows))                 // ⇒ [...,""]   ✓ 正常

Dict[string, any] d = {}
d["recent"] = rows
print(jsons.encode(d))                    // ⇒ {"recent":[[...,""]]}   ✓ 正常

var back = jsons.decode(jsons.encode(d))  // 往返第 6 项 = '' 长度 0   ✓ 正常
```

⇒ **"空串被编码成 0"这个猜测不成立**，真实来源未查明（可能是某次历史版本的写入，
或其它我未覆盖的装箱路径）。这条只作线索留档，别照着它去改 `jsons.c` 的 string 分支。

## L2【P1】单槽回调重复注册会静默覆盖

### 现象

设置窗的「蒙版透明度」滑块，注册了**两处** `on_change`：

```leno
veilS.on_change(func(float v) { … onVeil(v) … })    // ① 带实时预览
veilS.on_change(func(float v) { … note.set_text(…) }) // ② 旧的那份，写在后头
```

后注册的整段顶掉前一个 ⇒ 拖动时主窗口**完全没反应**，只有点「保存」才生效。
用户侧表现是"我拖动看不到窗口变化"，排查成本很高（两处代码隔了 40 行，肉眼看不出冲突）。

### 根因落点

```leno
// build/leno_module/LenoSDL3/lib/sdl_slider.leno:113
func on_change(func(float):void cb) { onChange = cb }
```

同类单槽（都在 `lib/` 里，`xxx = cb` 的写法）：

| 控件 | 方法 | 文件 |
|---|---|---|
| Slider | `on_change` | `sdl_slider.leno:113` |
| Window | `setOverlay` | `sdl_window.leno`（全局唯一渲染回调槽） |
| Table | `set_cell_builder` | `sdl_table.leno:1032` |
| 多个控件 | `on_click` / `on_select` / `on_dbl_click` … | 各自文件 |

### 建议修法（二选一，按代价排）

1. **最小改动**：重复注册时 `print("[warn] Slider.on_change 被重复注册，前一个回调已丢弃")`。
   保留"后覆盖前"的语义，但让人看得见。成本几乎为 0。
2. **更彻底**：改成 `add_change(cb)` 累加语义（数组存回调），`on_change` 保留为"清空后设一个"。
   注意这会改变现有调用方的语义，需要审计。

`setOverlay` 建议单独看：它是**全局唯一槽位**，Aria 的 `ARIA_SHOT` 截图钩子和 toast 曾经
互相顶掉（截图模式下 toast 不显示）。本轮通过"toast 上升为框架浮层"绕开了，但槽位本身
仍是 1 ⇒ 建议文档里明确写"一个窗口只能有一个 overlay 回调"，或改成数组。

### ★ 已修（2026-10-31）：4 处单槽注册补上"重复即警告"

按上面的**方案 1**（最小改动，保留"后覆盖前"语义，只让它可见）：

| 文件 | 方法 |
|---|---|
| `lib/sdl_slider.leno` | `Slider.on_change` |
| `lib/sdl_window.leno` | `Window.setOverlay` |
| `lib/sdl_table.leno` | `Table.set_cell_builder` |
| `lib/sdl_table.leno` | `Table.on_cell_draw` |

统一写法（以 Slider 为例）：

```leno
func on_change(func(float):void cb) {
    if onChange != null and cb != null {
        print("[warn] Slider.on_change 被重复注册：前一个回调已丢弃（同一控件只有一个槽位）\n")
    }
    onChange = cb
}
```

⚠ 只在"**原来已有值**且新值非 null"时才警告 —— `clear_*`（传 null 清空）是正常操作，不该吵。

`Button.on_click` 这一类**没加**：应用里按钮都是建好即用、极少在同一实例上二次注册，
加了只会给 `sdl_*.leno` 里那几十个控件各添三行噪音。真踩到了再按同一模式补 ✓

## L3【P1】`threads.start` 不校验参数个数（默认参数也不补齐）

### 现象

```leno
// 工作线程入口：后加了一个可空控制通道，给了默认值
export func fetch_url(string url, string path, Channel ch, Channel? ctl = null) { … }

// 调用点（改签名时漏改的那一处）
threads.start(workers.fetch_url, sg.url, f, urlCh)        // ← 3 个参数
```

编译 `--check` **通过**，运行到这条路径直接抛：

```
[错误] threads.start(): 入口函数期望 4 个参数，实际传了 3 个
（线程入口由 VM 直接调用，默认参数不会被补齐）
```

错误信息本身写得非常好（直接给了根因），问题是**发现得太晚**——只有真实播放/下载到那条
分支才炸，而它藏在 5000 行代码的一个播放回调里。

### 根因落点

`src/module/threads/threads.c`：`threads.start` 在运行期才按函数签名比对实参个数。

### 建议修法

`threads.start` 的第一个参数在**编译期**就能解析到具体函数（`workers.fetch_url` 是模块
符号）⇒ 参数个数不符在编译期报错，成本远低于运行期。

如果编译期做不到（比如目标可能是函数变量），退一步：

- 保留运行期检查，但在 `--check` 模式下也**静态扫描** `threads.start(函数名, ...)` 这种
  字面量形式，报"参数个数不符"；
- 或者在文档/`threads使用指南.md` 里显著标注：**线程入口禁止使用默认参数**。

### ⏸ 结论（2026-10-31）：**不做**编译期检查

查过注册方式了，编译期这条路被堵死：

```c
// src/module/threads/threads.c:573
native_register_module_method("threads", "start", threads_start,
    &NATIVE_T_THREAD_CB_RET0, NATIVE_VARARG(1, NATIVE_ARITY_ANY, 1, start_params, TYPE_ANY));
```

`threads.start` 是 **VARARG**（可变参数），native 签名层面"传几个都对"——参数个数是否合法
取决于**第一个实参指向哪个函数**，而这个函数在编译期可能是：

- 模块函数引用（`workers.fetch_url`）⇒ 可静态解析 ✓
- 局部变量 / 闭包 / 数组元素（`threads.start(f, ...)`）⇒ 静态不可知 ✗

要覆盖前者就得在 semantic 里给 `threads.start` 开一个特判（查函数声明表、比对 arity），
而后者一律漏掉 ⇒ **"有时能查、有时查不到"比"统一不查"更容易误判**。

**更划算的做法**（不需要改编译器）：线程入口**约定不用默认参数**，全实参显式给。
错误信息本身已经足够定位：

```
threads.start(): 入口函数期望 4 个参数，实际传了 3 个
（线程入口由 VM 直接调用，默认参数不会被补齐）
  [位置] aria.leno:3096 (func: play_ff_start)
```

带函数名 + 行号，一眼能改 ✓。本条真正的教训写进本文末的「防身规则」第 1 条。

## L4 ❌ **判断有误** —— 并不存在"两套下标并存"，API 是自洽的

> 本文档最初写的是「`len()` 是字节数、`slice()` 是字符下标 ⇒ 两套口径混用」。
> **这是错的**，2026-10-31 经源码 + 实测双重确认后撤销。

### 实现（`src/module/strings/strings.c:22`）

```c
static Value str_len(int argc, Value* args) {
    ObjString* str = (ObjString*)val_as_obj(args[0]);
    return val_int(str->char_len);      // ← 字符数，不是字节数
}
static Value str_byte_len(int argc, Value* args) {
    return val_int(str->len);           // ← 这才是字节数
}
```

`str_slice` 的注释里也写死了口径：

```c
//   · 索引按 **Unicode 字符**（不是字节）计算
//   · end >= char_len ⇒ 钳到 char_len-1（所以 `slice(0, x.len())` 仍是"到末尾" ✓）
```

### 实测（`"周杰伦abc"`，3 中文 + 3 ASCII = 12 字节）

| 表达式 | 结果 | 说明 |
|---|---|---|
| `s.len()` | `6` | **字符数** |
| `s.byte_len()` | `12` | 字节数 |
| `s.slice(0, 2)` | `周杰伦` | 字符下标（闭区间） |
| `s.slice(0, s.len() - 1)` | `周杰伦abc` | **与 `len()` 完全配套** ✓ |
| `s.take(0, 3)` | `周杰伦` | 字符，取 n 个 |
| `s.byte_slice(0, 2)` | `周` | 按字节切，中文被切断 |
| `s.byte_slice(0, s.len() - 1)` | `周杰` | 把字符数喂给字节 API ⇒ **静默切坏** |

### 结论：**不需要统一**

两套 API **各自内部自洽**，而且用前缀区分得清清楚楚：

| 文本语义（默认） | 字节语义（显式） |
|---|---|
| `len()` / `slice()` / `take()` / `[]` 切片语法 | `byte_len()` / `byte_slice()` |

全仓用量也印证了分工是对的：

```
.len()        3675 次（含数组/Dict，静态分不出，但字符串用法占多数）
.slice(        242 次
byte_* 系列    733 次 —— 集中在 crypto/、LenoWeb/、LenoZip/ 这些**二进制**场景
```

### 唯一真实风险：**跨套误用**

```leno
// ✗ 错：把字符数当字节偏移
string t = s.byte_slice(0, s.len() - 1)     // "周杰" —— 少了两字，还会切坏 UTF-8

// ✓ 对：字节语义就配字节长度
string t = s.byte_slice(0, s.byte_len() - 1)

// ✓ 对：文本语义（绝大多数场景）直接用 slice
string t = s.slice(0, s.len() - 1)
```

这类误用**不会报错**、只是结果悄悄变短/变乱，所以 Aria 里那句注释
（「别用 `byte_slice` 切文件名，中文会被切断」）是**对的**——但它说的是**误用**，
不是在说 API 设计有矛盾。

> 原始诱因：Aria 的 `downloads.scan` 里曾想用 `byte_slice` 去掉文件扩展名，实测把
> 中文文件名切坏了 ⇒ 改成 `strings.split(base, ".")`。问题出在"选错了 API"，不在语言。

## L5【P2】控件 `set()` 的未知选项只 print

### 现象

```leno
HBox box = SDL3.createHBox({w: 30, h: 14, tip: "来自小易"})   // HBox 没有 tip
```

运行日志：

```
[ui] HBox.set()：不认识的选项 'tip' —— 你是不是想要 'clip'？
```

程序继续跑，该属性静默丢弃。

**这个"did you mean"做得很好**，比大多数框架强。但因为它不阻断，问题只能在日志里发现
（我的截图验证跑了两轮才注意到这行）。

### 建议

- 保持 GUI 场景不崩（合理）；
- 但可以在 `--check` / 严格模式下把"未知选项"升级为编译期错误或非零退出码；
- 至少让这类日志带上文件:行号（现在只有选项名，一眼看不出是哪个 `createHBox`）。

### ⏸ 结论（2026-10-31）：**维持现状**

"带文件:行号"看起来是一行改动，实际做不到：告警走的是 `sdl_opts.leno` 里的 `warn_once()`
（纯 Leno），而**拿"当前脚本位置"是 C 层的能力**（`GET_CURRENT_LINE()` 只在 VM 的
`throw_runtime_error*` 里用）。Leno 层既没有 `_line()` 也没有 `_file()` 内建 ⇒
要么给语言加两个内建（新特性，得单独评估），要么把 `dochk.check` 下沉到 C 层（同样是大改）。

**现状其实够用**：`warn_once` 对同一个 `(控件, 键)` **只报一次**，且带"你是不是想要 `pad_x`？"。
排查时在输出里搜一次 `[ui]` 就能看到全部，再按选项名对回代码，成本可接受 ✓

真正该补的是**运行期升级开关**（`--check` 模式下未知选项直接失败），但那是构建期行为，
和这次的运行时告警是两件事，留作独立需求。

## 已修复（本轮，供对照提交）

### F1 `Table.set_cell` 改数据不请求重绘

```leno
// 修之前：只改数组，画面不动 ⇒ 调用方漏了 markFrameRedraw 就"进度条卡住"
func set_cell(int r, int c, string v) { _rows[r][c] = v; invalidate_fitted() }
```

修法：值真变了就 `core.markFrameRedraw()`，值没变直接返回（省一次重绘请求）。
副作用收益：下载进度可以只 `set_cell` 三格，不必整页重建 ⇒ **hover / 滚动位置不再丢失**。

### F2 `Table.recompute_cols` 与 `compute_sb` 扣减口径不一致

`recompute_cols` 用 `avail = w - iconW - gx()`，`compute_sb` 用 `bodyW0 = w - 8 - fw - gx()`
——差一个右边距 8px。后果：应用把 `col_ratios` 写成合计 **1.00**（最自然的写法）就必然
溢出 8px ⇒ 底部常驻横向滚动条，**放大窗口也不消失**（差值固定）。

修法：`avail` 改成与 `bodyW0` 同口径（减 8 / 冻结列 / 行号槽）。

### F3 通用 Toast（`sdl_toast.leno`）

- 与 `tooltip` 同构的全局浮层，不占布局、不吃事件、绝对时刻算淡入淡出；
- 停留期挂起，只在动画区间唤醒（替代应用侧 33ms 定时器空转）；
- 顺带解决 `setOverlay` 单槽被截图钩子顶掉的问题。

## 给应用的「防身规则」（不是语言 bug，但会被反复踩）

1. **线程入口函数不要用默认参数**，所有实参显式给全（见 L3）。
2. **单槽回调先判空再注册**，且全项目搜一遍同一个控件有没有第二处注册（见 L2）。
3. **持久化的数组元素类型要统一**（全 string 或全 int），脏一个元素就会让
   `as Array[Array[string]]` 整块返回 null、数据静默消失（见 L1）。
4. **回调里读 struct 字段前先确认捕获语义**：闭包拿到的是创建时的副本，可变状态放
   `Array[T]` 单元素数组（Aria 的 `toastTxt[0]` / `dlLyric[0]` 就是这个原因）。
5. **表格宽度别自己猜**：布局会按容器宽 `set_size` 重算，`col_ratios` 合计留 2% 余量最稳。
6. **字符串切分默认用 `slice` / `take`（字符语义）**；只有处理**二进制**（编码、协议、压缩）
   才用 `byte_slice`，而且长度必须来自 `byte_len()` —— 两套混用不报错、只是结果悄悄变短 ✗
