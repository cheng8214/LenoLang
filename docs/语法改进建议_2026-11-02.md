## A. 本轮已处理（留作记录）

### A1 ✅ `arr[:]` 双侧全省略切片（原路线图 T28）

- **修前**：`arr[:3]` / `arr[5:]` / `arr[-3:]` 都合法，唯独 `arr[:]` 报
  `期望表达式` + `期望 ']'` ⇒ 解析器不对称。
- **修法**：`src/parser/parser_expr.c` 的 `arr[:end]` 分支，消费 `:` 后先判 `]`，
  紧随 `]` ⇒ `end = NULL`。语义 / codegen / VM 本来就按 `null = 省略` 处理
  （`OP_SLICE`），所以改动只在解析器。
- **语义**：等价整段**浅拷贝**（与 `arr[0:arr.len() - 1]` 一致，且是副本不是别名）。
  字符串同样可用：`"hello"[:]`。
- **回归**：`assert/test_array_slice.leno` 测试 4b（副本非别名）/ 4c（字符串）。
- **文档**：module_arrays / 入门教程 / 语言陷阱速查 / INDEX / 路线图 T28 共 5 处已同步。

### A2 ✅ 文档纠错两处

1. 入门教程原写 `print(arr[:-3]) // [1,2,3,4,5]`，**实测是 `[]`**
   （Leno 的负下标只对**起点**生效；负终点恒为空，且编译期有 `[切片负终点]` 警告）。
   已改成 `[]` 并注明警告。
2. `docs/语言陷阱速查.md` ⑳ 说"源码浮点字面量不支持科学计数法"，**已过期**：
   实测 `1e3` / `1.5e-2` / `1.5e17` 都通过。只有**前导小数点** `.5` 仍不合法。已更新。

## B. 低成本、高一致性（建议优先做）

### B1 `??=` 空值合并赋值（P1，约 0.5–1 天）

```leno
int? a = null
a ??= 3          // 现在：语法错误「期望表达式」
```

- **现状**：`??` 表达式、`+=` / `&=` 等复合赋值都有，唯独 `??=` 没有 ⇒ 用户从
  C# / Dart / JS 过来必撞，只能写 `a = a ?? 3`（还可能重复求值左值）。
- **建议**：`??=` 只允许用于**可空变量/字段/下标**，语义 = `if lhs == null { lhs = rhs }`，
  **右侧惰性求值**（与 `??` 的短路一致，实测 `a ?? f()` 在 a 非空时不调用 f ✓）。
- **落点**：`src/lexer.c`（`?` 后跟 `=` 出 `TOK_COALESCE_ASSIGN`）+ `parser_stmt*` 复合赋值
  分支（复用 `AST_COMPOUND_ASSIGN` 或新增 `AST_NULL_COALESCE_ASSIGN`）+ codegen 转
  "判空跳转 + 赋值"；左值只求值一次（现有 `AST_INDEX_ASSIGN` 已有"左值只算一次"的元数据机制）。
- **风险**：低；唯一要注意的是**值类型** `int a`（非可空）用 `??=` 应直接编译报错
  （提示"a 不可空，??= 恒不生效"）。

### B2 前导小数点浮点 `.5` / `-.5`（P2，约 2 小时）

- **现状**：`var x = .5` 报「期望表达式」；必须写 `0.5`。
- **动机**：从 Python / JS / Swift 过来最顺手的写法之一；科学计数法已经支持，
  只剩"省略 0"这一种不认，形状不一致。
- **落点**：`src/lexer.c` 数字扫描入口：`.` 后紧跟数字 ⇒ 按浮点字面量扫描（与 `0.5` 同产物）。
  ⚠ 不要误伤 `obj.field` / `a.b` / `arr[0].x`：只有"`.` 前不是标识符/`)`/`]` 且后是数字"才算字面量。
- **风险**：低。需要补一条断言：`.5 + 1`、`x = -.5`、`arr[0].x` 不被误判。

### B3 数字分隔符 `1_000_000`（P2，约 2 小时）

- **现状**：`int a = 1_000_000` 报「同一行出现标识符」。
- **动机**：大整数 / 金额 / 时间常量（`3_600_000` ms）可读性；Leno 还支持 bigint，
  长数字更容易数错。多语言惯例（Rust / Swift / Java / C# / JS 提案）。
- **落点**：`src/lexer.c` 数字扫描里吞掉 `_`（仅当两侧都是数字字符），其余不变；
  `1_000` / `0xFF_FF` / `1_000.5` / `1_000e3` 都支持。
- **风险**：低。注意 `1_` / `_1` 应报错而不是静默接受。

### B4 `elif` 作为 `eif` 的别名（P3，约 1 小时）

- **现状**：`eif` 合法（`if c { } eif c2 { } else { }`），`elif` / `elseif` 会给出
  **很好的报错**（"Leno 没有 elif —— 用 eif"）⇒ 诊断已经到位，但每条从其它语言来的
  代码仍要手改。
- **建议**：把 `elif` 直接接受成 `eif` 的**同义关键字**（不新增 AST，只在 parser 的关键字
  匹配处并列）。`else if` 两词写法本来就合法，三种写法语义一致。
- **风险**：低（`elif` 目前不是合法标识符位置上的常用名；若担心破坏"变量叫 elif"的代码，
  可只在 if 链上下文识别）。

### B5 嵌套块注释（P3，约 2 小时）

- **现状**：`/* a /* b */ c */` 在 `c` 处报「期望表达式」—— 块注释在**第一个 `*/`** 结束。
- **动机**：注释掉含块注释的代码段时（调试常用），现有行为会把后半段当代码 ⇒ 报错
  甚至编译通过但语义变了（"注释吞代码"）。Rust / Swift / D 都支持嵌套。
- **落点**：`src/lexer.c` 的块注释扫描加深度计数（`/*` 深度 +1，`*/` 深度 -1，为 0 才结束）。
- **风险**：低；语义变化只影响"原本就不可能编译通过"的输入。⚠ 需确认没有工具链
  依赖"第一个 `*/` 结束"来生成注释（仓内 grep 一下）。
- **替代方案**：若不想改词法，至少把报错文案改成"块注释不支持嵌套"。

## C. 中等收益、需要设计（建议排期）

### C1 命名实参 `f(a = 1, b = 2)`（P1，约 2–3 天）

- **现状**：只有 `new Point(x = 10, y = 20)` 的 struct 构造支持 `键 = 值`；
  普通函数调用 `f(a = 1, b = 2)` 报「未定义变量: a」。
- **动机**：
  - 参数多的 native / 脚本函数（`files.write(path, content)`、`sdl.*` 一堆 opts）
    现在只能按位置传，读调用点看不出哪个参数是什么；
  - 与现有 struct 构造语法一致，学习成本几乎为零；
  - 可与默认参数组合，只写想覆盖的那几个。
- **建议规则**（保守版，避免歧义）：
  1. 命名实参只对**声明时形参有名字**的函数/方法生效；
  2. 一旦出现命名实参，其后**不允许**再出现位置实参（同 Python 的
     "positional after keyword" 错误）；
  3. 名字重复 / 不存在 / 与已给位置实参冲突 ⇒ 编译错误，文案列出可用形参名；
  4. 重排到形参顺序后再走现有 codegen（**字节码零变化**，只是 AST 实参顺序规范化）。
- **落点**：`src/parser/parser_expr.c` 调用实参解析（`TOK_IDENT` 后跟 `=` 且下一个实参
  上下文）→ `src/semantic/visit_expr.inc` 调用检查（按 `func_table`/符号表形参名重排）
  → codegen 不感知。
- **风险**：中。`=` 在表达式里目前不是运算符（Leno 没有赋值表达式），所以语法上不易歧义；
  真正要小心的是 **native 函数**（形参名来自注册规格）与**跨模块函数**（形参名是否完整保留）。
  建议先只对"脚本函数 + 本模块可见签名完整"开放，native 作为第二阶段。

### C2 箭头函数 `x => expr` / `(a, b) => expr`（P2，约 1–2 天）

- **现状**：`var f = (int x) => x + 1` 语法错误；必须写 `func(int x) { return x + 1 }`。
- **动机**：`arrays.map/reduce/filter`、回调字段、`threads.start` 大量使用小闭包，
  现有写法 3 行起步；箭头函数能把"单表达式回调"压成一行，且与 `if ... then ... else`
  的表达式风格一致。
- **建议**：纯语法糖 —— `(参数) => 表达式` 直接 desugar 成
  `func(参数) { return 表达式 }`（AST 仍用 `AST_FUNC_DEF`，**不动语义/字节码**）。
  允许 `x => expr`（单参免括号）与 `() => expr`（零参）。
- **落点**：`src/parser/parser_expr.c` 的表达式前缀分支（`(` 处需要前瞻 `=>`，
  或标识符后紧跟 `=>`）。
- **风险**：中低。`=>` 目前只用在 `if expr is Type => var`（绑定语法），
  两者上下文不同（一个在 if 头、一个在表达式位置），需确认词法/前瞻不会打架。

### C3 插值字符串格式说明符 `$"{x:.2f}"`（P2，约 2 天）

- **现状**：`$"pi={x:.2f}"` 报「期望 '}'」；只能 `format("%.2f", x)` 或字符串拼接。
- **动机**：UI / 日志里最常见的需求就是"保留 N 位小数"；现在要么写 `format`（格式串
  与参数分离、容易错位），要么 `_str(_round(...))`（还得自己补 0）。
- **建议**：`{expr:spec}` 内的 `spec` 复用现有 `format` 的转换子集（`%d/%f/%.Nf/%x/%s`），
  desugar 成 `format("%.<spec>", expr)`。
- **落点**：`src/parser/parser_expr.c` 插值字符串解析（当前遇到 `:` 即报错）+
  语义/代码生成侧复用 `format` 内建。
- **风险**：中。插值里出现 `:` 的既有写法（如 `$"{a ? b : c}"` 不存在，三元是 `if`；
  字典/类型注解一般不在表达式内）需盘点；建议只在 `{` 后**顶层** `:` 识别。

### C4 `switch` 区间 / 条件 case（P2，约 2 天）

- **现状**：`case 1:3 { }` 报「case 语句体必须用大括号包裹」；只能一个个列 `case 1` … `case 3`。
- **动机**：分数段 / 时间片 / 字符区间分类是常见写法；`switch` 已有"同类型 ≥4 个自动
  二分"的优化，区间 case 能进一步把"长 if 链"收进 switch。
- **建议**：`case 1:3 { }`（复用切片/`for 1:3` 的**闭区间**口径）与 `case in 1:3 { }` 二选一；
  codegen 降级为两次比较（或复用 CMPJMP 融合）。类型与 `switch` 现有口径一致（int/float）。
- **风险**：中。`case` 后本来就可以是表达式，`:` 在 case 头没有其它用途 ⇒ 语法歧义低；
  主要成本在语义/代码生成与二分优化的兼容。

### C5 `for x in arr` 作为 `for arr to x` 的别名（P2，约 1 天，需先定歧义）

- **现状**：`for x in a { }` 会报一条**很好的错**：
  "`in` 是成员测试运算符，for 是区间循环 ⇒ 请写 `for 集合 to x`（集合在前）"。
- **动机**：几乎所有主流语言都是 `for x in arr`；Leno 的"集合在前"（`for arr to item`）
  是独有语序，跨语言用户每天都会写反。诊断虽好，但每条都要手改。
- **建议**：**只在 for 头**把 `for IDENT in EXPR` 识别为遍历（`in` 在 for 头不可能是
  成员测试，因为 for 头本身只接受区间/遍历两种形状）⇒ desugar 成 `for EXPR to IDENT`。
  这样不动 `in` 运算符在其它位置的语义。
- **风险**：中。需要 parser 在 for 头前瞻：`for x in` 与 `for 0:5 to i` 的区分；
  另外 `for x in a` 中 `x` 若是已声明变量，会被当作"遍历目标"还是"成员测试" —— 需明确
  "for 头优先遍历"（并保留 `for (x in a)` 这种带括号的成员测试吗？建议明确不支持，给文案）。
- **备选**：若担心歧义，改用 `foreach arr as item` 之类的新关键字，零歧义但学习成本高。

### C6 批量导入 / 批量 use（P3，约 1 天）

- **现状**：`import io, times` 与 `use m.Button, m.Label` 都报语法错误 ⇒ 一行一个。
- **动机**：模块头部动辄十几行 import；跨模块类型 use 更碎。
- **建议**：`import io, times`（等价逐行）与 `use m.{A, B}`（等价逐条）。
- **落点**：parser 的 `AST_IMPORT` / `AST_USE` 解析循环追加；语义侧按现有单条路径展开。
- **风险**：低–中（语法扩展，不改语义）。`use m.{A,B}` 的 `{}` 与块语句无冲突。

## D. 低优先级 / 需作者拍板

### D1 `this` 作为 `self` 的别名（P3）

- 现状：方法里 `this` 报「未定义的变量: this」，**不带**"是否想用 self"的提示（M3 记录）。
- 两个选项：① 只加纠错提示（零风险，最推荐）；② 直接把 `this` 当 `self` 的同义关键字
  （降低跨语言摩擦，但和 Leno 一贯的 `self` 风格并行，可能造成两种写法混杂）。
- **建议先做 ①**；② 若做，仅在方法体内生效，顶层 `this` 仍报错。

### D2 负终点切片语义（不建议改，仅记录）

- 现状：`arr[:-1]` == `[]`（负终点恒为空），`arr[-3:]` 正常从末尾数。
- 改成 Python 语义（负终点 = `len + end`）**很诱人但破坏兼容**：仓里已有代码/测试依赖
  当前口径，且编译期已有 `[切片负终点]` 警告。**建议保持现状 + 文档**（本轮已纠错）。

### D3 三元 `cond ? a : b`（不建议加）

- 现状：明确报错并推荐 `if cond then a else b` / `eif` 链。
- 理由：Leno 已有"if 表达式"，再加 `? :` 会形成两套等价语法（与"单一事实来源"纪律冲突）。
  **保持现状**，诊断文案已经足够好。

## E. 顺带记录的工程/性能观察（非语法）

1. **maths 内联已覆盖别名**（`4bd06a4`）：`import maths as m` 后 `m.clamp()` 也走
   `OP_MATH_FAST`。`tools/bench_maths_native.leno` 实测：clamp ≈ 7 ns、abs ≈ 3.7 ns、
   max ≈ 5.2 ns、lerp ≈ 6.6 ns（300 万次×3 轮取最小）。**没有发现退化**。
2. **all 编译期可折叠的 maths 调用**：`try_gen_maths_fast` 目前只发射运行时指令；
   若参数全是字面量（`maths.clamp(0.5, 0.0, 1.0)` 这类配置常量），可在
   `src/optimize/optimize.c` 里常量折叠成 `LOADF/LOADI`，省一次 VM 分派。
   低风险、收益取决于项目里常量用法多不多（可先写探针统计）。
3. **`--check` 全量样例 788/788 通过**，说明当前语法/诊断没有明显回归；后续改语法时
   建议把"788 样例 --check 零错误"当作一条固定验收线（比 536 断言更覆盖真实写法）。
4. **ASAN 基线**：断言 + 模块测试 0 泄漏报告（含此前修掉的编译失败 chunk 泄漏）。
   新增语法特性（尤其 B1/C1/C2 这类会改 AST 的）建议都补一条 ASAN 跑法，防止引入新泄漏。
