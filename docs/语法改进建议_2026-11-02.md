### A1 ✅ `arr[:]` 双侧全省略切片（原路线图 T28）

- **修前**：`arr[:3]` / `arr[5:]` / `arr[-3:]` 都合法，唯独 `arr[:]` 报
  `期望表达式` + `期望 ']'` ⇒ 解析器不对称。
- **修法**：`src/parser/parser_expr.c` 的 `arr[:end]` 分支（消费 `:` 之后）先判 `]`，
  紧随 `]` ⇒ `end = NULL`。语义 / codegen / VM 本来就按 `null = 省略` 处理
  （`OP_SLICE`），所以改动只在解析器。
- **语义**：等价整段**浅拷贝**（与 `arr[0:arr.len() - 1]` 一致，且是副本不是别名）。
  字符串同样可用：`"hello"[:]`。
- **回归**：`assert/test_array_slice.leno` 测试 4b（副本非别名，`full[0] = 99` 后
  `arr[0]` 仍为 1）/ 4c（字符串）。
- **文档**：module_arrays / 入门教程 / 语言陷阱速查 / INDEX / 路线图 T28 共 5 处已同步。

### A6 ✅ `??=` 空值合并赋值（B1，2026-11-02 完成）

- **现状→结果**：`a ??= 3` 以前报「期望表达式」，现在合法。
- **实现（4 处）**：
  1. `src/lexer.c` 的 `'?'` 分支加三字符前瞻：`?` `?` `=` ⇒ `TOK_COALESCE_ASSIGN`
     （⚠ 该 token 追加在**枚举末尾**，避免挪动既有 token 数值）；
  2. `src/parser/parser_expr.c`：`AST_VAR` 走 `AST_COMPOUND_ASSIGN`（`op = TOK_COALESCE_ASSIGN`）；
     `obj.prop` 与 `obj[i]` 统一降级成 `AST_INDEX_ASSIGN`（带 op），**不**用 `obj["p"] = obj["p"] ?? v`
     那种"非 null 也写回"的脱糖；
  3. `src/codegen/codegen_stmt.c`：新增 `gen_coalesce_assign_var()`（局部/形参/全局/upvalue/模块/
     `__self_field__`）+ `gen_index_assign` 的判空分支 —— 都是
     `emit_is_null` → `emit_jmp_if_false` 跳过右值 → 写回，**右值只在该写时求值**；
  4. `src/semantic`：豁免 T11「确定是 null 还参与运算」的报错（`int? a = null; a ??= 3`
     正是它的头号用法），并新增"目标不可空 ⇒ 恒不生效"的编译错误。
- **回归**：`assert/test_coalesce_assign.leno`（变量/字段/全局/字典下标/upvalue/表达式位置/惰性）
  + `assert/test_diag_coalesce_assign.leno`（不可空、const、右值类型不匹配）。
- **文档**：入门教程 `??` 那一节后面补了 `??=` 小节 + 语法速查表一行。

### A7 ✅ 箭头函数 `x => expr` / `(a, b) => expr` / `(int x) => expr` / `() => expr`（C2，2026-11-02 完成）

- **实现**：纯语法糖，直接 desugar 成 `func(参数) { return expr }`（AST 仍是 `AST_FUNC_DEF`），
  **语义 / 闭包 / 类型推断零改动**。两个入口：
  1. `TOK_FAT_ARROW` 的中缀规则（`src/parser/parser_expr.c` 的 `rules[]` + `parse_arrow_infix`）；
  2. `(…) =>` 用**投机解析**：`parse_grouping` 先开静默段 + 保存词法状态试一遍参数表，
     失败就回滚成普通括号表达式 —— `(a + b)` / `(pr.sum())` 照旧。
- **与既有 `=>` 的关系（关键）**：`=>` 原本只用于类型绑定
  （`if x is T => v` / `case is A => v`）。两者共存靠两条：
  - `is` 的优先级（`PREC_IN`）比箭头（`PREC_ASSIGNMENT`）高 ⇒ 解析到 `AST_TYPE_CHECK` 时
    `parse_arrow_infix` 发现 left 不是裸变量、**原样返回不消费 token**，`=>` 留给绑定语法；
  - **新护栏** `check_arrow_in_cond()`：条件位置/`case` 值出现箭头函数 ⇒ 编译错误。
    否则 `if x => 1 { }`（以前是语法错误）会变成"条件 = 函数值"⇒ **恒真且一声不吭**。
- **口径**：省略类型的参数是 `any`；函数类型按**完整签名**比较，所以传给 `func(int):int`
  形参时要写 `(int x) => …`。
- **回归**：`assert/test_arrow_func.leno`（9 项：单参/零参/多参/带类型/当实参/括号表达式不受影响/
  if 表达式体/嵌套箭头）+ `assert/test_diag_arrow_func.leno`（if / while / case 三处护栏 +
  "`if x is T => v` 绑定不被误伤"的对照）。examples 812 个 `--check` 全过、断言 543 全过。
- **文档**：入门教程「匿名函数」一节后新增「箭头函数」小节 + 语法速查表一行。

### A8 ✅ 实参位置禁止裸赋值（C1 的前置闸门，2026-11-02 完成）

- **实测的旧行为**：`f(a = 1, 2)` ⇒ 返回 `12`，且事后 `a == 1` —— 因为 `=` 是优先级最低的
  中缀运算符（`parser_expr.c` 的 `rules[TOK_EQ] = parse_assignment`），实参位置会**先真的赋值**
  再把值当实参传，全程无错无警告。而 `new Point(x = 10)` 里同样长相的 `x = 10` 是**字段名**
  （`parse_new` 的 `AST_STRUCT_INIT` 路径）⇒ **一个写法两种语义**。
- **修法**：新增 `parse_call_arg()`（`src/parser/parser_expr.c`），6 处实参解析循环统一走它
  （普通调用 / 泛型调用 / 模块调用 / `obj.m(...)` / `(expr).m(...)` / `?.m(...)`）：
  实参若是 `AST_ASSIGN` / `AST_COMPOUND_ASSIGN` / `AST_INDEX_ASSIGN` ⇒ 报
  「实参位置不能写「名 = 值」……」。判据用**起始列差**区分"裸赋值"与"用户显式加括号"：
  `f(a = 1)` 拦、`f((a = 1))` 放行（既有 `assert_eq((c += 5), 6)` 靠这条）。
- **不动的部分**：`(a = 1)` / `1 or (a = 1)` / `var b = (a = 1)` 全部照旧；
  `new Point(x = 10)` 照旧。
- **回归**：`assert/test_diag_arg_assign.leno`（裸赋值 ×2 报错 + 括号赋值 / `new` 字段名 /
  `or` 短路三个对照）。仓内全量扫描：`examples` + `assert` + 20 个模块库，
  实参位置赋值 **0 处**（仅 `test_operator_precedence.leno` 的 2 处括号内赋值，不受影响）。
- **意义**：C1 现在可以直接做了 —— 实参里的 `名 = 值` 不再有第二种解释。

### A9 ✅ 命名实参 `f(b = 2, a = 1)`（C1，2026-11-02 完成，第一版）

- **口径**：只对**本模块的脚本函数**生效（能查到 `AST_FUNC_DEF` 的形参名）。
  位置实参必须在命名实参之前；同一形参不许既位置又命名；名字写错列出可用形参；
  中间形参可跳过，前提是它有**字面量默认值**（`= 2` / `= ""` / `= false` / `= null`）。
- **✅ 2026-11-03 补丁：求值顺序 = 书写顺序**。第一版把实参按形参名重排后交给 codegen，
  导致 `f(b = sideB(), a = sideA())` 先执行 sideA（**静默换序** ✗）。
  现在语义阶段额外生成 `Ast::call.arg_eval`（书写顺序的「表达式节点 → 形参槽」表），
  codegen 用 `gen_call_args_to()` 按书写顺序求值、直接写进对应形参槽；
  没有命名实参时该表为 NULL，仍走原循环（字节码零变化）。
  回归进 `assert/test_named_args.leno` ⑨（全命名 / 位置+命名两组副作用顺序）。
- **实现**：
  1. `src/parser/parser_expr.c`：`parse_call_arg(p, allow_named)` 多了个参数 ——
     裸标识符调用（`f(...)`）里形如 `名字 = 值` 的实参**不再报错**，留给语义阶段判定；
     方法 / 模块 / `?.` 调用仍然当场报「实参位置不能写「名 = 值」」（本期不支持）。
     用新增的 `Ast::arg_paren` 标记区分 `f(a = 1)` 与 `f((a = 1))`。
  2. `src/semantic/semantic_visit_func.c`：新增 `sem_normalize_named_args()` ——
     按形参名把实参**重排成纯位置实参**，然后整条链路（类型检查 / 默认参数补齐 /
     codegen）完全不用改，**字节码与按位置传参逐字节一致**。
  3. `src/semantic/visitinc/visit_expr.inc`：`case AST_CALL` 最前面调用它
     （必须在任何"逐个访问实参"之前，否则会先把它当赋值表达式处理）。
- **缺口（第一版故意留的）**：方法调用 / 跨模块 / 内置 native 函数不支持命名实参
  （拿不到形参名），会给出定向报错；跳过中间形参只支持字面量默认值。
- **回归**：`assert/test_named_args.leno`（重排 / 位置+命名 / 默认参数 / 跳过中间 /
  嵌套 / 泛型函数 / 方法体内 / 递归，共 8 组）+ `assert/test_diag_arg_assign.leno`
  重写为命名实参的错误路径（名字写错、重复、命名后写位置、方法调用不支持、括号对照）。
- **文档**：入门教程新增「命名实参」小节（含 4 条规则与限制）。

### A13 ✅ switch 区间 case `case 1:3`（C4，2026-11-02 完成，语法于 11-03 修正）

- **语法**：`case 1:3 { }` —— **闭区间**，与切片 `arr[2:8]` / 范围 `x in 0:9` **同符号同口径**；
  端点可以是任意数值表达式；与单值 case、`case 5, 6` 逗号多值混用无碍；int / float 都支持。
  - ⚠ **11-02 第一版用的是 `case 1 to 3`**（复用 `for` 的 `to`），当时理由是"`:` 已被
    切片/类型标注/字典占用"。**这个理由站不住**：case 头里 `:` 只可能是区间，没有歧义；
    而给"区间"造第二个词，反而让 Leno 有了两套等价写法（与"单一事实来源"冲突）。
    11-03 改成 `:`，旧写法 `to` 会报错并提示替换。
- **实现**：
  1. `src/parser/parser_stmt_control.c`：case 值解析完若紧跟 `TOK_COLON` ⇒ 造 `AST_RANGE`
    （`inclusive = 1`），端点就是两侧表达式；`TOK_TO` 走"报错 + 仍构造区间"，
     保证只报一条、不级联；

    （那样比的是 Range 对象，永远不成立），而是生成"两条不满足就跳过"的跳转
    （`tmp < lo` 跳过、`tmp > hi` 跳过，否则命中）；
  3. **`OP_IS_NUM` 守卫**（11-03 补，见 A16）：比较前先判"是不是数值"，
     否则 `switch any` 里遇到字符串会崩在 `<` 上；
  4. `src/semantic/visitinc/visit_control.inc`：区间 case 不参与「值 + 类型」匹配的类型告警。
- **回归**：`assert/test_switch_range.leno`（分档边界 / 越界 / 与单值+多值混用 / float 区间）
  + `assert/test_switch_range_mixed.leno`（与 `case is` 混用、非数值不崩）。

  比较链，`OP_SWITCH_LOOKUP` 早就不发且 VM 侧是空指令），已改写为现实描述 + 手写优化建议。

### A17 ✅ `??=` 之后的可空收窄（2026-11-03，交叉测试后的体验修补）

- **现象**：`int? a = null; a ??= 5; int r = a + 1` 仍报「nullable 值类型参与算术运算，
  运行时可能为 null」——`??=` 明明保证了非空，警告却是噪音（LenoHack 的 `n + cache` 就踩到）。
- **做法**：`Symbol` 加 `is_nonnull` 标记。`x ??= v` 置 1；**任何其它写点**
  （普通赋值 / 其它复合赋值）清零；算术的可空警告在 `is_nullable_value_kind` 命中后
  再用 `ast_var_is_nonnull()` 排一次（只认裸变量，`a.b` / `f()` 不追）。
- ⚠ 踩到的坑：`resolve_variable_with_upvalue*` 会 `free(ref->name)` 再赋值 ——
  栈上 `SymRef` 不清零就是 **free 野指针**，实测直接把编译器搞成堆损坏崩溃
  （`0xC0000374`）。现在 `memset` + `symref_dispose` 配对，并改用 `_raw` 版本
  （避免把"只写不读"洗成"读过"，影响未使用变量警告）。
- **保守性缺口（已知）**：`if cond { a ??= 1 }` 出块后仍保留标记 ⇒ 少报一条警告
  （不是误报错误）；与 `is_null_value` 的「宁漏勿误报」同一取舍。
- **回归**：`assert/test_coalesce_narrow.leno`（2 个"不该再警告" + 3 个"必须仍警告"的对照）。

### A18 ✅ 三处"用户体验级"修补（2026-11-03，实测反馈驱动）

1. **字面量里的 `null` 不再把容器类型锁死**
   - `Dict d = {"k": null}` 以前推成 `Dict[string, null]` ⇒ `d["k"] = 6` 报
     「期望类型: null，实际类型: int」，用户会以为"字典不能存别的值"。
   - 现在字典的**值类型**是 null 字面量 ⇒ 推成 `any`。
   - 数组走另一条路：`[null, null]` 仍推 `Array[null]`（否则
     `Array[int?] arr = [null, null]` 这条合法写法会因为"数组类型不变"而报错——实测回归），
     改在**下标赋值检查**里放行：元素类型是 `null` ⇒ 允许赋任何值（"待填"占位）。
2. **`??=` 过之后又被覆盖的可空警告**：文案改成按场景选 ——
   若该变量**在别处**用过 `??=`，直接说"那条 `??=` 不在本行之前的直线路径上（在别的分支
   里、或已被后续赋值覆盖），把它提到本行之前 / 或在这里再写一次"，比泛泛的"请先判空"有用。
   （判定靠 `Symbol.coalesce_inited`，跨分支保留。）
3. **`jsons.dig(obj, path)`**：`decode` 返回 `any`，而 Leno 不许在 any 上直接下标 ⇒
   取嵌套字段要每层 `as Dict[string, any]`。新增 `dig`：
   `jsons.dig(data, "user.name")` 或 `jsons.dig(data, ["cfg", "app.name"])`，
   逐层取、缺了给 null、**不放松任何类型检查**（仍返回 any）。空路径返回 null（不静默返回整个对象）。
- **回归**：`test_literal_null_infer.leno`、`test_json_dig.leno`、`test_coalesce_narrow.leno`
  追加"文案应指出提到本行之前"一条；断言 564/564、examples 812/812、模块库 134/134。

## B. 低成本、高一致性

### B1 `??=` 空值合并赋值（**已完成，见 A6**）

```leno
int? a = null
a ??= 3          // 现在：语法错误「期望表达式」
```

- **现状**：`??` 表达式、`+=` / `&=` 等复合赋值都有，唯独 `??=` 没有 ⇒ 用户从
  C# / Dart / JS 过来必撞，只能写 `a = a ?? 3`（还可能重复求值左值）。
- **实测**：`a ??= 3` 报 `[语法错误] 期望表达式`（列在 `??` 之后）。
- **建议**：`??=` 只允许用于**可空变量/字段/下标**，语义 = `if lhs == null { lhs = rhs }`，
  **右侧惰性求值**（与 `??` 的短路一致 —— 实测 `a ?? f()` 在 a 非空时 `f` 调用次数 **0** ✓）。
- **落点**：`src/lexer.c`（`?` `?` `=` 三字符出 `TOK_COALESCE_ASSIGN`；现有 `??` 分支在
  `peek_next(lex) == '?'` 处，需再加一层判 `=`）+ parser 复合赋值分支
  + codegen 转"判空跳转 + 赋值"；左值只求值一次。
- **⚠ 不要复用 `AST_COMPOUND_ASSIGN`**：该节点只存 `name / op / value`，codegen 走
  "读旧值 → 算 → 写回"（`src/parser/parser_expr.c` 复合赋值分支），**没有短路跳转的形状**；
  `??=` 必须新增节点（或 parser 阶段直接降级成 `if lhs == null { lhs = rhs }`，
  这样 codegen 零改动，代价是左值会被求值两次 —— 若左值是 `arr[f()]` 就不能降级）。
- **风险**：低。**值类型** `int a`（非可空）用 `??=` 应直接编译报错
  （提示"a 不可空，??= 恒不生效"）。

### B2 前导小数点浮点 `.5` / `-.5`（P3，约 2 小时 —— 优先级已下调）

- **现状**：`var x = .5` 报 `[语法错误] 期望表达式`；必须写 `0.5`。
- **动机**：从 Python / JS / Swift 过来最顺手的写法之一；科学计数法已经支持，
  只剩"省略 0"这一种不认，形状不一致。
- **但收益最小**：`0.5` → `.5` 只省一个字符，而 `.` 在 `a.b` / `arr[0].x` /
  `p.method()` 上下文里处处出现，误判的代价远大于收益 ⇒ **建议降到 P3 或不做**。
- **落点**：`src/lexer.c` 数字扫描入口：`.` 后紧跟数字、且 `.` 前不是标识符字符 /
  `)` / `]` / 数字 ⇒ 按浮点字面量扫描（与 `0.5` 同产物）。
- **风险**：低但需钉死 `arr[0].x`、`.5 + 1`、`x = -.5` 三条断言。

### B3 数字分隔符 `1_000_000`（P2，约 2 小时）

- **现状**：`int a = 1_000_000` 报 `[语法错误] 声明语句后期望换行或 ';'，但同一行出现标识符`
  （`1_000` 被当成 `1` + 标识符 `_000`）。
- **动机**：大整数 / 金额 / 时间常量（`3_600_000` ms）可读性；Leno 还支持 bigint，
  长数字更容易数错。多语言惯例（Rust / Swift / Java / C# / JS 提案）。
- **落点**：`src/lexer.c` 数字扫描里吞掉 `_`（仅当两侧都是数字字符），其余不变；
  `1_000` / `0xFF_FF` / `1_000.5` / `1_000e3` 都支持。
- **风险**：低。注意 `1_` / `_1` 应报错而不是静默接受。

### B4 `elif` 作为 `eif` 的别名（P3，约 1 小时 —— **建议不做**）

- **现状**：`eif` 合法（`if c { } eif c2 { } else { }`），`elif` / `elseif` 会给出
  **很好的报错**（实测文案："Leno **没有 `elif` / `elseif`** ✗ —— 用 `eif` ……`else if` 两个词的写法也合法 ✓"）。
- **建议语法**：把 `elif` 直接接受成 `eif` 的**同义关键字**（不新增 AST，只在 parser 的关键字
  匹配处并列）。`else if` 两词写法本来就合法，三种写法语义一致。
- **⚠ 风险被第一版低估了**：`elif` 现在**就是合法标识符** —— 实测
  `var elif = 1; print(_int(elif))` 正常输出 `1`。做成关键字会**静默改变**这类已有代码的语义。
  若一定要做，只能"if 链上下文相关识别"（`}` 之后紧跟 `elif` 才当关键字），
  否则属破坏兼容。
- **立场问题**：这与 D3 否掉三元运算符的理由（"会形成两套等价语法，与单一事实来源冲突"）
  直接矛盾 ⇒ **建议保持现状**，把跨语言摩擦交给已有的好诊断（见 §D 开头的"别名类统一立场"）。

### B5 嵌套块注释（P3，约 2 小时）

- **现状**：`/* a /* b */ c */` 在 `c` 处报 `[语法错误] 期望表达式`
  —— 块注释在**第一个 `*/`** 结束。
- **动机**：注释掉含块注释的代码段时（调试常用），现有行为会把后半段当代码 ⇒ 报错
  甚至编译通过但语义变了（"注释吞代码"）。Rust / Swift / D 都支持嵌套。
- **落点**：`src/lexer.c` 的块注释扫描加深度计数（`/*` 深度 +1，`*/` 深度 -1，为 0 才结束）。
- **风险**：低；语义变化只影响"原本就不可能编译通过"的输入。⚠ 需确认没有工具链
  依赖"第一个 `*/` 结束"来生成注释（仓内 grep 一下）。
- **替代方案**：若不想改词法，至少把报错文案改成"块注释不支持嵌套"。

## C. 中等收益、需要设计（建议排期）

### C1 命名实参 `f(a = 1, b = 2)`（**已完成，见 A9**）

- **现状**：只有 `new Point(x = 10, y = 20)` 的 struct 构造支持 `键 = 值`；
  普通函数调用 `f(a = 1, b = 2)` 报「未定义变量: a」（实测）。
- **⚠ 前置事实（第一版写错了）**：Leno **有赋值表达式**，`=` 在实参位置本来就能解析。
  实测：

```leno
func f(int x, int y): int { return x * 10 + y }
main() {
    int a = 0
    f(a = 1, 2)      // ⇒ 12，且事后 a == 1（静默赋值，不是命名实参）
    var b = (a = 2)  // ⇒ b == 2
    print(a = 3)     // ⇒ 打印 3
}
```

  ⇒ 需求 1（**已完成，见 A8**）：实参位置的**裸赋值现在直接报错**
  （`f(a = 1, 2)` ⇒ 「实参位置不能写「名 = 值」……」），`f((a = 1), 2)` 这种
  显式加括号的写法仍放行 ⇒ C1 不必再担心 `名 = 值` 有两种解释。
  ⇒ 需求 2（已完成）：赋值表达式已补文档（入门教程「赋值是表达式，但实参位置不许裸写」），
  口径定为"括号内可用、实参裸写不可用"。
- **动机**：
  - 参数多的 native / 脚本函数（`files.write(path, content)`、`sdl.*` 一堆 opts）
    现在只能按位置传，读调用点看不出哪个参数是什么；
  - 与现有 struct 构造语法一致，学习成本几乎为零；
  - 可与默认参数组合，只写想覆盖的那几个。
- **建议规则**（保守版，避免歧义）：
  1. 命名实参只对**声明时形参有名字**的函数/方法生效；
  2. 一旦出现命名实参，其后**不允许**再出现位置实参（同 Python 的
     "positional after keyword" 错误）；
  3. 名字重复 / 不存在 / 与已给位置实参冲突 ⇒ 编译错误，文案列出可用形参名；
  4. 重排到形参顺序后再走现有 codegen（**字节码零变化**，只是 AST 实参顺序规范化）。
- **落点**：`src/parser/parser_expr.c` 调用实参解析（`TOK_IDENT` 后跟 `=` 时先按
  "疑似命名实参"记账，不要直接生成赋值表达式）→ `src/semantic/visitinc/visit_expr.inc`
  调用检查（按 `func_table` / 符号表形参名重排）→ codegen 不感知。
- **风险**：中。真正要小心的是 **native 函数**（形参名来自注册规格）与
  **跨模块函数**（形参名是否完整保留）。建议先只对"脚本函数 + 本模块可见签名完整"开放，
  native 作为第二阶段。

### C2 箭头函数 `x => expr` / `(a, b) => expr`（**已完成，见 A7**）

- **现状**：`var f = (int x) => x + 1` 报 `[语法错误] 期望表达式`；
  必须写 `func(int x) { return x + 1 }`。
- **动机**：`arrays.map/reduce/filter`、回调字段、`threads.start` 大量使用小闭包，
  现有写法 3 行起步；箭头函数能把"单表达式回调"压成一行，且与 `if ... then ... else`
  的表达式风格一致。
- **为什么比 C1 划算**：纯语法糖、不动语义和字节码，成本只有 C1 的一半；
  调用点数量却远多于"参数多到需要命名"的调用。
- **建议**：纯语法糖 —— `(参数) => 表达式` 直接 desugar 成
  `func(参数) { return 表达式 }`（AST 仍用 `AST_FUNC_DEF`，**不动语义/字节码**）。
  允许 `x => expr`（单参免括号）与 `() => expr`（零参）。
- **落点**：`src/parser/parser_expr.c` 的表达式前缀分支（`(` 处需要前瞻 `=>`，
  或标识符后紧跟 `=>`）。
- **风险**：中低。`=>` 目前有两处既有用法：`if expr is Type => var`
  （`src/parser/parser_stmt_control.c`）与 **`case is A => var`**（同一文件，
  case 分支，第一版漏记），两者都在**语句/if 头**上下文，与表达式位置不重叠；
  需要确认词法/前瞻不会与它们打架。

### C3 插值字符串格式说明符 `$"{x:.2f}"`（P2，约 2 天）

- **现状**：`$"pi={x:.2f}"` 报 `[语法错误] 期望 '}'`；只能 `format("%.2f", x)` 或字符串拼接。
- **动机**：UI / 日志里最常见的需求就是"保留 N 位小数"；现在要么写 `format`（格式串
  与参数分离、容易错位），要么 `_str(_round(...))`（还得自己补 0）。
- **建议**：`{expr:spec}` 内的 `spec` 复用现有 `format` 的转换子集（`%d/%f/%.Nf/%x/%s`），
  desugar 成 `format("%.<spec>", expr)`。
- **落点**：`src/parser/parser_expr.c` 的 `parse_interp_string`（解析 `{` 内表达式后直接
  `if current != TOK_RBRACE ⇒ 期望 '}'`，当前 `:` 就死在这里）+ 语义/代码生成侧复用 `format` 内建。
- **风险**：中。插值里出现 `:` 的既有写法（Leno 三元是 `if`，所以没有 `a ? b : c`；
  字典/类型注解一般不在表达式内）需盘点；建议只在 `{` 后**顶层** `:` 识别。

### C4 `switch` 区间 / 条件 case（P2，约 2 天）

- **现状**：`case 1:3 { }` 报 `[语法错误] case 语句体必须用大括号 {} 包裹`
  （`1:3` 被当成表达式，逗号/冒号在 case 头没有专用语法）；只能一个个列 `case 1` … `case 3`。
- **⚠ 第一版的动机写错了**：原文说"`switch` 已有同类型 ≥4 个自动二分"，**实测不成立**。
  - `src/codegen/codegen_stmt.c` 的 `gen_switch` 只有**线性比较链**：逐 case
    `emit_eq` + `emit_jmp_if_true` + 跳板区，没有任何"≥4 个就换查找"的分支；
  - 全仓 codegen **没有一处发 `OP_SWITCH_LOOKUP`**；
  - VM 侧那条指令是空动作：`src/vm/vminc/run/14_switch_for.inc` 里
    `LABEL(OP_SWITCH_LOOKUP): DISPATCH();`；
  - `switch_lookup_index()`（`src/vm/vm.c`）**没有任何调用方**，是死代码；
  - 实测：6 个 int case 的 `--debug` 反汇编是 6 条连续的 `OP_EQ`，无 `SWITCH_LOOKUP`。
  ⇒ 所以"与二分优化兼容"这个成本项**不存在**；反过来，"switch 没有查找优化"本身
  是个可选的性能项（要做就得先让 codegen 发指令 + VM 实现，工作量独立于本条目）。
- **动机（改后）**：分数段 / 时间片 / 字符区间分类是常见写法；区间 case 能把
  "长 if 链"收进 switch，至少省掉重复的 `x >= a and x <= b`。
- **建议语法（11-03 修正）**：**`case 1:3 { }`** —— 与切片 `arr[2:8]`、范围 `x in 0:9`
  **同符号同口径**（闭区间）。
  - 第一版曾建议 `case 1 to 3`（复用 `for` 的 `to`），理由是"`:` 已被切片/类型标注/字典占用"。
    **这条理由不成立**：case 头里 `:` 后面只可能跟区间右端，没有第二种解释，不存在歧义；
    而另造 `to` 会让 Leno 有两套等价的区间写法，与"单一事实来源"冲突。
  - 11-03 已按 `:` 实现，`case 1 to 3` 保留为"报错 + 提示改成 `:`"（不静默兼容）。
- **落点**：parser 的 case 头（`case` 后表达式若紧跟 `to` ⇒ 造区间节点）；
  codegen 在 `gen_switch` 比较链里生成两次比较（`>= lo and <= hi`），
  现在有 `OP_CMPJMP_*` 可直接用。
- **风险**：中。主要成本在语义/代码生成与"`case is Type` 混合"的排序，
  以及区间 + 常量的重复/重叠检测（可选）。

### C5 `for x in arr` 作为 `for arr to x` 的别名（P2，约 1 天 —— **建议不做**）

- **现状**：`for x in a { }` 会报一条**很好的错**（实测原文）：
  「for 头的 `x in 集合` 不是遍历写法（`in` 是成员测试运算符，而 for 是区间循环
  ⇒ 循环体不会执行），且 x 未定义；遍历请写 `for 集合 to x`（**集合在前**）」。
- **动机**：几乎所有主流语言都是 `for x in arr`；Leno 的"集合在前"（`for arr to item`）
  是独有语序，跨语言用户每天都会写反。诊断虽好，但每条都要手改。
- **建议（若做）**：**只在 for 头**把 `for IDENT in EXPR` 识别为遍历
  （`in` 在 for 头不可能是成员测试）⇒ desugar 成 `for EXPR to IDENT`。
  这样不动 `in` 运算符在其它位置的语义。
- **为什么不建议做**：与 B4、D1 选项② 同属"给已有概念加第二套写法"，而 D3 已用
  "单一事实来源"否掉三元运算符。真要降低摩擦，把这条诊断的**文案**（已经很好）
  再往前推一步即可 —— 例如在 IDE/LSP 侧做 quick-fix，成本是零语法变更。
- **风险（若做）**：中。除了 for 头前瞻，还要定"for 里的 `x` 是已声明变量时算遍历还是
  成员测试"，并决定 `for (x in a)` 这种带括号形态是否保留（建议明确不支持 + 给文案）。

### C6 批量导入 / 批量 use（P3）

- **现状（2026-11-02 复核更正）**：
  - **批量 use 其实早就有了**，只是语法是 `use m.(A, B, C)`（圆括号，不是花括号）——
    实测 `use m.(A, B)` 正常（`tmp_c6` 验证）。原条目说"一行一个"是错的。
  - `import io, times` 仍然报 `[语法错误] 期望表达式` ⇒ 只有**批量 import** 是真缺口。
- **若要做批量 import**：`src/parser/parser_module.c` 的 `parse_import_stmt` 是**单条**实现
  （400+ 行，里面还夹着"预扫描模块的 use 行 / 包名解析 / 版本校验"），
  要支持 `import a, b` 得先把它拆成 `parse_one_import()` + 循环（返回 `AST_BLOCK` 包多条，
  与 `parse_var_decl` 多变量同款）。**属于结构性重构**，不是"加个循环"那么简单，
  收益（省几行 import）与风险不匹配 ⇒ 建议继续搁置。
- **替代方案**：模块头部继续一行一个；真要压缩，用包（`leno.toml`）或 `use module.(A, B)`。

## D. 低优先级 / 需作者拍板

> **"别名类"统一立场（本轮的评审结论）**：B4（`elif`）、C5（`for x in arr`）、
> D1 选项②（`this`）本质相同 —— 都是给已有概念加第二套写法；而 D3 用
> "两套等价语法与单一事实来源冲突"否掉了三元运算符。**两条立场不能同时成立**。
> 建议统一为**不加别名、只改诊断**（诊断已经普遍写得很好），
> 否则就三处一起加、一起写进语法文档。这个取舍需要作者拍板。

### D1 `this` → `self` 的纠错提示（**已完成，见 A5**）

- 选项①（只加提示）已落地；选项②（把 `this` 当 `self` 同义关键字）属"别名类"，
  立场见上面的统一说明 —— 与 B4 / C5 一起决定，不要单独加。

### D2 负终点切片语义（不建议改，仅记录）

- 现状（实测）：`arr[:-3]` == `[]`（负终点恒为空），`arr[-3:]` 正常从末尾数（得 3 个元素）；
  负**常量**终点在编译期给 `[切片负终点]` 警告（`WARN_SLICE_NEG_END`）。
- 改成 Python 语义（负终点 = `len + end`）**很诱人但破坏兼容**：仓里已有代码/测试依赖
  当前口径。**建议保持现状 + 文档**（本轮已纠错）。

### D3 三元 `cond ? a : b`（不建议加）

- 现状：明确报错并推荐 `if cond then a else b` / `eif` 链。
- 理由：Leno 已有"if 表达式"，再加 `? :` 会形成两套等价语法（与"单一事实来源"纪律冲突）。
  **保持现状**，诊断文案已经足够好。

### D4 `trim()` 只认 ASCII 空白（可选，P3）

- 现状（实测）：`"　你好　".trim().len()` 仍是 **4**（全角空格 U+3000 不修剪），
  `trim()` 结果仍是 `"　你好　"`。
- 动机：中文内容里全角空格很常见，用户会直觉认为 `trim` 应处理它。
- **建议（改后的方案）**：**不要改 `trim` 的默认语义**，另加
  `trim_unicode()` / `trim_start_unicode()`（或 `trim(chars)` 重载），
  边界扫描按 UTF-8 空白集（至少 U+3000、U+00A0；与 Python `str.strip` /
  Rust `char::is_whitespace` 同口径）。
- **理由**：改默认行为会**静默影响**"故意保留 NBSP/全角空格"的数据清洗代码；
  新增方法零破坏，用户按需选择。
- **风险**：低（纯新增）。
