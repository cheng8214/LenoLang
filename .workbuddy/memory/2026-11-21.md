## Android 弹窗方案评审（LenoMusic / LenoSDL3）

结论：桌面/Android 分流方向成立，但落点应在框架的 `sdl_dialog.leno` 两个工厂，不在 app 三个调用点。

关键事实（已核对代码）：

- `dl_window.leno` / `dl_settings_win.leno` / `dl_about_win.leno` 对 `dlg` 的调用全集只有
  `setRootAt` / `run` / `runModal` / `raise` / `ok`；**0 个 `addXxx`** ⇒ 弹窗内容 100% 是 `root` 布局树。
  这让"子窗口（离屏纹理）"方案在 app 侧零改动成立。
- `musicdl_gui.leno:1357` 的 `setOverlay` **不是歌词层**：它在 `if dlShot != "" or dlAuto > 0` 里，
  是截图/自动退出钩子。真歌词浮层是 `player_bar.leno` 的自绘画布挂进主窗口控件树（"同款挂摘"）。
  故"overlay 单槽被歌词占用"不是本项目的现实约束。
- 机制现成：`sdl_renderer.leno:434` 的 `present()` 在 SSAA 分支里就是
  "整帧画进离屏纹理 → setRenderTarget(null) → SDL_RenderTexture 缩放贴回窗口"。
  子窗口 = 同一套 machinery，换 dst rect。

## 已实现：虚拟子窗口（当日完成并测通）

四个触点全部落地，桌面路径零改动：

1. `sdl_window.leno`：`Window.virt` + `createVirtualWindow()`；`init` 不建 SDL 窗口、自造合成 ID
   （`0x40000000` 起，避免与 SDL windowID 撞号）；`getSize/setSize/show/hide/raise` 全部按 virt 分流。
2. `_registerVirtual()`：借父窗口 handle + Renderer，不 `SDL_SyncWindow`、尺寸取 opts；
   状态用 7 个并行数组（`_runVOn/_runVParent/_runVTexD/_runVX/_runVY/_runVS/_runVDrawn`），
   **不用 Dict** —— 裸 Dict 元素类型被"第一次写入"定死，装 bool/int/float/Ptr 会报类型错。
3. 渲染：把原 `run()` 里的绘制块抽成 `_drawTree(i, ren, opac)`（主循环与虚拟窗口共用一套顺序），
   新增 `_renderVirtChildren`：子窗口画进自己的离屏纹理（0,0 坐标，控件树零改动）→
   `setRenderTarget(null)`+`beginFrame()` → 模态遮罩 60% + 投影 + 1px 描边 → 等比贴图。
   **坑**：`beginFrame()` 只在开 SSAA 时才设目标，不先显式 `setRenderTarget(null)` 会把贴图画回纹理里（整块不显示）。
4. 事件：`_virtHitTarget` 把事件改投给虚拟窗口（模态=栈顶；非模态=矩形命中），
   `sdl_event.setGeometryOffset(dx,dy,s)` 让 `mousePos()` 返回子窗口局部坐标 ⇒ 控件命中判断零改动。
5. 销毁收敛到 `_destroyEntry(i)`（4 条收尾路径共用）：虚拟窗口只销毁自己的纹理。

入口：`createDialogWindow` / `createModelessDialog` 在 `_os()=="android"` 时自动走虚拟窗口。

## 修复 1：密度层（gap #1）

实测结论（都是读数，不是推断）：
- `SDL_GetWindowDisplayScale` 在 Android **恒 1.0**；`SDL_DisplayMode.pixel_density` 也**恒 1.0**。
- 而 `SDL_GetWindowSize` = 720x1217 = **物理像素**（扣 24dp 状态栏）⇒ 只按 SDL 算等于没适配。
- 唯一可靠来源：Java `getDisplayMetrics().density` = 2.625。

通路：`SdlActivity.setAndroidDensity()` → JNI `dlopen("libSDL3.so")` + `SDL_SetHint("LENO_ANDROID_DENSITY")`
→ `sdl_core.getPlatformDensity()` 读 hint（退 pixel_density，再退 1.0）。

三个触点：`Window.getSize()` 除 / `setSize()` 乘、`Renderer.setDensity()`（`beginFrame` 设
`ssaaScale*dens` 或 `dens`）、事件坐标除（`setGeometryOffset(0,0,dens)`）。
桌面一律 1.0（`_os()!="android"`）—— Windows 的 getSize 已是逻辑点，再除会缩成 2/3。

真机读数：`getSize 274x464` / `pixels 720x1217` / 密度 2.625 ✓

## 修复 2：★ `SDL_SetRenderTarget` 把渲染缩放重置为 1.0（框架真 bug）

症状：Android 上虚拟弹窗内容只画进离屏纹理**左上角 1/dens**，其余全黑；桌面 dens=1.0 永远正常。
根因：`setScale` 的"值没变就 return"短路 —— `bxSx` 缓存仍是 2.625，而 SDL 侧已被重置为 1.0。
修复：`setRenderTarget` 里同步缓存（`bxSx=bxSy=1.0`），让缓存永远诚实；
顺手修 `clear()` 的 SSAA 分支漏乘 dens（一清屏坐标空间就缩回 1/dens）。
（先在调用点用 `setScale(1);setScale(td)` 验证过，确认后才改成根治 —— 不在调用点留绕法。）

## 21:19 蓝屏 — 定性为内存条硬件缺陷（与模拟器无关）

结论：**这台机器的 DDR4 有列级（column）坏单元，3200 JEDEC 规格下依然错**。安卓模拟器不是根因，
只是把内存占用推高后让坏区进入活跃页，命中率上升，才显得"装了安卓就崩"。

证据链：

- 蓝屏码：`0x1A` 子码 `0x41792`（PTE 损坏）、`0x4E`（PFN 链表损坏）、`0x139` 子码 `0x1d`
  （LIST_ENTRY 损坏）。近 30 天 7 次，其中 10/31、11/07 两次早于使用模拟器。
- 用户在 4000(XMP) 跑过几个月，降 3600 仍崩，今天降到 3200。
- 自写用户态压测 `C:\Users\Administrator\memtest\memtest.c`（12GB / 4 线程 / 地址入地址 + 常量 + mix64）：
  **3200 下 FAIL，579 处 / 92s**，全部单 bit 翻转（bit19 0x80000、bit20 0x100000），
  集中在约 30KB 窗口；写 0 读 1、写 1 读 0，其余 63 位全对 ⇒ 存储单元保不住该位，非软件可为。
- **换布局复现**：虚拟基址 `0x028EB26E0000` 与首次不同，出错**页内偏移完全相同**
  （0x5A0 / 0x688 / 0xDD0 / 0x4F8），错误率恒定 6.3~6.45 次/秒 ⇒ 物理固定位置缺陷，非温度漂移。

已做处置：

- `bcdedit /bootsequence {memdiag}` 已写入 `{bootmgr}` ⇒ 下次开机跑一次 Windows 内存诊断
  （内核态、全 32GB），结果看事件日志 `MemoryDiagnostics-Results` 1201/1202。
  取消：`bcdedit /deletevalue {bootmgr} bootsequence`。
- 工具与用法留在 `C:\Users\Administrator\memtest\`（`memtest.c` / `memtest.exe` / `run_memtest.bat`）。
- **在内存换掉或定位到具体那根之前，暂停 x86_64 模拟器的一切真机验证**；框架侧工作改用桌面单测推进
  （`testClickAt` / `testTouchDown` / `testKeyDown` 钩子已具备）。
